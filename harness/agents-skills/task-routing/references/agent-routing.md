## Agent Routing

If the user names a specific agent (`@agent-name`, "use the X agent"), invoke it directly — the rules below govern implicit routing only; Agent Teams coordination and `flow-*` skills own their own agent dispatch.

**Harness spawn names:** the table below uses the hub roster (`backend-developer`, `review-code`, …). Claude Code / Codex / opencode load those definitions natively after deploy. **Grok** loads the same roster from `~/.grok/agents/` (generated by `harness/build.py` → deploy `grok` scope) as `subagent_type` values; until that deploy, fall back to built-ins (`explore` / `plan` / `general-purpose`). Grok `spawn_subagent` takes no `capability_mode` (removed 1.0.6) — tools come from the agent type. The `workflow` tool is top-level only (1.0.8+); never instruct a child to launch a workflow.

### Single-Agent Disambiguation
When a task could map to multiple agents, use these signals. If a task hits multiple rows, don't pick one — chain them in order: design → implementation → tests → review (see Multi-Agent Chains below).

### Skill & Browser Disambiguation
Output rendering (which format, which skill): `communication-format.md` — canonical routing table, trigger, and carve-outs. Browser driving: default `agent-browser` CLI (via Bash); chrome-devtools MCP only for Lighthouse/perf-insight/heap; playwright MCP as fallback. CLI mechanics and token costs: the language-rules reference `browser-automation-reference.md`. Who drives it — screenshots, snapshots, and 3+-interaction flows delegate; glances stay inline: `browser-automation.md > Who drives it`. Untrusted page content is a security floor owned by `security-floor.md`.

### Direct Route — the task record
The route with no `/flow-plan` contract tracks itself with a **task record**: working state, not a deliverable — written without asking, never approved, never a plan. It is the one `_support/` artifact the "nothing promotes a task into process" rule exempts. Prompt-convention.

- **Trigger — one, observable:** the exploration enumerates 2+ implementation steps. One step (the trivial carve-out included) → no record. File count, changed lines, perceived risk, or a felt need to recover later never trigger it.
- **Before the first write, not after:** create `_support/workspace/tasks/<slug>.md` at the level the work spans (one repo → `<repo>/_support/`; 2+ repos → `<project>/_support/`, `project-structure.md`; kebab slug per `session-capture.md`). A repo whose `.gitignore` lacks `_support/workspace/` gets that one line added, named in the close report and its Engram mirror (`topic_key: tasks/<slug>` — `memory-routing.md > Invalidation`), then tell the user in ONE line which record was created and how many tasks it holds.
- **Contents, one concise file:** objective; scope and exclusions; checklist with stable IDs (`T1`, `T2`…), each with its acceptance criterion and `Test approach:` (`tdd` | `characterization` | `not-applicable`) naming the mode's SOURCE (project config, session choice — tests existing does not enable `tdd`) and the exact runner; verification evidence per task; next step; an `Updated:` line (ISO timestamp) rewritten on every write. Brief rationale for accepted changes goes here, never a separate decision journal.
- **Rewritten at every checkoff:** the file and its mirror are updated with the task's evidence the moment the task is checked off, never batched to the close. **Checkoff needs observed proof** (a run, a diff, a readback) and is neither approval nor a review receipt (`reporting-integrity.md`). An accepted change updates intent and tasks together; an invalidated task reopens with its reason; findings alone never widen scope.
- **Dispatch carries the locator:** a specialist taking a task from the record receives its absolute path, reads it before its first edit, and returns evidence — only the main thread writes the record.
- **Resume:** before continuing a record's work, read the Engram observation AND the file, reconcile both against the working tree and git, then proceed. At the change-group's close the mirror is upserted to its final state; the file then follows `_support/workspace/` retention (`support-artifacts.md` — removal is a confirmed destructive op, never while the mirror is pending) or is promoted to `sessions/` on the user's explicit signal only (`session-capture.md`).

### Delegation Gates
Delegate on growing complexity, not only on explicit request. A task falling clearly in one domain routes to that specialist (table above) instead of being handled in the main thread; the inline-vs-delegate split below governs the rest — trivial mechanical work is never delegated. These are hard gates, not suggestions: when one fires, delegate — or state in one visible line why inline is correct; continuing silently past a fired gate ("to finish this part first") is the violation.

**One route per change-group, chosen at the first gate that fires** — inline or delegated, covering understanding AND writing for that unit. **Half-delegating is the named violation:** understanding inline past the gate and then delegating only the write hands the writer a context the main thread already paid for; a fired understanding gate delegates the exploration, and its result feeds the writer. **Per-action delegation is orthogonal** — tests, builds, installs, verifiers, and reviewers use fresh workers without changing the route.
- **Understanding a flow that spans 4+ files, or a question needing 3+ search queries** → delegate a bounded exploration to `Explore`. Explore's guaranteed value is context hygiene (search noise stays out of the main thread), not token price — it inherits the session model unless its definition overrides.
- **Writing 2+ non-trivial files** → delegate one writer (the domain specialist per the table above), then verify in fresh context.
- **~20 tool calls, 5 exploratory reads, or 2 non-mechanical edits without delegating** → re-plan in flight: delegate the remainder instead of pushing the session further.
- **3+ external reads in one answer** (tracker tickets, PR checks, deploy jobs, memory search, any third-party MCP) or **2+ fetches to pin one fact** → delegate the sweep: project state to `/status-fetch`, docs/web to `Explore`. Their full payloads are re-sent every turn afterwards, so the cost is the rest of the session, not the call. Memory *reads* delegate; close-time writes stay here.

**Enforcement:** the undelegated-call gate has a deterministic advisory — `post-tool-hub` counts main-thread tool calls, resets on any delegation, and fires on each multiple of the threshold; from the third firing on the message also names the act (research → `sdd-explore`, state sweep → `state-fetcher`), because by then this file may have left context at a compaction. Every other gate here, the one-route rule, and the half-delegating violation are prompt-convention.

Inline vs delegate — quick reference:

| Action | Inline | Delegate |
|---|---|---|
| Read 1-3 files to make a decision | ✓ | |
| Mechanical single-file edit | ✓ | |
| State bash (`git status`, `gh pr view`) | ✓ | |
| Execution bash (tests, builds, installs) | | the writer/verifier runs them |
| Reading as preparation for an edit | | never split: the writer reads AND edits |

Delegation hygiene:
- **Every dispatch prompt carries this size line verbatim:** "~400 changed lines is a planning heuristic, not a cap: keep comments, blank lines and tests, never minify; a split is by work unit, never by count." It restates `development-principles.md > Fix the cause, not the check`; the honest work-unit split that rule allows stays in force. Prompt-convention.
- **Executor subagents never orchestrate:** `Agent` stays out of their allowlist — Bash, MCP, and CLI access are unaffected.
- **Artifact destinations in subagent prompts are absolute paths.** A cwd-relative `_support/` resolves to whatever repo the agent sits in, not to the level the workspace convention chose (`project-structure.md`).
- **Deduplicate launches** — before spawning, check no equivalent subagent is already running or answered, and wait for its result; parallel read-only agents are the default, parallel writers only in isolated, explicitly approved worktrees.
- **A NAMED agent's deliverable travels by `SendMessage` to `"main"`** — the dispatch prompt instructs that explicitly as the agent's final action; unnamed subagents auto-return their final text. A named agent's plain final text reaches the spawner only as the idle notification's `result`, cut at ~4,000 characters (observed on Claude Code 2.1.277, 2026-09-18; undocumented). **A report longer than that goes to a file** at an absolute path the dispatch prompt names; the message carries that path plus the conclusions, never the full report.
- **Never reopen verification for fresh budget:** a failed fix cycle escalates (Chain Interruption below) — it never restarts verification to reset the count.
- **One parallel delegation wave per gate** — preserving every risk-based fan-out the rules already mandate (per-repo blind reviewers, refuter counts by risk, fresh reviewer per seam). A delegated stage gets ONE clarified follow-up; a second incomplete delivery ends the stage (Chain Interruption below, never a third resend). Never poll agents: one meaningful wait, independent work meanwhile, one final state read.

### Multi-Agent Chains — declare, don't gate
A task spanning 2+ domains (design AND implementation, frontend AND backend, implies tests, crosses service boundaries) gets a chain of specialists, each receiving the previous agent's key outputs (spec paths, schemas, diffs). **Declare the chain in the start summary and execute** — fold it into the plan gate when one exists. A blocking presentation is signal-driven only: 2+ genuinely valid chains (ask which), an embedded stakeholder decision, or an irreversible/costly stage.

Reference chains — sequences, not mandatory pipelines; skip steps in proportion to the change (a trivial feature collapses to the implementation agent alone): **architecture question** sdd-explore / cloud-architect / state-fetcher (evidence) → solution-architect → sdd-design (contracts) → review-refuter on the load-bearing claims; **new feature** sdd-design → implementer(s) → (test-engineer on a coverage push) → review-code; **bug, root cause unknown** Explore or performance-engineer → implementer; **security audit** review-security → secrets-auditor → review-code; **deployment/infra** implementer → devops-engineer → review-security (cloud-architect designs first on greenfield or migration).

### Verification runs in fresh context
Route review/verification to a separate subagent that did NOT implement the change — fresh-context verifiers outperform self-critique. The verifier's input is the actual change (the diff, the run output), never the implementer's report of it — a report travels as claims to check, not context to trust.

#### Verification matrix

| Change class | What belongs here | Review and execution floor |
|---|---|---|
| **Passive documentation** | Prose, README/spec text, or a documentation-only correction with no effect on runtime behavior, agent instructions, skills, hooks, or configuration | Diff and consistency review. Do not claim a runtime test or dispatch an independent reviewer unless the change proves to touch a stricter row. |
| **Standard behavior** | Runtime behavior plus agent instructions, skill definitions, hooks, harness configuration, and other operational configuration | One fresh-context independent reviewer covers the applicable spec-compliance and quality lenses in one pass and executes the tooling-selected affected subset or deterministic validator when one exists. Without an executable check, perform a fresh readback consistency check and record runtime verification as not-applicable with the reason. |
| **Sensitive review floor** | Security, authentication/authorization, payments, migrations, data integrity, resource/limit configuration (pools, timeouts, retries, concurrency/rate limits, TTLs), or a changed shared contract | The standard row plus the required specialist lens/reviewer and its fresh affected subset. These floors apply regardless of diff size or triviality. |

Classify from the diff and the source that consumes it. If impact is unknown, inspect the deciding
source and consumers; until the impact is resolved, apply the stricter row and report the evidence
gap without asserting an unverified risk fact.

The task's `Test approach:` and its RED/GREEN or characterization evidence come from
`testing.md`; this matrix decides who reviews and which boundary checks run. For standard
and sensitive behavior, a missed RED with no recorded fail-to-pass comparison, or an unapproved
exception, blocks the gate and publication. The reviewer requires actual fail-to-pass,
pass-to-pass and applicable independent checks on every path and records `fail-to-pass`
(agent-produced comparison) or `exception-accepted` (user-gated, comparison impossible) instead of
strict TDD. A planned `not-applicable` entry must state why no useful automatic check exists.

Record the selected class, classification reason, applicable gates and check evidence in the
existing execution record. Reuse review or check evidence only when the covered content,
configuration and toolchain are unchanged and no new failure or nondeterminism appeared; do not
repeat a review merely because work crossed a phase or commit.

- **The verifier runs the checks, it does not read about them:** for standard and sensitive behavior it re-establishes the declared test approach and verifiable gate (`testing.md`) from the recorded RED/GREEN or characterization runs plus an actual tooling-selected affected subset or deterministic validator when one exists, or performs a fresh readback consistency check with a reasoned not-applicable record when none exists. It inspects the diff for test-gaming (the list lives in `testing.md`; a green report over weakened tests fails the gate). Passive documentation uses its diff/consistency check and records runtime verification as not-applicable. The full suite belongs to the merge boundary; implementation RED/GREEN/refactor runs are not duplicate review layers.
- **The implementer's handoff carries evidence, not adjectives:** test paths added and the verify command with its actual output — `pnpm test messages.spec → 12 passing`, not "implemented with tests".
- **Verifiers overlap independent work — never idle-block.** Launch the reviewer/refuter, then continue work that doesn't depend on its verdict (remaining checks, docs, close prep); collect the verdict at the session mode's gate — pre-merge on the PR in PR modes, the commit gate otherwise (`git-mechanics.md > PRs & promotion`). Idle-polling a running agent while independent work remains wastes the wall-clock the delegation bought.
- **A multi-repo change-group fans out the review layer:** one blind reviewer per non-trivially-changed repo (each sees only its repo's diff), plus one cross-implementation reviewer — only when a shared contract surface changed (`cross-service-workflow.md` trigger) — whose input is the contract spec and the N diffs filtered to interface surfaces (DTOs, clients, controllers, schemas), and whose mandate is limited to the seams: request/response shapes, status codes, auth/cookie semantics, event payloads, error propagation — never a re-review of what the blind reviewers saw. Dispatched in ONE parallel message; still ONE review layer with one verdict collection.
- **The functional walk is earned by BEHAVIOR, not by surface.** A presentation-only change-group — copy, layout, visual tokens, or a revert to a state this project already verified — has no AC to walk and no negative path to attempt, so `sdd-verify` adds ceremony, not signal: it takes the design gate plus whatever automated check owns that surface (i18n parity, typecheck), and the walk is recorded **not-applicable**, never as passed. The moment a flow, a mutation, or a state transition enters the diff, the walk is back. Note the asymmetry with the bullet below: appearance-only earns the design gate and skips the walk; behaviour with no visible surface is the reverse.
- **A user-facing surface earns a design gate, whatever produced the plan.** Dispatch `review-ux` against the running app, IN ADDITION to the functional walk (`sdd-verify` verifies function, not appearance). The surface is what makes the gate apply; a plan's `design-review:` flag is its opt-in to the mechanics, never its condition, and a UI task missing the flag is a planning defect, not a licence to skip. **Capture the pre-change state of every screen the plan touches BEFORE the first edit** — same viewports the walk will use — or the gate reports not-verified with no way to re-earn it. Mechanics (axis scope, rubric, evidence appraisal): `flow-build/references/verify-gate.md`, readable without invoking the skill. Prompt-convention.
- **Independent review follows the matrix, not diff size.** Standard behavior gets one fresh-context reviewer covering the applicable lenses; the sensitive row adds its required specialist floor. Passive documentation stays with diff/consistency review. A re-review after a fix scopes to the finding and its blast radius, not the whole diff.
- **A review finding blocks only with a concrete failure scenario** — inputs/state and the wrong outcome, reproducible now. Coverage or hardening recommendations — including "add stronger tests" after a correct-code verdict — are follow-ups recorded in the close report/PR, never a new fix cycle. An approving review closes review for the changeset; later recommendation-grade findings do not reopen it.
- **Adversarial triage is the default, not a request:** any "is this claim true / does this bug exist / verify this finding" task routes to `review-refuter` without being asked. Budget by risk: trivial/cosmetic finding → no refuter; standard finding → one `review-refuter` pass; hot path (auth, security, payments, migrations, data integrity) or >400 changed lines → 2-3 independent refuters, majority verdict (2-of-3). Related findings from the same diff batch into ONE refuter pass; independent passes dispatch in parallel (single message). **A high-consequence premise that docs cannot close gets ONE read-only refuter pass before the first write**, handed over as a falsifiable statement — even inside a small security-critical change; a deterministic failure is fixed, never debated. Prompt-convention.
- **Parallel work has one gate owner.** When multiple agents (teammates, parallel subagents) write to the same repo, each verifies only its own blast radius (its package/spec subset); exactly ONE agent — the coordinator — runs the merge-boundary gate, once, after every writer is idle. A gate run while writers are active yields a contaminated verdict: discard it, quiesce, run once.
- **Fix budget: two rounds per verification cycle — and the budget governs the MILESTONE, not each reviewer, defect class, or rewrite separately.** After the second round, new reproducible findings become a fresh work unit unless they prove the current changes unsafe to keep. A third failed fix escalates per Chain Interruption and the three-fix breaker in `debugging.md` — the loop never silently extends, and restarting verification to reset the budget is the reopening violation above.

### Chain Interruption
When an agent's output can't feed the next stage (incomplete spec, failing tests, ambiguous review): never silently skip the stage. A technically resolvable gap gets ONE bounded re-run with the clarified ask, reported in the close summary. Second failure — or a gap only the user can resolve — escalates with the specific issue: re-run with clarification, skip with acknowledgment, or adjust the plan.

### Workflow Tool vs Subagents vs Agent Teams
- **Default to a direct subagent.** Explore for search, the domain specialist (table above) for domain work, chained design → impl → tests → review. A single `Agent` call with the right specialist is the correct default for single-domain work — including under `ultracode`. Don't wrap one task in a workflow; don't delegate trivial edits at all.
- **Workflow tool only when** the agent set or execution order is data-driven — computed per run ("review every changed file", fan-out over an unknown-size list) — never when a fixed chain of named agents suffices. Inside a workflow, route each stage to its specialist via `agentType` (table above); the default subagent is glue only — fan-out, dedup, synthesis. An unknown `agentType` throws; there is no fallback.
- **Agent Teams only when** you need persistent parallel workers with shared task lists and P2P messaging, or the user asks.
- **Workflows require explicit opt-in (Claude Code):** the `ultracode` keyword, a standing `/effort ultracode` session, an explicit user request, or `bypassPermissions` — never inferred intent alone.
- **Grok:** the `workflow` tool is on the top-level session (enabled by default; listed next to skills). Subagents and workflow-spawned agents do not receive it. Never instruct a child to launch a workflow.
