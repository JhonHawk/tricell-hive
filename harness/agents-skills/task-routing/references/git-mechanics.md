
## Git Mechanics — branching, commits, PRs, promotion, end-of-work hygiene

> The situational half of the git conventions. The **gates** — what authorizes an operation,
> protected branches, force-push, production promotion — stay always-on in
> `git-workflow.md` and are NOT restated here. Read that one for whether you may;
> this one for how.

### Branching
- **A work branch per change-group is the default** — cut from the base branch, named per Work branches below (`<type>/<TICKET>-<slug>` when a ticket exists). The repo's declared workflow wins: a direct-to-trunk repo (config hub, single-branch, specs) works on its trunk — session mode `direct-base` (`> Commits`). A pre-existing worktree implies the dedicated branch. An approved plan declaring git semantics settles this at the plan gate; deciding late is safe (`git switch -c` carries uncommitted changes losslessly).
- **The base (integration) branch resolves from the repo's own declaration.** Two levels exist: each repo's `AGENTS.md`/`CLAUDE.md` (versioned) and the workspace-level one (non-versioned). Read order: repo `AGENTS.md` (`## Git Workflow` → `Base branch: <name>`) → repo `CLAUDE.md` → the workspace file as project default (opened explicitly with Read — from a child-repo session no harness auto-loads it) → ask; per-repo wins. Known but undocumented → write/update the REPO file (versioned — the edit rides the session's commits; the workspace file is only touched for an explicitly requested project default); documented → respect it; the repo has neither file → derive/ask per session, never create the file just for this.
- **A branch's unit is a cohesive change-group** — one open thematic branch at a time; a new theme waits until the previous one integrates. A worktree is the explicit exception for genuine overlap. **The same theme continues on the checked-out work branch** — never a branch off it with its own PR; a different theme starts from the base. Unsure whether it is the same theme → ask one question before branching, never decide alone in either direction.
- **Long-lived branches follow the repo's class** (declared per repo in the project's naming table; undeclared → classify by "does this repo deploy to environments with their own state?"):
  - **Deployable multi-env** (app/service with its own environments): environment branches `development` (default) → `qa` → `production` — full env tokens per `infra-naming.md`, subset allowed when an environment doesn't exist (no QA env → `development` → `production`). Environment branches receive changes only by promotion.
  - **Platform-native deployable** (Vercel/Netlify-style): the platform's model wins — the trunk IS production, previews per PR; don't force environment branches against the platform.
  - **Specs / mocks / docs / config hub**: single-branch trunk.
  - **IaC/infra**: single trunk — environments live in directories/workspaces/var-files, never in branches.
  - **Library/package**: trunk + version tags.
- **Git-flow stays out:** no `develop`/`release/*`/`hotfix/*` branches unless the repo already uses them (migrating such a repo is a planned decision, not a cleanup). `development` above is an *environment branch* (it deploys the development environment), not git-flow's `develop`.
- **Work branches:** `<type>/<kebab-description>` mirroring commit prefixes (`feat/user-auth`), or `<type>/<TICKET>-<slug>` when a ticket exists (`fix/TRI-477-auto-login`) — cut from and merged back to the base branch (`development`, or the trunk).
### Commits
- **The WORK CLASS picks the RECOMMENDED option — a preselection, never a substitute for the question.** Work with a surface only the user can judge (a feature, a screen, a flow) → `interactive`: system-green is not evidence it is right. Work whose correctness a machine settles end to end (migration, infra, refactor, dependency or tooling change) → `automatic`. A single-branch repo → `direct-base`. **An explicit instruction in the session prompt outranks this** (`git-workflow.md > Authorization`).
- **Session mode: ask at first edit-intent, session-scoped only.** The question is mandatory (a structured question, conversation language) and **nothing silences it — the way of working changes within the same repo**, so a repo declaration would be a stale default, not an answer. **Reading this section does not discharge the ask — the ask is an ACT:** emit the structured question before the first Edit or git verb acts on the session's work. **The qualifier is load-bearing: no changeset, no ask.** A read-only or sync-only git verb (`fetch`, `pull --ff-only`, `clone`, `status`, `log`, `diff`, `show`, `blame`) and work on a repo whose changes are not the session's produce nothing to carry, so all four options are undefined and asking is noise rather than caution — the ask fires at the session's first own change instead. Not a silencer: what is deferred is the moment, never the question. The trigger that LOADS this reference stays the broader one (any git verb), since loading is cheap and asking is not. **Never persisted across sessions:** no saved preference, no memory lookup. One answer covers the session; a collision with one repo's state (protected checkout) asks punctually for that repo without re-asking the mode. **ALL FOUR options, every time** — the work class or a repo declaration preselects the RECOMMENDED option; it never shrinks the menu: a subset offered is the ask not made. The options, each with its close contract stated in the question:
  1. **`automatic`** — work branch → seam commits → push → PR to the base → checks green + the PR review pass (`> PRs & promotion`) → merge. **Where the change-group lands on a surface only the user can judge, the chain stops before publishing and waits for their validation — that stop is PART of the mode, never an exception to it** (`> PRs & promotion`). Nothing stays on the work branch: the change-group ends integrated in the base. Done = PR merged, plus deploy-job success where the branch deploys an environment.
  2. **`interactive`** — work branch → seam commits → local gate → the in-vivo pass → **STOP: nothing is pushed and no PR is opened.** The app stays UP on that same production build (`build` then `start` — never a second stack), handed over with the concrete steps to exercise the change: module, action, expected result. On the user's validation the chain resumes — push → PR → checks → Phase B — and **the agent merges when all four hold: checks green (never pending or red), no conflicts with the base, no open Phase B finding at medium or above, and the base is not the production-deploying branch.** The merge is part of the mode, never reserved for the user — what the mode reserves for them is the validation. Any one failing asks for approval naming which — except an open finding, which is fixed, never asked around (Phase B bullet below). **One route ends the chain earlier:** a `human` review route (`> PRs & promotion`) closes the change-group at the open PR with the reviewer requested — the merge is theirs after approval, and Done = PR open and handed to the reviewer. Until that validation the seam commits live on the work branch and nowhere else — nothing has left the machine. Done = merged, or approval requested with the reason.
  3. **`direct-base`** — no work branch, no PR: seam commits pushed directly to the base branch — the mode for a single-branch repo or one whose history shows direct-to-default as the norm. Done = change-group verified, committed, and pushed.
  4. **`hold`** — working tree only; diffs at close; commit on the USER's approval (the "review" here is the user's read of the diff — distinct from the agent review pass). Done = the user approved and the commit landed.
  An ambiguous answer defaults to `hold` (the safe mode). **Non-interactive with no way to ask** (bypass flags alone do NOT qualify — they remove permission prompts, not the ability to ask) → `interactive`, which publishes nothing without a validation that cannot arrive. **No mode authorizes out-of-scope work, and the safety gates stand in every one of them.** **"Keep it local" is an instruction, not a mode:** implement, verify, commit locally, and list the pending publish steps — never leave verified work uncommitted. When the chosen mode includes a PR, the same question block also resolves the Phase B review route (`> PRs & promotion`) — always: a repo declaration is the recommended option, never the answer. A verbal change overrides the session — but only phrases naming a mode; "espera" / "no commits aún" are pauses, not mode changes. A project may declare squash-only or other semantics.
- **The mode answer publishes authorized work; it never authorizes implementation.** `automatic` or `interactive` answered on its own is a delivery grant for work that is or becomes authorized — the implementation verb ("hazlo", "implementa", an approved plan) is a separate act, and a design-decision answer is not it either. **In a flow workspace, a ticket batch or multi-task objective gets NO standalone mode ask:** the only place it is asked is the `/flow-plan` gate, folded below — asked earlier it reads as approval of a plan that does not exist yet.
- **Multi-task plans fold the ask into the plan gate as a VISIBLE decision line**, seeded from the WORK CLASS — never buried in a plan's assumptions, and recorded as the plan's delivery grants (`flow-core/references/plan-format.md > Delivery grants from the session mode`): `interactive` and `automatic` both grant the merge into the base — a plan omitting `merge` under either records a narrowing the user asked for, never the mode's reading. **Legacy tokens:** `publish-autonomous`/`full-autonomous` and `pr-merge`/`pr-open` read as `automatic`/`interactive`. A repo still declaring a `Git mode:` at all only preselects with it — it never answers, and the line is removed on the next pass through that file (`agents-md-primary`). Unattended runs never ask: `automatic` on the dedicated branch, bounded at the production line — the run's own PR merges into the integration branch once green, promotion into a non-prod environment branch is declared, and a merge or promotion into the production-deploying branch waits for a human. Protected refs keep per-changeset confirmation for DIRECT commits regardless of mode.
- **Conventional commits** (`feat:`, `fix:`, `refactor:`, `chore:`, `docs:`, `test:`, `perf:`, `ci:`; optional scope), small and focused — one concern per commit, split mixed ones. Never any AI attribution in commits, PRs, messages, or file outputs.
- **Checkpoints** (plans with 4+ file-modifying tasks): a progress pulse roughly every 3 such tasks — a brief note by default; a blocking question only when something is decision-relevant (deviation, concern, red tests).
### PRs & promotion
- PR title in conventional commit format; description covers what/why plus verification. One logical change per PR.
- **Shared integration branches receive changes via PR**, never a direct local merge, wherever the project uses a PR gate; a solo repo without one may merge locally.
- **The user's validation is what launches the publication block — and nothing that costs money or an iteration fires before it.** Work whose surface only the user can judge (a screen, copy, a flow) verifies locally first — the affected subset, then the in-vivo pass on the production build — and STOPS there. **The validation is of the RESULT, never of the request:** what launched the work — "hazlo", "aplícalo también a X", the ticket itself — is authorization to BUILD and can never be the sign-off, because the user cannot have approved something that did not exist when they spoke; an earlier session's sign-off covers what it saw, never the next change. It arrives after they were handed the running build and the steps to exercise it. Push, PR, Phase B, and the merge then fire as ONE chain on that sign-off, no re-ask per step, **up to the boundary the declared mode sets** — `interactive` resumes the whole chain on that sign-off and merges under the four conditions above; `automatic` runs it through the merge. A paid review app spent on a diff they may still send back buys another paid round for every change they ask for, which is why **a repo declaring `PR review: <app>` declares WHICH app to recommend, not that the agent may spend it unprompted**: the trigger comment goes out on the user's approval or their explicit request. **In `interactive` the stop IS the mode; in `automatic` it is the user-judged-surface carve-out** — so `automatic` gets it too, and no repo needs to declare that it has user-judged surface. What a repo MAY declare is the opposite — that it has none, so the chain never stops — and that exemption is visible and auditable, which "nobody thought about it" is not. Confirm-gated (their sign-off IS the key); for machine-settled work (migration, infra, refactor, tooling) `automatic` runs unchanged.
- **A documentation-only change-group goes direct-to-base, whatever the mode declares.** Prose with no runtime — READMEs, ADRs, instruction files (`AGENTS.md`/`CLAUDE.md`), docs, evidence write-ups — has nothing a PR gate can verify: CI exists to prove code still works, and there is no code. Commit, push to the base branch, done; the review is the diff the user already saw. **Strictly exclusive, and split rather than waved through:** one file of code, config, schema, dependency manifest, hook manager, or CI workflow in the group and the declared mode applies to the whole thing — a `lefthook.yml` or a `.github/workflows/*` riding along makes it a code change-group, not a docs one. Protected refs are untouched: direct-to-base means the integration branch, never the production-deploying one. **Prompt-convention** — its deterministic backstop lives in the repo's own CI, whose change selector must exclude non-build inputs (`devops-principles.md`); without that filter a docs commit still lights every app pipeline the moment anyone does open a PR.
- **Review runs in two phases with different jobs — never a third PHASE** (Phase B re-runs per push are not new phases). **Phase A:** the change-group's ONE independent agent review (`agent-routing.md > Verification runs in fresh context`; budget in `testing.md > Execution Scope`) runs on the diff before commit/push; a flow skill's own verify gate discharges it with its declared placement. **Its verdict names the candidate it read** — the commit SHA, or for a working tree `git diff HEAD -- <reviewed paths> | shasum -a 256` plus the untracked reviewed paths listed — goes in the evidence; a later change to the reviewed files re-reviews the delta, never inherits the verdict. Prompt-convention. **Phase B:** a bug-hunt pass on the OPEN PR — a release gate of the merge, analogous to CI, not a second review, and **correctness-only** (it fires only once the user has validated, wherever their validation gates publication — bullet above: reviewing a diff they may still send back spends the gate twice): bugs that would break production; reuse/simplification/altitude belong to Phase A and are not reported at the gate (for the harness-native route the scope instruction rides the invocation prompt). Phase B re-runs on each push that answers one of its findings, scoped to the finding and its blast radius; from round 2 it reports medium or above only — nits and recommendations accumulate to the close report, never open another round. **A Phase B finding is fixed, never dispositioned by the agent — severity decides only when.** Critical/high/medium on the app's own scale (P0–P2) → fixed on the PR before the merge; under a `/flow-plan` contract the fix reopens the `verified` plan through its declared path first (`plan-format.md`, action/state compatibility), never an edit on a closed plan. Low → fixed at once when small; broad work becomes a follow-up ticket, reported in the close table. Two exits from fixing, no third: a refutation with evidence (`review-refuter`), cited on the PR; or a fix that reverses a frozen plan decision or crosses a contract/migration boundary — asked before the merge, with the finding, the decision it contradicts, and a recommendation. "Out of the plan's scope" is neither exit, and a disposition comment on the PR is not asking. Prompt-convention. **The route is the user's cost decision, never the agent's.** **The route is ASKED every session that opens a PR — a repo declaration never silences the question.** The repo's `## Git Workflow` → `PR review: <app-name> | native | human | none` names the RECOMMENDED option: it goes first, marked recommended, in the session-mode question block when the chosen mode includes a PR, with `none` always among the options — the user sizes the change (a logo swap does not earn a paid round), the agent never does. Undeclared → the same question with no recommendation. Session-scoped like the mode: **repo app** (Bugbot, `@codex review`, Copilot — the agent posts the trigger comment itself: that launches the gate, it doesn't duplicate it; the wait starts there, and the app's review is async, NOT part of "checks green") · **harness-native** (no marginal cost: Claude Code `/code-review <PR#> --comment`, which posts its findings as PR comments · Grok `/review --pr <n>`, whose comments land PENDING until the user submits them — the submit only publishes; the findings are already the agent's to fix · Codex `codex review --base <base>` pre-push · opencode's GitHub App. **Under every route but `human`, waiting for the review and fixing its findings is the agent's step** — a review still running is never handed over as the user's to-do) · **human** (a reviewer who is not us — a teammate, the client's team: the agent opens the PR, requests the reviewer, and the change-group CLOSES there under every mode; the merge is the reviewer's after approval, never the agent's, and a session ending at that open PR reports done-for-this-level, not a pending merge) · **none** (the merge gates on checks alone — reported as such at close). `/code-review ultra` is the user's explicit escalation, never an automatic step. A single-commit PR whose identical diff Phase A already reviewed gets Phase B only — a manual review is never repeated without a finding motivating it. **A promotion PR (environment branch → environment branch: `development → qa`, `qa → production`) gets NEITHER phase and no review-app trigger:** it carries diffs already reviewed and merged on the source branch, so its gate is deploy verification (`promotion-playbook.md`), never a correctness re-run — posting the review app there spends a paid round on reviewed code. A declared review app that posts NOTHING on the PR is reported at close as "Phase B: did not run (app posted nothing)", never counted as a pass — the merge may proceed on its remaining conditions, but the vacuity is named in the close report.
- **A long change-group with no plan gets the same proposal before the push**, not after: past the point where a reviewer could judge it in one sitting, offer the cuts — named seams, not a line count — or a single delivery (`flow-core/references/plan-format.md > Proportionality and delivery`).
- **You own the CI of any PR you open, and of the landed branch until it is green:** watch the PR checks from the push — a merge outside your grants, or reserved for a reviewer, does not release them: red checks are read, reported with their cause, and fixed when the failure is yours, never left for whoever merges. Wait for them before merging (never on red or pending), watch the post-merge run, and fix failures you triggered instead of handing them back. CI is authoritative over local runs — a green local gate never stands in for a red check. The post-merge run includes the branch's deploy job where the branch deploys an environment (Amplify, Vercel, pipeline) — "merged" is not "deployed": report the promotion done only on the job's terminal success, watching it in overlap with remaining work.
- **CI watching overlaps remaining work.** After a push, start the watch and run the rest of the close work (docs, ledger, memory, report) while CI executes; idle-watch only when nothing else remains. A push without a merge in the session mode's scope (`interactive` before its four conditions, `direct-base`, a `human` review route) may close the turn with CI pending — report the run link and pending state; ownership carries into the next interaction. Under `automatic` an open PR never closes the turn: the close is the merge. After a merge, the deploy job's outcome is part of the same turn — a pending deploy never closes it. Merging never proceeds on pending. **`automatic` authorizes the publication MECHANICS, not unlimited continuation:** a milestone breaker, a new rollback boundary, or a moving baseline closes the session at a durable checkpoint — draft PR + pushed work branch + state recorded — even with the ticket open; the checkpoint is reported as a checkpoint, never counted as done.
- **Promotion moves the integration branch's whole current state**, not the session diff, unless the user explicitly scopes a partial promotion. **Hops run in the chain's order** — each environment promotes from the previous one and is done only on its deploy job's terminal success, so a red or unverified hop blocks the next one rather than being jumped over.
- **Capture the exact candidate SHA before deployment preparation.** If the integration branch moves and introduces an unrelated migration, contract, or runtime change, the milestone closes and the new baseline is revalidated as a separate unit — never absorbed implicitly.
- **A merge never deletes its branch** — no `--delete-branch` on `gh pr merge`, no `git push --delete` in the same step. Branch deletion is end-of-work hygiene (below), after confirming nothing still points at the branch: the base of an open stacked PR, a shared integration branch. Prompt-convention.
- **Stacked PRs:** when a task depends on an unmerged prior PR, branch from that PR's branch and chain the PRs, declaring the merge order in the close report — never block mid-session waiting for a merge. When the parent merges, retarget the child to the new base (`gh pr edit <child> --base <base>`) BEFORE the parent's branch is deleted: deleting the base of an open PR makes GitHub close it, and a closed PR cannot be retargeted.
### End-of-work hygiene (standing-authorized, automatic)

> Fires when the plan or change-group finishes — never on the session ending, and it needs no
> declaration from the user. It is not a wrap-up: the end-of-session consolidation (memory) is
> triggered by the user declaring the session over (`memory-routing.md`).
- Prune branches confirmed 100% merged (`git branch --merged <target>`): delete the local and its merged remote counterpart; return the checkout to the integration branch. Then `git fetch --prune` and fast-forward local integration branches behind their upstream.
- **Unmerged branches are decisions, not noise:** check for real work (`git log <target>..<branch>`), recommend integrating before close, or ask if it looks abandoned. Never silently leave, delete, or auto-reconcile a diverged branch.
- Report: deletions, fast-forwards, divergences, unmerged branches with their recommendation, and the branch now checked out. Report what the WORK reached — never declare the session closed (`reporting-integrity.md`).
### Recovery
- `push` returns 404 on a private repo: check `gh auth status` / `gh auth switch` before assuming the repo is missing; cache the active account for the session.
