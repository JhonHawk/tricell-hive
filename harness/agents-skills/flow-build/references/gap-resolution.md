## Gap Resolution

> Owns **prerequisites** (missing-and-required). Risks (present-but-fragile) → `critical-thinking.md`; conflicts between present-but-disagreeing sources → Divergence below. **Principle:** resolve required gaps within scope or surface their blocking decisions before dependent work; record them in a plan only when that route is selected.

**Gap vs observation.** A gap is a missing condition required for the authorized deliverable — source access, metric definition, dependency, interface, migration, contract or verification evidence. Resolve it within scope or surface the decision it needs. An unrelated finding is an observation: recommend, never silently add it to the work.

### Gap analysis — investigate always, ritualize only on findings

- **Investigate prerequisites for the requested deliverable before writing tasks.** Verify source access, currency, definitions and evidence method for research/analysis; constraints and decision owners for proposals; target, permissions and rollback for operations. For software changes, also verify files/tests, interfaces, dependency versions, configuration and the infrastructure needed for implementation, verification and authorized promotion. Never invent app, CI or publication prerequisites for a conversational answer.
- **Resolve applicable in-vivo prerequisites before the first edit:** account/role, tenant scope, seed data and starting state. Missing is a prerequisite, not a blocker when an authorized isolated setup can supply it; seed or create it and name the task (`testing.md > Execution Scope`). Access or authority only the user holds remains an explicit blocker.
- **Findings drive the formality.** Clean check and no open decisions → continue the selected route. Real gaps or blocking decisions → classify below; document them in the requested deliverable or existing work record, without creating a plan by default.
- **Within a selected plan, classify by size:** a gap resolvable in ≤3 tasks leads the plan (first tasks, visible at the plan gate); >3 tasks → propose a separate prerequisite plan. Other routes resolve required gaps proportionally within scope. Observations remain recommendations.
- **When a plan gate applies, consolidate applicable delivery decisions:** session git mode, PR review route, contract confirmations (`cross-service-workflow.md`) and routing chain (`agent-routing.md`). **Design doubts do not wait for it:** ask scope changes and user-owned decisions before writing tasks on their premise. An analysis or proposal without delivery effects does not acquire a publication gate.

### Decisions to close before executing

A decision that blocks task detail is resolved before the tasks are written, never mid-execution. After the gap analysis, enumerate them and classify by owner:

- **Technical** (the implementer's to make): state the recommendation and proceed. Verify against a peer/tool only on signal — version-sensitive surface (context7), low reversibility, or genuine dispute — not as ritual for every choice.
- **Consequential-design classes carry their evidence with the recommendation.** For architecture, cross-service contracts, persistence, concurrency and security, verify against authoritative sources and include consensus citations (official docs/standards, context7/web) in the requested deliverable; use the plan artifact and gate when that route is selected. Presenting a recommendation without citations names why not (stable surface, repo precedent) explicitly. **A citation is a claim→source mapping** (`sdd-explore` in `evidence` mode produces it) — source identified (URL or doc + version, access date) with contradictions recorded, not a bare link. Research outcomes are **resolved** (sources support the recommendation) or **partial** — a partial outcome remains an open question, never an established decision.
- **Stakeholder/PO: ask while the plan is being designed, routed by what the ANSWER does — never by how many have been asked.** One that **redirects, narrows, expands or resequences** the design is asked IN THE MOMENT, before writing on its premise (the test: would a different answer change what gets written next?); no question budget applies — answered there it costs one exchange, discovered after the contract is frozen it costs a revision. A follow-up, or one whose answer changes nothing structural, ACCUMULATES and is emitted as one batch at FOUR or when the design finishes, whichever comes first — **emitting it pauses the work until the answers arrive**. Either the harness's question tool or a prose block whose every option carries its effect in one line, answered by exception (silence takes the recommendation). Never pre-answered into the plan, never absorbed by a blanket contract approval (`CLAUDE.md > Communication`). **Every question is answered before the plan summary is presented** — one still open means the plan is unfinished, not that the gate inherits it. **A plan that asked nothing states that at the gate**, in one line: a question-free plan is a claim that the user had nothing to decide, made out loud rather than inferred from an absence. When ownership is unclear → treat as stakeholder.
- **Replacement scope** (what survives of a legacy path being replaced) is always stakeholder-owned — the gate and its three shapes (complete / frozen retention / functional coexistence) live in `CLAUDE.md > Agent Behavior > Task Execution`; a recorded prior decision discharges it.
- **Work crossing independent rollback boundaries** (IaC state, database schema, application release, external integration) **is split into separately TERMINAL milestones before execution**, at the plan gate when present. One session owns one milestone unless the user explicitly authorizes a multi-milestone run; each milestone closes with durable evidence before the next starts.
- **3+ blocking decisions → present a table** (`Decision · What's at stake · Owner · State · Recommendation · Blocks`, where State is `open` or `resolved`); 1-2 → plain prose. Use the conversation or existing work record; include them at the plan gate when present. A decision that blocks nothing resolves inline.
- **Batching ≠ deferral.** The gate covers what is knowable at plan time; a blocker DISCOVERED mid-execution escalates in the moment — that it was discoverable earlier is a planning defect, but never a reason to sit on it.

### Exceptions
Simple single-task changes (bug fix, config tweak, docs): no ritual — the principle (investigate cheaply, never drop a gap) still applies.

## Divergence Between Sources

> Owns **conflicts**: two authoritative sources disagreeing on the same decision — spec vs ticket, comment vs code, test vs implementation, two specs vs each other. Never pick a side silently, and never hard-code a permanent winner ("spec over code", "tests over implementation") — hard-coded priority hides drift. The rule is surface, then resolve.

- **Default: surface it.** Cite both sources (paths, lines, last-modified context) and get a resolution — which source is authoritative for this case, or update one to match the other.
- **Resolve-by-evidence carve-out** — proceed without a round-trip only when ALL hold: (1) live state or the record trail proves one source verifiably stale (older AND pre-decision); (2) the decision is genuinely the implementer's — stakeholder, contract, migration, and security calls stay hard-blocking; (3) following the current source is reversible. **The carve-out is always reported** — handoff/close summary, plus the commit message when committing. An unreported resolution is a silent one.
- **Unattended runs fail closed:** no human present → report blocked; never self-authorize either side (`reporting-integrity.md > Fix at the Root`). An explicitly-delegated run (the `unattended-delegation` skill) queues the conflict with both sources cited and continues independent work instead.
