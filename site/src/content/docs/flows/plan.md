title: Plan
description: Turn a larger change into settled decisions and small tasks that each come with a way to check them.
---

Plan settles the how. [Hive mode](/flows/hive-mode/) has already settled what you need; Plan sorts out the remaining choices with you first, so whoever builds it does not have to guess.

## When it starts

Hive mode sends a request here only when its how has a decision that is yours, or when the work cannot be finished from your request and the `git diff` alone, such as work handed to another session or agent. You can also ask for a plan directly. A change whose how leaves you no decision needs no plan; Hive mode continues it into [Build](/flows/build/).

Example requests:

```text wrap
Plan the API change, including compatibility and acceptance checks.
Plan moving our uploads to the new storage service. Ask me before choosing anything that affects existing data.
Break this feature into tasks I can review one at a time.
```

## What it asks you

The agent reads the code, your project settings and the existing specs, when the project keeps any, first, then asks only for the decisions that are yours. Facts it can find, it looks up itself. For work that is a ticket, it also checks the ticket's neighbors, unless the assessment already did, as the [neighbor tickets leaf](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/hive-core/tracker/neighbor-tickets.md) sets, so a capability a later ticket owns is decided before the tasks are written.

- When the how has more than one sensible way, two or three approaches in a message of their own before the tasks, each with its tradeoff and one recommended, preferring what the codebase, the standard library or an installed dependency already does over new code or a new dependency; you choose, and they are recorded in the plan's `## Design`. When only one way is sensible, the agent says so and why.
- Choices that change the outcome, asked in rounds and in the shared question format, in the question card where your host's card waits and shows a description per option, and otherwise in the message: each decision carries its situation, what you get and pay with every option, and a recommendation, and the round says how many decisions are still to come. A change to what an interface sends or receives counts as a contract change, and you decide whether it stays compatible.
- For a changed screen, the layout and its states, shown as before-and-after sketches you can choose between; when the Create design stage left an approved screen example, the plan records it in place of the after sketch, adds the task that writes each convention you agreed to record in `DESIGN.md`, and the Figma file and library you agreed to record, which that stage never writes, instead of drawing that region again, and does not settle that composition with a design helper. The business rules you approved in that stage become decisions of the plan, a rule still waiting for your answer is asked before the plan is ready, the plan keeps the business rules in a section of its own, a decision that replaces one marks it cancelled instead of deleting it, and one that changes the scope sends you to Hive mode first, unless Hive mode already settled it. Before that, the agent loads the project's design system through the [UI criteria skill](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/create-design/references/ui-criteria.md): the library, its installed version and its customization layer, recorded in a `DESIGN.md` at the root of the app that owns the screens. When that file is missing or out of date, the plan includes a task that writes or refreshes it, delivered with the change and shown as a diff; outside a plan, the agent writes it only when you ask.
- When the chosen approach reads or changes a system outside the repository, such as a cloud account, an organization or a third-party service, the facts the plan depends on, such as what an account allows or what a branch holds, before the tasks are written. Each external fact is measured with a read-only command and recorded with its source; with two or more systems, one read-only helper per system measures in parallel, and the agent accepts a fact only with the command and an excerpt of its output, checked against the provider's current documentation when it is about a capability, a limit or a permission. A fact that cannot be checked that way is listed as not measured, with the task that meets it first.
- Once the plan is written, how the work is delivered and which code review runs, unless you already answered in this session and repository and the new work does not call for a validation stop your answer lacks. These gate questions carry a fixed header, such as **Delivery** and **Review**, instead of a decision ID. Every change that is not mechanical gets a code review, so the review question picks only its mechanism; when your project's guidance names a mechanism that runs on the agent's host, the agent states it in one line instead of asking. When the delivery in force is `hold` and an earlier work item left uncommitted changes, the next work item asks the delivery again before its first edit. A review by another provider's agent is never offered: it runs only when you ask for it. The recommended delivery follows what you can judge: interactive when the work changes a screen, the text an interface shows or the steps of a flow, or your project requires human validation; automatic for everything else, such as a backend fix or a migration, where a stop would give you nothing to validate. The recommended option is the first one in the card. A one-off operation that leaves nothing in the repository, such as a database dump, gets neither question.
- In the same round, one decision per class of effect the tasks foresee outside the repository: a kind of action on a named target, such as changing access policies in an account, with its spending ceiling. A class you approve covers each effect of that class that the plan's tasks take, within the ceiling, and does not carry over to other work; a class you refuse is not taken and not asked again. Deploying to production and anything irreversible or that interrupts a service people use keep their own question. A plan with no such effects adds no question.

The rules for questions are in the [questions leaf](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/hive-core/messages/questions.md), those for the delivery questions in the [delivery questions leaf](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/hive-core/git/delivery-ask.md), and the delivery modes in the [shared guidance](https://github.com/JhonHawk/tricell-hive/blob/master/content/guidance/global.md); the measurement of external facts and the question per class of effect are in the [outside the repository reference](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/hive-core/plan/external-facts.md).

## What it produces

Plan publishes nothing to the [viewer](/viewer/); a plan with a file stays on your machine, and you review it there or in the message.

A plan stays in the message only when the work fits one session on this machine: it spans no other session, waits on nothing external and is not handed to helpers. Such a plan carries its decisions, criteria, prerequisites and tasks in the message, and the agent keeps a checkpoint file in the host's temporary folder with the decisions, the pending tasks and anything it created outside the repository, so a compacted session can pick up where it left off. The file is removed at Close. The agent writes a plan file when the plan fails that test, such as work that spans sessions or is handed to helpers, when you ask for one, when its delivery spans more than one pull request or repository, or when it changes a contract, stored data, security, money, concurrency or a dependency. A one-off operation always keeps its plan in the message; when one of those conditions applies, it is handled as a regular change. Without a ticket, the file is named by a short slug; a plan never waits for a ticket to exist.

The plan file is one local Markdown file, never committed, in the work's own folder under the project's `workspace/`, named with the date and the work. The folder is the one home of the work: the plan, its research and reports, its captures and its evidence. The plan follows the [plan template](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-plan/assets/plan.md) in one file:

- The header, your request quoted, your decisions in plain words, the business rules, the scope with numbered acceptance criteria, and what the build needs from outside the repository, including the measured external facts and one line per class of effect with your answer, under `## Effects`.
- `## Tasks`: small tasks, each saying which criteria it closes, what it depends on and how to check it, with a `## Checkpoint` and a progress section the build keeps up.
- `## Design`, only when the change has design decisions.

A name the plan fixes, such as a route, a translation key, a table or a field, is written in English even when the plan's prose is in your language, since the build implements it as written; the plan's reviewer reports one that is not. The [naming language rule](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/hive-core/principles/naming-language.md) sets which names stay as written.

When the plan chooses or creates the name of an infrastructure resource or a repository, or infrastructure code such as a Terraform module generates it, the agent compares it with the names your project recorded and reports each one that does not match. A project with no recorded names is compared with the shape its existing resources share, or with a default shape when it has none, as a recommendation, and the agent records the names only if you agree; an existing resource keeps its name unless you ask for the rename. The [infrastructure naming rule](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/hive-core/plan/infra-naming.md) holds the steps.

Before it writes how a task is checked, the agent runs each command that check names once on the base branch, so the plan never prescribes a check that cannot run. It never switches branches or stashes your work to do so. For a command that needs the change, such as a test the task will add, it runs the same runner on an existing test, plus a throwaway test that only imports the project modules the new one will use. Commands that share no database, port, lock or output folder run at the same time, and the others one after another. A command that would change tracked files, a non-local database or a shared resource is not run. A command that took over 5 minutes runs only in its shortest form, such as one test file, and one never timed is cut to that form at 5 minutes. Each command gets one line with its result and date in the proposal's verified context, or in the summary of a plan kept in the message, or `not measured` with the task that meets it first. A command whose runner, script or dependency is missing, and that no task adds, is fixed before the review; one a task adds is written as `not measured` with that task.

Every criterion is one observable behavior, with the observation that would show it false today and an `Observed in:` place where its real effect shows: for a screen or an API the project serves, the candidate served locally with the real build and seeded data, never a mock or emulation of a service the project does not own. A criterion that shows data, such as a count, a total, a report or a generated file, names its expected value and where that value comes from, such as the seed or a database query rather than the screen being tested, and the walk closes it only when the two match, so data that only looks right does not pass. Until a walk observes a criterion in that place it is reported as not verified: Verify's walk closes the ones it reaches, and a criterion that names a deployed environment waits for the functional walk of [Deploy](/flows/deploy/), which naming the environment does not ask for. A criterion that is already true, or that only restates your request, is rewritten or dropped. When the plan has a file, the agent first runs the [coherence check](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-plan/scripts/check_change.py), which reports criteria no task closes, `Closes:` lines naming criteria that do not exist, and malformed `## Business rules` lines, and then an independent plan reviewer checks the plan before it is ready. A plan whose tasks touch two or more domains (server, client, agent guidance, infrastructure, or a screen where you enter or choose data) gets one reviewer per domain, up to three, launched together; each is briefed with the contracts it shares with the others, and a finding several of them report is merged into one. The domains and how they are counted are in the [plan review reference](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-plan/references/plan-review.md).

When the ticket or your request asks for the change in a named environment, the plan includes the promotion to that environment as a task run through [Deploy](/flows/deploy/). Only your own request in the conversation counts as the instruction to deploy there; when only the ticket asks for it, the task asks you first, as Deploy does. Otherwise the plan has no promotion task, and promotions are grouped and run when you ask.

A plan file never enters Git: the pull request body is the public record, with each acceptance criterion and its evidence, and the plan stays as local support material that the retention of [project-layout](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/project-layout/SKILL.md) prunes. A change to an observable contract, permission or stored data that a spec describes edits that spec in the same pull request, as a task of the plan. A project without specs needs none: `Specs` is optional. For work under `Delivery: direct-base` the plan is the same local file; nothing about it is committed.

For explicitly delegated E2E work, the plan binds the objective, acceptance criteria, delivery endpoint, permitted effects, isolation and stopping conditions. The coordinator tracks independent units and their evidence; the [coordination procedure](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-build/references/e2e-coordination.md) defines the handoffs and recovery.

A plan delivered in two or more units (pull requests, commits to the base, or candidates) also gets a `## Delivery units` section in the plan, with one box per unit-level check that Verify ticks from evidence; the [plan record leaf](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/hive-core/plan/plan-record.md) sets when and how. The delivery mode you chose decides what a unit is and whether it stops for you.

## Revising a plan in progress

When a written plan changes during planning or the build, the agent updates in one pass every place the plan states the change: its decisions, criteria, design, the tasks' text, `Closes:` and verification. It marks the new item with `Replaces:`, or a dropped criterion with `Retired:`, reopens the tasks the revision invalidates, and runs the check, which also reports a criterion that names no `Observed in:` place, until it is clean. A verification command the revision changes, or whose runner, dependency or imported module it changes, runs again before the next review round, against the working tree when the build has started. When the revision changed a contract, an interface, a criterion, a decision, an assumption, an external fact, or a verification line, the plan reviewer (`hive-review-plan`) rereads it, through a message to the same reviewer, or a new one given the earlier findings when that message cannot be sent; a revision that applies a reviewer's own proposal as proposed is not reread by that reviewer. While the plan is being planned it gets one reread round at most, and a gap that survives it, or one a later revision brings, comes to you as a decision in the plan summary; during the build, each such revision gets its own round. With several reviewers, only those whose domain the revision touched reread it. The revision is recorded in the progress section and the agent tells you in one line. The steps are in the [flow-plan skill](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-plan/SKILL.md).

## How it ends

The agent summarizes the plan in the message: the objective with the files and areas recounted, and what changed since Hive mode when the count moved by more than a quarter, each criterion, your decisions and the list of decisions it took without asking, the tasks on one line each, what is still missing, the checks and the delivery mode. It then gives the Build command as the next step, and offers to compact the session first, with what to keep, so the build starts without the research and planning history; after you compact, it shows the same next step again. A plan does not authorize implementation: typing that command is what approves the criteria shown and starts [Build](/flows/build/). A correction to a criterion is not approval; the agent revises and shows it again. The summary also names each external fact and each verification command not measured, and each class of effect you answered, with the effects left unauthorized. The steps are in the [plan handoff reference](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-plan/references/plan-handoff.md).

## What it does not do

- It does not write the implementation, or approve commits, pushes, pull requests, merges or deployments.
- It does not hide open technical doubts inside later tasks.

## FAQ

### Do I need a plan for a small change?
No. A change whose how leaves you no decision goes from Hive mode to Build in the same turn.

### Does a ready plan mean the agent may start building?
No. Your reply starts Build, unless you asked beforehand to build after the plan without stopping, unattended delegation is active, or an explicit [E2E coordination](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-build/references/e2e-coordination.md) grant covers the continuation.
