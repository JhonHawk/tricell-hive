title: Verify
description: Check a built candidate at a level you can see and change, then integrate it as your delivery answer allows.

Verify is the step between a built change and a finished one. [Build](/flows/build/) hands over a candidate; Verify gathers the evidence that it meets what you asked for, and says what was not checked. The [Verify skill](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-verify/SKILL.md) owns the steps and their order.

## When it starts

Verify starts when a candidate exists: commits, or the working tree when your delivery answer is to hold. It follows Build in the same turn, with no command to type, unless you asked to stop after Build or to skip Verify. You can also start it on a change that is already built. Without a candidate, it says what is missing and returns the work to Build.

Verify also answers a walkthrough or demo you ask for of an interface that is already built: it follows only its [walkthrough](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/hive-core/ui/walkthrough.md), publishing the captures to the [viewer](/viewer/) and walking you through them, without the suite, reviews or delivery.

```text wrap
Verify the change on this branch and integrate it if everything passes.
Skip verify for this one; I will check it myself.
```

The [project verification contract](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/hive-core/build/project-verification.md), which Verify reads for end-to-end work or when a verification command changes, indexes existing commands and feature journeys for launch, readiness, exercise, evidence and cleanup. A structurally valid contract or a recorded pass is not proof the behavior was exercised: the agent checks the actual results and reports gaps.

For E2E units, an independent verifier checks the exact returned head. The coordinator integrates verified heads into the declared target and checks them together; local integration is reported separately from remote publication. See [E2E coordination](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-build/references/e2e-coordination.md).

## What it does

- Establishes passing evidence for the full local suite, reusing Build's results when they still cover the candidate and running missing or invalidated checks. It serves the candidate the way production would, using and updating what the project's `HIVE.local.md` and the machine file `~/.config/hive/HIVE.local.md` record, and exercises the changed behavior through its real path, checking each numbered acceptance criterion in the place its `Observed in:` line names. A check against a mock or emulation of a service the project does not own does not close a criterion, and a criterion that names a deployed environment is reported as not verified, since only that deployment's functional walk, when it runs, observes it. A screen that shows a sign-in page, an error or an empty list counts as a setup failure, not as evidence. Before it signs in, it reuses an account from your project's account index when one fits, as the [test accounts rule](https://github.com/JhonHawk/tricell-hive/blob/master/content/guidance/global.md) sets.
- In a desktop app with a built-in browser pane, such as Claude, Codex, Cursor or Antigravity, serves the candidate through the app's own preview when it has one and opens each address it shows you for review in that pane, at the port the served app reports. Its automated checks and captures still run in its own browser tool. In a terminal, it gives the addresses as links. See [Show it in the host's pane](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/hive-core/ui/walkthrough.md#show-it-in-the-hosts-pane).
- For an interface change, captures the changed screens and states on desktop and, when the layout is responsive, mobile at the iPhone width of 440 px, the only mobile width it checks unless your project or the ticket names another, including that the changed regions reflow without horizontal scrolling; it does not run the 320 px test of WCAG 1.4.10, even when your project declares an accessibility requirement, unless your project or the ticket names that width, as the [UI verification reference](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/hive-core/ui/ui-verification.md) sets. An independent UX reviewer works from those captures and runs an automated accessibility audit, plus any UI linter your project declares, on each screen and state it reviews. Its brief also says how to reach each state it must check, such as loading, empty, error and the longest values; a state it cannot reach is listed as not covered, and Verify then checks it in its own walk or tells you it was not verified. It reads the project's `DESIGN.md` and also reports, as defects with a priority, the changes that fail the measured checks of the [UI criteria skill](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/create-design/references/ui-criteria.md), such as touch target size, focus handling, reduced motion, or the states of a search or a list, when the change introduced them. A default of your component library that the change uses as the library publishes it, such as its error color, is not reported as a finding or asked to you, even when it misses a WCAG threshold: the review records that check as not applicable. When your project declares an accessibility requirement, that default is listed among the defects that were already there, with its priority and marked as failing that requirement. A component your project customized earlier that fails one of those checks is also listed there, not charged to the change. A decision you recorded in that file is not a deviation, but it never excuses an accessibility minimum in what the change builds. The reviewer's verdict judges only the defects the change introduced; defects that were already there come in a separate list.
- For a native or cross-platform mobile app, serves the build on a device or emulator instead of a browser and captures that screen, which the [viewer](/viewer/) shows at the mobile width. The main agent uses an emulator or simulator already running; otherwise it asks you whether to use a connected Android phone, and with neither it reports the device check as not run. It passes that device's serial or simulator ID to each helper. It never uninstalls an app or clears data on a physical device without asking you, and restores any setting it changes. A physical iPhone is reported as not exercised, and the automated accessibility audit does not run for a native app. See the [device tool section](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/hive-core/ui/ui-verification/device-tool.md) of the UI verification rules.
- Before any review runs, corrects each name the change introduces in a language other than English, such as an identifier, a file, a route, a translation key or a database or API name, and reports it instead when renaming it changes a contract or leaves the work's scope. This runs with every review mechanism. When the change brings such a name and your project runs no spelling check on identifiers, it proposes one and adds it only if you accept. The [naming language rule](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/hive-core/principles/naming-language.md) sets which names stay as written.
- Runs the code review, with the review mechanism in force, alongside the walk: every change that is not mechanical gets one, in every delivery mode. When you chose a host's native review and the work continues on another host, it runs that host's native review instead, and asks again only when that host has none. Every reviewer works in a separate helper that gets the change, its requirements and the check outputs, never the builder's account of why it is right; for an interface change, the UX reviewer also checks how the changed regions affect the layouts and components around them. Findings are checked against the candidate, with a local reproduction when available and authorized or cited source evidence for contradictions established by reading. An unconfirmed concern stays identified as such. A security review runs when you ask for it, or accept it when the agent recommends it for a change that touches a security boundary.
- Records in the work's rule record, in the same turn, a business rule that one of your corrections or answers adds, replaces or cancels; the close writes it to the ticket, as the [business rules reference](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/hive-core/business/business-rules.md) sets.
- Fixes, in one round, your corrections, every interface defect the change introduced, and each confirmed blocking finding, fixing a defect at its cause even when the finding names only where it showed. A second review covers only that round's fixes, and runs only when they change code or a contract: a fix limited to Markdown, tests or comments is committed with an `Unreviewed:` line instead, and files the diff only moves stay out of every code review. A fix to a UX reviewer's finding is reread by that same reviewer, limited to what changed and the layouts that contain it, with its accessibility audit and its layout, keyboard and focus checks, never by a new full UX review. Other findings go to the close instead of another round.

Every review mechanism also examines added or widened suppressions, skipped tests and exclusions. Each gets an evidence-backed disposition; a justified exception is not automatically a defect. The [weakened-check review](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/hive-core/review/suppression-review.md) owns that procedure.

## What it asks you

Whatever your delivery answer, the final report carries a fixed defect's test output seen failing then passing and, when you can see or operate the change as its users do, a **Try it** block: the URL to open or the command its users run, the test account by its index row, the steps and the expected result. A command that only reruns a test is not offered, since the report already names the checks that passed. A validation request ends with the same block.

Under `interactive`, Verify stops for your validation only when the work changes a screen, the text an interface shows or the steps of a flow, or when your project requires human validation. Other work continues to the push, with one line saying it has nothing for you to validate. When your delivery answer stops for validation, Verify publishes the captures of the changed screens to the [viewer](/viewer/), each correction as a new iteration of the same screen, while the reviews still run, naming each difference from the approved example when there is one, saying that approval is subject to their findings, and asks you to approve or request corrections. After a round that changed something visible, it captures only those screens again and asks again. The findings it does not fix are not asked one by one. In its one round of fixes it also fixes a P2 finding whose fix stays in the files the change already touched; it asks on its own only about a finding at a security boundary, on stored data or on a contract, a blocking finding it could not fix, and a visible defect that was already there in a region the change affects; it groups the other P2 findings into one ticket proposal; and it lists the rest, such as a P3, without asking. Each finding appears in one line with its decision and how to reverse it. The ticket proposal and the findings asked on their own come before the push when your delivery stops for validation, at the `ready` stop with the pull request still open, so a fix joins it and its CI, and in the close's findings otherwise, including findings that arrive after the push. A fix you ask for at the `ready` stop is pushed to the same pull request, which waits for its CI again. Decisions follow the [delivery and question rules](https://github.com/JhonHawk/tricell-hive/blob/master/content/guidance/global.md). When your delivery answer does not stop for validation, the final report lists each difference from the approved example that remains after the fix round.

When the pull request opens, its body carries a before and after table of the changed regions, with the images uploaded to GitHub and never committed. In a private repository on github.com only people with access to it can see them. In a public repository, or on GitHub Enterprise Server, anyone with the link can, and only GitHub Support can delete them: there the agent attaches only captures of seeded data and test accounts, and only after you authorize that upload once for the work. Without that, or when the installed `gh` cannot attach files, the body stays in text and the captures stay in the work's folder. See [pull request captures](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/git-workflow/references/pr-captures.md).

## How it ends

Before the push, it ensures the locally runnable CI jobs have current passing evidence, repeating checks affected by changed or uncertain inputs and naming the rest as CI-only. The [Verify skill](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/hive-core/build/checks.md#check-reuse) defines when evidence stays valid; the real-path walk and required independent verification remain. Each check is judged by its own exit status, and a round of fixes reruns the narrowest checks after each fix and the broader ones once, at its end. Then it integrates as your delivery says: push, pull request, a single wait for CI to end, one read of the reviews, and merge. Review bots count only for the latest commit, their findings are checked against the code and the blocking ones get one round of fixes, the rest sorted the same way, and a bot that has not reviewed yet does not hold the merge. With the `ready` delivery it stops before the merge instead, with the pull request open, checked against the current base, for you to merge. A failing CI job is diagnosed from its log and fixed at the cause. [Close](/flows/close/) follows; after a merge or a push to the base, on hosts that can run a command in the background, the base branch's CI is awaited there while the close proceeds, and its result is reported when it ends.
