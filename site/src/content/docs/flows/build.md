---
title: Build
description: Make an approved change in your project and hand over a built candidate with the evidence of its own checks.
---

Build is where the work gets done. The agent changes code or configuration, runs the checks your project has, and reports what it verified and what it could not. It ends at a built candidate and hands it to [Verify](/flows/verify/), which decides the level of independent checking, integrates the result and leaves the close and any deployment to their own steps.

## When to use

Use Build when you have approved a change and the outcome is clear. That can be a saved plan, or just a sentence.

Example requests:

```text wrap
Implement the agreed change locally and verify it. Do not commit or publish.
Continue the plan in the change folder from the next unfinished task.
Fix the date parsing bug and add a test that would have caught it.
```

You do not need a plan first for a small change you understand.

The global core still controls scope, authorization, preservation and secrets.
Build links to canonical procedures when a decision, delegation, artifact or
verification needs them. Reporting applies to findings, relayed results,
explanations and messages with external links or IDs; greetings and short
direct answers need no reference read. Neither an installed reference nor an
optional loader proves that a helper followed it.

## What it produces

A changed working tree, plus evidence:

- The agent checks the current state before editing. If a plan exists, it treats the plan as a claim to confirm, not a script to replay.
- It works in small steps, often with helper agents for pieces that do not overlap, and tells you how it split the work. A helper reads its task, your quoted request and the criteria from the plan itself instead of a summary; without a saved plan, it gets your request word for word.
- For behavior that would hurt if it broke, such as calculations, stored data, permissions or public contracts, it writes the test first and watches it fail, when the project's tests can exercise that behavior. It takes one behavior at a time, and it fakes only what lies outside the project, such as an external service or the clock, never the project's own code.
- Before it writes a test, it asks which realistic change to the code would make that test fail, and skips the test when there is none. It extends the test that already covers the behavior instead of writing a duplicate, and skips an example test that computes its expected value with the code it tests, and it never adds an entry point to the code only so tests can reach it. For pure logic that has a check independent of the code, it can use a property-based test instead of examples, as [test-first development](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-build/references/tdd.md) sets.
- When a change replaces or migrates a writer, parser, query or system and the old path can still run, it runs the old and the new path on the same inputs, with no real external effects, and treats each difference as a defect or a change the plan documents. This old-against-new comparison is part of the [verification reference](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-build/references/verification.md).
- It runs the project's own tests, builds and linters and reports the results, including any that failed or could not run.
- A defect that blocks or breaks what you authorized, such as a failing check, a review finding or a failed verification round, is fixed as part of the work and reported in one line, without asking. The agent asks only when the fix needs something you have not authorized or a choice that is yours. The rule is in the [guidance](https://github.com/JhonHawk/tricell-hive/blob/master/content/guidance/global.md).
- Other side findings are reported, never silently absorbed or dropped; a small, low-risk one may still be fixed in the work and reported apart. That includes a command or tool that failed and that the agent worked around, such as by retrying with another path: the report names the failure and the workaround, and the agent proposes a fix or a ticket for it only when it lies in this project, reporting one in another project for that project's own session. Before proposing a finding as a fix or a ticket, during the build or at the close, the agent searches both the tracker and its memory for duplicates and for findings you declined or asked not to hear about, as [incidental findings](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-close/references/incidental-findings.md) sets.
- For visible interface changes, [Verify](/flows/verify/) has independent reviewers look at the running result. The agent's own look does not count for that. The reviewers report problems that were already there only on the screens the change touches, and a review of a deployed environment whose code matches what was already reviewed locally starts from that local report instead of repeating it. The agent ranks those earlier problems from P0 to P3 by their impact before deciding whether to propose a ticket; breakage the change introduced or made worse is fixed as part of the work, except a fix that would customize the UI library's theme or installed components, which needs your decision or one the project already recorded. The rules live in the [UI gate](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-verify/references/ui-gate.md).
- Every progress or decision message opens with a bold context line, stage · ticket · progress, so you can tell which piece of work it belongs to when you follow several at once, as [reporting](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-close/references/reporting.md) sets. Between tasks it reports progress in a line and keeps going; the completion report and the closing question come when the scope you authorized is done, not after every task. On an iterative route you chose in Research, each finished round is one more progress line; the report and the closing question come when the route stops.
- If you ask how it is going, it answers in a line and keeps working. When a helper or a background process reports back and nothing changes for you, the agent answers in one line too, without listing again what is still running or repeating a question that waits for you. When the notice only says that a process the agent stopped on purpose has exited, such as a server it shut down while cleaning up, the agent writes nothing. A helper that stops while it still waits on work of its own, such as a watcher, a wait or a background command, counts as stopped, not as in progress: the agent checks at once whether the helper and that work are alive and resumes it, as [delegation](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-research/references/delegation.md#check-returned-work) sets. When work is still running at the end of a message, it tells you what will wake it and the duration or deadline of its next wait. Builds, deployments and CI runs it starts are watched with your CLI's monitor tool when it has one, until they finish, with a time limit so a run that hangs still wakes the agent, and a failure does not go unnoticed.
- Topics you add during the build go on a list of open topics. The agent tells you in one line how it classifies each, closes none without a destination, and names them all in its findings and completion reports and in the route and close questions. The rule is in the [guidance](https://github.com/JhonHawk/tricell-hive/blob/master/content/guidance/global.md).
- When your CLI has a task list, the agent keeps the plan's tasks there, also when it continues a plan after a close, so you can see what is left.
- When a plan has numbered criteria, a separate verifier checks each task that is proven by a test or a named check, at the checkpoint the plan assigns to that task rather than after every task. Tasks of one checkpoint are verified together, those that share a file one after another, and a task that depends on a task of its own checkpoint starts without waiting for a verdict, while a task that depends on an earlier checkpoint starts once those tasks are verified. A plan that sets no checkpoints is verified task by task. The verifier starts with a clean context, reads the plan itself and reruns the checks, and never sees the implementer's reasoning or claims; where your CLI offers it, it runs on a different model, but the clean context is what makes its verdict independent. Other tasks are marked done on the evidence of their own check.
- A task added to the plan during the build or after you validated the result is planned and checked like any other: it gets its criteria and a way to check it, and when that is a test written first or a named check, the separate verifier runs before the work is published for merge. If it arrives after the code review ran, the agent reviews what changed since the reviewed commit when an earlier review answer covers it, and otherwise asks you, as the [Plan flow's revision rules](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-plan/references/plan-revision.md) set.
- When it opens a pull request you authorized, the description says what stayed unverified and which assumptions the result relies on. When the work has numbered criteria, it lists the evidence recorded for each criterion and names anything you accepted without verification, as the [Git workflow skill](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/git-workflow/SKILL.md) sets.

Before the first edit, the agent moves a tracked ticket to its in-progress state. If Git delivery was not settled earlier, it then asks once for the delivery mode and the review mechanism, and for a visible interface change also the `UI verification` value, which sets the independent checks that run before you validate; a mechanical change gets only the delivery question. The agent asks these every session, and a `Review`, `UI verification` or `Delivery: automatic` or `interactive` line still left in the repository's `## Hive` section does not answer them. An answer you gave earlier in the session for the same repository and branch is reused, and the agent states the reused values in one line instead of asking again. When the work has a change record that is published with the code, each delivery option also says how that record is versioned at close, so the same answer settles it; a reused answer that did not settle it gets only that question, before the first edit. A narrower instruction in your request still wins. The same round asks for the authorizations the work foresees for later steps, such as a costly check or a shared environment, so the work does not stop for them while you are away; one you leave unanswered stays unauthorized, and an environment the plan did not cover is asked for in one round when the work there starts. When you delegate unattended work or say you are leaving before this round, the agent asks it in text right away and keeps working; without your answers it stops at a verified local result with nothing committed or published. The modes, the questions and the effect of each answer are in [delivery decisions](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-plan/references/delivery-decisions.md), with the review question in [review decisions](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-plan/references/review-decisions.md); how effects beyond your machine are classified is in the [effect authorization reference](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-plan/references/effect-authorization.md), and when a costly check needs your confirmation is in the [verification reference](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-build/references/verification.md#gate-selection-and-timing). The security review runs only when you ask for it, as [flow-security](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-security/SKILL.md) sets: when the change crosses a security boundary, the agent says which in a line and offers the review without stopping the work, as [security boundaries](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-build/references/security-boundaries.md#offer-the-security-review) sets.

The dedicated code review runs once on the local candidate, after the full suite, at the point your delivery mode sets: before the validation request under `interactive`, before the push under `automatic` and under `direct-base` chosen for a code repository, and on the working tree under `hold`, as [dedicated review timing](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-plan/references/review-decisions.md#dedicated-review-timing) sets. Its findings are fixed as part of the work, by severity, as [Verify](/flows/verify/) sets in its [review rules](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-verify/references/review-and-gates.md). The corrections you ask for during validation get one more review, limited to what changed since the reviewed candidate. A follow-up pull request that fixes the same ticket's change, such as a CI or defect fix after its merge, is covered by the delivery you already chose, without a new question. A condition you attach to a grant, such as "no merge until I return", lasts only for the scope you stated. When a human reviewer is assigned or requested on the pull request, the agent reads each of their comments against the code, asks in the thread when one is unclear, applies them blocking-first and replies in each thread, as the Git workflow skill sets.

## What it does not do

- It does not commit, push, open pull requests or merge unless you asked for that effect.
- It does not run the independent verification, the dedicated code review, the close or a deployment; [Verify](/flows/verify/), [Close](/flows/close/) and [Deploy](/flows/deploy/) do.
- It does not mark a check as passed when it could not run it.
- It does not edit a test you supplied as the acceptance check just to make it pass.
- It does not treat a successful build or a ticked box as proof by itself.

## Related flows

- [Plan](/flows/plan/) comes first for larger work and gives Build its tasks and checks.
- [Research](/flows/research/) helps when the cause of a failure is still unknown.
- [Verify](/flows/verify/) follows with the independent checks, the review and integration; [Security](/flows/security/) runs inside it when you ask.
- [Close](/flows/close/) follows when the work is finished, abandoned or paused.
- [Deploy](/flows/deploy/) promotes an integrated change through your environments.

In the viewer, opening a session shows its fixed toolbar above scrolling deliveries and walkthroughs. Rename, archive/restore, keep and confirmed deletion act on the entire session, across tickets; work status remains on each walkthrough. The local name is searchable, and archiving offers Undo. New deliveries inherit archive and keep preferences. Selecting a walkthrough or searching its ticket jumps to it; refreshing the tab restores that selection. Work-state indicators belong to individual walkthroughs; they do not mark the host conversation as closed. Closed describes the work's lifecycle, not approval of its content.

## FAQ

### Do I need a plan for a small change?
No. Give Build the outcome and its limits.

### Who commits and merges?
You decide. Say so in your request or answer the delivery question the agent asks; the answer holds for the rest of the session in that repository. Without that, the agent stops at a verified local result. Under `interactive` it also stops before the push, with the diff and the checks that cover it, even when Verify is skipped, and continues with push, pull request and merge after you validate. When you chose a delivery that commits, the agent commits each task as soon as it is written, before its verification, with the task ID in the message, so the branch history shows each step; each fix, whether from verification, the full suite, a security review you asked for, the UI review or your validation, goes in an additional commit that names the task, and history is never rewritten. A commit records a task, not a verdict: the work is published for merge only when every task is verified or accepted by you, and, in a mode that stops for your validation, a change with a visible interface effect also passes its first rendered view and UI review first, as the [plan execution reference](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-build/references/plan-execution.md) sets. Commits and pushes run the repository's hooks. The agent skips one only with your approval, which lasts for the session in that repository. When a hook cannot run its checks in this environment, the agent runs them another way or tells you which did not run and which tools are missing, before pushing; when you cannot answer, it pushes only if the repository's CI runs those checks. Before merging, the agent makes sure the checks ran on the current base branch, updating the branch and waiting for them again when the base moved, or using the repository's merge queue when it has one.

### What about an urgent fix for production?
[Deploy](/flows/deploy/) handles it: the fix enters the base branch and is promoted at once through each environment, in order. If a promotion would also carry work you are holding back, the agent stops and offers a hotfix branch from production, only where your repository's branch policy accepts it, and asks you before that push. Afterwards it offers a short postmortem, written only if you want it. The procedure is in the [urgent fixes reference](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-deploy/references/urgent-fixes.md).

### What if the agent finds that the plan no longer matches the code?
It looks into the mismatch and updates the plan or asks you for the missing decision before it keeps editing. The update follows the Plan flow's rules for revising a plan in progress: a changed criterion, decision or contract goes back to the plan reviewers once, and a change of intent becomes a new change.

### What happens to a user interface change?
When a change adds or rearranges a layout, the agent captures its first rendered version as soon as it exists and writes it to a small `walkthrough.json` with selected captures, and gives you the artifact's path in one line. In a delivery mode that stops for your validation it then asks you to confirm the composition, while independent work keeps running. Under `automatic`, `direct-base` and unattended delegation there is no such stop: the path goes in a progress line, with no question, and the UI gate judges the composition. The agent leaves the running result available for you to check, with steps to follow, and keeps its screen captures in the work's support folder until the session ends, then cleans up the ones you did not ask to keep. With Hive installed, the viewer renders the JSON; only an absent binary selects a standalone HTML fallback. When you validate a change, the manifest carries the checks table and captures of relevant states, as [flow-walkthrough](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-walkthrough/SKILL.md) sets. Before it asks you to validate, in any mode that stops for your validation, [Verify](/flows/verify/) runs in order the UI review, the full test suite of each affected application locally, even when CI will run it later, and the dedicated code review. The [security review](/flows/security/) is not part of that run unless you asked for it; when the change crosses a security boundary, the validation message names it and offers the review, unless an earlier offer already named it, as [Verify](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-verify/SKILL.md) sets. You can have the agent open the viewer with `hive view open`, approve, or write your corrections in the answer's free-text field so they arrive with their detail; the agent opens nothing any other way. To keep walkthroughs after the session and browse them by project and session, you can run the local viewer `hive view`, which the agent never starts; how the viewer stores, lists and retires them is in the [README](https://github.com/JhonHawk/tricell-hive#review-ui-walkthroughs-in-one-place).

The UI review keeps the design system of your UI library as its baseline: a value the library sets by default, or one your project recorded, is not reported as a contrast, color or sizing problem, though broken layout, missing states, keyboard order, a missing focus indicator or a missing accessible name still are, and a fix that would customize the library's theme or components is applied only with your decision or the project's. When a problem comes from a shared source, such as a theme token, it is reported once and recorded in the project's UI guide, so it does not come back for every screen you touch. The rules live in [UI review criteria](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-verify/references/ui-review-criteria.md#design-baseline).

Approval applies to the result you saw. If a later fix, including one from code review, affects verified views or journeys, the agent refreshes that evidence before delivery. It asks for approval again when the visible result you accepted changes, as [the UI gate](https://github.com/JhonHawk/tricell-hive/blob/master/content/skills/flow-verify/references/ui-gate.md#changes-after-a-gate-or-approval) sets.
