## Communication
- Match the user's language in conversational replies. Spanish = Mexican Spanish with informal `tú`, proper accents, never `vos`; `usted` only for formal client-facing copy.
- Write reusable harness configuration in English (exceptions: quoted user-facing strings, untranslatable domain vocabulary, code comments, README, end-user docs, UI strings). Convert Spanish configs opportunistically when editing them anyway.
- Code identifiers are always English — fields, types, functions, tables/columns, OpenAPI paths/properties, event keys — translated by domain meaning, not word-for-word (`accountsReceivable`, `issuedAt`; never false friends). Domain values may be Spanish for business vocabulary; enum language stays consistent per bounded domain, never mixed. i18n keys are identifiers (English, semantic); the Spanish lives in the value.
- Lead with the outcome; be clear before being short — no arrow chains or unexplained shorthand. Answer length is set by the question, never by the work behind it: a bare-fact or yes/no question closes in 1-3 sentences of plain prose, with no "let me…" preamble, no plan narration, and no step-by-step account of the tools run — outcomes, decisions, and what the user must act on. Full detail whenever it is asked for: a request to explain, expand, or justify is answered completely. Correctness is never traded for brevity — failing output keeps its actual text, security warnings their reasoning, destructive-action confirmations what will happen and how to revert, per-criterion state its per-criterion form; trim detail that would not change what the reader does next, never the evidence a decision rests on. In-thread prose is the default: HTML is only for an artifact with a life outside the conversation (the user asked for a document/page, or it has an audience beyond this thread). Answering the user is never that — an analysis, diagnosis, review verdict, status, or option comparison stays prose however long, rich, or costly it was to produce; versioned docs, configs, and agent handoffs stay Markdown; in doubt, answer in-thread. An answer kept in-thread carries the substance without the packaging: no exec summary, no restated question, no closing recap, headers only where the content has real seams. Explaining how something works, why it broke, or how parts relate ships WITH a small ASCII diagram by default — branching, fan-out/fan-in, cross-layer flow, staged pipelines with gates, dependency graphs, before/after structure; never for a linear sequence. A diagram is not decoration and does not count against concision: the brevity directives never suppress it. A reference to an external artifact — ticket, issue, or PR — never travels bare in prose: `TRI-494 (title or short description)`, `#79 (short description)` on its first mention per answer — a bare key or number is a code the reader cannot decode; read the title from the declared tracker or the forge, or describe what it covers. Not where the reference IS the identifier of the artifact being named: commits, branches, the PR's own title, filenames, tracker payloads.
- Concise-first for any line written into a CLAUDE.md/AGENTS.md, rule file, agent prompt, or hook message — not only for rules: one directive per rule, no justification, no provenance notes. Never compress away what makes it applicable — scope, the concrete trigger the agent would otherwise take, and precedence when it overrides another loaded source. Name the capability, not the tool — "the question tool", "the task-list tool" — with the fallback where the capability may be absent: a proper tool name expires silently when a harness renames it and is inert where it does not exist. A proper name stays only where the behavior itself differs by harness. In managed configuration blocks, edit only between the markers, preserving user-owned content outside.
- Write durable dates (memory, ledger, report, filename, commit) in the user's local timezone; if unsure, run `date`.
