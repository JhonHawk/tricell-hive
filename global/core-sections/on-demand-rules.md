## On-Demand Rules
- The routers are `language-rules`, `task-routing` (also fired from the Git section above, at first edit-intent or the first git verb), `workspace-conventions`, `memory-policy` and `unattended-delegation`. Not invoking one is identical to not having its rule. Load it BEFORE acting, never after; being wrong costs one read, skipping costs the rule. "Simple edit", "I know this convention", "I'll check it afterwards", and "too small to route" are rationalizations, not exemptions — size decides delegation, never whether a rule applies. A reference already read this session (and not compacted away) is not re-read.
- MANDATORY FIRST ACTION for any code task on Codex, opencode or PI: invoke `language-rules` and read the references matching the files in play for THIS task — stack rows plus the quality depth rows whose triggers fire — not the repo's whole stack inventory. A delegated task's rules are the executor's, not the orchestrator's — which loads rows only for code it writes itself, when it touches it inline. Review/verification subagents load only their lens's rows. No rule loads by file kind: on Codex and PI the `rule-delivery` hook holds your first matching write until its reference is read — read it first and skip the hold, which on Codex never re-arms after a compaction. opencode has only this skill. Exception everywhere: naming identifiers before the file exists (new fields, enums, table/spec properties) fires nothing — invoke `language-rules` and read `identifier-language.md` BEFORE choosing the names; the gate states the rule, that reference the judgment.
- Before substantive research, BI, architecture, infrastructure, agent configuration or development, invoke `task-routing` for deliverable, effects, evidence and stopping condition. Also load it before project edit-intent, the first git verb, delegation or plan tasks. Short self-contained questions and trivial mechanical work skip intake; project edit/git gates still apply. Mechanics and prerequisites live in the router; git mechanics apply to project edits or git operations.
- Before creating/moving/naming ANY file outside application source in a `projects/<group>/<project>/` workspace (or a repo with `_support/` or a `<project>-specs` sibling), before STATING in an answer or plan where an artifact, script, report, or doc will live (a path or folder named in prose is the act), before "what's next" with a ledger, before offering `/flow-*`, and before changing a cross-service contract: invoke `workspace-conventions`.
- Before the FIRST Engram memory operation of a session in a multi-repo workspace: invoke `memory-policy`. Floor even if it never loads: one unified Engram project `<group>-<project>` per workspace (`.engram/config.json`; ambiguous → pass `project` explicitly); status facts upsert via deterministic `topic_key`, never append duplicates. Plugin protocol wins on mechanics; mid-session `mem_save` only for facts that would hurt to lose now (decision, root cause, correction) — the rest consolidates at close in ONE pass (upserts plus one summary, updating any mid-session summary). No Engram in session → skip.
- On an explicit unattended handover ("full control tonight", "don't ask until I'm back"), or on a scheduled/background turn whose ledger declares a matching standing job: invoke `unattended-delegation` BEFORE declaring the mode accepted. Silence, absence, or a long task never activates it; non-delegated unattended runs fail closed.
- With a project ledger (`_support/PROJECT.md`): never execute a flow command uninvited; never offer a production deploy as an automatic next step.
- An endpoint another service consumes, changed cross-service shapes, or new events/webhooks: define or update the contract BEFORE implementation (`workspace-conventions`); touching multiple repos is not itself a trigger.
- Answer "what's pending / where are we" from ground truth by claim type: implementation → git first, on a FETCHED ref (`git fetch`, then read `origin/<branch>` — never the local checkout: a stale checkout turns "zero usages" into a false absence claim); tool/library behavior → docs for the installed version, never latest. A workflow, script, command, or path named in prose → the artifact itself, starting with whether it exists: prose describes the system as of the day it was written, and a migration falsifies it without editing a line, so N documents agreeing are not N confirmations when all derive from the same superseded state. A negative claim carries the evidence for the negative (the validation that refuses it, the absent file, the date checked). Ledgers, tickets, and memory corroborate, never substitute; on conflict, live state wins. Beyond one quick call, delegate the external reads (tracker, PRs, deploy jobs, remotes) to state-fetcher; reading the local ledger and deciding what is pending stays yours.

Code discovery: `rg` for search and absence claims — including the absence you assert by fixing one occurrence and moving on — then Read. Full routing and the anti-conclusion discipline: the language-rules `code-search` reference — load it before discovery/search work.
