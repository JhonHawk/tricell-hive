## Work Style
- Non-trivial multi-step work: create and maintain a task list before editing. Read before writing; follow repo conventions. A mechanism copied from another repo carries preconditions — verify each in the DESTINATION before shipping it (platform feature enabled, permission scope, secret, runner label, branch/env name); where one cannot exist, adapt rather than port it broken. Keep edits scoped to the request — no unrelated refactors or cleanup. Code comments state only what the code cannot show (a constraint, a why) — never restate the line, narrate the change, or address the reviewer.
- Act when you have enough information; do not re-derive established facts, re-litigate settled decisions, or narrate options you will not pursue. Verify cheaply before reasoning expensively — the cost of the check decides the order: a command, file read, query, or a read of the authoritative source for a documented fact settles the assumption before any diagnosis or plan is built on it (a wrong premise discards everything built on top; the check costs seconds); a check that is slow, remote or irreversible inverts the order — enumerate first (next bullet). Not measuring: a check with no named assumption to falsify, and a proxy that can read true while the question stays open (a grep miss, an early-green status). Only the user can resolve it → ask.
- Before an action verified by something slow, remote or costly (a CI run, a deploy, a migration) or irreversible, answer one question by enumeration: how many instances of this class exist, and did I list them? Deep investigation of one hypothesis covers depth, never breadth — the same invariant in a second file, a sibling gate never read, a call site outside the module you fixed. The sweep costs seconds against a cycle that costs minutes; that asymmetry is the trigger, never a feeling of having investigated enough. A known cause bounds the diagnosis, never the scope: the failing check names what is wrong, never how many times.
- A doubt with a documentary answer is resolved, never handed over: before classifying a decision as the user's, name the question blocking it and read the authoritative source (official docs, the spec, the standard; web search when no docs exist). Low reversibility raises the investigation depth required, never moves ownership — "delicate" is not "irreversible". Applies while the doubt is nameable as a question with an expectable authoritative source.
- **Consequential design decisions (architecture, cross-service contracts, persistence, concurrency, security): cross-reference the recommendation against industry consensus UNPROMPTED** — official docs/standards, citing the why — before presenting it; version-sensitive library surfaces go through context7 anchored to the installed version; the plan gate carries the citations.
- **Before writing a library call, option, prop, flag, or config shape, query the context7 docs tool for the version the lockfile/manifest pins** — one query returns that version's API surface: seconds, against a build failure from a wrong signature; web search is the fallback. A pattern-level answer already in hand does not cover the call detail you are about to write. Signals, version anchoring, mechanics and fallback: `context7.md` via the `language-rules` skill.
- Decisions get a recommendation, not a survey. Sources disagree → surface both with paths; proceed only when live evidence proves one stale AND the call is the implementer's and reversible (never contracts, migrations, security), reporting at close. Close blocking decisions during planning: technical → stated recommendation; stakeholder/contract/migration/security → one up-front gate. A mid-execution blocker escalates in the moment.
