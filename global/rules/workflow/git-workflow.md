## Git Workflow

> Universal conventions. Project `CLAUDE.md`/`AGENTS.md` overrides (protected branches, branching model, commit semantics) win. **Precedence:** explicit user verb > invoked flow skill's declared git scope > session defaults — never re-ask at a lower level what a higher level settled. Safety gates apply at every level.

### Authorization
- **An explicit git verb IS the authorization** for that operation on the changeset at hand. Zero redundant confirmations: consolidate anything genuinely ambiguous (file scope, destination, strategy, a safety gate's confirmation) into ONE question block up front, execute the whole chain without interruption, then summarize — SHAs, refs updated, tree state, next step as a suggestion, never an action.
- **Infer before asking:** draft the Conventional Commit message from the diff; stage the session's files (all, when the whole tree is the session's); use the single remote/upstream. Ask only what the diff, session, or repo state cannot answer.
- **Strict scope:** execute only the requested verbs plus what the question block authorized — never chain unrequested operations or "complete the flow". Authorization does not extend to later changesets unless commit autonomy applies (below). Session-close hygiene (below) is standing-authorized.
- **Flow skills:** a user-invoked flow skill's declared git semantics (per-task commits, push, PR, merge to a non-protected integration branch) are authorized by its invocation and approved plan. Safety gates never relax.
- **No pre-commit gates inside git commands** — lint/build/tests run at task level, before the git task.

### Branching
- **A work branch per change-group is the default** — cut from the base branch, named per Work branches below (`<type>/<TICKET>-<slug>` when a ticket exists). The repo's declared workflow wins: a direct-to-trunk repo (config hub, single-branch, specs) works on its trunk — session mode `direct-base` (`> Commits`). A pre-existing worktree implies the dedicated branch. An approved plan declaring git semantics settles this at the plan gate; deciding late is safe (`git switch -c` carries uncommitted changes losslessly).
- **The base (integration) branch resolves from the repo's own declaration.** Two levels exist: each repo's `AGENTS.md`/`CLAUDE.md` (versioned) and the workspace-level one (non-versioned). Read order: repo `AGENTS.md` (`## Git Workflow` → `Base branch: <name>`) → repo `CLAUDE.md` → the workspace file as project default (opened explicitly with Read — from a child-repo session no harness auto-loads it) → ask; per-repo wins. Known but undocumented → write/update the REPO file (versioned — the edit rides the session's commits; the workspace file is only touched for an explicitly requested project default); documented → respect it; the repo has neither file → derive/ask per session, never create the file just for this.
- **A branch's unit is a cohesive change-group** — one open thematic branch at a time; a new theme waits until the previous one integrates. A worktree is the explicit exception for genuine overlap.
- **Long-lived branches follow the repo's class** (declared per repo in the project's naming table; undeclared → classify by "does this repo deploy to environments with their own state?"):
  - **Deployable multi-env** (app/service with its own environments): environment branches `development` (default) → `qa` → `production` — full env tokens per `infra-naming.md`, subset allowed when an environment doesn't exist (no QA env → `development` → `production`). Environment branches receive changes only by promotion.
  - **Platform-native deployable** (Vercel/Netlify-style): the platform's model wins — the trunk IS production, previews per PR; don't force environment branches against the platform.
  - **Specs / mocks / docs / config hub**: single-branch trunk.
  - **IaC/infra**: single trunk — environments live in directories/workspaces/var-files, never in branches.
  - **Library/package**: trunk + version tags.
- **Git-flow stays out:** no `develop`/`release/*`/`hotfix/*` branches unless the repo already uses them (migrating such a repo is a planned decision, not a cleanup). `development` above is an *environment branch* (it deploys the development environment), not git-flow's `develop`.
- **Work branches:** `<type>/<kebab-description>` mirroring commit prefixes (`feat/user-auth`), or `<type>/<TICKET>-<slug>` when a ticket exists (`fix/TRI-477-auto-login`) — cut from and merged back to the base branch (`development`, or the trunk).

### Commits
- **Session mode: ask at first edit-intent, session-scoped only.** The question is mandatory (`AskUserQuestion`, conversation language) unless the repo declares a default (`## Git Workflow` → `Git mode: <token>`, same read order as the base branch) — a declared default is announced in one line, not re-asked. **Never persisted across sessions:** no saved preference, no memory lookup. One answer covers the session; a collision with one repo's state (protected checkout) asks punctually for that repo without re-asking the mode. The options, each with its close contract stated in the question:
  1. **`pr-merge` (recommended)** — work branch → seam commits → push → PR to the base → checks green + the PR review pass (`> PRs & promotion`) → merge. Done = PR merged, plus deploy-job success where the branch deploys an environment.
  2. **`pr-open`** — same through a green PR with the review landed; merging stays the user's call. Done = the open, green, reviewed PR.
  3. **`direct-base`** — no work branch, no PR: seam commits pushed directly to the base branch (the mode direct-to-trunk repos declare). Done = change-group verified, committed, and pushed.
  4. **`hold`** — working tree only; diffs at close; commit on the USER's approval (the "review" here is the user's read of the diff — distinct from the agent review pass). Done = the user approved and the commit landed.
  An ambiguous answer defaults to `hold` (the safe mode). When the chosen mode includes a PR, the same question block also resolves the Phase B review route (`> PRs & promotion`) unless the repo declares it. A verbal change overrides the session — but only phrases naming a mode; "espera" / "no commits aún" are pauses, not mode changes. A project may declare squash-only or other semantics.
- **Multi-task plans fold the ask into the plan gate as a VISIBLE decision line**, seeded from the repo's declared default — never buried in a plan's assumptions. The autonomy ladder maps onto the tokens: `publish-autonomous` ≈ `pr-open`, `full-autonomous` ≈ `pr-merge`. Unattended runs never ask: `pr-open` on the dedicated branch — a merge always waits for a human. Shared/protected branches keep per-changeset confirmation regardless of mode.
- **Conventional commits** (`feat:`, `fix:`, `refactor:`, `chore:`, `docs:`, `test:`, `perf:`, `ci:`; optional scope), small and focused — one concern per commit, split mixed ones. Never any AI attribution in commits, PRs, messages, or file outputs.
- **Checkpoints** (plans with 4+ file-modifying tasks): a progress pulse roughly every 3 such tasks — a brief note by default; a blocking question only when something is decision-relevant (deviation, concern, red tests).

### Safety gates (all modes — fold confirmations into the task's single question block)
- **Protected branches** (project-declared; default: the production-deploying branch — `production`, or `main`/`master` where the trunk IS production — plus `qa` where it exists): no direct commits unless the project allows it. Exceptions: a single-branch repo (bare `master` IS the workflow), or a repo whose history shows direct-to-default as the norm (no PR gate, no CI on branches) — confirm once per session and treat as standing; a project declaration removes even that first ask.
- **Force-push and published-history rewrites** (`rebase` on shared branches, `reset --hard`, `amend` on pushed commits): always confirm, presenting what gets overwritten.
- **Merge/promotion into the production-deploying branch** (`production`, or `main`/`master` where the trunk IS production): always confirm — it is a production deploy (`CLAUDE.md > Destructive Operations`), and no rollback path substitutes for the confirmation. Promotion into `qa` follows that rule's non-prod carve-out — declared, not asked.
- **Push:** an explicit push verb is the confirmation; otherwise ask. Session-close remote pruning and declared-workflow repos (exceptions above) are standing-authorized.
- **Branch deletion:** confirm — except confirmed-merged branches at session close (below). Unmerged deletion, force-delete, or unverifiable merge status always asks.

### PRs & promotion
- PR title in conventional commit format; description covers what/why plus verification. One logical change per PR.
- **Shared integration branches receive changes via PR**, never a direct local merge, wherever the project uses a PR gate; a solo repo without one may merge locally.
- **Review runs in two phases with different jobs — never a third PHASE** (Phase B re-runs per push are not new phases). **Phase A:** the change-group's ONE independent agent review (`agent-routing.md > Verification runs in fresh context`; budget in `testing.md > Execution Scope`) runs on the diff before commit/push; a flow skill's own verify gate discharges it with its declared placement. **Phase B:** a bug-hunt pass on the OPEN PR — a release gate of the merge, analogous to CI, not a second review, and **correctness-only**: bugs that would break production; reuse/simplification/altitude belong to Phase A and are not reported at the gate (for the harness-native route the scope instruction rides the invocation prompt). Phase B re-runs on each push that answers one of its findings, scoped to the finding and its blast radius; from round 2 it reports blocking severity only — nits and recommendations accumulate to the close report, never open another round. **The route is the user's cost decision, never the agent's.** Resolve it from the repo's declaration (`## Git Workflow` → `PR review: <app-name> | native | none`); undeclared → ask, folded into the session-mode question block when the chosen mode includes a PR, session-scoped like the mode: **repo app** (Bugbot, `@codex review`, Copilot — the agent posts the trigger comment itself: that launches the gate, it doesn't duplicate it; the wait starts there, and the app's review is async, NOT part of "checks green") · **harness-native** (no marginal cost: Claude Code `/code-review <PR#> --comment` · Grok `/review --pr <n>` — lands PENDING, the step closes only on the user's submit · Codex `codex review --base <base>` pre-push · opencode's GitHub App) · **none** (the merge gates on checks alone — reported as such at close). `/code-review ultra` is the user's explicit escalation, never an automatic step. A single-commit PR whose identical diff Phase A already reviewed gets Phase B only — a manual review is never repeated without a finding motivating it.
- **You own the CI of any PR you merge until the landed branch is green:** wait for PR checks before merging (never on red or pending), watch the post-merge run, and fix failures you triggered instead of handing them back. CI is authoritative over local runs. The post-merge run includes the branch's deploy job where the branch deploys an environment (Amplify, Vercel, pipeline) — "merged" is not "deployed": report the promotion done only on the job's terminal success, watching it in overlap with remaining work.
- **CI watching overlaps remaining work.** After a push, start the watch and run the rest of the close work (docs, ledger, memory, report) while CI executes; idle-watch only when nothing else remains. A push without a merge in the session mode's scope (`pr-open`, `direct-base`) may close the turn with CI pending — report the run link and pending state; ownership carries into the next interaction. Under `pr-merge` an open PR never closes the turn: the close is the merge. After a merge, the deploy job's outcome is part of the same turn — a pending deploy never closes it. Merging never proceeds on pending.
- **Promotion moves the integration branch's whole current state**, not the session diff, unless the user explicitly scopes a partial promotion.
- **Stacked PRs:** when a task depends on an unmerged prior PR, branch from that PR's branch and chain the PRs, declaring the merge order in the close report — never block mid-session waiting for a merge.

### Session close (standing-authorized, automatic)
- Prune branches confirmed 100% merged (`git branch --merged <target>`): delete the local and its merged remote counterpart; return the checkout to the integration branch. Then `git fetch --prune` and fast-forward local integration branches behind their upstream.
- **Unmerged branches are decisions, not noise:** check for real work (`git log <target>..<branch>`), recommend integrating before close, or ask if it looks abandoned. Never silently leave, delete, or auto-reconcile a diverged branch.
- Report: deletions, fast-forwards, divergences, unmerged branches with their recommendation, and the branch now checked out.

### Recovery
- `push` returns 404 on a private repo: check `gh auth status` / `gh auth switch` before assuming the repo is missing; cache the active account for the session.
