# Asking the delivery mode and the review

Read before the first edit of a work item, when the answers for this session and repository are not already in force. The modes and what each authorizes stay in the global guidance's «Delivery». These are session questions: write and ask them as [questions](../hive-rule-questions/SKILL.md) sets, under a fixed header and with no decision ID.

- **When.** Ask the delivery mode and the code review mechanism once per session and repository, in one round, before the first edit of the first work item that needs them: `flow-plan` at its step 4, beside each plan's own effects round, whose answers no later work item reuses, and `flow-build` before the first edit of work without a plan. Later work items reuse the answers in force, named in one line. Ask one again, alone, when the user asks to change it, when this work item has a surface only the user can judge that the earlier one did not, or when it needs a code review and none was asked. Commits not this work item's follow [foreign commits](../hive-rule-foreign-commits/SKILL.md). A mechanical change gets only the delivery question and no review. Work that leaves nothing to commit or publish, such as an operational task («Proportionality»), deleting untracked or ignored files or repairing the local environment, gets neither; a repository whose `## Hive` declares `Delivery: direct-base` skips the delivery question and uses that mode, and still gets the review question for a change that is not mechanical.
- **Delivery.** Recommend `interactive` when the result has a surface only the user can judge, such as a screen, copy or a flow, or the project guidance requires human validation; otherwise `automatic` when the checks, the review and the verification establish the result, such as infrastructure, CI/CD, migrations or tooling with no visible change; when neither applies, `interactive`.
- **Review.** Ask which code review runs on the candidate before your validation or the push, worded to hold under every delivery answer, with a `Situation:` line that says what the change touches. Every change that is not mechanical gets one, so its options are mechanisms, by these names in the session language: `Native: <host> <command>`, such as `Native: Claude Code /code-review`, only when your host has one, and `Agent: hive-review-code`. Recommend the one the project guidance prefers when it runs on this host, otherwise the native one, otherwise the agent, and say when the preferred one does not run here. A review the repository already runs on every pull request, such as Bugbot, is not an option: name it in the `Situation:` line. When the answer names another host's native review, run yours without asking; ask again only when your host has none.
- **Adversarial review.** For each work item that gets a code review, ask in the delivery round, or alone before its first edit when the answers are reused, whether an adversarial review by another provider ([interrogate](../hive-rule-interrogate/SKILL.md)) also runs on this candidate. Its options are each agent that leaf's «Availability» finds, and no; say it spends that provider's quota and is never reused. Choosing an agent authorizes that spend for this work item. Unattended, ask it only with an amount authorized beforehand.
