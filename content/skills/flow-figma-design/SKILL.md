# Design a screen in Figma before the plan

An example is a drawing of one screen, a frame in the project's Figma file, that the user picks or corrects before the work is planned. It settles what the screen is; the plan, the build and the verification then compare against it. This stage is optional and publishes nothing to the viewer. It writes only in that Figma file and in the work's folder under `_support/workspace/`: it never edits the repository's files.

Enter by the user's typed command, by their choice of this stage in the next-step block of [flow-research](../flow-research/SKILL.md), or by a request whose deliverable is the design, such as replicating a screen in Figma. That reply or request is the user's instruction for the writes this stage makes to the Figma file, limited to what the work creates. It replaces no question a critical effect takes: a write that spends money or paid quota still gets its own.

Follow the steps in order.

1. **Check the connection.** Check yourself that the host has a connection that can write to Figma; never ask which tool to use. Without it, draw nothing and report the blocker with what is missing: for a screen that will be built, end with the next-step block toward [flow-plan](../flow-plan/SKILL.md), which draws its text sketches; for a request whose deliverable is the design, the only route is connecting Figma.
2. **Load before drawing.** Read the usage instructions the Figma connection ships, when it ships any, such as a skill it marks as required before writing to the canvas. Then load the project's design system as [hive-ui-criteria](../hive-ui-criteria/SKILL.md) sets: the app's `DESIGN.md`, its library and its customization layer. Draw nothing before both are read.
3. **Resolve the file.** Use the file the app's `DESIGN.md` declares in its `**Design file:**` field, as [design record](../hive-ui-criteria/references/design-record.md) sets, or the file the user named in the conversation. With neither, ask the user for the file once, as an open question in the text, and say that without one the work goes to the plan with text sketches; when they give none, end with the next-step block toward `flow-plan`.
4. **Say what the user will do by hand.** Before the first drawing, list each step in Figma that only the user can take for this work, such as publishing a library the frames need or accepting its update in the file, and when each one comes. When there is none, say so.
5. **Draw.** Draw two or three examples when the composition is open, and one when the request or an existing screen fixes it. Draw each at desktop width with the project's tokens and components, the real labels, and data of realistic volume, as frames on a page named after the work. In that file:
   - create frames on the work's page, and components and variables local to the file when the frames need them; write the node or identifier of each one this work creates in the record of step 7;
   - change or delete only what this work created;
   - never change or delete an existing variable, style, component or page, nor anything of a shared library: return each such change to the user as a decision, as the precedence of [hive-ui-criteria](../hive-ui-criteria/SKILL.md#precedence) sets.

   One `hive-design-ui` child draws the frames when the host gives its children that connection, as [delegation](../flow-build/references/delegation.md) sets; otherwise the main thread draws them. The child's brief carries the file, the page, the desktop width and the 440 px mobile width, the frames a request for the design names as its target and, for a correction or a removal, the nodes this work created.
6. **Choose.** Ask the user to pick or correct, as one decision with one option per example: each option carries its frame's location and a summary of its composition; with a single example, the options are to approve it or to correct it. Redraw the chosen example for each correction. When the screen is served on mobile, draw the chosen example at 440 px wide too, and ask the user to approve or correct that frame before recording it. When the file is not declared in the app's `DESIGN.md`, ask in the same round, once per work, whether to record it there; this stage does not edit `DESIGN.md`: a yes is the user's instruction, kept in the record of step 7 for the plan to act on.
7. **Record.** Write the approved example in the report and in `examples.md` in the work's folder under `_support/workspace/`, placed as [artifact layout](../workspace-conventions/references/artifact-layout.md) sets: the tool, the file's location, each frame's node, the identifiers of the components and variables this work created, the path of each frame's local image in that folder's `images/`, the user's answer about recording the file in `DESIGN.md`, and a status line. Write the status as `drawn, pending the user's approval` while the choice is open, and replace it with `approved <date>` in the same turn the user approves. The location and the nodes are the record: the image is a local copy, read again from them where it is missing. A plan with a change folder copies the record into its `UI` section, and work without one into its checkpoint file, so a stage that runs in another checkout finds it. Remove the examples not chosen, with the components and variables only they used.
8. **Close the stage.** End with the next-step block toward `flow-plan`, as the global guidance's «Questions and routes» sets, naming the approved example and its record. The plan takes it as the screen's reference, as [UI decisions](../flow-plan/SKILL.md#ui-decisions) sets, and adds the task that writes the `**Design file:**` field when the record holds that instruction.

## A request for the design itself

When the request's deliverable is the design, the request is the instruction: follow the same steps. When it names a page or frames as the target, draw there instead of on a page of the work's own: change, and never delete, the frames it names, and change or delete only what this work creates. Do not report the work as done before the user approves the example. After the approval, report the result with the example's record, name as pending a yes to recording the file in `DESIGN.md`, since no plan follows to write it, and run [flow-close](../flow-close/SKILL.md), which closes it as an operational task.

## Unattended delegation

While [unattended delegation](../unattended-delegation/SKILL.md) is active, ask none of the questions of steps 3 and 6: keep every example, report the choice or the approval as unresolved, and continue without an approved example, so the plan settles the UI.
