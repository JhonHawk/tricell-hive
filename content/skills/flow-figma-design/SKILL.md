# Design a screen in Figma before the plan

An example is a drawing of one screen, a frame in the project's Figma file, that the user picks or corrects before the work is planned. It settles what the screen is; the plan, the build and the verification then compare against it. This stage is optional and publishes nothing to the viewer. It writes only in that Figma file and in the work's folder under `_support/workspace/`: it never edits the repository's files.

Enter by the user's typed command, by their choice of this stage in the next-step block of [flow-research](../flow-research/SKILL.md), or by continuation from research for a request whose deliverable is the design, such as replicating a screen in Figma. That reply or request is the user's instruction for the writes this stage makes to the Figma file step 3 resolves, limited to what the work creates. It replaces no question a critical effect takes: a write that spends money or paid quota still gets its own.

Follow the steps in order.

1. **Check the connection.** Check yourself that the host has a connection that can write to Figma; never ask which tool to use. Without it, draw nothing and report the blocker with what is missing: for a screen that will be built, end with the next-step block toward [flow-plan](../flow-plan/SKILL.md), which draws its text sketches; for a request whose deliverable is the design, the only route is connecting Figma.
2. **Load before drawing.** Read the usage instructions the Figma connection ships, when it ships any, such as a skill it marks as required before writing to the canvas. Then load the project's design system as [hive-ui-criteria](../hive-ui-criteria/SKILL.md) sets: the app's `DESIGN.md`, its library and its customization layer; and the decisions already recorded for the app in the **Decisions** of its `DESIGN.md`. Also gather the sources that settle a business rule, as step 5 uses them: the request, the ticket's criteria, research's decisions as the conversation, the ticket or the work's record holds them, and those recorded decisions. Draw nothing before all of them are read.
3. **Resolve the file.** Use the Figma file the user named in the conversation, otherwise the one the app's `DESIGN.md` declares in its `**Design file:**` field, as [design record](../hive-ui-criteria/references/design-record.md) sets; a declared file of another design tool does not count for this stage. With neither, ask the user for the Figma file once, as an open question in the text, and say that without one the work goes to the plan with text sketches; when they give none, end as step 1 sets for a missing connection: the next-step block toward `flow-plan` for a screen that will be built, and for a request whose deliverable is the design, the report that it needs a Figma file. When the file comes from `DESIGN.md` and neither the block that offered this stage nor the user named it, name it, say that you will create a page with frames in it, and ask the user to confirm it once before the first write. Then read the file through the connection: when the connection cannot write to that file, such as an account with view-only access, draw nothing and report it as step 1 sets. Read the screen's siblings, the frames of the same module or navigation in that file and the screens of its code, and measure them: they fix the app shell, the page header, the toolbar, the table, the row actions, whether a form is a page or a dialog, and the spacing. Search for the file's location together with each sibling's frame node, since node identifiers repeat across files, a filtered read, in the project's change folders, archived ones included, and in the `examples.md` files of its work folders under `_support/workspace/`, and read the record of the example it was approved from when one is found: its corrections are decisions too.
4. **Say what the user will do by hand.** Before the first drawing, list each step in Figma that only the user can take for this work, such as publishing a library the frames need or accepting its update in the file, and when each one comes. When there is none, say so.
5. **Draw and record.** When this work's record already lists screens stopped by a `scope` rule, as after research settled it, write each such rule research settled as `approved <date>: <answer>` and draw only those screens; the others keep their status. Otherwise, draw one example per screen, following its siblings and the recorded decisions. Draw two or three examples only for a screen the user names when asking for alternatives, and one for each other screen of the work. Draw each at one desktop width, the one the screen's existing frames in that file use, otherwise 1440 px, with the project's tokens and components, the real labels, and data of realistic volume, as frames on a page named after the work. In that file:
   - create frames on the work's page, and components and variables local to the file when the frames need them;
   - change or delete only what this work created;
   - never change or delete an existing variable, style, component or page, nor anything of a shared library: return each such change to the user as a decision, as the precedence of [hive-ui-criteria](../hive-ui-criteria/SKILL.md#precedence) sets.

   The main thread draws the frames; no child draws them, since a child starts without the conventions and corrections this session holds. When the connection runs scripts in the file, draw by script: each write defines once the pieces its frames use, such as a container on the tool's automatic layout, a button, a field, a table row and a badge, bound to the file's variables, with the app shell cloned from an existing screen, and composes the frames from them. When the app's `DESIGN.md` declares a `**Design library:**`, each piece the library holds is an instance of its component bound to its variables; define a piece only for what it lacks, and list each such piece in the record as a candidate for the library. Correct a frame by changing a piece or its data and drawing that frame again, never by moving or resizing its nodes one by one: separate fixes drift from each other and from the siblings.

   While drawing, list each business rule the frames show that step 2's sources do not settle and that the siblings or their code do not already implement. A rule is a behavior in a situation: what an action requires, who may take it, which state follows it, what it blocks or keeps, or where a setting that applies beyond this screen lives. Draw the behavior you recommend and record the rule as `proposed`, so approving the screen does not decide it unseen. A rule whose options all leave the scope, a contract, stored data, the cost, reversibility and who may act unchanged is an `assumption`: state it in step 6's message instead of asking it. A rule that adds a capability the request did not name, changes data or settings that other screens or modules use, or changes a permission is a `scope` rule: mark each screen it shapes `stopped by <the rule>`, delete any part of their frames you drew, and finish this step for the other screens; stopped screens are not reviewed, step 6 does not ask the rule, and step 8 ends toward research.

   As soon as the frames are drawn, before the review and before asking anything, write `examples.md` in the work's folder under `_support/workspace/`, placed as [artifact layout](../workspace-conventions/references/artifact-layout.md) sets: the tool, the file's location, each frame's node, the identifiers of the components and variables this work created, the path of each frame's local image in that folder's `images/`, one status line per screen of the work, `drawn, under review` or `stopped by <the rule>`, and, apart from those, one line per rule: `rule: <the rule> · screen <name> · proposed | assumption | scope | approved <date>: <answer> · found by drawer | reviewer`. The location and the nodes are the record: the image is a local copy, read again from them where it is missing.

   Then have one `hive-review-ux` child review the frames against the request, the siblings, the recorded decisions and their alignment, briefed as [Reviewer brief](../flow-build/references/delegation.md#reviewer-brief) sets for frames in a design file. The reviewer lists apart the rules it found unsettled: check each one the record lacks against step 2's sources and the siblings and their code, drop those they settle, and record the rest, found by the reviewer, as this step sets for the drawer's rules, a `scope` one stopping its screen as it sets. Fix the findings that hold as this step sets for a correction, have only the corrected frames reviewed again once, and set each status line that reads `drawn, under review` to `drawn, pending the user's approval`. Name in step 6's message the findings that remain and the alignment checks the review reports as not run.
6. **Choose.** Ask the user, in one round, one decision per screen: approve or correct its example, each option carrying its frame's location and a summary of its composition; for a screen drawn with alternatives, one option per alternative, plus correcting. In the same round, ask each `proposed` rule as a decision of its own, and word the approve option of the screen it shapes to hold under every answer, naming that decision, such as "approve the composition, with the rule you choose in D12; a different answer is redrawn and shown to you again"; list the assumptions in the message, where a reply can turn one into a decision. When a rule's answer differs from what is drawn, redraw that part and keep the screen pending, even when its approve option was chosen, until the user approves it as redrawn. Redraw the example for each correction and update the record. When the screen is served on mobile, draw the chosen example at 440 px wide too, have it reviewed as step 5 sets, and ask the user to approve or correct that frame before step 7. A correction the user asks for gets no other review: they see it as it is drawn. When a correction of the user sets a convention for screens beyond this one, such as the row actions of every list, ask in the round that asks the approval, once per convention, whether to record it among the **Decisions** of the app's `DESIGN.md`; a yes is the user's instruction, kept in the record for the plan to act on. When the app's `DESIGN.md` declares no design file, ask in the same round, once per work, whether to record this one there; this stage does not edit `DESIGN.md`: a yes is the user's instruction, kept in the record for the plan to act on.
7. **Record the approval.** In the same turn the user answers a rule, write its line as `approved <date>: <answer>`. In the same turn the user approves a screen's example, except one step 6 keeps pending for a redraw, replace that screen's status line with `approved <date>`, leaving the others as they are, add the user's answers about recording the file and each convention in `DESIGN.md`, and remove the alternatives not chosen, with the components and variables only they used, from the file and from the record; the approved examples of the other screens stay. Write the approved example in the report. A plan with a change folder copies the record into its `UI` section, and work without one into its checkpoint file, so a stage that runs in another checkout finds it.
8. **Close the stage.** When the record holds a `scope` rule, ask the approval of the other screens as step 6 sets, then end with the next-step block toward [flow-research](../flow-research/SKILL.md) naming those rules instead of the block toward the plan. When the stage runs again for this work, step 5 resumes from its record. A request whose deliverable is the design ends as [A request for the design itself](#a-request-for-the-design-itself) sets, not here. Otherwise, once every screen is approved, end with the next-step block toward `flow-plan`, as the global guidance's «Questions and routes» sets, naming the approved example and its record. Recommend `flow-build` instead only when all of these hold: the block that offered this stage listed `flow-build` as a reply, the approved examples add no region the request did not name, the record holds no yes to recording the file or a convention in `DESIGN.md`, and no rule in it is still `proposed`. The plan takes the example as the screen's reference, as [UI decisions](../flow-plan/SKILL.md#ui-decisions) sets, and adds the task that writes the `**Design file:**` field and each convention when the record holds that instruction; a build without a plan keeps the record in its checkpoint file, as [flow-build](../flow-build/SKILL.md) sets.

## A request for the design itself

When the request's deliverable is the design, the request is the instruction: follow the same steps. When it names a page or frames as the target, draw there instead of on a page of the work's own: change, and never delete, the frames it names, and change or delete only what this work creates. Do not report the work as done before the user approves the example; a rule that changes the scope leaves it not done and ends as step 8 sets for it. After the approval, report the result with the example's record, name as pending each yes to recording the file or a convention in `DESIGN.md`, since no plan follows to write it, and run [flow-close](../flow-close/SKILL.md), which closes it as an operational task.

## Unattended delegation

While [unattended delegation](../unattended-delegation/SKILL.md) is active, ask none of the questions of steps 3 and 6:

- with no Figma file named or declared, or one that needs the confirmation of step 3, draw nothing and report the file as unresolved;
- when step 4 lists a step only the user can take before a frame can be drawn, do not draw that frame and report it as unresolved;
- otherwise draw, keep every example with the record's status as pending, and report the choice or the approval as unresolved;
- keep each rule `proposed` or `scope` and report it as unresolved; a `scope` rule still stops the screens it shapes, the stage does not end toward research, and the stopped screens stay unresolved while the plan covers the others.

Work that will be built then continues without an approved example, so the plan settles the UI. A request whose deliverable is the design stays not done, with its approval reported as unresolved, and does not run the close.
