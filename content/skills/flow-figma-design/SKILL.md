# Design a screen in Figma before the plan

An example is a drawing of one screen, a frame in the project's Figma file, that the user picks or corrects before the work is planned. It settles what the screen is; the plan, the build and the verification then compare against it. This stage is optional and publishes nothing to the viewer. It writes only in that Figma file, in the work's folder under `_support/workspace/` and, at step 7, the rules of the work's ticket; in the repository it edits only the two `DESIGN.md` fields step 3's reference sets.

Enter by the user's typed command, by their choice of this stage in the next-step block of [flow-research](../flow-research/SKILL.md), or by continuation from research for a request whose deliverable is the design, such as replicating a screen in Figma. That reply or request is the user's instruction for the writes this stage makes to the Figma file step 3 resolves, limited to what the work creates. It replaces no question a critical effect takes: a write that spends money or paid quota still gets its own.

Follow the steps in order.

1. **Check the connection** as [design stage](../hive-rule-design-stage/SKILL.md) sets. Without it, draw nothing and report the blocker with what is missing: for a screen that will be built, end with the next-step block toward [flow-plan](../flow-plan/SKILL.md), which draws its text sketches; for a request whose deliverable is the design, the only route is connecting Figma.
2. **Load before drawing.** Read the usage instructions the Figma connection ships, when it ships any, such as a skill it marks as required before writing to the canvas. Then load the project's design system as [hive-ui-criteria](../hive-ui-criteria/SKILL.md) sets: the app's `DESIGN.md`, its library and its customization layer; and the decisions already recorded for the app in the **Decisions** of its `DESIGN.md`. Also gather the sources that settle a business rule, as step 5 uses them: the request, the ticket with its criteria and comments, research's decisions as the conversation, the ticket or the work's record holds them, and those recorded decisions. Draw nothing before all of them are read.
3. **Resolve the file** as [design stage](../hive-rule-design-stage/SKILL.md) sets: the file the user or the offering block named, otherwise the one the app's `DESIGN.md` declares as [design record](../hive-ui-criteria/references/design-record.md) sets, with the one question that leaf sets when neither exists or the declared file needs confirming. Then read the file through the connection: when the connection cannot write to that file, such as an account with view-only access, draw nothing and report it as step 1 sets. Read the screen's siblings, the frames of the same module or navigation in that file and the screens of its code, and measure them: they fix the app shell, the page header, the toolbar, the table, the row actions, whether a form is a page or a dialog, and the spacing. Then read and follow [design library](references/design-library.md): it sets the siblings' records to read, the library to bind, the inventory written before the first drawing, the pieces to reuse, and how steps 6 and 7 record the file and the library.
4. **Say what the user will do by hand.** Before the first drawing, list each step in Figma that only the user can take for this work, such as publishing a library the frames need, adding the bound library to the file or accepting its update, and when each one comes. When there is none, say so.
5. **Draw and record.** When this work's record already lists screens stopped by a `scope` rule, as after research settled it, write each such rule research settled as `approved <date>: <answer>` and draw only those screens; the others keep their status. Otherwise, draw the examples per screen that [design stage](../hive-rule-design-stage/SKILL.md) sets, following its siblings and the recorded decisions. Draw each at one desktop width, the one the screen's existing frames in that file use, otherwise 1440 px, with the project's tokens and components, the real labels, and data of realistic volume, on a page named after the work, grouped as [sections](references/sections.md) sets: read it before drawing. When the work has more than one screen, first draw, at that width only, the one that uses the most inventory pieces, record it, have it alone reviewed and that review reconciled as this step sets for the set, without cards or a follow-up, and give the user its location without asking or ending the turn; then draw the others and every 440 px frame from its pieces. The review below covers the whole set, that screen too. In that file:
   - create frames and sections on that page, and local components and variables when the frames need them;
   - change or delete only what this work created;
   - never change or delete an existing variable, style, component or page, nor anything of a shared library: return each such change to the user as a decision, as the precedence of [hive-ui-criteria](../hive-ui-criteria/SKILL.md#precedence) sets.

   The main thread draws the frames, never a child, since a child starts without the conventions and corrections this session holds. When the connection runs scripts in the file, draw by script: each write defines once the pieces its frames use, such as a container on the tool's automatic layout, a button, a field, a table row and a badge, bound to the file's variables, with the app shell cloned from an existing screen, and composes the frames from them. Each piece comes from the bound library or the siblings' components, as the reference's «Draw with it» sets. Correct a frame by changing a piece or its data and drawing that frame again, never by moving or resizing its nodes one by one: separate fixes drift from each other and from the siblings.

   As soon as the frames are drawn, before the review and before asking anything, read [example record](references/example-record.md) and follow it: list the business rules, as [business rules](../hive-rule-business-rules/SKILL.md) defines them, that the frames show and step 2's sources leave unsettled and record each as `proposed`, `assumption` or `scope` (a `scope` rule stops the screens it shapes); write the record in `examples.md`; have one `hive-review-ux` child review the frames; fix the findings that hold; draw the rule cards beside the frames as [rule cards](references/rule-cards.md) sets; and have only the corrected frames and the cards reviewed again once.
6. **Choose.** Read [approval](references/approval.md). Finish drawing and reviewing the work's screens, including their 440 px frames when mobile applies, before asking approval, and list screens stopped by a `scope` rule apart. Ask one approval for the completed set, never per screen, and in the same round each `proposed` rule as a decision of its own, once per convention whether to record it in `DESIGN.md`, and whether to record the file or the library.
7. **Record the approval** in the turn the user answers, as [approval](references/approval.md#record-the-approval) sets: each rule's line, each approved screen's status line, the user's answers about conventions, the file and the library, and the work's rules in its ticket, as [business rules ticket](../hive-rule-business-ticket/SKILL.md) sets; the alternatives not chosen are removed.
8. **Close the stage** as [approval](references/approval.md#close-the-stage) sets: with a `scope` rule in the record, end toward [flow-research](../flow-research/SKILL.md) naming it; otherwise, once every screen is approved, end toward `flow-plan`. A request whose deliverable is the design ends as [A request for the design itself](#a-request-for-the-design-itself) sets.

## A request for the design itself

When the request's deliverable is the design, the request is the instruction: follow the same steps, as [special cases](references/special-cases.md#a-request-for-the-design-itself) sets for its target, its not-done state and its close.

## Unattended delegation

While [unattended delegation](../unattended-delegation/SKILL.md) is active, ask none of the questions of steps 3 and 6, and follow [special cases](references/special-cases.md#unattended-delegation).
