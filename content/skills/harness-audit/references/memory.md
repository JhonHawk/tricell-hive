# Memory and folder trust

Read with [hierarchy](hierarchy.md) when sessions start at more than one entry point, when the caller asks why they behave differently by where they start, or when the audit covers memory (HA-HI-08 to HA-HI-11).

## Memory per entry point

A host's own memory, the store it writes for itself and reloads in later sessions, is part of what a session starts with, and most hosts key it by the repository or directory where the session starts. Two entry points with the same instructions still start different sessions when their stores differ. For each host and entry point, locate the store that loads:

| Host | Store and key | Basis |
| --- | --- | --- |
| Claude Code | `<Claude home>/projects/<project>/memory/`, whose `MEMORY.md` loads at start; `<project>` comes from the Git repository, shared by its subdirectories and worktrees, or from the start directory outside a repository; `autoMemoryDirectory`, read from any settings scope, project and local ones only in a trusted folder, moves it | Documented (code.claude.com/docs/en/memory, read 2026-10-28, Claude Code 2.1.312) |
| Grok Build | `~/.grok/memory-v2/global/` plus one `workspaces/<project>-<hash>/` per repository, shared by its clones and worktrees, or per start directory outside a repository; both indexes enter the prompt once per session, topics are read on demand | Documented (`~/.grok/docs/user-guide/13-memory.md`, Grok Build 1.0.72) and observed 2026-10-28 |
| Codex | `<Codex home>/memories/`, one store for every directory; `MEMORY.md` entries carry `applies_to: cwd=…` as a hint the model weighs, with no documented filter by directory | Documented (learn.chatgpt.com/docs/customization/memories, read 2026-10-28) and observed on 0.165.0 |

## Changing an accepted entry

To change an accepted entry, use only the path its host documents, and leave any other entry as a decision for the caller:

- Claude Code: edit the Markdown files in the store.
- Grok Build: edit the Markdown files under `topics/` and `observations/_inbox/` of either scope, never the generated `MEMORY.md` or the scope's state files. Dream folds later sessions into topics and can learn a removed fact again (`13-memory.md`, 1.0.73).
- Codex: never edit the memory files. Add one small update note, `<timestamp>-<short slug>.md`, under `<Codex home>/memories/extensions/ad_hoc/notes/` that states what to remove or change; Codex folds it in later (Codex source, `ext/memories` read-path template, read 2026-10-30; installed 0.165.0).

A store setting that stops a store from loading or growing is the user's global configuration, so only propose it: Claude Code `autoMemoryDirectory` moves the store; Grok Build `[memory_v2] enabled = false` stops it, and `--no-memory` or `GROK_MEMORY=0` stops it for one process; Codex `[memories] use_memories = false` stops loading and `generate_memories = false` stops new entries.

A store may hold credentials or client details: before reading one, read the global guidance's «Secrets» section. Read each store's index and topic titles; open a topic only to confirm a finding, and quote no more than the finding needs, never a secret value.

## Rules

- **HA-HI-08 — Memory by entry point.** Compare the stores that load at each entry point of the same project, for the hosts in use. A store holding a rule, a gotcha, a user preference or project state that another entry point in use does not load is `medium`, because sessions then behave differently by where they start. Exempt what the global guidance's «Persistent memory» section keeps in a host's own store: facts that concern only that host, and `engram:<project>/<topic_key>` pointers. Give each finding a home, never a copy in the other store: a rule or gotcha is `relocate` into the instruction file of the level whose sessions need it (HA-HI-05); project state and decisions go to the shared persistent memory as the global guidance's «Persistent memory» section sets; a user preference is `propose-global`. Propose a store setting, such as `autoMemoryDirectory`, only where the host documents one. Ask about a store fact that a current source contradicts, and the store entry a relocation leaves behind, as decisions; after the answer, change them as [apply](apply.md) sets.
- **HA-HI-11 — Memory that restates guidance.** Compare every entry of the stores that load at each entry point of the project, for the hosts in use, with the whole guidance those sessions follow: the effective set HA-HI-01 computes, including the global guidance and the project's instruction files, plus the installed skills and roles. Read each host store entry by entry. For the project's Engram records under the name HA-HI-09 resolves, search that project for the subjects the guidance governs, such as delivery, review, commit, push, merge, promotion, plan approval, verification, secrets, language and reporting, and for skill, role and command names. An entry that states as standing procedure what that guidance already governs, whether or not it names the rule, such as when implementation may start, which review runs, when to merge, or how to handle a secret, is a restatement: `medium`. It is `high` when it grants a standing authorization for an effect that needs explicit authorization, such as a merge, push, administrative bypass, deployment or deletion, beyond the work item that granted it, because a remembered preference never answers a delivery or review question (the global guidance's «Delivery» section). An entry that names a skill, role or command the installed Hive does not carry is `stale`. Give each a home, never a copy: a restatement is `delete`, or `stale` rewritten as the decision of the work item it came from; a user preference that holds without Hive, such as not promoting to QA unless asked, is `relocate` into the instruction file of the level that needs it (HA-HI-05). An entry about something no guidance governs belongs to HA-HI-08. Keep a decision scoped to one work item and, in the repository that authors the guidance, a record of a change to that guidance, since both are project state. In the report, state that a host that consolidates captured turns, such as Grok Build, can learn a removed rule again from later sessions.
- **HA-HI-09 — Shared memory project.** When the project uses Engram, every entry point must resolve the same Engram project (`.engram/config.json`, or directory detection without one), and sessions must pass that name as the global guidance's «Persistent memory» section sets. Entry points that resolve different names, or records of the same project stored under another name, such as the `## Hive` `Project` value or a directory name, are `medium`. Confirm a split by searching a recent record under both names and name the host or adapter that wrote under the other one. Propose creating a missing `.engram/config.json`, or aligning a differing one, through `engram-init-workspace`; report an adapter that ignores the configured name for its maintainer, as an external project's finding; and leave merging the existing records to the caller.
- **HA-HI-10 — Folder trust.** A host that loads project instructions only in a trusted folder loads none at an untrusted entry point, including the entry point of a delegated child. Grok Build requires it (`~/.grok/docs/user-guide/12-project-rules.md`, 1.0.72) and treats a repository nested under a trusted folder as a separate workspace that needs its own grant; its grants are listed in `~/.grok/trusted_folders.toml`, and it records each child as a session of its own at the child's entry point (`summary.json` `session_kind: subagent`). When histories show sessions or children at an entry point whose project files never appear in their recorded startup set, and that folder has no grant, report it as `medium`, or `high` when no host in use then receives the repository's needed guidance by any path; granting trust is the user's action, since it changes the host's global configuration.
