# Proportional UI verification

Read for a UI change, including its first view, final verification and corrections. Drive the browser as [Browser tool](#browser-tool) sets. Exercise changed screens, relevant states and regions displaced, resized or reflowed, with realistic data; capture what a person needs to review. Check desktop and, whenever the application has a responsive layout (a breakpoint or a viewport meta tag) and the diff changes a rendered component, style or layout, the mobile viewport of 440 × 956 CSS pixels (iPhone 16 Pro Max), and each affected supported theme. That is the only mobile width: check the reflow of [criteria](../../hive-ui-criteria/references/criteria.md#accessibility-floors) in it, and load another narrow width only when the project or the ticket names it. Record which widths, themes and states were actually checked.

For a correction, check and recapture only affected screens and states, including any neighbors, widths or themes whose layout can change. Preserve earlier evidence for unaffected views and distinguish the new revision. Repeat a complete mobile journey only when navigation or the flow changed or the user explicitly requests it. Reuse suitable captures already made; do not claim coverage for a width, theme or state that was not exercised.

## Automated accessibility audit

Read when reviewing the UX of a UI change. The audit measures; it does not replace the keyboard, focus and interaction checks of the review.

- When `agent-browser` drives the review, run `agent-browser a11y --tags wcag2a,wcag2aa,wcag21a,wcag21aa,wcag22aa,best-practice --json` in that review's session, under the time limit of [Browser tool](#browser-tool), on each reviewed state at each width and theme the review checks: every changed screen and every state reached by interaction, such as an open dialog, popover, menu, panel or mobile navigation, since the audit sees only what is rendered. Scope it with `--selector` to the container of the reviewed regions when one holds them all; otherwise audit the page and report only the results inside the reviewed regions. Before each run, wait for a selector or text that shows the state is ready, or for `--load networkidle` on a page that does not poll or stream, not a fixed delay. Its embedded axe-core needs no network and runs under a strict page content security policy, as its documentation states. When another browser tool drives the review, run the audit there only when that tool can execute axe-core in the same page; otherwise report the audit as not run.
- A violation with a `wcag*` tag is a defect. Give it the priority that [Findings](../../flow-close/SKILL.md#findings) defines from the observed effect on users, not from axe's `impact` field: axe `critical` is not P0 by itself. A violation with no `wcag*` tag, only `best-practice` and category tags, is a P3 finding marked best-practice, never reported as a WCAG failure.
- Treat each `incomplete` result as pending manual review, not as a pass; check it with rendered colors, keyboard or focus as the rule requires, and name the ones left unchecked. When an `incomplete` result comes from markup the project's UI library generates by design, such as its focus guards, portal containers or the `aria-controls` of a closed popup, note it once and do not report it as a defect.
- Count affected elements from `nodeCount`, since the JSON lists at most 10 nodes per rule, and record `axeVersion` with the evidence.
- axe-core finds on average 57% of WCAG issues, by its maintainer's measure: a run with no violations is not evidence of conformance, and the report never claims conformance from it.
- When the project guidance names a UI linter and the command that runs it, and that command is already installed in the project or on the machine, also run it on the running URL, with JSON output when it has one; never install it or fetch it with a one-off package runner, and report it as not run when it is missing. Report its findings on contrast, overflow, structure, broken images and script errors as measured defects, and its aesthetic or style rules as informational only, since the project's design system governs the look.

## Browser tool

- Use the `agent-browser` skill through the shell when it is installed (`command -v agent-browser`): its snapshots are smaller than an MCP browser's, and a stable flow chains in one command. An installed MCP browser server is not a reason to prefer it. A child uses the tool its brief assigns.
- Use Chrome DevTools MCP only for Lighthouse audits, performance traces, CPU throttling and heap snapshots, or for an independent reproduction after `agent-browser` failed twice. Without `agent-browser`, use the host's browser tool. Report which tool drove each check.
- `agent-browser` has no timeout for `open`, `eval`, `snapshot`, `screenshot` or `close`, and one stuck command blocks its session. Run each command through a 45-second limit: `timeout 45 agent-browser …`, or `gtimeout 45`, or `perl -e 'alarm shift; exec @ARGV' 45 agent-browser …` when neither exists. When the limit expires, run `agent-browser doctor`, close that session and continue in a fresh one; do not resend the command into it.
- Give each flow its own `--session` and close every session you opened with `agent-browser close --session <name>` when the flow ends.

The caller owns acceptance and review. For publishing evidence and instructions, use [flow-walkthrough](../../flow-walkthrough/SKILL.md); follow [artifact layout and retention](../../workspace-conventions/references/artifact-layout.md) for the evidence destination.
