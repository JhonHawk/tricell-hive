# Runtime and UI gates for a candidate

## When to read

Read by [flow-verify](../SKILL.md) before the local runtime checks or the human UI handoff on a candidate, and wherever another procedure points to its runtime and UI gates, such as a reported prerequisite. The dedicated code review and the checks before a push are in [review and gates](review-and-gates.md), Verification does not grant deployment, publication, destructive effects, or external access.

## Runtime and UI gates

Decide local in-vivo applicability from the actual changed behavior. When needed, include and execute the relevant walk within authorized implementation without asking whether to run it. When judged unnecessary, say why in one line of the report and do not run it; the user can ask for it. That judgment never waives a required gate, overrides paused model pilots, or grants external effects. Deployed-environment walks retain the explicit authorization boundary in [gate selection and timing](../../flow-build/references/verification.md#gate-selection-and-timing).

For local implementation, always exercise the applicable changed path and relevant failure or permission states. Perform the corresponding deployed-environment exercise only within its explicit gate authorization. A mocked integration or source inspection does not establish behavior in the running system. Resolve authorized local setup, accounts, roles and seed data; a failure while setting one up is a defect that blocks the work, fixed within the stage's fix-round limits; access only the user can supply, or local setup still failing after those rounds, remains a reported prerequisite, named with its cause. Before any request for the user's validation, and before any capture shown to the user, such as the first rendered view that [flow-walkthrough](../../flow-walkthrough/SKILL.md) shows even when it asks no question, open each target the request or capture names as the user will, such as a page with its seeded record, rendered under the browser rules below, or a running service: a target that fails, such as one that shows a sign-in page, an error or an empty list instead of the state it names, is such a setup failure, fixed before the request, and one still failing after those rounds is named in the request with its cause.

Use dev/HMR for iteration. For the final in-vivo or UI handoff, build and serve the compiled candidate using the project's production-style start or preview command where the stack distinguishes build from dev. Services without a build step use their normal runtime. Build only the affected applications and required dependencies, not every app per edit.

Default the handoff stack to local frontend, backend, database and necessary dependencies unless a different target was explicitly specified. Check effective connections, including build-time frontend URLs and backend persistence targets, without exposing credentials; localhost in the browser does not prove the whole path is local. Prepare authorized local accounts, roles and seed data before the walk, reusing what already exists before creating anything. Reuse a running dependency, such as the database or a cache, when it answers and, checked read-only, already holds what this candidate needs, such as its migrations; reuse an application server only when it runs this candidate's code, such as one this task started from this working tree, in the kind the paragraph above sets. Look for local accounts and seed data where the project's guidance or support folder declares them, or where an earlier session left them, such as the project's secret location, reading a secret file only as [secrets](../../hive-core/references/secrets.md) sets. Create only what is missing, through the project's seed scripts, API or database. Store an account created for later walks in the project's declared untracked secret location, named by its environment and purpose rather than its ticket, and name that file, never its values, in the report; when the project declares none, keep it in the session copy and propose a location in the report. Pass each child the URLs, the identifiers of the records it needs and the file of the account it uses, and tell it not to restart a server it shares; a child creates data through the interface only when that creation is a journey under test. Report missing dependencies and any uncovered integration; never silently substitute a remote environment. External authentication, messaging, payments and similar effects need their own authorized boundary.

For any change with a rendered UI effect, read and follow [the UI gate](ui-gate.md): it owns the implementer's rendered inspection, the independent children that the `UI verification` answer selects with their briefs and stops, and the accepted-candidate gate, in every delivery mode. Before delivering a later fix, including a code-review fix after approval, apply its [changes after a gate or approval](ui-gate.md#changes-after-a-gate-or-approval) rule.

Before driving a browser, read [browser automation](../../flow-build/references/browser-automation.md) and pass it to children that drive one.

## Human UI handoff

Before showing a user interface to the user for validation, read and follow [flow-walkthrough](../../flow-walkthrough/SKILL.md): it owns the early composition check on the dev server, the captures of relevant states, and the handoff message and page. [flow-verify](../SKILL.md) owns the validation loop: the correction rounds, their task markers and the accepted-candidate gate.
