# Viewer publication

Read once per session, when the first build or verify flow that [walkthrough](walkthrough.md) gives a viewer session takes its first UI capture, and again after a compaction. The viewer holds only UI captures and their iteration: publish no stage, task, document or reason during the flow, never read `hive view work contract`, and publish nothing for a flow without captures. This procedure changes only local viewer state and does not authorize project, tracker or external writes. Hive's session hooks already report the session's start, activity and end. Delegated children return captures and findings to the primary producer, which alone publishes.

## Publish captures

1. Never start or restart the viewer service; a stopped viewer is handled by the queue below.
2. Publish each batch of captures of one screen with one command: `hive view work capture --stage build|verify --view-title SCREEN --image FILE[:caption] ...`. On the work's first capture add `--key KEY`, the ticket key or otherwise the change folder name or a short descriptive key, kept in the checkpoint (it also selects the work later), and `--summary TEXT`, one paragraph on what the work is about, never the research report. The command opens the work and its stage when needed, links the current commit and numbers the iteration: a later capture with the same `--view-title` supersedes the earlier view as `SCREEN · #2`. Keep a screen's title identical across iterations, give each screen its own title, and after a correction capture only the screens it changed. `--help` lists the other options.
3. Pass no `--host` and no `--native-session-id`. When a command reports the identity missing or ambiguous, read [host session identity](host-session-identity.md) and follow it; never substitute another session's identity or invent an ID.
4. The reply confirms the write: never read the work back after a capture. A reply that is not `queued` shows the capture is visible; `unchanged` means it was already published.
5. A `queued` reply (the viewer is stopped or silent) is not a failure: the capture is stored, and the next command or hook run with a running viewer sends it in order. Continue, do not start the viewer, and keep its image files until a later reply is not queued. Read `queue.rejected` in each reply and report those at the next handoff instead of repeating them.
6. When a reply reports a pending or uncertain operation, follow the next action it names; never delete the publisher journal or send a new request in its place. A missing `capture` command needs a Hive upgrade (`hive update`), not a publication helper. When the binary, the viewer or the identity is unavailable, keep the inputs, record what was not published in the checkpoint, report it at handoff and continue independent work. Never claim a capture was stored.

## Open the viewer

Never open the viewer on your own, and never ask about it on its own. At each stop where the user reviews captures, a UI walkthrough including a build's first rendered view, offer it inside what that stop already asks:

- **In the card.** Add one option, "Open the viewer", to the stop's own acceptance or validation question, written in the visible text as that decision's last option line: never first, never with `(★)`, without an `If you choose it:` line and without a decision ID of its own. When the question already holds the most options the tool accepts, use the reply line below.
- **When the user picks it.** Run `hive view open` once for the work (`--session-id ID` when several sessions are open), then ask the same question again through the question tool, with the same ID, title, situation and options except this one, keeping the round's other answers; the message before it is one line, such as "The viewer is open; D7 again". This changes four rules of the global guidance's «Questions and routes»: an ID is never reused, a round's text is written in full before its card, nothing follows the round's last card but the reply that ends its cards early, and every option carries an `If you choose it:` line. Ask the round's remaining cards first, unless one ends the round's cards early, then open the viewer and ask the question again.
- **Without a card, or when the round was already asked.** Add the reply line "or reply *open the viewer*" to the waiting line or the next-step block; when the user uses it, run `hive view open` once while the stop keeps waiting.
- **After that.** Once the user opened it, do not offer or reopen it in this conversation unless asked; when the user answers without opening it, offer it again at the next such stop.

## Close and input hygiene

At the work's completion phase, as [flow-close](../../flow-close/SKILL.md) step 1 sets, and only for a work with captures: run `hive view work close --outcome completed|abandoned --reason TEXT` for integrated or abandoned work. For a work that waits, run `hive view work sync --stage STAGE --state in_review|paused|awaiting_validation --reason TEXT` instead, with the stage of its last capture: `in_review` while its open pull request waits for the user's merge or a human reviewer, `paused` for a pause. Both read the work back; never close an already closed work again, and never infer a close from a document's status. Remove the task's disposable capture inputs only after that readback confirms the work and no capture reply is still `queued`; what to keep, and for how long, is set by [artifact retention](../../flow-close/references/artifact-layout.md).

## Manage a work

Renaming, archiving, restoring, pinning, unpinning and deleting run in the authenticated viewer or through `hive view work rename|archive|restore|pin|unpin|delete`, which act as `local_viewer` and take no identity flags. Run one only when the user asks for that action on a named work, once per request. `delete` removes the work and its evidence: ask it as a critical effect every time, even when the user named the work (the one exception to the global guidance's «unless the user asks for it on a named target»), and pass `--confirm` with the same work ID. Never use `local_viewer` in a publication command, and never expose viewer credentials or access fragments in evidence.
