# Review and gates for a candidate

Read by [flow-verify](../SKILL.md) when it runs the dedicated code review or the local checks before a push on a candidate. [Verification by risk and surface](../../flow-build/references/verification.md) keeps the evidence selection, the gate authorization rule and the frequency rules, and [runtime and UI gates](runtime-gates.md) keeps the local runtime checks and the human UI handoff; this reference sets what a candidate goes through before it is accepted and integrated. Verification does not grant deployment, publication, destructive effects, or external access.

## Local candidate and publication

| Boundary | Required decision or evidence |
| --- | --- |
| Local candidate | Complete applicable local in-vivo and UI verification, as [runtime and UI gates](runtime-gates.md) sets, using the built artifact for final UI/runtime validation where the stack has a build step; a rendered UI effect adds the independent children that [the UI gate](ui-gate.md) selects, then deliver it with [flow-walkthrough](../../flow-walkthrough/SKILL.md), after the sequence that [flow-verify](../SKILL.md) sets before asking the user to validate. Run the dedicated code review that the review question settled, at the moment [Dedicated review timing](#dedicated-review-timing) sets; propose it here only when it was not settled. |
| Publication / integration | Run the [local checks before publication](#local-checks-before-publication) and inspect actual CI coverage; the selected review mechanism ran on the local candidate, or runs on the pull request for a mechanism that only works there, as [Dedicated review timing](#dedicated-review-timing) sets. Account for automatic review/deployment effects before the push or PR event that triggers them. |

## Local checks before publication

**Condition:** a change that is not mechanical is about to be pushed with commits not yet integrated, in a repository whose CI runs on that push or its pull request, and the user did not skip verify or the check. A push that carries only commits already integrated, such as a merge from the base or a promotion, is not covered.

**Actions:** before the push, run locally:

1. the lint, typecheck and unit or convention tests of each package the change touches and of each package in the repository that depends on one of them, with the project's changed-package selection against the merge base with the freshly fetched base branch when it has one, otherwise each such package's own commands;
2. each job that the push or its pull request will trigger for the changed paths, read from the workflow files, that is deterministic and needs no external service, secret or deployment, such as a contract-compatibility or generated-artifact check, by the commands it runs.

A full local suite already run on the same candidate counts for its tests. When later edits change the candidate, such as review fixes or validation corrections, rerun the checks whose packages or paths they changed before the push and before the review that covers those edits. The service-dependent jobs that this push or its pull request triggers, such as an integration suite against a database, end-to-end jobs and deployments, stay in CI, beyond the affected tests and runtime checks verify already selects: name them CI-only in the report; a suite that CI runs only after merge follows [verification](../../flow-build/references/verification.md#frequency-and-coverage). A failure here is a defect that blocks the work, under the global rule. A check that cannot run here, such as one whose tool is missing, does not hold the push when a job this push or its pull request triggers runs it: report it as not run, as [verification](../../flow-build/references/verification.md#report-check-status) sets. These are routine checks; one expected to run longer than 30 minutes is costly, as [verification](../../flow-build/references/verification.md#gate-selection-and-timing) sets.

## Dedicated code review

Whatever the mechanism, and whatever its output says about how it checked its findings, send each P0 or P1 finding, and any finding that would block the merge, to a `hive-refute-claim` child before acting on it. Fix confirmed and plausible findings under the normal rules, drop refuted ones with the refuter's evidence, and report both.

Apply these rules to the findings of a code review:

- **Severity.** Map each finding to P0–P3 as the severity definitions in [incidental findings](../../flow-close/references/incidental-findings.md#which-findings-are-listed-and-how) set, before the refutation above and the rules below: translate a mechanism's own levels, or assign one when it reports none. Record in the report each finding's level, and name the P0 or P1 finding and its fix, or the later edit, that starts the re-review, or say that none does.
- **P0 and P1.** Fix the ones that are confirmed or plausible after refutation.
- **P2.** Fix one the change introduced when the fix is local and inside the change's scope; otherwise handle it under the shared incidental-findings rule.
- **P3.** Report without fixing or recording elsewhere; a P3 finding is not a defect under the shared incidental-findings rule. The one exception is a P3 global finding of the UI review, which the [UI gate](ui-gate.md#the-independent-children) records once in the project UI guide without a question.
- **Pre-existing findings.** Dispose of them under the shared incidental-findings rule. A pre-existing defect in a path the change makes reachable, or whose access it widens, counts as introduced by the change, whatever label the reviewer gave it; check that against the diff for each finding labeled pre-existing.
- **Review count.** Review each candidate in full once, at the moment [Dedicated review timing](#dedicated-review-timing) sets, with one code reviewer per candidate.
- **Re-review.** Re-review at most once, limited to the diff of the fixes against the reviewed point, and only when a P0 or P1 fix changed logic or a contract, or a later edit starts it as below. The reviewed point is the reviewed commit or, when the reviewed candidate was not committed, its candidate identity that [the UI gate](ui-gate.md#the-independent-children) defines, recorded when the review starts. From that round, act only on its P0 and P1 findings confirmed or plausible after refutation: fix each one without another review when its fix is local, inside the change's scope and changes no contract, cover it with a test, and report it as fixed without review; any other goes to the user as a decision. Its P2 and P3 findings stay unfixed: propose the P2 ones under the shared incidental-findings rule and report the P3 ones.
- **Later edits.** Later edits to the same candidate, including added scope, never start a full review. A validation correction made after the code review ran gets only the review of validation corrections that [Dedicated review timing](#dedicated-review-timing) sets, and that review is the last code review of the candidate, whether or not a re-review ran before it: act on its findings as the Re-review bullet sets for the findings of the re-review round, without another review. Until a re-review or that last review has run, an edit that an earlier review answer covers, other than a review fix or a validation correction, starts or joins the re-review: review the diff since the reviewed point, fixes included, with the same mechanism; without such an answer, report what changed and ask the user whether to review it. After the re-review, no other code review runs except that last review, and none runs after it. After the re-review or that last review, report a local edit inside the change's scope that changes no contract as unreviewed, and ask the user about any other edit. Record an unreviewed edit in the report, in the pull request body or, without one, the change record when either exists, and as a line `Unreviewed: <reason>` in the message of the commit that carries it, including a commit made later.

A technical verdict does not authorize delivery. A required gate declined or unavailable remains an unmet transition condition; an optional gate may be deferred explicitly. Interpret actual findings and terminal status rather than treating absent comments, a queued run, or a non-failing check as approval.

## Security review findings

Offer `hive-review-security` only as [Offer the security review](../../flow-build/references/security-boundaries.md#offer-the-security-review) sets, and run it only as [flow-security](../../flow-security/SKILL.md) sets. That stage reports and does not fix; when the candidate is not yet integrated, the stage that asked for the review then handles its findings with the rules above:

- Map each finding to P0–P3 and refute it as [Dedicated code review](#dedicated-code-review) sets.
- Fix, drop and report as the code-review rules set, and re-review at most once under the same limits, with `hive-review-security` limited to the diff of the fixes. After its last round, whether or not a security re-review ran, a later edit that crosses no security boundary starts no other security review and is reported as not security-reviewed, while its code review follows the Later edits bullet above; one that crosses a boundary gets the review that [flow-security](../../flow-security/SKILL.md) sets for boundaries that appear later, the only exception.
- When both reviews are asked before the code review starts, run them in parallel, not one after the other; a security review asked later, such as at the validation or beside a code review that only runs on the pull request, runs when asked. Handle both reports before the re-review round.
- A finding on a merged commit is not handled here: its fix goes in a follow-up pull request, as [delivery decisions](../../flow-plan/references/delivery-decisions.md) sets.

## Dedicated review timing

The dedicated code review, whichever mechanism the answer selects, runs once on the local candidate, after the affected tests, the full suite when it runs locally and the [local checks before publication](#local-checks-before-publication), and before the next step that publishes it or asks for its validation: under `interactive`, before the validation request; under `automatic`, and under `direct-base` chosen for a code repository, before the push; under `hold`, on the verified working tree. Fix its findings before that step, so the user validates, and the pull request carries, a reviewed candidate. A mechanism that only works on a pull request, such as a pull-request bot or a human reviewer, runs on the pull request right after the push instead, and the merge waits for its findings; under `interactive` that push follows the validation, so the validation message says the review is still due and that it will cover the corrections, and under `hold` or a chosen `direct-base`, which open no pull request, ask for a local mechanism or report the review as not run. Record in the pull request body which mechanism reviewed which commit, so a later promotion can tell which commits were reviewed. When a code review ran before the validation, the corrections the user's validation asks for get one more review, limited to the diff between the reviewed candidate and the accepted one, alongside the accepted-candidate gate of [the UI gate](ui-gate.md); no correction round runs a full review. A later edit to the same candidate follows [Dedicated code review](#dedicated-code-review). A follow-up pull request of the same ticket gets its review on its own local candidate in the same way, and a promotion pull request reviews only the commits not reviewed before their integration, as the promotion rule in [delivery decisions](../../flow-plan/references/delivery-decisions.md) sets.
