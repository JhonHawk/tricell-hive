# Review and gates for a candidate

Read by [flow-verify](../SKILL.md) when it runs the dedicated code review, the local runtime checks or the human UI handoff on a candidate. [Verification by risk and surface](../../flow-build/references/verification.md) keeps the evidence selection, the gate authorization rule and the frequency rules; this reference sets what a candidate goes through before it is accepted and integrated. Verification does not grant deployment, publication, destructive effects, or external access.

## Local candidate and publication

| Boundary | Required decision or evidence |
| --- | --- |
| Local candidate | Complete applicable local in-vivo and UI verification, using the built artifact for final UI/runtime validation where the stack has a build step; a rendered UI effect adds the independent children that [the UI gate](ui-gate.md) selects, then deliver it with [flow-walkthrough](../../flow-walkthrough/SKILL.md), after the sequence that [flow-verify](../SKILL.md) sets before asking the user to validate. Run the dedicated code review that the review question or the declared `Review` setting settled, at the moment [Dedicated review timing](../../flow-plan/references/delivery-decisions.md#dedicated-review-timing) sets; propose it here only when neither settled it. |
| Publication / integration | Inspect actual CI coverage; the selected review mechanism already ran on the local candidate, as [Dedicated review timing](../../flow-plan/references/delivery-decisions.md#dedicated-review-timing) sets. Account for automatic review/deployment effects before the push or PR event that triggers them. |

## Dedicated code review

When the selected mechanism is `hive-review-code`, or any review that does not verify its own findings, send each P0 or P1 finding, and any finding that would block the merge, to a `hive-refute-claim` child before acting on it. Fix confirmed and plausible findings under the normal rules, drop refuted ones with the refuter's evidence, and report both. Native reviews that already verify each finding, such as Claude Code's `/code-review` at medium effort or above, need no second pass.

When a mechanism reports its own severity levels, map each finding to P0–P3 by the same observable impact before applying these rules. Fix P0 and P1 findings that are confirmed or plausible after refutation, or verified by a mechanism that checks its own findings. Fix a P2 finding the change introduced when the fix is local and inside the change's scope; otherwise handle it under the shared incidental-findings rule. Report P3 findings without fixing or recording them elsewhere; they are not defects under the shared incidental-findings rule. The one exception is a P3 global finding of the UI review, which the [UI gate](ui-gate.md#the-independent-children) records once in the project UI guide without a question. Dispose of pre-existing findings under the shared incidental-findings rule; a pre-existing defect in a path the change makes reachable, or whose access it widens, counts as introduced by the change, whatever label the reviewer gave it, and you check that against the diff for each finding labeled pre-existing. Review each candidate in full once, at the moment [Dedicated review timing](../../flow-plan/references/delivery-decisions.md#dedicated-review-timing) sets. Re-review at most once, limited to the diff of the fixes against the reviewed commit, and only when a P0 or P1 fix changed logic or a contract. After that round, fix a finding still open or newly reported, without another review, when it would be fixed under these rules, its fix is local and inside the change's scope, and it changes no contract; cover it with a test and report it as fixed without review. Any other finding still open after that round goes to the user as a decision. Later edits to the same candidate, including added scope, never start another full review: when the declared `Review` value or an earlier answer covers them, review the diff since the reviewed commit with the same mechanism; otherwise report what changed since that commit and ask the user whether to review it. Use one code reviewer per candidate. Offer `hive-review-security` only as [Offer the security review](../../flow-build/references/security-boundaries.md#offer-the-security-review) sets, and run it only as [flow-security](../../flow-security/SKILL.md) sets, without waiting for the code reviewer.

A technical verdict does not authorize delivery. A required gate declined or unavailable remains an unmet transition condition; an optional gate may be deferred explicitly. Interpret actual findings and terminal status rather than treating absent comments, a queued run, or a non-failing check as approval.

## Runtime and UI gates

Decide local in-vivo applicability from the actual changed behavior. When needed, include and execute the relevant walk within authorized implementation without asking whether to run it. When judged unnecessary, say why in one line of the report and do not run it; the user can ask for it. That judgment never waives a required gate, overrides paused model pilots, or grants external effects. Deployed-environment walks retain the explicit authorization boundary in [gate selection and timing](../../flow-build/references/verification.md#gate-selection-and-timing).

For local implementation, always exercise the applicable changed path and relevant failure or permission states. Perform the corresponding deployed-environment exercise only within its explicit gate authorization. A mocked integration or source inspection does not establish behavior in the running system. Resolve authorized local setup, accounts, roles and seed data; access only the user can supply remains a reported prerequisite.

Use dev/HMR for iteration. For the final in-vivo or UI handoff, build and serve the compiled candidate using the project's production-style start or preview command where the stack distinguishes build from dev. Services without a build step use their normal runtime. Build only the affected applications and required dependencies, not every app per edit.

Default the handoff stack to local frontend, backend, database and necessary dependencies unless a different target was explicitly specified. Check effective connections, including build-time frontend URLs and backend persistence targets, without exposing credentials; localhost in the browser does not prove the whole path is local. Prepare authorized local accounts, roles and seed data before the walk, through the project's seed scripts, API or database, and pass each child the identifiers of the records it needs; a child creates data through the interface only when that creation is a journey under test. Report missing dependencies and any uncovered integration; never silently substitute a remote environment. External authentication, messaging, payments and similar effects need their own authorized boundary.

For any change with a rendered UI effect, read and follow [the UI gate](ui-gate.md): it owns the implementer's rendered inspection, the independent children that the repository's `UI verification` value or answer selects with their briefs and stops, and the accepted-candidate gate, in every delivery mode. Before delivering a later fix, including a code-review fix after approval, apply its [changes after a gate or approval](ui-gate.md#changes-after-a-gate-or-approval) rule.

Before driving a browser, read [browser automation](../../flow-build/references/browser-automation.md) and pass it to children that drive one.

## Human UI handoff

Before showing a user interface to the user for validation, read and follow [flow-walkthrough](../../flow-walkthrough/SKILL.md): it owns the early composition check on the dev server, the captures and recordings, and the handoff message and page. [flow-verify](../SKILL.md) owns the validation loop: the correction rounds, their task markers and the accepted-candidate gate.
