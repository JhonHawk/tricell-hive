# Verify a built candidate

For a UI change, the primary producer publishes the walk's captures as [walkthrough](references/walkthrough.md) sets, which a walkthrough or demo the user asks for follows alone, and reads [UI verification](references/ui-verification.md) for the verification and capture scope.

Enter with a built candidate: commits, or the working tree under `hold`. Without one, say what is missing and return the work to `flow-build`.

1. At entry, launch the reviews of step 2 that need only the candidate, then establish passing evidence for the full local suite as [Check reuse](#check-reuse) sets, serve the candidate with the project's production-style build or preview command where the stack has a build step, using and updating what `HIVE.local.md` records as the global guidance's «Local instructions» sets, and exercise the changed behavior through its real path, reading the global guidance's «Test accounts» before choosing an account. Check each `AC<n>` by its observation, in the place its `Observed in:` names when it names one, as [flow-plan](../flow-plan/SKILL.md#acceptance-criteria) sets; report a criterion that names a deployed environment as not verified, since only that deployment's functional walk observes it. Open each changed screen as the user would: one that shows a sign-in page, an error or an empty list is a setup failure to fix, not evidence. Neither are a claim that checks passed without their output, a capture taken before the last change it should show, or a child's report that the main thread did not check against the code or the running result. During this walk, capture the relevant screens and states as the UI verification reference sets; those are the walkthrough's captures. When the work has an approved example, as [flow-figma-design](../flow-figma-design/SKILL.md) sets, recorded in the plan's `UI` section or, for work without a change folder, in its checkpoint file, compare the capture of each region it shows against the example, through its frame's image. When a frame's image is not on disk where the walk runs, read the frame again from its recorded location and node; when it cannot be read, report the comparison as not run. A difference is a region, a component, an action's placement or an order that differs from the example; rendering variance between the design tool and the built screen is not one, and neither is what the plan records as decided otherwise, nor a correction the user asked for after approving the example, which the example's record names. Each difference is a UI defect the change introduced.
2. Run the reviews and show the result:
   - launch the code review with the mechanism the user chose, and `hive-review-security` only when the user asks for it, at verify entry alongside step 1, since they need the candidate and not the captures; only for a UI change does one `hive-review-ux` child wait for step 1's captures, briefed with them so it measures and interacts instead of capturing again. Brief each review child as [delegation](../flow-build/references/delegation.md#reviewer-brief) sets, which also sets the UX reviewer's scope. `hive-verify-change` runs only when the user asks for it;
   - when the delivery stops for validation, show the result while they run, with the walkthrough for a UI change, naming each difference from the approved example that step 1 found, and saying that the reviews are still running and that approval is subject to their findings; ask the user to approve or request corrections, with the open-viewer option that [viewer publication](references/viewer-publication.md#open-the-viewer) sets. This and any other question of verify, such as an authorization the walk needs, goes as visible text before the question tool's card, as the global guidance's «Questions and routes» sets.
3. When the user's answer and the reviews are in, apply [Review evidence](#review-evidence) before accepting a code finding as confirmed, then fix in one round the user's corrections, every UI defect the change introduced, and each confirmed blocking finding; never recommend approving a known defect as is. When a correction or an answer of the user adds, replaces or cancels a business rule, record it in the same turn as [business rules](../flow-plan/references/business-rules.md) sets. When the delivery does not stop for validation, list in the final report each difference from the approved example that remains after this round. A UI defect that was already there in a region the change's layout affects goes to the user before the push, as a finding in that validation round, with fix now or a ticket recommended as the global guidance's «Scope changes» ticket rule sets; fix in this round the ones the user picks. When the delivery does not stop for validation, it goes to the close's findings instead, as [flow-close](../flow-close/SKILL.md#findings) sets. A blocking finding, P1 or higher on the scale of [flow-close](../flow-close/SKILL.md#findings), is one that breaks a criterion, a contract, data, security or the build. Fix only what each finding names, and report instead of fixing each finding the reviewer marked plausible rather than confirmed, or whose evidence you cannot confirm. Recheck and recapture corrections as the UI verification reference sets. Reread a correction of the UX reviewer's finding with one follow-up to that same child that names the corrected regions and states, which it rereads as its role's step 3 sets; when the host has no tool to message that child, or the message returns an error, brief a new `hive-review-ux` child with the corrected findings, those regions and states, and the means to reach their states that [delegation](../flow-build/references/delegation.md#reviewer-brief) sets; never run a new full UX review. Cover in your own walk each state the UX reviewer listed as not covered, or report it as not verified in the validation round or, when the delivery does not stop for validation, in the final report. When a fix changed logic or a contract, review once more, limited to the fixes' diff and the callers of what changed; after that review, a blocking finding gets a local fix with its test and an `Unreviewed: <reason>` line in its commit message, or goes to the user when the fix is not local. Non-blocking findings go to the close's findings, never to another round, and the report says that the second review does not cover what the first one missed.
4. When that round changed something visible, show only those screens with the walkthrough and ask again; otherwise continue.
5. Before the push, ensure passing evidence covers every repository CI job that can run locally, for the packages the change touches and those that depend on them, applying [Check reuse](#check-reuse) to run missing or invalidated checks. Read the workflow files to establish that set. Report the jobs that need an external service, a secret or a deployment by name as CI-only.
6. Integrate as the delivery says: push and open the pull request. Wait for CI with one command that blocks until the run ends, such as `gh pr checks --watch` or `gh run watch --exit-status`, or the CI tool's own blocking wait, and read its result when it returns: in the foreground, or as a background command whose exit the host reports. When the host stops the command before the run ends, start the same command again, with no message between runs. Never redirect it to a file to read at intervals, never wait with a loop of sleeps and status queries, and send one message when it ends, not one per check or per interval. Then answer the reviews as [git-workflow step 7](../git-workflow/SKILL.md) sets, and merge as its step 8 sets: under `ready`, stop instead of merging once that step's current-base check passes, and stop the same way while a human reviewer's approval is pending. When a CI job fails, diagnose it from its log first and fix its cause; rerun it only when the log shows a transient failure. After the merge or a push to the base, wait for the CI run it triggered there with a blocking command on that run, such as `gh run watch <run-id> --exit-status`. When the host reports a background command's exit, run it in the background and run `flow-close` meanwhile: the close's cleanup leaves that command running, and its final report names the base CI as still running. When it ends, report its result; handle a failure as this step sets, on a new branch from the base. Without background commands, wait in the foreground, then run `flow-close`. Without a merge or a push to the base, run `flow-close` after the steps above.

Keep the checkpoint that `flow-build` sets, in `tasks.md`, through the script it names, or the checkpoint file of a plan kept in the conversation, with the reviewed commit and each finding's decision, and resume from it after a compaction.

## Check reuse

The full local suite must have passing evidence for the candidate. Reuse a passing check from this work only when its command and output are available and its covered code and dependencies, tests, configuration and relevant environment are unchanged since that run. Compare the candidate, including uncommitted changes, with the checked state. A stage change alone does not invalidate a result. Run checks with missing evidence, changed inputs or inputs whose equivalence you cannot establish; repeat only the affected checks when their scope is known, otherwise the full check. Record reused and rerun checks in the existing checkpoint. Reuse never replaces the real-path acceptance walk or the reruns a required independent verifier performs.

Read each check's result from the exit status of the check command itself. When its output is filtered, such as through a pipe into `tail` or `grep`, keep the check command's own status, not the filter's, in the same command, such as with bash's `${PIPESTATUS[0]}`, or save the whole output to a file in the host's temporary location and filter the file. Read an unclear result from that saved output; run the check again, keeping its status, only when neither the status nor the output was kept.

A round of fixes is every fix made for the failures, corrections and findings known when the round starts, such as step 3's round. In any flow, after each fix of a round, run first the tests of the edited files' packages or folders, then each failing test alone when those tests do not include it, and each failing check that is not a test run, such as a lint or a build. Once the round's last fix is in, run the checks the first paragraph requires, the full suite when the fixes' scope is not known; never the full suite after each fix.

## Review evidence

This applies to the code reviewer and to the main thread adjudicating findings, including output from a native review. Read the affected code and cited sources against the current candidate before treating a finding as confirmed. When a suspected behavior can be reproduced locally with the available tools and environment, within authorized effects and without changing another task's work, run a focused reproduction and report its command, expected result and actual output. For a contradiction in instructions, a contract or a project rule that reading establishes, cite the conflicting sources. When a reproduction is unavailable or would need an unauthorized effect, state that limit and distinguish conclusive source evidence from a plausible concern. A reviewer's assertion alone does not confirm a finding.
