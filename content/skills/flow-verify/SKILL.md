# Verify a built candidate

At verify entry, the primary producer follows [flow-walkthrough](../flow-walkthrough/SKILL.md), which sets when a viewer session applies, for the viewer stage. For a UI change, read [UI verification](references/ui-verification.md) for the verification and capture scope.

Enter with a built candidate: commits, or the working tree under `hold`. Without one, say what is missing and return the work to `flow-build`.

1. At entry, launch the reviews of step 2 that need only the candidate, then establish passing evidence for the full local suite as [Check reuse](#check-reuse) sets, serve the candidate with the project's production-style build or preview command where the stack has a build step, and exercise the changed behavior through its real path. Check each `AC<n>` by its observation. Open each changed screen as the user would: one that shows a sign-in page, an error or an empty list is a setup failure to fix, not evidence. Neither are a claim that checks passed without their output, a capture taken before the last change it should show, or a child's report that the main thread did not check against the code or the running result. During this walk, capture the relevant screens and states as the UI verification reference sets; those are the walkthrough's captures.
2. Run the reviews and show the result:
   - launch the code review with the mechanism the user chose, and `hive-review-security` only when the user asks for it, at verify entry alongside step 1, since they need the candidate and not the captures; only for a UI change does one `hive-review-ux` child wait for step 1's captures, briefed with them so it measures and interacts instead of capturing again. `hive-verify-change` runs only when the user asks for it;
   - when the delivery stops for validation, show the result while they run, with `flow-walkthrough` for a UI change, saying that the reviews are still running and that approval is subject to their findings; ask the user to approve or request corrections, with the open-viewer question that [viewer publication](../flow-walkthrough/references/viewer-publication.md#open-the-viewer) sets. This and any other question of verify, such as an authorization the walk needs, goes as visible text before the question tool's card, as the global guidance's «Questions and routes» sets.
3. When the user's answer and the reviews are in, apply [Review evidence](#review-evidence) before accepting a code finding as confirmed, then fix in one round the user's corrections, every UI defect the change introduced, and each confirmed blocking finding; never recommend approving a known defect as is. A UI defect that was already there in a region the change's layout affects goes to the user before the push, as a finding in that validation round, with fix now or a ticket recommended as the global guidance's «Scope changes» ticket rule sets; fix in this round the ones the user picks. A blocking finding is one that breaks a criterion, a contract, data, security or the build. Fix only what each finding names, and report instead of fixing each finding the reviewer marked plausible rather than confirmed, or whose evidence you cannot confirm. Recheck and recapture corrections as the UI verification reference sets. When a fix changed logic or a contract, review once more, limited to the fixes' diff and the callers of what changed; after that review, a blocking finding gets a local fix with its test and an `Unreviewed: <reason>` line in its commit message, or goes to the user when the fix is not local. Non-blocking findings go to the close's findings, never to another round, and the report says that the second review does not cover what the first one missed.
4. When that round changed something visible, show only those screens with `flow-walkthrough` and ask again; otherwise continue.
5. Before the push, ensure passing evidence covers every repository CI job that can run locally, for the packages the change touches and those that depend on them, applying [Check reuse](#check-reuse) to run missing or invalidated checks. Read the workflow files to establish that set. Report the jobs that need an external service, a secret or a deployment by name as CI-only.
6. Integrate as the delivery says: push, open the pull request, wait for CI with one command that blocks until the run ends, such as `gh pr checks --watch` or `gh run watch --exit-status`, or the CI tool's own blocking wait; never with a loop of sleeps and status queries, and with one message when it ends, not one per check, answer the reviews as [git-workflow step 7](../git-workflow/SKILL.md) sets, and merge; under `ready`, stop instead of merging once git-workflow step 8's current-base check passes. When a CI job fails, diagnose it from its log first and fix its cause; rerun it only when the log shows a transient failure. Then run `flow-close`.

Keep the checkpoint that `flow-build` sets, in `tasks.md` or the checkpoint file of a plan kept in the conversation, with the reviewed commit and each finding's decision, and resume from it after a compaction.

## Check reuse

The full local suite must have passing evidence for the candidate. Reuse a passing check from this work only when its command and output are available and its covered code and dependencies, tests, configuration and relevant environment are unchanged since that run. Compare the candidate, including uncommitted changes, with the checked state. A stage change alone does not invalidate a result. Run checks with missing evidence, changed inputs or inputs whose equivalence you cannot establish; repeat only the affected checks when their scope is known, otherwise the full check. Record reused and rerun checks in the existing checkpoint. Reuse never replaces the real-path acceptance walk or the reruns a required independent verifier performs.

## Review evidence

This applies to the code reviewer and to the main thread adjudicating findings, including output from a native review. Read the affected code and cited sources against the current candidate before treating a finding as confirmed. When a suspected behavior can be reproduced locally with the available tools and environment, within authorized effects and without changing another task's work, run a focused reproduction and report its command, expected result and actual output. For a contradiction in instructions, a contract or a project rule that reading establishes, cite the conflicting sources. When a reproduction is unavailable or would need an unauthorized effect, state that limit and distinguish conclusive source evidence from a plausible concern. A reviewer's assertion alone does not confirm a finding.
