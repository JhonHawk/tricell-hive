# Verify a built candidate

At verify entry, the primary producer follows [flow-walkthrough](../flow-walkthrough/SKILL.md), which sets when a viewer session applies, for the viewer stage. For a UI change, read [UI verification](references/ui-verification.md) for the verification and capture scope.

Enter with a built candidate: commits, or the working tree under `hold`. Without one, say what is missing and return the work to `flow-build`.

1. At entry, launch the reviews of step 2 that need only the candidate, then run the full local suite, serve the candidate with the project's production-style build or preview command where the stack has a build step, and exercise the changed behavior through its real path. Check each `AC<n>` by its observation. Open each changed screen as the user would: one that shows a sign-in page, an error or an empty list is a setup failure to fix, not evidence. Neither are a claim that checks passed without their output, a capture taken before the last change it should show, or a child's report that the main thread did not check against the code or the running result. During this walk, capture the relevant screens and states as the UI verification reference sets; those are the walkthrough's captures.
2. Run the reviews and show the result:
   - launch the code review with the mechanism the user chose, and `hive-review-security` only when the user asks for it, at verify entry alongside step 1, since they need the candidate and not the captures; only for a UI change does one `hive-review-ux` child wait for step 1's captures, briefed with them so it measures and interacts instead of capturing again. `hive-verify-change` runs only when the user asks for it;
   - when the delivery stops for validation, show the result while they run, with `flow-walkthrough` for a UI change, saying that the reviews are still running and that approval is subject to their findings; ask the user to approve or request corrections, with the open-viewer question that [viewer publication](../flow-walkthrough/references/viewer-publication.md#open-the-viewer) sets.
3. When the user's answer and the reviews are in, fix in one round the user's corrections, every UI defect the change introduced, and each confirmed blocking finding, opening its cited lines yourself; never recommend approving a known defect as is. A UI defect that was already there in a region the change's layout affects goes to the user before the push, as a finding in that validation round, with fix now or a ticket recommended as the global guidance's «Scope changes» ticket rule sets; fix in this round the ones the user picks. A blocking finding is one that breaks a criterion, a contract, data, security or the build. Fix only what each finding names, and report instead of fixing each finding the reviewer marked plausible rather than confirmed, or whose cited lines you cannot reproduce. Recheck and recapture corrections as the UI verification reference sets. When a fix changed logic or a contract, review once more, limited to the fixes' diff and the callers of what changed; after that review, a blocking finding gets a local fix with its test and an `Unreviewed: <reason>` line in its commit message, or goes to the user when the fix is not local. Non-blocking findings go to the close's findings, never to another round, and the report says that the second review does not cover what the first one missed.
4. When that round changed something visible, show only those screens with `flow-walkthrough` and ask again; otherwise continue.
5. Before the push, when the candidate changed since `flow-build` ran its checks, reproduce the repository's CI: read its workflow files and run locally every job that needs no external service, secret or deployment, for the packages the change touches and those that depend on them. Report the jobs that need a service, a secret or a deployment by name as CI-only.
6. Integrate as the delivery says: push, open the pull request, wait for CI with one command that blocks until the run ends, such as `gh pr checks --watch` or `gh run watch --exit-status`, or the CI tool's own blocking wait; never with a loop of sleeps and status queries, and with one message when it ends, not one per check, answer the reviews as [git-workflow step 7](../git-workflow/SKILL.md) sets, and merge; under `ready`, stop instead of merging once git-workflow step 8's current-base check passes. When a CI job fails, diagnose it from its log first and fix its cause; rerun it only when the log shows a transient failure. Then run `flow-close`.

Keep the checkpoint that `flow-build` sets, in `tasks.md` or the checkpoint file of a plan kept in the conversation, with the reviewed commit and each finding's decision, and resume from it after a compaction.
