# Verify a built candidate

For explicit E2E work, read [coordination](../flow-build/references/e2e-coordination.md) before accepting owner returns. Before the real-path walk, read [project verification](../hive-rule-project-verification/SKILL.md). For every candidate, read [suppression review](../hive-rule-suppression-review/SKILL.md), including when the chosen review is native or there is no dedicated review; supply it in review requirements and keep missing coverage unverified.

For a UI change, the primary producer publishes the walk's captures as [walkthrough](../hive-rule-walkthrough/SKILL.md) sets, and reads [UI verification](../hive-rule-ui-verification/SKILL.md) for the verification and capture scope.

Enter with a built candidate: commits, or the working tree under `hold`. Without one, say what is missing and return the work to `flow-build`. A walkthrough or demo the user asks for, with or without a candidate, follows only [walkthrough](../hive-rule-walkthrough/SKILL.md), on what is already built, and none of the steps below.

Keep the checkpoint as [checkpoint](../hive-rule-checkpoint/SKILL.md) sets, and resume from it after a compaction.

1. At entry, first read [no comments](../hive-rule-no-comments/SKILL.md), [blast radius](../hive-rule-blast-radius/SKILL.md) and [prose](../hive-rule-prose/SKILL.md) and apply each to the candidate, so their corrections join it before any review or check runs; when the user chose an adversarial review for this work item, read [interrogate](../hive-rule-interrogate/SKILL.md) before launching it. Then launch the reviews of step 2 that need only the candidate, then establish passing evidence for the full local suite as [check reuse](../hive-rule-checks/SKILL.md#check-reuse) sets, serve the candidate with the project's production-style build or preview command where the stack has a build step, using and updating what `HIVE.local.md` records as [local record](../hive-rule-local-record/SKILL.md) sets, and exercise the changed behavior through its real path, reading [test accounts](../hive-rule-test-accounts/SKILL.md) before choosing an account. Check each `AC<n>` by its observation, in the place its `Observed in:` names when it names one, as [flow-plan](../flow-plan/SKILL.md#acceptance-criteria) sets; report a criterion that names a deployed environment as not verified, since only that deployment's functional walk observes it. Open each changed screen as the user would: one that shows a sign-in page, an error or an empty list is a setup failure to fix, not evidence. Neither are a claim that checks passed without their output, a capture taken before the last change it should show, or a child's report that the main thread did not check against the code or the running result. During this walk, capture the relevant screens and states as [UI verification](../hive-rule-ui-verification/SKILL.md) sets; those are the walkthrough's captures. When the work has an approved example, as [flow-figma-design](../flow-figma-design/SKILL.md) sets, recorded in the plan's `UI` section or, for work without a change folder, in its checkpoint file, compare the capture of each region it shows against the example, through its frame's image. When a frame's image is not on disk where the walk runs, read the frame again from its recorded location and node; when it cannot be read, report the comparison as not run. A difference is a region, a component, an action's placement or an order that differs from the example; rendering variance between the design tool and the built screen is not one, and neither is what the plan records as decided otherwise, nor a correction the user asked for after approving the example, which the example's record names. Each difference is a UI defect the change introduced.
2. Run the reviews and show the result:
   - launch the code review with the mechanism the user chose, and `hive-review-security` only when the user asks for it, at verify entry alongside step 1, since they need the candidate and not the captures; only for a UI change does one `hive-review-ux` child wait for step 1's captures, briefed with them so it measures and interacts instead of capturing again. Brief each review child as [reviewer brief](../hive-rule-reviewer-brief/SKILL.md) sets, which also sets the UX reviewer's scope. `hive-verify-change` runs only when the user asks for it;
   - when the delivery stops for validation, show the result while they run, with the walkthrough for a UI change, naming each difference from the approved example that step 1 found, and saying that the reviews are still running and that approval is subject to their findings; ask the user to approve or request corrections, with the open-viewer option that [viewer publication](../hive-rule-viewer-open/SKILL.md) sets. This and any other question of verify, such as an authorization the walk needs, is asked as [asking a round](../hive-rule-questions/SKILL.md) sets.
3. When the user's answer and the reviews are in, read [review findings](../hive-rule-review-findings/SKILL.md) and follow it: it sets how to judge each finding and the one round of fixes. Fix a defect as [defect fix](../hive-rule-defect-fix/SKILL.md) sets, and when a correction or an answer of the user changes a business rule, read [business rules](../hive-rule-business-rules/SKILL.md).
4. When that round changed something visible, show only those screens with the walkthrough and ask again; otherwise continue. In a plan with a `## Delivery units` section, tick each box whose check passed and record its result under the checkpoint's `### Evidence`, as [change folder](../hive-rule-change-folder/SKILL.md) sets.
5. Before the push, ensure passing evidence covers every repository CI job that can run locally, for the packages the change touches and those that depend on them, as [local CI](../hive-rule-checks/SKILL.md#local-ci) sets.
6. Integrate as the delivery says: push and open the pull request. Then read [merge gate](../hive-rule-merge-gate/SKILL.md) and follow it: it sets the CI wait, the reviews' answer, the merge or the `ready` stop, and the wait for the base CI after the merge or a push to the base. Without background commands, wait in the foreground, then run `flow-close`. Without a merge or a push to the base, run `flow-close` after the steps above.
