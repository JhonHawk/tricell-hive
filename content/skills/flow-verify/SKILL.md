# Verify a built candidate

At entry, read `stage-entry.md` in this skill's folder whole: it holds the leaves verification-floor, no-comments, blast-radius, naming-language, prose, checks, checkpoint. At step 2, read `stage-exit.md` there whole: it holds reviewer-brief, questions, review-findings, merge-gate, pr-reviews. A step that links one of those leaves needs no new read until a compaction, after which read again each packet already read. If a packet is missing, read the linked leaves instead; if its last line is not its packet end line, read the rest; if a `## ` heading the end line names is missing, read that leaf; if the output says it was cut, read the linked leaves.

For explicit E2E work, read [coordination](../flow-build/references/e2e-coordination.md) before accepting owner returns. Before the real-path walk of E2E work, or of a change that adds or changes a project verification command, read [project verification](../hive-core/build/project-verification.md). For every candidate, read [suppression review](../hive-core/review/suppression-review.md). For a UI change, the primary producer publishes the walk's captures as [walkthrough](../hive-core/ui/walkthrough.md) sets, and reads [UI verification](../hive-core/ui/ui-verification.md) for the verification and capture scope.

Enter with a built candidate: commits, or the working tree under `hold`. Without one, say what is missing and return the work to `flow-build`. A walkthrough or demo the user asks for, with or without a candidate, follows only [walkthrough](../hive-core/ui/walkthrough.md), on what is already built, and none of the steps below.

Keep the checkpoint as [checkpoint](../hive-core/plan/checkpoint.md) sets, and resume from it after a compaction. At entry, read the work's `Playbook` record in it; a kind with no file in `hive-mode/playbooks/` is read from its row in [Pick the playbook](../hive-mode/SKILL.md#pick-the-playbook). When the user changes the work while it is open, classify the change as [scope changes](../hive-core/plan/scope-changes.md) sets; report a blocker or a failure as [reasons and blockers](../hive-core/messages/reasons-and-blockers.md) sets.

1. At entry:
   1. Read the [verification floor](../hive-core/build/verification-floor.md), which sets the checks this candidate's kind always gets and what its final report carries.
   2. Read [no comments](../hive-core/review/no-comments.md), [blast radius](../hive-core/review/blast-radius.md), [naming language](../hive-core/principles/naming-language.md) and [prose](../hive-core/build/prose.md) and apply each to the candidate, so their corrections join it before any review or check runs. When the user asked for a review of this work item by another provider's agent, read [interrogate](../hive-core/review/interrogate.md) before launching it.
   3. Launch the reviews of step 2 that need only the candidate, together as [delegation](../hive-core/delegation/delegation.md#when-children-run-at-the-same-time) sets, then establish passing evidence for the full local suite as [check reuse](../hive-core/build/checks.md#check-reuse) sets.
   4. Serve the candidate with the project's production-style build or preview command where the stack has a build step, using and updating what `HIVE.local.md` records as [local record](../hive-core/local/local-record.md) sets, and, when the delivery stops for validation and the session has a browser pane, through the host's preview, as [Show it in the host's pane](../hive-core/ui/walkthrough.md#show-it-in-the-hosts-pane) sets. Exercise the changed behavior through its real path, reading [test accounts](../hive-core/local/test-accounts.md) before choosing an account.
   5. Check each `AC<n>` by its observation, in the place its `Observed in:` names when it names one, as [flow-plan](../flow-plan/SKILL.md#acceptance-criteria) sets. Report a criterion that names a deployed environment as not verified, since only that deployment's functional walk observes it.
   6. Open each changed screen as the user would. One that shows a sign-in page, an error or an empty list is a setup failure to fix, not evidence, and neither is a capture taken before the last change it should show or a child's report the main thread did not check against the code or the running result.
   7. During this walk, capture the relevant screens and states as [UI verification](../hive-core/ui/ui-verification.md) sets; those are the walkthrough's captures.
   8. When the work has an approved example ([create-design](../create-design/SKILL.md)), recorded in the plan's `UI` section or, without a plan file, in its checkpoint file, compare the capture of each region it shows against the example's frame image. Read the frame again from its recorded location and node when the image is not on disk, and report the comparison as not run when it cannot be read.
      In that comparison, a region, component, action placement or order that differs is a UI defect the change introduced. Rendering variance between the design tool and the built screen is not one, and neither is what the plan records as decided otherwise or a correction the user asked for after approving the example.
2. Run the reviews and show the result:
   - launch the code review with the review mechanism in force, or, for a fix of findings an earlier round left, only the review «Fixing findings after the round» of [review findings](../hive-core/review/review-findings.md) sets, and `hive-review-security` when the user asked for it or accepted it as [security boundaries](../hive-core/build/security-boundaries.md) recommends, at verify entry alongside step 1, since they need the candidate and not the captures; only for a UI change does one `hive-review-ux` child wait for step 1's captures, briefed with them so it measures and interacts instead of capturing again. Brief each review child as [reviewer brief](../hive-core/delegation/reviewer-brief.md) sets, which also sets the UX reviewer's scope. Each review, whatever its mechanism, covers the checks the candidate weakens, as [weakened checks](../hive-core/review/suppression-review.md) sets. `hive-verify-change` runs only when the user asks for it;
   - under `interactive`, when the work item has no surface, as the global guidance's «Delivery» defines it, say in one line that it has nothing for the user to validate and continue without asking;
   - when the delivery stops for validation, which is `interactive` with a work item that has a surface, show the result while they run, with the walkthrough for a UI change, naming each difference from the approved example that step 1 found, and saying that the reviews are still running and that approval is subject to their findings; ask the user to approve or request corrections with the Validation template of [gate questions](../hive-core/messages/questions/gate.md), with the open-viewer option that [open the viewer](../hive-core/ui/viewer-open.md) sets. This and any other question of verify, such as an authorization the walk needs, is asked as [asking a round](../hive-core/messages/questions.md) sets.
3. When the user's answer and the reviews are in, read [review findings](../hive-core/review/review-findings.md) and follow it: it sets how to judge each finding, the one round of fixes, and how the findings not fixed are sorted and when their questions are asked. Fix a defect as [defect fix](../hive-core/build/defect-fix.md) sets, and when a correction or an answer of the user changes a business rule, read [business rules](../hive-core/business/business-rules.md).
4. When that round changed something visible, show only those screens with the walkthrough and ask again; otherwise continue. In a plan with a `## Delivery units` section, tick each box whose check passed and record its result under the checkpoint's `### Evidence`, as [plan record](../hive-core/plan/plan-record.md#plan-file) sets.
5. Before the push, ensure passing evidence covers the repository's CI jobs, as [local CI](../hive-core/build/checks.md#local-ci) sets.
6. Integrate as the delivery says: push and open the pull request as [git-workflow](../git-workflow/SKILL.md) step 6 sets. Then read [merge gate](../hive-core/git/merge-gate.md) and follow it: it sets the CI wait, the reviews' answer, the merge or the `ready` stop, and the wait for the base CI after the merge or a push to the base. Without background commands, wait in the foreground, then run `flow-close`. Without a merge or a push to the base, run `flow-close` after the steps above.

Reply: at a validation stop the message ends with step 2's question; once integrated, `flow-close` writes the report as the row of [close report](../hive-core/close/close-report.md#variants) that the delivery mode picks, and this flow writes none.
