# Viewer publication

Read once per session, when the first plan, build or verify flow that [flow-walkthrough](../SKILL.md) gives a viewer session starts, and again after a compaction; follow it at each stage change, new capture or document snapshot, and at close. A work has its own viewer ID and accepted native producers; the current lead coordinates it. Delegated children return findings and evidence to their parent rather than opening another work. This procedure changes only local viewer state and does not authorize project, tracker or external writes. Hive's session hooks already report the session's start, activity and end to the viewer, and the host's native task list where the host has one; they publish no stage, reason, document, capture or validation. Those stay yours.

## Connect and resume

1. Check that `hive` and an already running compatible viewer are available; never start or restart the service. Read `hive view work contract` once per flow for the commands, limits and complete inputs, and again only after a compaction or an unexplained validation error. It is authoritative. A missing `work` capability needs a Hive upgrade, not an agent-generated publication helper.
2. Pass no `--host` and no `--native-session-id`: the binary resolves the real session from the host's session variable or the map that the session hook wrote, and registers the project root when `work open` runs. When a command reports the identity missing or ambiguous, read [host session identity](host-session-identity.md) and follow it; never substitute the lead's identity, an Engram ID, a timestamp or an invented ID.
3. Name the work with the ticket key when there is one, otherwise a descriptive key, and keep that key in the checkpoint. The binary keeps the returned IDs and the session's current work, so omit `--work-id` while exactly one work of this session is open; pass it when several are (a second ticket or change folder in the same native session gets its own key). A moved change directory needs `work bind`.
4. A `queued` result (the viewer is stopped or silent) is not a failure: the declaration is stored. Continue the work and do not start the viewer; the next command or hook run with a running viewer sends the queue in order. Read `queue.rejected` in that command's reply: it lists declarations that no longer apply, such as a stage already completed; report them at the next handoff instead of repeating them. Keep the inputs of a queued `evidence` until a later reply is not queued.
5. On an uncertain publication, run `work resume` and do not replace the unresolved request with a new one. A definitively rejected intent is released only with `work reconcile --action archive-rejected --pending ID --reason TEXT`. Never delete the publisher journal to clear an error. `work list` and `work show` (the current work, or `--work-id ID` when several are open) recover observed state and never reopen closed work.

If identity, binary, service or a capability is unavailable, preserve inputs, record the unpublished state in the checkpoint, report it at handoff and continue independent work. Never claim an event was stored.

## One declaration per stage change

Publish when a stage starts, changes state, or needs a capture or document; never per file edit or per message. Each command replies with at most 4096 bytes; a repeat of the same declaration answers `unchanged`.

1. `work open --key KEY --title TEXT --summary TEXT` creates the work and needs no change folder. A plan with a change folder adds `--project ROOT --change DIR`.
2. `work sync --stage STAGE --state STATE --reason TEXT [--tasks FILE|-] [--summary TEXT] [--previous-stage OCCURRENCE] [--close completed|abandoned]` starts or updates the stage and applies the task states of «Tasks» in one call. Use it at stage start, whenever the state changes (`in_review`, `awaiting_validation`, `paused`, `completed`, `failed`) and when a task of a plan completes or blocks. The stage, state and reason are your choice and are never inferred from a document status or an index. A terminal stage needs `--previous-stage` to re-enter.
3. `work publish --change DIR --stage STAGE` publishes the change folder's Markdown as immutable snapshots (see «Plan documents»).
4. `work evidence --stage STAGE --view-title TEXT --image FILE[:caption] ...` uploads captures, registers the candidate when its commit is new (`--candidate COMMIT`) and appends one validation view; `--supersedes VIEW` makes an iteration replace that view. Group images by the views and tickets they cover: one view per screen. Give changed captures distinct paths and captions and leave unaffected earlier views current.
5. `work close --outcome completed|abandoned --reason TEXT`, or `sync ... --close`, completes the active stage, closes the work and reads it back.

Stage names come from the stage key (`research|plan|build|verify|delivery`); the viewer translates them, so leave `--summary` for concrete context and never repeat the stage name. Start the stage before substantive work, including before captures. Concurrent reviews do not claim the foreground stage. When waiting for the user, declare the stage `awaiting_validation` with the actual reason and resume it with the next `sync`; a CI wait is a different wait, not human validation. Report status as recorded, not as proof that a process is alive.

Use the IDs each reply returns instead of reading the work after every write. Before telling the user a publication is visible, and when resuming after an interruption or conflict, confirm with `work show` (a close that read back satisfies this at close). Verify stored images through the authenticated viewer when available. If confirmation is incomplete, keep the inputs and report the limit. Do not expose viewer credentials or access fragments in evidence.

## Tasks

- **A work without plan tasks** (a build with no `tasks.md`): when the host reports a native task list, the viewer takes it as the work's tasks, so register nothing and pass no `--tasks` for them. Today Claude Code and OpenCode (its `todowrite` list) report one; on a host that reports none, or when you want a task the list lacks, declare it in `sync --tasks`: a JSON array `[{"key":"T1","title":"Parse input","state":"in_progress"}]` of keys `T<n>` from 1, states `not_started|in_progress|in_review|blocked|completed`. A `blocked` task carries `block` {reason, steps, owner, resume_when} and leaving blocked carries `resolution`. Once you declare one task of a work, declare all of them: the viewer then ignores the host's list for that work except for activity.
- **A work with plan tasks**: when a build starts, register the whole agreed plan once with `work tasks register --plan-revision REV --json FILE` (stable keys, unique order, stage segments, the confirmed revision of the published plan; the contract lists the JSON). Identical registration is skipped without resetting progress. Then carry the states in `sync --tasks` (key and state; omitted tasks stay as they are), at each stage change and when a task completes or blocks. Completion, blocking and reopening affect only the declared segment, never plan approval or work closure. The registry owns the counts; a published checklist is a snapshot, never live state. The host's native task list does not replace it.

## Plan documents

Publish plan documents as immutable snapshots only where the user reviews them: the first at the stop where the user chooses between changes and build, and one more after each round of changes the user asks for; never an internal draft before the plan review. Source files stay authoritative. Open the work with its change folder, declare the plan stage with `sync`, then run one `work publish --change DIR --stage plan` (default selection: proposal, tasks, optional design, sorted spec deltas; `--document` and `--explicit-documents` select others; non-plan stages need explicit documents and a document key). The binary respects the contract's tab and size bounds, freezes the original bytes, verifies them and returns the revision or `unchanged`. It does not parse checkboxes, follow links or manufacture approval. Record an approval or a requested change only from the conversation, linked to the document revision when known, and never invent a timestamp.

## Shared work and authority

Read current membership and versions before a join, handoff or continuation. The lead accepts producers and controls task registration, shared metadata and explicit foreground transfer. Accepted collaborators keep their own actor and operate within the contract's permissions; a review does not take the foreground or complete another producer's stage. A native ID is provenance, not proof that a process is running.

If the lead is unavailable, do not infer abandonment, kill a process or transfer authority silently. Recovery and the other local management actions (rename, archive, restore, pin, unpin, delete) run in the authenticated local viewer or through `hive view work rename|archive|restore|pin|unpin|recover|delete`, which act as `local_viewer` and take no identity flags. Run one only when the user asks for that action on a named work, once per request; otherwise report that it needs the user. To recover a work whose lead ended, send `hive view producer request` first, run `recover --request-id ID`, then complete the active stage before `work close`. `delete` removes the work and its evidence: ask it as a critical effect every time, even when the user named the work (the one exception to the global guidance's «unless the user asks for it on a named target»), and pass `--confirm` with the same work ID. Never use `local_viewer` in a publication command.

## Delivery and CI observations

Use the `delivery` stage for delivery work and its typed wait node. Register tickets, deliveries and candidates once with the advanced operations below, from their observed provider namespace, repository and external ID (a display key or editable URL is not identity). Publish the observed candidate commit, the pull request delivery ID, the confirmed required-check policy and immutable run observations from already-authorized authenticated provider reads; do not send private repository identifiers to an anonymous third-party service. No access or no confirmed required set means unknown, never success from an empty list. Keep one wait for reruns of the same candidate and policy; a new commit or changed policy gets a linked new wait. A late older attempt is historical. Green checks do not imply acceptance or merge, and reading a wait never triggers a rerun.

**Advanced operations:** membership, tickets, deliveries, candidates outside `evidence`, CI waits and explicit reopening use `hive view contract --for FLOW` or `--operation NAME`, and the low-level `hive view` operations; they take `--host` and `--native-session-id` as that contract says.

## Open the viewer

Never open the viewer on your own, and never ask about it on its own. At each stop where the viewer holds something for the user to review, a plan at its approval stop and a UI walkthrough, including a build's first rendered view, offer to open it inside what that stop already asks. Where that stop asks a round through the host's question tool, add "Open the viewer?" as one more question of that round; otherwise, or when that round was already asked, add one reply line to the message's waiting line or to its next-step block of the global guidance's «Questions and routes», such as "or reply *open the viewer*". Never give it its own decision ID or its own call to the question tool. When the user accepts, run `hive view open` for the work once (with `--session-id ID` when several are open); after that, do not ask again or reopen it in this conversation unless the user asks. When the user declines or does not answer, ask again at the next such stop. Return the nonsecret target and evidence to the calling flow; it owns validation and review gates.

## Close and input hygiene

On pause, `work sync` the active stage to `paused` and keep the inputs for resumption. On completion or abandonment, `work close` (or `sync --close`) with an honest outcome and reason; closing is never inferred from document status. When the work stops at an open pull request that waits for the user's merge or a human reviewer, its completion point under [flow-close](../../flow-close/SKILL.md), declare the active stage `in_review` instead of completing it or closing the work; the session that finds the pull request merged closes it. Follow flow-close for the completion phase; keep its readback and do not close an already closed work again. Remove task-owned disposable upload inputs only after the close reply or `work show` confirms the work and the evidence reply was not `queued`. What to keep, and for how long, is set by [artifact retention](../../workspace-conventions/references/artifact-layout.md). Never discard inputs based on an unconfirmed copy.
