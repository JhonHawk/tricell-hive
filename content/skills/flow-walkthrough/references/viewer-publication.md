# Viewer publication

Read when a research, plan, build or verify flow that [flow-walkthrough](../SKILL.md) gives a viewer session starts, at each stage change, new capture or document snapshot, and at close. A work has its own viewer ID and accepted native producers; the current lead coordinates it. Delegated children return findings and evidence to their parent rather than opening another work. This procedure changes only local viewer state and does not authorize project, tracker or external writes.

## Connect and resume

1. Check that the `hive` binary and an already running compatible viewer are available. Do not start or restart the service. Use `hive view contract --operation NAME` offline for the operation needed; request the complete `hive view contract` only when its catalog is needed. The returned contract is authoritative for commands, schemas, limits, preconditions and examples. Request bodies use `--json FILE` or `--json -`; upload bytes with `--file` as the contract specifies.
2. Resolve the registered project, canonical host and actual native session ID from the current runtime. If identity is not directly available, read [host session identity](host-session-identity.md). Register the project root with `hive view register --dir <root>`. Create your work using the contract, with the ticket key as `work_key` when the work has a ticket: a later flow of that ticket in the same native session gets the same work back. Without a ticket, omit `work_key`: each creation makes a new work, so resume it by its retained viewer ID, never with another creation. When another native session is working on that same authorized work, join its explicit viewer work ID instead of redeclaring the work: request membership using your own actual Source and have its lead accept the request. Never substitute another session's ID, an Engram session/project ID, a timestamp or an invented identity. Work ID, native Source and producer_id are different fields; retain each returned value.
3. Keep returned work, producer, task/segment, ticket, delivery, candidate, wait, event, view, artifact, document and revision IDs, versions, sequence numbers and operation IDs in the existing work checkpoint or current conversation. Reuse the tuple and read current state before continuing after an interruption. If it is closed and the user explicitly requests new or resumed work in this conversation, use the version-conditional session update to set it active before publishing; a read, refresh or create alone must never reopen it. Deleted identities remain unavailable. Retry an operation with the same ID only for the exact same request; use its receipt and readback to resolve uncertainty.

If identity, binary, service or required capability is unavailable, preserve inputs, record the unpublished state in the existing checkpoint, report it at handoff and continue independent work. Never claim an API event was stored.

## Shared work and authority

Read current membership and versions before a join, handoff or continuation. The lead accepts producers and controls task registration, shared ticket/delivery metadata and explicit foreground transfer. Accepted collaborators retain their own actor/source and operate only within the contract's permissions; they do not impersonate the lead. A review does not take the foreground or complete another producer's stage. A native ID is provenance, not proof that a process is still running.

If the lead is unavailable, do not infer abandonment, kill a process or transfer authority silently. The authenticated local viewer offers explicit recovery to an eligible pending producer with a reason and version check. Report that required human action and continue independent work. Browser management/recovery uses local_viewer; native publishers never use that actor to bypass publication authority.

## Register once, reference by ID

When a build starts, before its first task, register the whole agreed plan once as work-owned tasks, with stable task keys, explicit unique plan_order and the required stage segments. A task can span stages; bind and update the actual segment for the current occurrence instead of recreating the task in Build, Verify or Delivery. Current counts derive from that one registry; a published Markdown checklist is an immutable editorial snapshot, never a second state store.

Use task/segment transitions for declared progress, with the actor, reason and expected versions. A blocked transition includes its real reason, actionable unblock steps, responsible party and resolution criterion. Completion, review, blocking and reopening affect only their declared scope; a task transition does not approve a plan or close a stage/work. Scope/order/assignment changes use the required plan or decision reference. Transition a task's segment when the task starts and when it is done. A host's native task list does not replace this registry: the viewer cannot read it. Do not manufacture progress from a checklist, elapsed time or a refresh.

Register tickets and Git deliveries once using their observed provider namespace/repository and native external ID. A display key or editable URL is not identity. Create deduplicates identical values; differing metadata needs an explicit patch by its stable ID. Correct the registry once so current references update everywhere. Events/views take ticket IDs; delivery events take delivery IDs. The server captures publication context. Never resubmit copied objects or rewrite earlier publications to make their links/status look current.

Register immutable candidate descriptors before publishing candidate-bound evidence or CI. Select candidate_id explicitly; a moving HEAD does not retarget earlier evidence. Same-byte artifact reuse retains its first provenance and candidate: created:false is reuse, not a fresh capture. No operation here fetches a provider, runs CI or performs a remote Git action.

## Stages and evidence

Use the existing stage enum as the only reserved stage key. The viewer translates that heading for the browser; do not put the stage name again in title. Send title as an empty string when no additional context is needed, or concise context only, such as the scope being revised. Non-stage activity retains its required free title. Stage title patches can clear that context with an empty string; omission preserves it. Do not infer a stage from its title or publish a second label/key collection. Consult the offline catalog's localization metadata rather than inventing translated enum values.

Start the applicable research, plan, build, verify or delivery stage before substantive work, including before captures. Use the returned versions for conditional transitions. Update the same occurrence when its state changes; a completed or failed occurrence is terminal, so a later stage or substantive plan revision gets a new related occurrence. Concurrent reviews do not claim the foreground stage. When waiting for the user, pause the applicable stage and set the work to awaiting validation with its actual reason; resume explicitly when work continues. A background review may continue without claiming that foreground stage. A CI wait is a different kind of wait, not human validation. Report status as recorded, not as proof of process liveness.

Publish plan documents and already-authorized research records as immutable uploaded snapshots only where the user reviews them: a plan's first snapshot at the stop where the user chooses between changes and build, one more after each round of changes the user asks for, and a research record when the research reports; never a snapshot no one is asked to review, such as an internal draft before the plan review. Source files remain authoritative. Research without an authorized retained document publishes its concise stage summary, not an extra report created solely for the viewer. Link actual approvals or requested changes to the specific document revision or evidence when known, as agent-reported events from the conversation. Never infer an approval or invent a timestamp.

Give activity titles and summaries concrete, concise meaning rather than repeating status, metadata or the whole plan. Group images and instructions by the views and tickets they actually cover: one shared view may reference multiple tickets; different screens get separate views. Upload captures as artifacts and append evidence using the contract, linking task_id/segment_id and the actual stage where applicable. Keep general activity outside tasks when it is not task-specific. For an iteration, give changed captures distinct source paths and captions, publish replacement views with their superseded references, and leave unaffected earlier views current. Read back the committed session and check the identity tuple, versions, event sequence, document and artifact references, sizes and hashes against the receipts and source bytes. Read document content back through the supported CLI. Verify stored images through the authenticated viewer when available. If confirmation is incomplete, retain the inputs and report the limit; do not claim successful publication. Do not expose viewer credentials or access fragments in evidence.

## Delivery and CI observations

Use the Delivery stage for delivery work and its typed wait node. Publish the observed candidate commit, canonical PR delivery ID, confirmed required-check policy/source/time and immutable run observations from already-authorized authenticated provider reads. Do not send private repository identifiers to an anonymous third-party service. No access or no confirmed required set means unknown, not success from an empty list.

Keep the same wait for reruns of the same candidate/policy; explicitly start/promote the applicable attempt for each required check using current provider evidence. A late successful older attempt is historical and cannot replace the current failed/waiting one. A new commit or changed policy gets a linked new wait, without carrying success forward. Green checks do not imply acceptance, merge or integration. Reading a wait never triggers a rerun or changes provider policy.

## Open the viewer

Never open the viewer on your own. At each stop where the viewer holds something for the user to review, ask whether to open it: a plan at its approval stop, a research report, and a UI walkthrough, including a build's first rendered view. Where that stop already asks through the host's question tool, add "Open the viewer?" as one more question of that round; where it ends with the next-step block of the global guidance's «Questions and routes», add one reply line to that block, such as "or reply *open the viewer*". When the user accepts, open the work once with `hive view open --session-id ID` and, when needed, the event target from the contract; after that, do not ask again or reopen it in this conversation unless the user asks. When the user declines or does not answer it, ask again at the next such stop. Return the nonsecret target and evidence to the calling flow; it owns validation and review gates.

## Close and input hygiene

On pause, conditionally pause the active stage and session and retain inputs for resumption. On terminal completion or abandonment, conditionally complete or pause the active stage, then close the session using its current version and an honest outcome. When the work stops at an open pull request that waits for the user's merge or a human reviewer, its completion point under [flow-close](../../flow-close/SKILL.md), conditionally set the active stage to `in_review`, which sets the session to `in_review`, instead of completing it or closing the session; the session that finds the pull request merged closes it. Keep the current review inputs for the rest of the session. At session-end hygiene, remove task-owned disposable API upload inputs only after reading back the exact tuple and committed version, revision and artifact references and verifying their sizes and hashes against the receipts and sources. What to keep, and for how long, is set by [artifact retention](../../workspace-conventions/references/artifact-layout.md).

Never manufacture API IDs or discard inputs based on an unconfirmed copy.
