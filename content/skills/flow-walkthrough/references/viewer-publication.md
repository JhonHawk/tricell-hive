# Viewer publication

Read once per session, when the first plan, build or verify flow that [flow-walkthrough](../SKILL.md) gives a viewer session starts, and again after a compaction; follow it at each stage change, new capture or document snapshot, and at close. A work has its own viewer ID and accepted native producers; the current lead coordinates it. Delegated children return findings and evidence to their parent rather than opening another work. This procedure changes only local viewer state and does not authorize project, tracker or external writes.

## Connect and resume

1. Check that `hive` and an already running compatible viewer are available; never start or restart the service. Read `hive view work contract` once per flow for the semantic publisher's commands, limits and complete inputs; repeat only after compaction or an unexplained validation error. For advanced operations not covered there (membership, tickets, deliveries, candidates, captures, CI waits and explicit lifecycle reopening), use `hive view contract --for FLOW` or `--operation NAME`. The returned contract is authoritative. A missing `work` capability needs a Hive upgrade, not an agent-generated publication helper.
2. Resolve the registered project, canonical host and actual native session ID from the current runtime. If identity is not directly available, read [host session identity](host-session-identity.md). Register the root with `hive view register --dir ROOT`. Use `work open` or the creation form of `work publish` with explicit project, source directory and stable key; use the ticket key when present, otherwise a descriptive work key retained in the checkpoint. Keep the returned work ID. A second ticket or change folder in the same native session gets its own key and work ID. Updates use the retained work ID and explicit directory, never whichever directory happens to be current. A moved directory needs `work bind`; changing directories is not permission to replace a binding. A build with no plan, such as a small understood change, has no change folder for `work open` and no plan revision for `work tasks register`: create its work with `hive view session create`, its tasks with `hive view task create` without a plan revision, and follow its stages and tasks with the same contract's low-level operations (`hive view contract --for build`).
3. Pass your verified `--host` and `--native-session-id` on publication mutations; the local management commands of «Shared work and authority» take neither. Another native session first joins the explicit work ID through the existing membership contract and obtains lead acceptance. Never substitute the lead's identity, an Engram ID, a timestamp or an invented identity. The binary resolves accepted producers, internal IDs, versions and exact request receipts. Retain work/revision IDs and semantic task keys in the checkpoint; retain low-level operation tuples only for advanced operations you issue directly. Use `work list` and `work show` to recover observed state. Neither reads nor `work resume` reopen closed work; an explicitly authorized semantic reopening still uses the existing conditional session operation.
4. On an uncertain publication, retain the pending ID and run `work resume` with the same native source. The binary replays frozen bytes and exact requests even if source files changed. Do not replace an unresolved request with a new publication. A definitively rejected intent can be retained and released through explicit `work reconcile --action archive-rejected --pending ID --reason TEXT`; this does not roll back remote content or discard unknown outcomes. After reconciliation, a new publication uses current source bytes and current remote state. Never delete the publisher journal to clear an error.

If identity, binary, service or required capability is unavailable, preserve inputs, record the unpublished state in the existing checkpoint, report it at handoff and continue independent work. Never claim an API event was stored.

## Shared work and authority

Read current membership and versions before a join, handoff or continuation. The lead accepts producers and controls task registration, shared ticket/delivery metadata and explicit foreground transfer. Accepted collaborators retain their own actor/source and operate only within the contract's permissions; they do not impersonate the lead. A review does not take the foreground or complete another producer's stage. A native ID is provenance, not proof that a process is still running.

If the lead is unavailable, do not infer abandonment, kill a process or transfer authority silently. Recovery, with a reason and version check, and the other local management actions (rename, archive, restore, pin, unpin and delete) run in the authenticated local viewer or through `hive view work rename|archive|restore|pin|unpin|recover|delete`, which act as `local_viewer` with `origin: cli`. Run one of these commands only when the user asks for that action on a named work, once per request; otherwise report that the action needs the user and continue independent work. To recover a work whose lead session ended, first send a join request with `hive view producer request`, then run `recover` with that request ID; after it, complete the active stage before `work close`. `delete` removes the work and its evidence: ask it as a critical effect every time, even when the user named that work, which is the one exception to the global guidance's «unless the user asks for it on a named target» for critical effects, and pass `--confirm` with the same work ID. Never use `local_viewer` in a publication command.

## Register once, reference by ID

When a build starts, before its first task, register the whole agreed plan once through `work tasks register` (a build with no plan follows step 2 of «Connect and resume»), with stable task keys, explicit unique order, required stage segments and a confirmed plan revision. The compact JSON carries semantic intent; never copy internal server IDs or expected versions into it. Identical registration is skipped without resetting progress; changed scope requires explicit metadata updates. A task can span stages. The one registry owns current counts; a published Markdown checklist is an immutable editorial snapshot, never another live state store.

Use `work task update` with the task key, stage, state and real reason when each segment starts and finishes. Lead-owned registration and stage commands bind applicable segments to the current occurrence, so accepted assignees can transition their own segments. The binary resolves the task keys; it does not infer progress from Markdown. Supply the contract's complete block, resolution or review fields when applicable. Completion, blocking and reopening affect only the declared segment, never plan approval or work closure. Scope/order/assignment changes use explicit metadata mode and the required plan or decision reference. The host's native task list does not replace this registry.

Register tickets and Git deliveries once using their observed provider namespace/repository and native external ID. A display key or editable URL is not identity. Create deduplicates identical values; differing metadata needs an explicit patch by its stable ID. Correct the registry once so current references update everywhere. Events/views take ticket IDs; delivery events take delivery IDs. The server captures publication context. Never resubmit copied objects or rewrite earlier publications to make their links/status look current.

Register immutable candidate descriptors before publishing candidate-bound evidence or CI. Select candidate_id explicitly; a moving HEAD does not retarget earlier evidence. Same-byte artifact reuse retains its first provenance and candidate: created:false is reuse, not a fresh capture. No operation here fetches a provider, runs CI or performs a remote Git action.

## Stages and evidence

Use the existing stage enum as the only reserved stage key. The viewer translates that heading for the browser; do not put the stage name again in title. Send title as an empty string when no additional context is needed, or concise context only, such as the scope being revised. Non-stage activity retains its required free title. Stage title patches can clear that context with an empty string; omission preserves it. Do not infer a stage from its title or publish a second label/key collection. Consult the offline catalog's localization metadata rather than inventing translated enum values.

Start the applicable plan, build, verify or delivery stage before substantive work, including before captures, using `work stage`. Update the same occurrence when its state changes; a completed or failed occurrence is terminal, so reentry requires the explicit prior occurrence. The binary owns conditional versions; stage choices and reasons remain yours. Concurrent reviews do not claim the foreground stage. When waiting for the user, pause the applicable stage and set the work to awaiting validation with its actual reason; resume explicitly when work continues. A background review may continue without claiming that foreground stage. A CI wait is a different kind of wait, not human validation. Report status as recorded, not as proof of process liveness.

Publish plan documents as immutable uploaded snapshots only where the user reviews them: a plan's first snapshot at the stop where the user chooses between changes and build, and one more after each round of changes the user asks for; never a snapshot no one is asked to review, such as an internal draft before the plan review. Source files remain authoritative. Publish them with one `work publish` invocation for the retained work ID, source directory and stage. The default plan selection is proposal/tasks, optional design and sorted spec deltas; explicit document mode replaces discovery when deliberately selected. Respect the contract's file/tab bounds instead of truncating or splitting silently. The binary freezes and uploads original Markdown, verifies stored bytes and returns a compact confirmed revision or `unchanged`. It does not parse checkboxes, follow linked files or manufacture approval. A publication to an existing work requires an existing stage; only the explicit creation form starts its declared stage. Link actual approvals or requested changes to the specific document revision or evidence when known, as agent-reported events from the conversation. Never infer an approval or invent a timestamp.

Give activity titles and summaries concrete, concise meaning rather than repeating status, metadata or the whole plan. Group images and instructions by the views and tickets they actually cover: one shared view may reference multiple tickets; different screens get separate views. Upload captures as artifacts and append evidence using the contract, linking task_id/segment_id and the actual stage where applicable. Keep general activity outside tasks when it is not task-specific. For an iteration, give changed captures distinct source paths and captions, publish replacement views with their superseded references, and leave unaffected earlier views current. Use the IDs and versions each write returns for the next write instead of reading the session after each one. For advanced low-level writes, read the committed session back before telling the user a publication is visible, at close, and when resuming after an interruption or a version conflict, and check the identity tuple, versions, event sequence, document and artifact references, sizes and hashes against the receipts and source bytes. Read document content back through the supported CLI. Verify stored images through the authenticated viewer when available. If confirmation is incomplete, retain the inputs and report the limit; do not claim successful publication. Do not expose viewer credentials or access fragments in evidence.

## Delivery and CI observations

Use the Delivery stage for delivery work and its typed wait node. Publish the observed candidate commit, canonical PR delivery ID, confirmed required-check policy/source/time and immutable run observations from already-authorized authenticated provider reads. Do not send private repository identifiers to an anonymous third-party service. No access or no confirmed required set means unknown, not success from an empty list.

Keep the same wait for reruns of the same candidate/policy; explicitly start/promote the applicable attempt for each required check using current provider evidence. A late successful older attempt is historical and cannot replace the current failed/waiting one. A new commit or changed policy gets a linked new wait, without carrying success forward. Green checks do not imply acceptance, merge or integration. Reading a wait never triggers a rerun or changes provider policy.

## Open the viewer

Never open the viewer on your own, and never ask about it on its own. At each stop where the viewer holds something for the user to review, a plan at its approval stop and a UI walkthrough, including a build's first rendered view, offer to open it inside what that stop already asks. Where that stop asks a round through the host's question tool, add "Open the viewer?" as one more question of that round; otherwise, or when that round was already asked, add one reply line to the message's waiting line or to its next-step block of the global guidance's «Questions and routes», such as "or reply *open the viewer*". Never give it its own decision ID or its own call to the question tool. When the user accepts, open the work once with `hive view open --session-id ID` and, when needed, the event target from the contract; after that, do not ask again or reopen it in this conversation unless the user asks. When the user declines or does not answer it, ask again at the next such stop. Return the nonsecret target and evidence to the calling flow; it owns validation and review gates.

## Close and input hygiene

On pause, use `work stage` to pause the active occurrence and retain inputs for resumption. On terminal completion or abandonment, explicitly complete or pause the active stage, then use `work close` with an honest outcome and reason. The binary handles conditional versions; closing is never inferred from document status. When the work stops at an open pull request that waits for the user's merge or a human reviewer, its completion point under [flow-close](../../flow-close/SKILL.md), conditionally set the active stage to `in_review`, which sets the session to `in_review`, instead of completing it or closing the session; the session that finds the pull request merged closes it. Keep the current review inputs for the rest of the session. Follow [flow-close](../../flow-close/SKILL.md) for the completion phase and later hygiene; retain its readback and receipts rather than closing an already closed work again. Remove task-owned disposable API upload inputs only after reading back the exact tuple and committed version, revision and artifact references and verifying their sizes and hashes against the receipts and sources. What to keep, and for how long, is set by [artifact retention](../../workspace-conventions/references/artifact-layout.md).

Never manufacture API IDs or discard inputs based on an unconfirmed copy.
