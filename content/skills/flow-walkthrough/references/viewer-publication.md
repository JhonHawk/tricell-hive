# Viewer publication

Read when a substantive research, plan, build or verify flow starts, when publishing a meaningful stage, document or UI revision, and at close. The primary producer owns the session; children return findings and evidence to it. This procedure changes only local viewer state and does not authorize project, tracker or external writes.

## Connect and resume

1. Check that the `hive` binary and an already running compatible viewer are available. Do not start or restart the service. Use `hive view contract --operation NAME` offline for the operation needed; request the complete `hive view contract` only when its catalog is needed. The returned contract is authoritative for commands, schemas, limits, preconditions and examples. Request bodies use `--json FILE` or `--json -`; upload bytes with `--file` as the contract specifies.
2. Resolve the registered project, canonical host and actual native session ID from the current runtime. If identity is not directly available, read [host session identity](host-session-identity.md). Register the project root with `hive view register --dir <root>`, then create or resume the unique session for that tuple using the contract. Never substitute a timestamp or invent an API identity.
3. Keep returned viewer session, event, view, artifact, document and revision IDs, versions, sequence numbers and operation IDs in the existing work checkpoint or current conversation. Reuse the tuple and read current state before continuing after an interruption. If it is closed and the user explicitly requests new or resumed work in this conversation, use the version-conditional session update to set it active before publishing; a read, refresh or create alone must never reopen it. Deleted identities remain unavailable. Retry an operation with the same ID only for the exact same request; use its receipt and readback to resolve uncertainty.

If identity, binary, service or required capability is unavailable, preserve inputs, record the unpublished state in the existing checkpoint, report it at handoff and continue independent work. Do not silently import legacy history or claim an API event was stored. A missing binary permits only the UI fallback described in [the legacy manifest](walkthrough-manifest.md); an unavailable service does not.

## Stages and evidence

Start the applicable research, plan, build or verify stage before substantive work, including before captures. Use the returned versions for conditional transitions. Update the same occurrence when its state changes; a completed or failed occurrence is terminal, so a later stage or substantive plan revision gets a new related occurrence. Concurrent reviews do not claim the foreground stage. When waiting for the user, set the session to awaiting validation; resume explicitly when work continues. Report status as recorded, not as proof of process liveness.

Publish plan documents and already-authorized research records as immutable uploaded snapshots at meaningful draft and completion milestones; source files remain authoritative. Research without an authorized retained document publishes its concise stage summary, not an extra report created solely for the viewer. Link actual approvals or requested changes to the specific document revision or evidence when known, as agent-reported events from the conversation. Never infer an approval or invent a timestamp.

Group images and instructions by the views and tickets they actually cover: one shared view may reference multiple tickets; different screens get separate views. Upload captures as artifacts and append evidence using the contract. For an iteration, give changed captures distinct source paths and captions, publish replacement views with their superseded references, and leave unaffected earlier views current. Read back the committed session and check the identity tuple, versions, event sequence, document and artifact references, sizes and hashes against the receipts and source bytes. Read document content back through the supported CLI. Verify stored images through the authenticated viewer when available. If confirmation is incomplete, retain the inputs and report the limit; do not claim successful publication. Do not expose viewer credentials or access fragments in evidence.

For a first UI presentation, open the session with `hive view open --session-id ID` and, when needed, the event target from the contract. Do this once per session or when the user explicitly asks, not for every update. Return the nonsecret target and evidence to the calling flow; it owns validation and review gates.

## Close and input hygiene

On pause, conditionally pause the active stage and session and retain inputs for resumption. On terminal completion or abandonment, conditionally complete or pause the active stage, then close the session using its current version and an honest outcome. Keep the current review inputs for the rest of the session. At session-end hygiene, remove task-owned disposable API upload inputs only after reading back the exact tuple and committed version, revision and artifact references and verifying their sizes and hashes against the receipts and sources. Keep failed, uncertain, paused, user-selected and unique evidence, and source plans. There is no default age-based expiry.

For an existing legacy `walkthrough.json`, preserve its separate close protocol: run `python3 <flow-walkthrough dir>/scripts/render_walkthrough.py <work folder> --session-status closed --confirm-viewer`; exit 2 means the closed viewer copy was not confirmed, so retain the evidence unit. Apply [artifact retention](../../workspace-conventions/references/artifact-layout.md) before cleanup. Do not manufacture API IDs or import a legacy document automatically.
