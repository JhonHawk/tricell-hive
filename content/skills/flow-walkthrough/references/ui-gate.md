# UI gate

Read before a change with a rendered UI effect reaches a verification gate: the implementer's own rendered inspection, the independent children that the repository's `UI verification` value or answer selects, and the gate on the candidate the user accepted. This reference applies in every delivery mode, including `automatic`: the gate is verification, not a human validation stop. [Verification](../../flow-build/references/verification.md) owns test depth and the runtime, CI, deployment and deployed-environment gates; [flow-walkthrough](../SKILL.md) owns the human handoff; [browser automation](../../flow-build/references/browser-automation.md) governs how the browser is driven; [UI review criteria](ui-review-criteria.md) is the reviewer's brief.

## Scope

This gate applies to any change with a rendered UI effect other than one that changes only text or a style value without altering layout, state, or flow. The implementer checks such a text or style change in the rendered page at the affected viewports, with the longest realistic text and in each theme; if the check shows it alters layout, the gate applies. Backend or infrastructure work without a UI effect needs neither the inspection nor the children below; add other specialists by actual risk rather than by default.

## The implementer's inspection

For UI changes, local rendered and interactive inspection is part of completion, not an optional gate: layout, content, feedback, error recovery, responsive behavior, keyboard/focus and accessibility relevant to the change. Capture the prior state when comparing an existing interface and practical before editing; missing baseline limits claims of visual improvement, not unrelated functional checks. Automated accessibility or screenshot checks support, but do not replace, inspection of the affected experience.

Compare changed UI with the selected application/area's accepted shell and screen pattern, including justified differences. Distinguish pattern conformity, functional behavior, and user suitability. A screenshot diff against a prior baseline does not establish that a new screen follows a different reference screen's pattern. When shared UI code changes, inspect affected consumers across applications according to impact.

The implementer checks its own change only with bounded inline checks, such as a `read`, the console, or a one-off `eval`; the walk and any measurement suite belong to the children below. Before reporting the task, at least one of those checks loads the changed view in a real browser against the running application, on the dev server or a build, with no test doubles on the paths the change uses, such as the network, storage, or native browser APIs, and reads the console and the view: tests that mock these paths can pass while the running page fails. Seed data and prepared local accounts are fine, as [verification](../../flow-build/references/verification.md) allows. A change that only alters text or a style value, under [Scope](#scope), needs only its rendered check. When a child implements the change, its brief assigns the browser tool for this check, selected as [browser automation](../../flow-build/references/browser-automation.md) sets, since a delegated agent uses only the tool its brief assigns.

## The independent children

The repository's `UI verification` value or answer, resolved as [delivery decisions](../../flow-plan/references/delivery-decisions.md) sets, selects the independent children that run on the built local candidate before completion is reported: `full` runs a `hive-review-ux` review and a `hive-verify-change` in-vivo check of the changed journeys; `functional` runs only the `hive-verify-change` check; `none` runs neither and leaves the implementer's bounded checks and the human handoff of [flow-walkthrough](../SKILL.md). The selected children are part of authorized local implementation and need no separate approval; the rest of this section applies to each child that runs.

Give each child a fixed candidate and its candidate identity, so a later edit cannot change what it verifies:

- **Candidate identity.** When `git status --porcelain` prints nothing, the candidate is the `HEAD` commit. Otherwise, as UI tasks usually stay uncommitted until the gate passes, it is the tree hash this command prints, which includes untracked files and leaves the real index and the working tree untouched: `idx=$(mktemp); cp "$(git rev-parse --git-path index)" "$idx"; GIT_INDEX_FILE="$idx" git add -A && GIT_INDEX_FILE="$idx" git write-tree; rm -f "$idx"`. `git diff <old> <new>` between two identities gives the diff between candidates. Name the identity in each child's brief and ask the child to repeat it in its report.
- **Serving.** Serve each candidate from its own build directory and port, which later edits do not rebuild; never from a server that reloads on edit. Name in the brief the state candidates share, such as the database and accounts.

Brief the reviewer with [UI review criteria](ui-review-criteria.md), the affected screens, the base revision for comparison, realistic and extreme data, and the viewports and themes; do not pre-rate findings or say what to ignore; pass the skills and project documents that [delegation](../../flow-research/references/delegation.md#deliver-and-resolve-instructions) sets, which is not pre-rating findings. The reviewer judges layout, pattern conformity, accessibility and usability; the functional journeys of the acceptance criteria belong to `hive-verify-change` alone, so do not brief the same journey to both. Give each child a stop: one observation per affected area, viewport and theme is enough, and a check that hangs or fails twice is reported as not verified rather than retried. Resolve its findings before completion: fix introduced or worsened Blocker and High findings and re-review, and dispose of pre-existing ones under the shared incidental-findings rule, listing them as [incidental findings](../../flow-close/references/incidental-findings.md#which-findings-are-listed-and-how) sets. Run the selected children in parallel with isolated data, accounts and browser sessions; otherwise serialize state-changing work. If a child, the browser or the stack is unavailable, report the gate as not passed. When the host's sandbox blocks the browser or the local network, as [browser automation](../../flow-build/references/browser-automation.md) describes, report the gate as not passed naming the block as the host reported it, so the user can lift it in the host's sandbox or network settings.

**Pre-existing findings.** Ask the reviewer for pre-existing findings only on the touched views: the screens with changed files or components, the screens the change makes reachable, plus the regions the change displaces. This exception narrows, by name, the rule above that the brief does not say what to ignore, the same rule in the stance of [UI review criteria](ui-review-criteria.md#stance), and the whole-screen scope of its first comparison step; it changes nothing else. A review against a deployed environment whose tree matches the locally reviewed one, meaning `git diff <local identity> <deployed commit>` is empty on the application's source, including shared styles, components and configuration, receives the local report as its baseline and does not report its findings again; when the diff is not empty, it reviews the views the difference affects. Introduced and worsened findings keep the fix rule for Blocker and High above and the verdict in UI review criteria, whatever their priority. Only to dispose of pre-existing findings, map the reviewer's severity to a priority: Blocker to P1 (P0 when it blocks a core flow for every input), High to P2, Medium to P3, Nit to P3, and at least P2 for a WCAG AA failure or a task that cannot be done by keyboard or assistive technology. The definitions of P0 to P3 are in [incidental findings](../../flow-close/references/incidental-findings.md#which-findings-are-listed-and-how).

## When the gate runs

- **On the built local candidate**, before completion is reported and first in the order [flow-build](../../flow-build/SKILL.md) sets before asking the user to validate, and after the first rendered view that [flow-walkthrough](../SKILL.md) shows the user for a new or rearranged layout, so a composition the user rejects is not reviewed and repaired first. Under `automatic` delivery there is no human validation stop; later changes still follow the rule below.
- **A fix during a running gate.** A fix made while gate children still run builds a new candidate and leaves the running children on theirs; when they return, apply [changes after a gate or approval](#changes-after-a-gate-or-approval) to the diff between those candidates.
- **On the accepted candidate.** When the user accepts the walkthrough after one or more correction rounds, run one gate scoped to the diff between the last candidate that passed the gate and the accepted one, with the children the value selects: under `full`, `hive-review-ux` on the changed views and `hive-verify-change` on the journeys that touch changed files; under `functional`, only `hive-verify-change`; under `none`, neither; and in every case `hive-verify-task` on the tasks whose files changed. The recorder re-records the stale flows at this gate, as [flow-walkthrough](../SKILL.md) sets. If no gate has run yet, run the full gate for the value. Between correction rounds, no gate child runs. When a gate child reports an introduced Blocker or High finding, fix it and apply [changes after a gate or approval](#changes-after-a-gate-or-approval). The delivery's dedicated code review runs on the accepted candidate, at the point the delivery mode sets, which that order does not move.

## Changes after a gate or approval

Any later change to code, configuration, dependencies or runtime state invalidates the evidence it affects, including a fix from code review after the user approved. Compare the new candidate with the last verified one and identify the affected views and journeys, including consumers of changed shared code. Keep evidence for unaffected scope.

Before reporting the fix complete, pushing it or merging it, repeat only the affected checks: the implementer's rendered inspection, and the children selected by `UI verification` on the changed views and journeys. Under `none`, no UI gate child runs. Apply the accepted-candidate task verification above when task files changed. Use the same child stops and finding rules; this does not restart the full gate or the dedicated code review, whose timing and round limit stay unchanged.

Refresh affected captures and mark affected recordings `stale`; re-record those flows at this gate. If the fix changes the visible result the user accepted, show the refreshed result through [flow-walkthrough](../SKILL.md) and obtain approval again before delivery. A fix with no change to that accepted result needs no new approval. Under `automatic`, no approval is requested. Further fixes follow this same affected-scope rule; an unavailable or failed required check stays unverified, never covered by the earlier approval.
