# Walk a user interface for human validation

This skill supports the user's validation of a user-interface change: what the user sees before validating and what evidence accompanies the handoff. [flow-verify](../flow-verify/SKILL.md) owns the stage around it: [the UI gate](../flow-verify/references/ui-gate.md) with its independent children, the correction rounds and the accepted-candidate gate. Test depth and the runtime, CI and deployment gates stay in [verification](../flow-build/references/verification.md).

## When it applies

- At the human validation stop of `flow-verify` under `interactive` or `hold` delivery, after the children that [the UI gate](../flow-verify/references/ui-gate.md) selects have run; during a build, as soon as a new or rearranged layout exists, for the first rendered view below; and when the user asks for a walkthrough or a demo of a feature already built.
- Under `automatic` delivery and `direct-base` chosen for a code repository, which never stop for human validation, the UI gate of [flow-verify](../flow-verify/SKILL.md) runs, the first rendered view below is captured and reported without a question, and the handoff below runs only when the user asks. Under [unattended delegation](../unattended-delegation/SKILL.md), the first rendered view is also reported without a question, and the handoff still runs at a validation stop.
- A change that alters only text or a style value without changing layout, state, or flow is covered by the implementer's rendered check in [the UI gate](../flow-verify/references/ui-gate.md); its captures still go to the folder below.

## Prepare

Before driving a browser, read [browser automation](../flow-build/references/browser-automation.md). Before the handoff message, read [questions](../hive-core/references/questions.md) and [reporting](../flow-close/references/reporting.md). Before writing captures or the page, read [artifact layout and retention](../workspace-conventions/references/artifact-layout.md).

Serve the built candidate as [review and gates](../flow-verify/references/review-and-gates.md#runtime-and-ui-gates) sets for the final handoff: the production-style start or preview command where the stack has a build step, local frontend, backend, database, and dependencies unless another target was explicitly specified, and the accounts, roles, and seed data prepared before the walk. Leave that same verified stack running, confirm its URLs are reachable, and name the candidate and the relevant local targets. Provide clickable application URLs and the required account or role without secrets.

## First rendered view

When a change adds or rearranges a layout, such as a new screen, dialog, or component composition, show the user the first rendered version as soon as it exists: one capture per changed view at a desktop width with realistic data volume, taken on the dev server as a bounded check. Write a `first_view` manifest with those captures, publish it as [Deliver](#deliver) sets, and give the returned artifact path as [Give the opening command](#give-the-opening-command) sets. In a delivery mode that stops for validation, outside unattended delegation, then ask whether the composition is right, with the options and channel that [Give the opening command](#give-the-opening-command) sets, by following [questions](../hive-core/references/questions.md), opening with the in-progress item: the message ends with the pause line, also while children keep running; a result that arrives while the question waits is handled as [reporting](../flow-close/references/reporting.md#report-a-running-or-completed-item) sets for a turn that a notification starts. Keep independent work, such as backend tasks, running in parallel rather than holding it for the answer. Do this before the independent UI review, so a composition the user rejects is not reviewed and repaired first. Otherwise give the artifact path in the progress line and continue without a question; the UI gate judges the composition. The final validation still happens on the built candidate. When the user rejects the composition, apply each requested correction as a round during the build and capture the affected views again; these rounds count for the repeated-corrections rule of [scope changes](../hive-core/references/scope-changes.md), which also classifies a request that goes beyond a correction.

## Capture relevant states

During every UI walk before a human validation pause, including the implementer's own walk of a text or style change, capture a small useful selection of changed screens and relevant states, such as an open modal or menu, an error, or a confirmation; do not repeat the walk solely to produce images. Caption each capture with the action and expected result. Use screenshots for the walkthrough; do not record flows. The assigned reviewer returns screenshots, observed state and reproduction steps to the orchestrator without editing the application. When delegating, grant the review-image folder as the evidence destination; an observe role does not imply general filesystem write permission. If the host cannot capture there, return observations and have the orchestrator capture within its available tools. Avoid credentials and sensitive user data in images.

Put captures where [artifact layout and retention](../workspace-conventions/references/artifact-layout.md) places UI review images, never in the host's temporary location, which the system may clear before the user sees them. Show them through the walkthrough below even when the user did not ask, in a delivery mode that stops for validation. Their retention follows that reference. Screenshots do not replace interactive checks.

## Deliver

Write the walkthrough in the message as [questions](../hive-core/references/questions.md) sets for a manual validation request: one block per flow, headed by the ticket and a short description, with bullet steps from a named starting point. Put preconditions such as the role and signed-in state in parentheses on the first step, navigation with `>` between screens, the action, and what the user should see; condense obvious steps. When several tickets share one flow or module, cite the ticket in the step it concerns; separate flows get separate blocks. Link the selected captures, state what the agent verified and what remains for the human, and explain how to stop task-owned processes. The walkthrough goes complete in the message and ends with the pause line, followed by the question that [Give the opening command](#give-the-opening-command) sets, also while children are running. Do not claim availability beyond the host's process lifetime; disclose inability to keep the stack alive and give the exact restart instructions.

Also publish the walkthrough: write `walkthrough.json` as [the walkthrough manifest](references/walkthrough-manifest.md) sets, including its delivery metadata procedure when a PR or commit is known. Before publication, follow its [publication target](references/walkthrough-manifest.md#publication-target) rule. Run [the publisher](scripts/render_walkthrough.py) with `python3 <skill-dir>/scripts/render_walkthrough.py <work folder> --session-status in_progress`: it validates the manifest, explicitly marks this active or resumed work in progress, and returns the current output path. Fix the manifest, never generated output. Before closing this work or removing its review artifacts, follow [Close the current walkthrough](../flow-close/SKILL.md#close-the-current-walkthrough). When `command -v hive` finds the binary, run `hive view register --dir <work folder>` so the viewer collects its JSON; a failure or sandbox refusal does not block the handoff or change the publication target. Otherwise deliver the standalone output without asking the user to install or start Hive. Never search for the binary or run `hive view start`. Then give the opening command as [Give the opening command](#give-the-opening-command) sets.

### Give the opening command

In the message that asks for the decision or validation, give one line with the publisher's returned absolute artifact path (JSON for the viewer or the standalone fallback). When the first rendered view or the final validation asks its question, it offers these choices:

- **Open the viewer**, only when `hive view register` succeeded: run `hive view open`, and no other command, then ask the same question again, unchanged and with the same ID. The command opens the viewer's start page rather than a specific walkthrough, so keep the artifact path line. Opening does not answer the question, so asking it again overrides the rules in [questions](../hive-core/references/questions.md) to ask each open choice once and not to re-ask an answered question.
- **Approve**: at the first rendered view, it accepts the composition, the build continues, and flow-verify runs the gate on the built candidate; at the final validation, it accepts the walkthrough, which the accepted-candidate gate of [flow-verify](../flow-verify/SKILL.md) handles.
- **Corrections** get no option: the question says to write them in the free-text answer, so they arrive with their detail in the same reply.

Ask through a native card that waits for the answer only when its question tool accepts a free-text answer, as its schema or documentation shows, and the card has at least two options. Otherwise ask in text, with the options and one line saying to write corrections in the reply; this overrides the conditions in [questions](../hive-core/references/questions.md) for asking in text and its rule against a reply example.

When `hive view open` prints that the viewer is not running, which it does with exit status 0, say in one line that the user can start it with `hive view start`, and ask again. On any other error, report it in one line and ask again in text without the Open option. Never run a command the output suggests, and never retry it. Never open the page, the viewer, or a browser in any other way, including your own browser. A command never publishes; [Share](#share) governs that.

## Corrections and the accepted candidate

The correction rounds a user requests during a validation pause, their task markers and the accepted-candidate gate are [flow-verify](../flow-verify/SKILL.md)'s. In each round with a visual effect, capture the affected views and deliver them as [Deliver](#deliver) sets.

For UI work awaiting human validation, leave the verified built local stack available and deliver the walkthrough, captures, and page defined in this skill; do not ask again merely to keep this handoff available. Pending human review means these resources are still needed. Once no longer needed, stop only the temporary processes the task or its children started and apply the UI-image hygiene in [artifact layout and retention](../workspace-conventions/references/artifact-layout.md), preserving user-selected captures and pre-existing services, sessions and evidence. Report remaining resources and how to stop them, and respect an explicit shutdown request.

## Share

Captures and the page stay local. Attach them to a pull request only when the user asks for it, with `gh pr comment <number> --attach <file>#<alt text>`. Retaining a file never authorizes publishing it.
