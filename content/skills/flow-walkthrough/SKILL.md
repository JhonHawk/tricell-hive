# Walk a user interface for human validation

This skill owns the human side of a user-interface change: what the user sees before validating, how corrections flow, and what evidence accompanies the handoff. The independent checks before this point stay in [verification](../flow-build/references/verification.md).

## When it applies

- At the human validation stop of `flow-build` under `interactive` or `hold` delivery, after the independent checks that [verification](../flow-build/references/verification.md) selects have run; during a build, as soon as a new or rearranged layout exists, for the first rendered view below; and when the user asks for a walkthrough or a demo of a feature already built.
- Not under `automatic` delivery, which never stops for human validation; run it there only when the user asks.
- A change that alters only text or a style value without changing layout, state, or flow needs no recording: the implementer's rendered check in [verification](../flow-build/references/verification.md) covers it, and its captures still go to the folder below.

## Prepare

Before driving a browser, read [browser automation](../flow-build/references/browser-automation.md). Before the handoff message, read [questions](../flow-plan/references/questions.md) and [reporting](../flow-close/references/reporting.md). Before writing captures, recordings, or the page, read [artifact layout and retention](../workspace-conventions/references/artifact-layout.md).

Serve the built candidate as [verification](../flow-build/references/verification.md) sets for the final handoff: the production-style start or preview command where the stack has a build step, local frontend, backend, database, and dependencies unless another target was explicitly specified, and the accounts, roles, and seed data prepared before the walk. Leave that same verified stack running, confirm its URLs are reachable, and name the candidate and the relevant local targets. Provide clickable application URLs and the required account or role without secrets.

## First rendered view

When a change adds or rearranges a layout, such as a new screen, dialog, or component composition, show the user the first rendered version as soon as it exists: one capture per changed view at a desktop width with realistic data volume, taken on the dev server as a bounded check. Ask whether the composition is right with the pause line that [questions](../flow-plan/references/questions.md) defines, opening with the in-progress item; while children keep running, keep the choice in the message alone, with each option written out, and end the turn so their results can arrive, and otherwise also ask through a native question card that waits for the answer; keep independent work, such as backend tasks and code review, running in parallel rather than holding it for the answer. Do this before the independent UI review, so a composition the user rejects is not reviewed and repaired first. The final validation still happens on the built candidate.

## Capture and record

During every UI walk before a human validation pause, including the implementer's own walk of a text or style change, capture a small useful selection of changed screens and relevant states; do not repeat the walk solely to produce images. The recording below is the one exception: it is a deliverable for the user, not evidence. The assigned reviewer returns screenshots, observed state and reproduction steps to the orchestrator without editing the application. When delegating, grant the review-image folder as the evidence destination; an observe role does not imply general filesystem write permission. If the host cannot capture there, return observations and have the orchestrator capture within its available tools. Avoid credentials and sensitive user data in images and recordings.

Put captures and recordings where [artifact layout and retention](../workspace-conventions/references/artifact-layout.md) places UI review images, never in the host's temporary location, which the system may clear before the user sees them. Link or display them in the handoff, and offer them even when the user did not ask. Preserve them until the session ends; hygiene then removes the task's images, recordings, and page except those the user selected to keep. Screenshots and recordings do not replace interactive checks.

Record one clean pass per flow of the walkthrough, after that flow's checks have passed: no retries, no diagnostic waits, at most 90 seconds. Do not record the verification itself: it includes waits and retries, and no host reads video to trim them.

- **Who records.** The `hive-verify-change` child that walked the flows, when the repository's `UI verification` value or answer is `full` or `functional`; its brief names the destination folder as an absolute path and the flows to record, and without that request the role does not record. When the value is `none`, launch a `hive-verify-change` child only to record, with a brief limited to the clean passes and no verdict. The orchestrator never drives the pass itself, and `hive-review-ux` never records: it judges, it does not demonstrate.
- **How.** In the recorder's own named `agent-browser` session, each command under the time wrapper that [browser automation](../flow-build/references/browser-automation.md) sets: `record start <images>/<flow>.mp4 --cursor`, the flow's steps, `record stop`. Use mp4 (H.264), which the browser, the page below, and desktop players open without conversion. Use Chrome DevTools MCP `screencast_start` with a `filePath` only when the brief assigns that tool.
- **Preconditions.** Recording needs ffmpeg with the libx264 encoder on the recorder's PATH, and the check below needs `ffprobe`. When either is missing, install nothing: report the flow as `not recorded`, recommend `agent-browser doctor`, and deliver the handoff with the captures. A sandbox that blocks the browser or the folder is reported as [browser automation](../flow-build/references/browser-automation.md) describes.
- **Check.** The orchestrator cannot watch the video. Verify each file with `ffprobe -v error -show_entries format=duration,size -show_entries stream=codec_name -of default=noprint_wrappers=1 <file>`: it exists, lasts more than one second and no more than the bound, and its codec is `h264`. State the duration in the handoff. A recording that fails twice is reported as `not recorded` and not retried.
- **Candidate and staleness.** Each recording names the commit or candidate it shows. A correction round makes the recordings of the flows that touch changed files `stale`: mark them so in the message and the page, and re-record them only at the accepted-candidate gate below, never between rounds.

## Deliver

Write the walkthrough in the message as [questions](../flow-plan/references/questions.md) sets for a manual validation request: one block per flow, headed by the ticket and a short description, with bullet steps from a named starting point. Put preconditions such as the role and signed-in state in parentheses on the first step, navigation with `>` between screens, the action, and what the user should see; condense obvious steps. When several tickets share one flow or module, cite the ticket in the step it concerns; separate flows get separate blocks. Link the selected captures and each recording with its duration, state what the agent verified and what remains for the human, and explain how to stop task-owned processes. The walkthrough goes complete in the message and ends with the pause line, with a native question card that waits for the answer only when no children are running. Do not claim availability beyond the host's process lifetime; disclose inability to keep the stack alive and give the exact restart instructions.

Also write the walkthrough page: copy [the walkthrough skeleton](../flow-report/assets/skeleton-walkthrough.html) to `walkthrough.html` beside the `images/` folder, in the work's workspace folder, and fill it in the session language: the candidate, a validation table with one row per verified criterion plus the UX verdict when it ran and the tests, build, and lint that ran, one block per flow with its steps, captures, and recording or its `not recorded` or `stale` mark, the action required from the user, the environment with URLs and account without secrets, and the provenance footer. Reference captures and recordings by relative path; embed nothing else from outside the file. Run `python3 <flow-report>/scripts/self_check.py walkthrough.html` and fix failures before the handoff. Give the page's complete absolute path in the message: terminal hosts do not render images inline, so the user opens the page in a browser or from the editor.

## Correction rounds and markers

While the user requests corrections during a validation pause, whether to text, behavior, or layout, run one correction round per request: apply the correction; write its test in the same round when it alters behavior of a kind the build skill's test-first rule covers; run the affected tests; rebuild; capture the affected views; and ask again right away in the same way. Between rounds, run no `hive-review-ux`, `hive-verify-change`, `hive-verify-task`, or dedicated code review. When you offer alternatives, sketch them as [UI planning](../flow-plan/references/ui-planning.md) describes.

When the user accepts, run one gate scoped to the diff between the last candidate that passed the gate and the accepted one, with the children that the repository's `UI verification` value or answer selects: under `full`, `hive-review-ux` on the changed views and `hive-verify-change` on the journeys that touch changed files; under `functional`, only `hive-verify-change`; under `none`, neither; and in every case `hive-verify-task` on the tasks whose files changed. The recorder re-records the stale flows at this gate. If no gate has run yet, run the full gate for the value. When a gate child reports an introduced Blocker or High finding, fix it, show the user the result, and re-review it only with the child that reported it. The delivery's dedicated code review runs on the accepted candidate, at the point the delivery mode already sets.

Markers: when a correction changes the files of a task marked `[x]`, set that task back to `[?]` with a line `reopened by correction round <n>`, and verify it at the accepted-candidate gate. Record a correction outside the plan's tasks in the progress section; `hive-verify-change` covers it at that gate when the value runs it. A correction that changes the retained plan follows [Revise a plan in progress](../flow-plan/SKILL.md#revise-a-plan-in-progress); the plan re-review it may make due runs with the accepted-candidate gate above, not between rounds.

## Share

Captures, recordings, and the page stay local. Attach them to a pull request only when the user asks for it, with `gh pr comment <number> --attach <file>#<alt text>`; GitHub accepts images up to 10 MB and videos up to 10 MB on a free plan or 100 MB on a paid plan. Retaining a file never authorizes publishing it.
