# Walk a user interface for human validation

This skill owns a user-interface change from the moment it renders until the user validates it: what the user sees before validating, how corrections flow, what evidence accompanies the handoff, and, in [the UI gate](references/ui-gate.md), the implementer's rendered inspection and the independent children that the repository's `UI verification` value selects. Read that reference before any gate on a change with a rendered UI effect. Test depth and the runtime, CI and deployment gates stay in [verification](../flow-build/references/verification.md).

## When it applies

- At the human validation stop of `flow-build` under `interactive` or `hold` delivery, after the children that [the UI gate](references/ui-gate.md) selects have run; during a build, as soon as a new or rearranged layout exists, for the first rendered view below; and when the user asks for a walkthrough or a demo of a feature already built.
- Under `automatic` delivery, which never stops for human validation, only [the UI gate](references/ui-gate.md) runs; the handoff below runs there only when the user asks.
- A change that alters only text or a style value without changing layout, state, or flow is covered by the implementer's rendered check in [the UI gate](references/ui-gate.md); its captures still go to the folder below.

## Prepare

Before driving a browser, read [browser automation](../flow-build/references/browser-automation.md). Before the handoff message, read [questions](../flow-plan/references/questions.md) and [reporting](../flow-close/references/reporting.md). Before writing captures, recordings, or the page, read [artifact layout and retention](../workspace-conventions/references/artifact-layout.md).

Serve the built candidate as [verification](../flow-build/references/verification.md) sets for the final handoff: the production-style start or preview command where the stack has a build step, local frontend, backend, database, and dependencies unless another target was explicitly specified, and the accounts, roles, and seed data prepared before the walk. Leave that same verified stack running, confirm its URLs are reachable, and name the candidate and the relevant local targets. Provide clickable application URLs and the required account or role without secrets.

## First rendered view

When a change adds or rearranges a layout, such as a new screen, dialog, or component composition, show the user the first rendered version as soon as it exists: one capture per changed view at a desktop width with realistic data volume, taken on the dev server as a bounded check. Write a `first_view` manifest with those captures, render it as [Deliver](#deliver) sets, and give its path as [Give the opening command](#give-the-opening-command) sets. Then ask whether the composition is right, with the options and channel that [Give the opening command](#give-the-opening-command) sets, by following [questions](../flow-plan/references/questions.md), opening with the in-progress item: the message ends with the pause line, also while children keep running; a result that arrives while the question waits is handled as [reporting](../flow-close/references/reporting.md#report-a-running-or-completed-item) sets for a turn that a notification starts. Keep independent work, such as backend tasks, running in parallel rather than holding it for the answer. Do this before the independent UI review, so a composition the user rejects is not reviewed and repaired first. The final validation still happens on the built candidate.

## Capture and record

During every UI walk before a human validation pause, including the implementer's own walk of a text or style change, capture a small useful selection of changed screens and relevant states; do not repeat the walk solely to produce images. A recording, when the rule below calls for one, is a deliverable for the user, not evidence. The assigned reviewer returns screenshots, observed state and reproduction steps to the orchestrator without editing the application. When delegating, grant the review-image folder as the evidence destination; an observe role does not imply general filesystem write permission. If the host cannot capture there, return observations and have the orchestrator capture within its available tools. Avoid credentials and sensitive user data in images and recordings.

Put captures and recordings where [artifact layout and retention](../workspace-conventions/references/artifact-layout.md) places UI review images, never in the host's temporary location, which the system may clear before the user sees them. Show them through the page below even when the user did not ask. Their retention follows that reference. Screenshots and recordings do not replace interactive checks.

Captures are the default. Record a flow only when it validates an interaction or a transition that captures cannot show, such as expanding a menu or dragging an item, or when the user asks: one clean pass, after that flow's checks have passed, with no retries, no diagnostic waits, and at most 90 seconds. Do not record the verification itself: it includes waits and retries, and no host reads video to trim them.

- **Who records.** The `hive-verify-change` child that walked the flows, when the repository's `UI verification` value or answer is `full` or `functional`; its brief names the destination folder as an absolute path and the flows to record, and without that request the role does not record. When the value is `none`, launch a `hive-verify-change` child only to record, with a brief limited to the clean passes and no verdict. The orchestrator never drives the pass itself, and `hive-review-ux` never records: it judges, it does not demonstrate.
- **How.** In the recorder's own named `agent-browser` session, each command under the time wrapper that [browser automation](../flow-build/references/browser-automation.md) sets: `record start <images>/<flow>.mp4 --cursor`, the flow's steps, `record stop`. Use mp4 (H.264), which browsers and desktop players open without conversion. Use Chrome DevTools MCP `screencast_start` with a `filePath` only when the brief assigns that tool.
- **Preconditions.** Recording needs ffmpeg with the libx264 encoder on the recorder's PATH, and the check below needs `ffprobe`. When either is missing, install nothing: report the flow as `not recorded`, recommend `agent-browser doctor`, and deliver the handoff with the captures. A sandbox that blocks the browser or the folder is reported as [browser automation](../flow-build/references/browser-automation.md) describes.
- **Check.** The orchestrator cannot watch the video. Verify each file with `ffprobe -v error -show_entries format=duration,size -show_entries stream=codec_name -of default=noprint_wrappers=1 <file>`: it exists, lasts more than one second and no more than the bound, and its codec is `h264`. State the duration in the handoff. A recording that fails twice is reported as `not recorded` and not retried.
- **Candidate and staleness.** Each recording names the commit or candidate it shows. A correction round makes the recordings of the flows that touch changed files `stale`: mark them so in the message and the manifest, and re-record them only at the accepted-candidate gate below, never between rounds. For other changes after a gate or approval, follow [the UI gate's evidence refresh rule](references/ui-gate.md#changes-after-a-gate-or-approval).

## Deliver

Write the walkthrough in the message as [questions](../flow-plan/references/questions.md) sets for a manual validation request: one block per flow, headed by the ticket and a short description, with bullet steps from a named starting point. Put preconditions such as the role and signed-in state in parentheses on the first step, navigation with `>` between screens, the action, and what the user should see; condense obvious steps. When several tickets share one flow or module, cite the ticket in the step it concerns; separate flows get separate blocks. Link the selected captures and any recording with its duration, state what the agent verified and what remains for the human, and explain how to stop task-owned processes. The walkthrough goes complete in the message and ends with the pause line, followed by the question that [Give the opening command](#give-the-opening-command) sets, also while children are running. Do not claim availability beyond the host's process lifetime; disclose inability to keep the stack alive and give the exact restart instructions.

Also write the walkthrough page: write `walkthrough.json` as [the walkthrough manifest](references/walkthrough-manifest.md) sets. Run [the renderer](scripts/render_walkthrough.py) with `python3 <skill-dir>/scripts/render_walkthrough.py <work folder> --session-status in_progress`: it validates the manifest, explicitly marks this active or resumed work in progress, and writes `walkthrough.html` beside it. Fix the manifest, never the page. Before closing this work or removing its review artifacts, follow [Close the current walkthrough](../flow-close/SKILL.md#close-the-current-walkthrough). Then, when `command -v hive` finds Hive's binary, run `hive view register --dir <work folder>` so the user's viewer collects the page; a failure or sandbox refusal does not block the handoff. When it finds none, the message asks the user, in the session language, to register the repository once, quoting `hive view register --dir <work folder>` and `~/.local/share/hive/packages/hive-<version>-<os>-<arch>/bin/hive`; never search for the binary. Never run `hive view start`. Then give the opening command as [Give the opening command](#give-the-opening-command) sets.

### Give the opening command

In the message that asks for the decision or validation, give one line with the page's absolute path. The question that the first rendered view and the final validation ask offers these choices:

- **Open the viewer**, only when `hive view register` succeeded: run `hive view open`, and no other command, then ask the same question again, unchanged and with the same ID. The command opens the viewer's start page, not this page, so keep the path line. Opening does not answer the question, so asking it again overrides the rules in [questions](../flow-plan/references/questions.md) to ask each open choice once and not to re-ask an answered question.
- **Approve**: at the first rendered view, it accepts the composition and the build continues to the gate on the built candidate; at the final validation, it accepts the walkthrough, which [Correction rounds and markers](#correction-rounds-and-markers) handles.
- **Corrections** get no option: the question says to write them in the free-text answer, so they arrive with their detail in the same reply.

Ask through a native card that waits for the answer only when its question tool accepts a free-text answer, as its schema or documentation shows, and the card has at least two options. Otherwise ask in text, with the options and one line saying to write corrections in the reply; this overrides the conditions in [questions](../flow-plan/references/questions.md) for asking in text and its rule against a reply example.

When `hive view open` prints that the viewer is not running, which it does with exit status 0, say in one line that the user can start it with `hive view start`, and ask again. On any other error, report it in one line and ask again in text without the Open option. Never run a command the output suggests, and never retry it. Never open the page, the viewer, or a browser in any other way, including your own browser. A command never publishes; [Share](#share) governs that.

## Correction rounds and markers

While the user requests corrections during a validation pause, whether to text, behavior, or layout, run one correction round per request: apply the correction; write its test in the same round when it alters behavior of a kind the build skill's test-first rule covers; run the affected tests; rebuild; capture the affected views; and ask again right away in the same way. Between rounds, run no `hive-review-ux`, `hive-verify-change`, `hive-verify-task`, or dedicated code review. When you offer alternatives, sketch them as [UI planning](../flow-plan/references/ui-planning.md) describes.

When the user accepts, run the accepted-candidate gate as [the UI gate](references/ui-gate.md) sets, with the reruns [flow-build](../flow-build/SKILL.md) sets, before any further step.

Before delivering a later fix, including one from code review after approval, follow [changes after a gate or approval](references/ui-gate.md#changes-after-a-gate-or-approval).

Markers: when a correction changes the files of a task marked `[x]`, set that task back to `[?]` with a line `reopened by correction round <n>`, and verify it at the accepted-candidate gate. Record a correction outside the plan's tasks in the progress section; `hive-verify-change` covers it at that gate when the value runs it. A correction that changes the retained plan follows [Revise a plan in progress](../flow-plan/references/plan-revision.md); the plan re-review it may make due runs with the accepted-candidate gate above, not between rounds.

## Share

Captures, recordings, and the page stay local. Attach them to a pull request only when the user asks for it, with `gh pr comment <number> --attach <file>#<alt text>`; GitHub accepts images up to 10 MB and videos up to 10 MB on a free plan or 100 MB on a paid plan. Retaining a file never authorizes publishing it.
