# Walk a user interface for human validation

This skill supports the user's validation of a user-interface change: what the user sees before validating and what evidence accompanies the handoff. [flow-verify](../flow-verify/SKILL.md) owns the stage around it: [the UI gate](../flow-verify/references/ui-gate.md) with its independent children, the correction rounds and the accepted-candidate gate. Test depth and the runtime, CI and deployment gates stay in [verification](../flow-build/references/verification.md).

## When it applies

- At the human validation stop of `flow-verify` under `interactive` or `hold` delivery, after the children that [the UI gate](../flow-verify/references/ui-gate.md) selects have run; during a build, as soon as a new or rearranged layout exists, for the first rendered view below; and when the user asks for a walkthrough or a demo of a feature already built.
- Under `automatic` delivery and `direct-base` chosen for a code repository, which never stop for human validation, the UI gate of [flow-verify](../flow-verify/SKILL.md) runs, the first rendered view below is captured and reported without a question, and the handoff and recordings below run only when the user asks. Under [unattended delegation](../unattended-delegation/SKILL.md), the first rendered view is also reported without a question, and the handoff still runs at a validation stop.
- A change that alters only text or a style value without changing layout, state, or flow is covered by the implementer's rendered check in [the UI gate](../flow-verify/references/ui-gate.md); its captures still go to the folder below.

## Prepare

Before driving a browser, read [browser automation](../flow-build/references/browser-automation.md). Before the handoff message, read [questions](../flow-plan/references/questions.md) and [reporting](../flow-close/references/reporting.md). Before writing captures, recordings, or the page, read [artifact layout and retention](../workspace-conventions/references/artifact-layout.md).

Serve the built candidate as [review and gates](../flow-verify/references/review-and-gates.md#runtime-and-ui-gates) sets for the final handoff: the production-style start or preview command where the stack has a build step, local frontend, backend, database, and dependencies unless another target was explicitly specified, and the accounts, roles, and seed data prepared before the walk. Leave that same verified stack running, confirm its URLs are reachable, and name the candidate and the relevant local targets. Provide clickable application URLs and the required account or role without secrets.

## First rendered view

When a change adds or rearranges a layout, such as a new screen, dialog, or component composition, show the user the first rendered version as soon as it exists: one capture per changed view at a desktop width with realistic data volume, taken on the dev server as a bounded check. Write a `first_view` manifest with those captures, publish it as [Deliver](#deliver) sets, and give the returned artifact path as [Give the opening command](#give-the-opening-command) sets. In a delivery mode that stops for validation, outside unattended delegation, then ask whether the composition is right, with the options and channel that [Give the opening command](#give-the-opening-command) sets, by following [questions](../flow-plan/references/questions.md), opening with the in-progress item: the message ends with the pause line, also while children keep running; a result that arrives while the question waits is handled as [reporting](../flow-close/references/reporting.md#report-a-running-or-completed-item) sets for a turn that a notification starts. Keep independent work, such as backend tasks, running in parallel rather than holding it for the answer. Do this before the independent UI review, so a composition the user rejects is not reviewed and repaired first. Otherwise give the artifact path in the progress line and continue without a question; the UI gate judges the composition. The final validation still happens on the built candidate.

## Capture and record

During every UI walk before a human validation pause, including the implementer's own walk of a text or style change, capture a small useful selection of changed screens and relevant states; do not repeat the walk solely to produce images. A recording, when the rule below calls for one, is a deliverable for the user, not evidence. The assigned reviewer returns screenshots, observed state and reproduction steps to the orchestrator without editing the application. When delegating, grant the review-image folder as the evidence destination; an observe role does not imply general filesystem write permission. If the host cannot capture there, return observations and have the orchestrator capture within its available tools. Avoid credentials and sensitive user data in images and recordings.

Put captures and recordings where [artifact layout and retention](../workspace-conventions/references/artifact-layout.md) places UI review images, never in the host's temporary location, which the system may clear before the user sees them. Show them through the walkthrough below even when the user did not ask, in a delivery mode that stops for validation. Their retention follows that reference. Screenshots and recordings do not replace interactive checks.

Captures are the default. Record a flow only when it validates an interaction or a transition that captures cannot show, such as expanding a menu or dragging an item, or when the user asks: one clean pass, after that flow's checks have passed, with no retries, no diagnostic waits, and at most 90 seconds. Do not record the verification itself: it includes waits and retries, and no host reads video to trim them.

- **Who records.** The `hive-verify-change` child that walked the flows, when the repository's `UI verification` value or answer is `full` or `functional`; its brief names the destination folder as an absolute path and the flows to record, and without that request the role does not record. When the value is `none`, at a validation stop, launch a `hive-verify-change` child only to record, with a brief limited to the clean passes and no verdict. The orchestrator never drives the pass itself, and `hive-review-ux` never records: it judges, it does not demonstrate.
- **How.** In the recorder's own named `agent-browser` session, each command under the time wrapper that [browser automation](../flow-build/references/browser-automation.md) sets: `record start <images>/<flow>.mp4 --cursor`, the flow's steps, `record stop`. Use mp4 (H.264), which browsers and desktop players open without conversion. Use Chrome DevTools MCP `screencast_start` with a `filePath` only when the brief assigns that tool.
- **Preconditions.** Recording needs ffmpeg with the libx264 encoder on the recorder's PATH, and the check below needs `ffprobe`. When either is missing, install nothing: report the flow as `not recorded`, recommend `agent-browser doctor`, and deliver the handoff with the captures. A sandbox that blocks the browser or the folder is reported as [browser automation](../flow-build/references/browser-automation.md) describes.
- **Check.** The orchestrator cannot watch the video. Verify each file with `ffprobe -v error -show_entries format=duration,size -show_entries stream=codec_name -of default=noprint_wrappers=1 <file>`: it exists, lasts more than one second and no more than the bound, and its codec is `h264`. State the duration in the handoff. A recording that fails twice is reported as `not recorded` and not retried.
- **Candidate and staleness.** Each recording names the commit or candidate it shows. A correction round makes the recordings of the flows that touch changed files `stale`: mark them so in the message and the manifest, and re-record them only at the accepted-candidate gate that [flow-verify](../flow-verify/SKILL.md) sets, never between rounds. For other changes after a gate or approval, follow [the UI gate's evidence refresh rule](../flow-verify/references/ui-gate.md#changes-after-a-gate-or-approval).

## Deliver

Write the walkthrough in the message as [questions](../flow-plan/references/questions.md) sets for a manual validation request: one block per flow, headed by the ticket and a short description, with bullet steps from a named starting point. Put preconditions such as the role and signed-in state in parentheses on the first step, navigation with `>` between screens, the action, and what the user should see; condense obvious steps. When several tickets share one flow or module, cite the ticket in the step it concerns; separate flows get separate blocks. Link the selected captures and any recording with its duration, state what the agent verified and what remains for the human, and explain how to stop task-owned processes. The walkthrough goes complete in the message and ends with the pause line, followed by the question that [Give the opening command](#give-the-opening-command) sets, also while children are running. Do not claim availability beyond the host's process lifetime; disclose inability to keep the stack alive and give the exact restart instructions.

Also publish the walkthrough: write `walkthrough.json` as [the walkthrough manifest](references/walkthrough-manifest.md) sets, including its delivery metadata procedure when a PR or commit is known. Before publication, follow its [publication target](references/walkthrough-manifest.md#publication-target) rule. Run [the publisher](scripts/render_walkthrough.py) with `python3 <skill-dir>/scripts/render_walkthrough.py <work folder> --session-status in_progress`: it validates the manifest, explicitly marks this active or resumed work in progress, and returns the current output path. Fix the manifest, never generated output. Before closing this work or removing its review artifacts, follow [Close the current walkthrough](../flow-close/SKILL.md#close-the-current-walkthrough). When `command -v hive` finds the binary, run `hive view register --dir <work folder>` so the viewer collects its JSON; a failure or sandbox refusal does not block the handoff or change the publication target. Otherwise deliver the standalone output without asking the user to install or start Hive. Never search for the binary or run `hive view start`. Then give the opening command as [Give the opening command](#give-the-opening-command) sets.

### Give the opening command

In the message that asks for the decision or validation, give one line with the publisher's returned absolute artifact path (JSON for the viewer or the standalone fallback). When the first rendered view or the final validation asks its question, it offers these choices:

- **Open the viewer**, only when `hive view register` succeeded: run `hive view open`, and no other command, then ask the same question again, unchanged and with the same ID. The command opens the viewer's start page rather than a specific walkthrough, so keep the artifact path line. Opening does not answer the question, so asking it again overrides the rules in [questions](../flow-plan/references/questions.md) to ask each open choice once and not to re-ask an answered question.
- **Approve**: at the first rendered view, it accepts the composition, the build continues, and flow-verify runs the gate on the built candidate; at the final validation, it accepts the walkthrough, which the accepted-candidate gate of [flow-verify](../flow-verify/SKILL.md) handles.
- **Corrections** get no option: the question says to write them in the free-text answer, so they arrive with their detail in the same reply.

Ask through a native card that waits for the answer only when its question tool accepts a free-text answer, as its schema or documentation shows, and the card has at least two options. Otherwise ask in text, with the options and one line saying to write corrections in the reply; this overrides the conditions in [questions](../flow-plan/references/questions.md) for asking in text and its rule against a reply example.

When `hive view open` prints that the viewer is not running, which it does with exit status 0, say in one line that the user can start it with `hive view start`, and ask again. On any other error, report it in one line and ask again in text without the Open option. Never run a command the output suggests, and never retry it. Never open the page, the viewer, or a browser in any other way, including your own browser. A command never publishes; [Share](#share) governs that.

## Corrections and the accepted candidate

The correction rounds a user requests during a validation pause, their task markers and the accepted-candidate gate are [flow-verify](../flow-verify/SKILL.md)'s. In each round, capture the affected views and deliver them as [Deliver](#deliver) sets.

For UI work awaiting human validation, leave the verified built local stack available and deliver the walkthrough, captures, recordings, and page defined in this skill; do not ask again merely to keep this handoff available. Pending human review means these resources are still needed. Once no longer needed, stop only the temporary processes the task or its children started and apply the UI-image hygiene in [artifact layout and retention](../workspace-conventions/references/artifact-layout.md), preserving user-selected captures and pre-existing services, sessions and evidence. Report remaining resources and how to stop them, and respect an explicit shutdown request.

## Share

Captures, recordings, and the page stay local. Attach them to a pull request only when the user asks for it, with `gh pr comment <number> --attach <file>#<alt text>`; GitHub accepts images up to 10 MB and videos up to 10 MB on a free plan or 100 MB on a paid plan. Retaining a file never authorizes publishing it.
