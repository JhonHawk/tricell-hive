# Technical review

Read at [create-prd](../SKILL.md) step 1, when the user asks whether a requirement document is ready for development or asks to check it against the code. It replaces that skill's steps 3 to 7; its steps 8 and 9 then run on the result. This review is the only step that sets `ready for development`.

1. **Check where the session runs.** The review runs only in a session with the repository whose code the document describes. In a session without it, do not review and never set `ready for development`: say that the technical review needs a session in that repository, and end as the skill's step 9 sets.
2. **Take an approved version.** Review the frozen copy of the latest version that is `approved by business`, and set the live document to `technical review`. When no version is approved, say so; compare the document with the code only if the user asks, write the verdicts, and leave its state as it was.
3. **Compare each rule with the code.** For each rule that is not `cancelled`, find the code that serves it by searching its literal values, such as names, routes, roles, states and messages, read it, and give the rule its verdict, as [PRD format](prd-format.md) defines the five. For a `contradicts` or `blocked` verdict, note the location and what the code does today. When the comparison needs more than 5 large reads, as the global guidance's «Proportionality» defines one, send it by module to read-only `hive-research` children, as [delegation](../../flow-build/references/delegation.md) sets, and check the file and line each returns before writing its verdict. A rule you could not compare stays `not checked`, with the reason.
4. **Never rewrite a rule.** The document's owner is the person its opening names. Take the case that holds:
   - **The user is not the owner.** Leave every rule as it is written. Write only the verdicts and the section of step 5, and for each `contradicts` or `blocked` rule write one question for the owner: what the code does today, the options, such as changing the rule, changing the existing behavior or adding what is missing, a recommended answer with its reason, and what each option costs, in words the owner can read. Show the user the list; after they confirm it, post each question as a comment on its rule where the tool has comments, and otherwise hand the list over in the report.
   - **The user is the owner.** Ask those questions in this session, at most three per round, as the skill's step 3 sets, and record each answer in the version's list of changes.
5. **Write the technical review section.** At the end of the live document, write a section named for the technical review, in the document's language: its date, the repository and commit compared, who reviewed, the code location and one sentence of what the code does today for each `contradicts` and `blocked` rule, and each question with its answer or that it is open. Code locations stand only in this section.
6. **Set the state.** Set `ready for development` only when both hold: no rule that is not `cancelled` is `not checked`, and every `contradicts` and `blocked` rule has its owner's answer recorded. Otherwise the document stays in `technical review`, and the report says which rules hold it back. When an answer changes or cancels a rule, the document gets a new version in `iterating`, as «States» of [PRD format](prd-format.md) sets: it returns to this review once that version is `approved by business`, and the review then compares only the rules that version changed.

The verdicts and the section make a new version, with its row in the version history; the skill's step 8 writes it and freezes it when it reached `ready for development`. At the skill's step 9, offer creating the tickets with [create-issue](../../create-issue/SKILL.md) or planning the work as the next step.
