# Write a requirement document

A requirement document states what a module or feature must do and why, as rules that development can build without deciding a business rule on its own. It holds no screen design, which [create-design](../create-design/SKILL.md) draws, no technical how, which [flow-plan](../flow-plan/SKILL.md) settles, no ticket, which [create-issue](../create-issue/SKILL.md) writes, and no schedule. This skill sets how to draft one, restructure one that arrives already written, update one with answers, and review one against the code. It runs in the main thread, with the repository or without it, changes no application code, and is used when the user asks for the document directly, also when [hive-mode](../hive-mode/SKILL.md) hands that request over; it then asks its own questions.

1. **Pick the use.** Take the first that holds:
   - **Technical review**: the user asks whether a document is ready for development, or to check it against the code. Read [technical review](references/technical-review.md) and follow it in place of steps 3 to 7.
   - **Incoming document**: the user hands over a requirement document that this skill did not write. Read [incoming document](references/incoming-document.md) and follow it in place of steps 3 and 4.
   - **Update**: answers or corrections arrive for a document this skill wrote. Follow the steps below; the result is a new version, as «Versions» of [PRD format](references/prd-format.md) sets.
   - **Draft**: otherwise, follow the steps below.
2. **Read before asking.** Read the source: the request, the notes or documents the user names, and the existing document with its frozen versions. Read [documents](references/documents.md) to find where the document lives. With the code at hand, read the module's code enough to give each rule its verdict; without it, every verdict is `not checked`. Never ask what these reads answer.
3. **Ask what is missing.** Ask only what changes a rule and no read answers, each as a decision with a recommended answer, as [decision format](../hive-core/messages/questions.md) formats one. Ask in one round every such question whose prerequisites are settled, as [what to ask](../hive-core/messages/questions.md#what-to-ask) sets, the ones whose answer changes the most rules first. Stop asking when the questions left would change no rule, or when the user says to go on. A business rule that the user does not decide, because it belongs to someone else or they do not know yet, is not assumed, since it is not yours to decide: write it as `to decide`, with who answers it. Complete a rule yourself, as an `assumption`, only when it passes the test that [business record](../hive-core/business/business-record.md) sets for that status.
4. **Draft.** Read [PRD format](references/prd-format.md) and write its sections, with each requirement as one rule entry. Write the document in the session language unless the project guidance or the author's own document sets another. When the source holds a screen layout, a technical solution or a date, leave it out of the document and name it in the report as material for the design, the plan or the schedule.
5. **Check.** Run `python3 -I <create-prd-dir>/scripts/check_prd.py <file>` ([check PRD](scripts/check_prd.py)) when a local Markdown draft exists and `python3` runs it. Check the remaining ready-list judgments of [PRD format](references/prd-format.md) in this thread; without a runnable helper or a local Markdown draft, check the whole list. Correct the writing yourself where a check asks for it, such as a rule entry that states two behaviors. Where a check needs a decision, never invent it: the rule becomes `to decide`, or the gap becomes an open question, each with who answers it.
6. **Have it reviewed.** Before offering a version for approval, launch one `hive-review-prd` child, once per version, briefed as [reviewer brief](../hive-core/delegation/reviewer-brief.md) sets with the current text of the document or the path of a local Markdown file that holds it (never its link alone, since the child may not reach the document tool), the source it was written from, and the ready list with the result of each check. Apply what holds: correct the writing yourself, and turn a finding that needs a decision into a `to decide` rule or an open question. When the user answers those questions in this session, ask them all in one round as step 3 sets and write their answers before step 9 reports the version, so that one version holds them; a question someone else answers stays open. Never decide a rule because the reviewer proposed an answer. When the host cannot launch a child, say that the review did not run; the document then stays in `iterating`.
7. **Set the state.** «States» of [PRD format](references/prd-format.md) sets what each state requires. Set the state that the checks support, never the one the author or the source claims. When the ready list passes, the review ran on this version and no rule is `to decide`, ask the user whether they approve it as a decision, saying what approval means: the version is frozen as a copy, where [documents](references/documents.md) sets, and its rules go to development as written. Only the answer that approves it makes the document `approved by business`. Otherwise report what is missing and do not ask.
8. **Write and freeze.** Read [documents](references/documents.md) before the first write and write the document where it lives, adding the version's entry with its list of changes. When this version reached `approved by business` or `ready for development`, freeze it as that reference sets.
9. **End.** Report the document's link or path, its version and state, what holds the next state back (each `to decide` rule and each open question with who answers it, and each failed check), the assumptions it carries, and what the source held that the document leaves out. Then offer the next step as a reply of [the reply block](../hive-core/messages/report-endings.md#the-reply-block), such as creating its tickets with [create-issue](../create-issue/SKILL.md), designing its screens, running its technical review in a session with the repository, or planning it, and stop: writing the document starts no work on it.
