# Deliver an authorized Git change

Global «Scope and authorization» and «Delivery» authorize effects. For E2E assignments, read [coordination](../flow-build/references/e2e-coordination.md) before Git actions.

**State read.** Where a step below reads Git or pull-request state, run `python3 -I <git-workflow-dir>/scripts/git_state.py --base <base>` ([state](scripts/git_state.py)), adding `--fetch` where the step fetches, `--pr <n>` for a pull request that is not the branch's open one, and `--since <push time>` at step 7; it prints that step's facts as JSON. When it is missing or exits 2, run the step's own commands; when it exits 1, read each field that holds `error`, and a pull request marked unavailable, with those commands. After a failed fetch it compares nothing: neither do you until a fetch succeeds. It decides nothing: which commits are this work's, which account is a bot and whether a thread still applies stay with the steps below.

1. **Read the repository.** Read, in any order, its documented conventions for branches, commits, pull requests, review and merges, and the current branch, upstream, remotes, and staged and unstaged changes. Name the paths that belong to this delivery; everything else, including another person's staged changes, is preserved. Without conventions, `type/short-slug` branches and Conventional Commits with an optional scope are suitable defaults; they do not require creating a branch or committing.
2. **Analyze the situation before acting.** Check for commits that are not this work item's as [foreign commits](../hive-rule-foreign-commits/SKILL.md) sets. When another session works in the same checkout, as commits or changes you did not make that appear during the work show, never switch, reset or delete its branch; ask about a worktree as step 3 sets. When the conventions and the state you read do not settle a Git choice, such as which branch to work on, whether to create a branch, how to split the commits, what to do with commits or changes you did not make, or how to resolve a diverged branch, a conflict or a rejected push, ask before acting: describe the state you found and give concrete proposals as one decision, each option with its effect and the recommended one first. Never pick one silently, and never stop without proposals.
3. **Choose where to work.** Create a worktree the user asked for in authorized build work (not a question). At the base or on this work's branch, with no tracked changes you did not make, work in place, branching when the delivery commits. Otherwise it is the user's decision whether to create a worktree: ask before any branch or switch, naming what you saw, unless the session already works in one; unattended work decides it to keep working ([step 5](../unattended-delegation/SKILL.md)). A child never creates one; isolating a child in one is creating one. It goes in the host's native worktree location, or an asked path when that is missing or unverified; inside the repository, add it to `$(git rev-parse --git-common-dir)/info/exclude`. Name it in the checkpoint and report, find it with `git worktree list`, and remove it with its branch as [branch cleanup](../flow-close/references/branch-cleanup.md) sets. For the coordinator’s worktree, when `Specs` is in this repository, move the change folder's files that are not committed, never copy them, from the main checkout to the same paths in the new worktree before the worktree's first edit, and edit the folder only there. When `Specs` is in another repository that declares `Delivery: direct-base`, edit the change folder in that repository's main checkout on its base, never on a branch or in a worktree, even when another session writes there. When that checkout is not on its base, never switch it: ask as step 2 sets. Stage the folder's paths by name, commit only them with `git commit --only -- <paths>`, run the check of [foreign commits](../hive-rule-foreign-commits/SKILL.md) before the push, and when the push is rejected, stop with step 2's decision and never rebase over uncommitted changes.
4. **Commit.** Before any `git add` or commit, read the file [git commit](../hive-rule-git-commit/SKILL.md) and follow it: it sets staging, the commit helper, history and hooks.
   - A change folder under `Specs` is committed with the code it plans, even while some tasks stay open. When `Specs` is in this repository, commit it on the work's branch before the push, and each later edit (such as a checkpoint line) with the next commit, or after the merge with the hygiene batch's archive. When `Specs` is in another repository, commit it there when the work reaches its completion point as [ticket state](../hive-rule-ticket-state/SKILL.md) defines it, including a `ready` stop, and deliver it as that repository's `Delivery` sets (otherwise as the work's delivery mode sets) without a second validation stop; the check of [foreign commits](../hive-rule-foreign-commits/SKILL.md) still applies. Under `hold`, it stays uncommitted.
   - At a pause close outside `hold`, commit the change folder too: in another repository with `Delivery: direct-base`, commit and push to that base with step 3's checks; with `Specs` in this repository, on the work's branch without a push when that branch exists. Otherwise leave it uncommitted and record it as pending with its path; for another repository without `Delivery: direct-base`, also recommend declaring it there.
5. **Let hooks run,** as [git commit](../hive-rule-git-commit/SKILL.md) sets.
6. **Push and open the pull request.** Before the push, run the checks of [flow-verify step 5](../flow-verify/SKILL.md) under its condition. Before a Git action that triggers CI, review, preview, deployment or merge, read that automation: an effect the authorization does not cover is resolved first, and automation settings are never changed to avoid one. Under `ready`, when that automation would merge the pull request, such as once its checks pass, ask before opening it. A review grant does not authorize autofix writes, a push or a merge. The pull request body states the problem, the resulting behavior, the checks run, the dedicated review with its mechanism and the commit it reviewed, what stayed unverified, and the assumptions the result relies on. With acceptance criteria `AC<n>`, list each one with its recorded evidence and name any task the user accepted unverified; a pull request that only publishes the change record needs none of this. When the verification produced captures, add them as [pull request captures](references/pr-captures.md) sets. When a review runs on the pull request after it opens, add its result and reviewed commit to the body. Say whether a revert fully undoes the merge or an effect would remain, such as migrated data, a published contract or a released version, and what a wrong change would affect. Follow the repository's template and contribution rules.
7. **Answer reviewers.** When the CI wait ends, read [PR reviews](../hive-rule-pr-reviews/SKILL.md) and follow it.
8. **Merge.** After the push, read [merge gate](../hive-rule-merge-gate/SKILL.md) and follow it. Before a push or merge into an environment branch after the base, read [promotion path](../hive-rule-promotion-path/SKILL.md).
9. **Verify each effect.** After each authorized action, check the resulting state instead of the command's intent: the commit and its diff, the remote branch after a push, the pull request, its checks and its merge state. When `gh` fails with a GraphQL rate-limit error, read the pull request and its checks through REST, as the state read does, which has its own limit: `gh api repos/<owner>/<repo>/pulls/<n>` and `.../commits/<sha>/check-runs`, and wait for CI with `gh run watch <run-id> --exit-status` as [merge gate](../hive-rule-merge-gate/SKILL.md) sets. Never query the REST endpoints in a loop. After a merge or a push to the base, check the CI it triggered there, waiting and handling a failure as [merge gate](../hive-rule-merge-gate/SKILL.md) sets, which also sets when that wait runs in the background. Complete the remaining effects the delivery already authorizes. When step 10 runs `flow-close`, hand it what you observed, the checks omitted and the steps left, and write no report here, since it writes the [final report](../hive-rule-close-report/SKILL.md#variants); otherwise report them yourself, as that final report sets.
10. **Close.** After verifying a merge you performed, a push to the base, or a `ready` stop, or after step 8's stop for a human reviewer's pending approval, run [flow-close](../flow-close/SKILL.md), which decides whether the whole close, only its cleanup, or nothing runs yet; when flow-close is already running, as when it merges the change record's closing pull request, continue it instead.
