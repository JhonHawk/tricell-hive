# Deliver an authorized Git change

At entry, read `stage.md` in this skill's folder whole: it holds the leaves git-commit, foreign-commits, pr-reviews, merge-gate, prose, so a step that links one of them needs no new read until a compaction, after which read the packet again. If it is missing, read the linked leaves instead; if its last line is not its packet end line, read the rest; if a `## ` heading the end line names is missing, read that leaf; if the output says it was cut, read the linked leaves.

Global «Scope and authorization» and «Delivery» authorize effects. For E2E assignments, read [coordination](../flow-build/references/e2e-coordination.md) before Git actions.

**State read.** Where a step below reads Git or pull-request state, run `python3 -I <git-workflow-dir>/scripts/git_state.py --base <base>` ([state](scripts/git_state.py); `--help` lists `--fetch`, `--pr <n>` and `--since <push time>`, used at step 7); it prints that step's facts as JSON. When it is missing or exits 2, run the step's own commands; when it exits 1, read each field that holds `error`, and a pull request marked unavailable, with those commands. After a failed fetch it compares nothing, and neither do you until a fetch succeeds. It decides nothing: which commits are this work's, which account is a bot and whether a thread still applies stay with the steps below.

1. **Read the repository.** Read its documented conventions for branches, commits, pull requests, review and merges, and the current branch, upstream, remotes, and staged and unstaged changes. Name the paths that belong to this delivery; everything else, another person's staged changes included, is preserved. Without conventions, `type/short-slug` branches and Conventional Commits with an optional scope are the defaults; they require no branch or commit by themselves.
2. **Analyze the situation before acting.** Commits that are not this work item's are checked at the moments [foreign commits](../hive-core/git/foreign-commits.md) sets, not here. When another session works in the same checkout, as commits or changes you did not make that appear during the work show, never switch, reset or delete its branch; ask about a worktree as step 3 sets. When the conventions and the state you read do not settle a Git choice, such as which branch to work on, whether to create a branch, how to split the commits, what to do with commits or changes you did not make, or how to resolve a diverged branch, a conflict or a rejected push, ask before acting: describe the state you found and propose concrete options as one decision, the recommended one first.
3. **Choose where to work.** Create a worktree the user asked for in authorized build work (not a question). At the base or on this work's branch, with no tracked changes you did not make, work in place, branching when the delivery commits. Otherwise it is the user's decision whether to create a worktree: ask before any branch or switch, naming what you saw, unless the session already works in one; unattended work decides it to keep working ([step 5](../unattended-delegation/SKILL.md)). A child never creates one, and isolating a child in one is creating one. It goes in the host's native worktree location, or an asked path when that is missing or unverified; inside the repository, add it to `$(git rev-parse --git-common-dir)/info/exclude`. Name it in the checkpoint and report; [branch cleanup](../flow-close/references/branch-cleanup.md) removes it with its branch. The work's plan file stays in the main checkout, and for an sbx sandbox its copy follows [plan record](../hive-core/plan/plan-record.md#plan-file).
4. **Commit.** Before any `git add` or commit, read [git commit](../hive-core/git/git-commit.md) and follow it: it sets staging, the commit helper, history and hooks.
   - The plan file lives in the ignored `workspace/` folder and is never staged or committed.
5. **Let hooks run,** as [git commit](../hive-core/git/git-commit.md) sets.
6. **Push and open the pull request.** Before the push, ensure passing evidence covers the repository's CI jobs, as [local CI](../hive-core/build/checks.md#local-ci) sets. Before a Git action that triggers CI, review, preview, deployment or merge, read that automation: resolve an effect the authorization does not cover first, and never change automation settings to avoid one. Under `ready`, when that automation would merge the pull request, such as once its checks pass, ask before opening it. A review grant does not authorize autofix writes, a push or a merge. The pull request body states the objective and the problem, the resulting behavior, the checks run, the dedicated review with its mechanism and the commit it reviewed, what stayed unverified, and the assumptions the result relies on. It is the work's public record, since the plan file stays local: with a plan, list each acceptance criterion `AC<n>` with its recorded evidence and name any task the user accepted unverified, the decisions taken, and the business-rule record (the plan's `## Business rules` lines, or that there are none). When the verification produced captures, add them as [pull request captures](references/pr-captures.md) sets. When a review runs on the pull request after it opens, add its result and reviewed commit to the body. Say whether a revert fully undoes the merge or an effect would remain, such as migrated data, a published contract or a released version, and what a wrong change would affect.
7. **Answer reviewers.** When the CI wait ends, read [PR reviews](../hive-core/git/pr-reviews.md) and follow it.
8. **Merge.** After the push, read [merge gate](../hive-core/git/merge-gate.md) and follow it. Before a push, merge or branch on an environment branch after the base, read [promotion path](../hive-core/git/promotion-path.md).
9. **Verify each effect.** After each authorized action, check the resulting state instead of the command's intent: the commit and its diff, the remote branch after a push, the pull request, its checks and its merge state. When `gh` fails with a GraphQL rate-limit error, read the pull request and its checks through REST, as the state read does (`gh api repos/<owner>/<repo>/pulls/<n>` and `.../commits/<sha>/check-runs`), once per check and not in a loop, since REST has its own limit, and wait for CI with `gh run watch <run-id> --exit-status` as [merge gate](../hive-core/git/merge-gate.md) sets. After a merge or a push to the base, check the CI it triggered there as that leaf sets. Complete the remaining effects the delivery already authorizes, then hand what you observed, the checks omitted and the steps left to `flow-close`, which writes the [final report](../hive-core/close/close-report.md#variants): the one step 10 runs or continues, or the one that called this delivery. A commit or push that no close follows, such as one before a validation stop, ends its message with the state you verified, which is not a final report.
10. **Close.** After verifying a merge you performed, a push to the base, or a `ready` stop, or after the stop for a human reviewer's pending approval that [merge gate](../hive-core/git/merge-gate.md) sets, run [flow-close](../flow-close/SKILL.md), which decides whether the whole close or only its cleanup runs; when flow-close is already running, continue it instead.

Reply: a delivery ends by running `flow-close`, which writes the row of [close report](../hive-core/close/close-report.md#variants) the delivery mode picks; a commit or push that no close follows ends with the state step 9 verified, which is not a report.
