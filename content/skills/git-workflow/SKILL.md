# Deliver an authorized Git change

The global guidance's «Scope and authorization» and «Delivery» sections set which Git effects are authorized; this skill sets how to perform them.

1. **Read the repository.** Read, in any order, its documented conventions for branches, commits, pull requests, review and merges, and the current branch, upstream, remotes, and staged and unstaged changes. Name the paths that belong to this delivery; everything else, including another person's staged changes, is preserved. Without conventions, `type/short-slug` branches and Conventional Commits with an optional scope are suitable defaults; they do not require creating a branch or committing.
2. **Analyze the situation before acting.** Before the validation, or before the push when the mode does not stop for one, run `git fetch` and `git log --oneline origin/<base>..HEAD`. Commits that are not this work item's are named and asked about, as «Delivery» sets. When another session works in the same checkout, as commits or changes you did not make that appear during the work show, never switch, reset or delete its branch; do your own work in a worktree. When the conventions and the state you read do not settle a Git choice, such as which branch to work on, whether to create a branch or a worktree, how to split the commits, what to do with commits or changes you did not make, or how to resolve a diverged branch, a conflict or a rejected push, ask before acting: describe the state you found and give concrete proposals as one decision, each option with its effect and the recommended one first. Never pick one silently, and never stop without proposals.
3. **Choose where to work.** Create a worktree only when the current checkout holds changes this task did not make or sits on a branch other than the base, another session writes in the same repository, or the task needs two checkouts at once; otherwise create the work branch in the current checkout, where a delegated child also works when no other work writes in it. Use the host's own worktree feature when it has one, otherwise `git worktree add` where the repository's guidance places worktrees, never in a temporary directory. When its path is inside the repository, make sure Git ignores it, adding it to `.git/info/exclude` if needed. Record its path, branch and purpose in persistent memory right after creating it, name it in the report, and remove it with its branch as [flow-close](../flow-close/SKILL.md#branch-cleanup) sets.
4. **Commit.**
   - Stage only the paths and portions that belong to the result, naming each file. Never run `git add -A`, `git add .`, or `git add` on a directory, even one such as `openspec/changes/`, since it takes other work in it. A `git mv` stages its source and destination; name both.
   - Before committing, record the pre-existing index. When unrelated paths were already staged, never run a bare `git commit`: use `git commit --only -- <paths>` when the whole working-tree content of each named path is authorized, otherwise stage the authorized portions in isolation. Afterwards, compare the remaining index with the recorded one and check the commit's paths and diff.
   - Make each commit one reviewable, revertable concern. Never rewrite, amend, force-push, clean or otherwise alter existing history or unrelated work without explicit authorization. The one exception is the force-push [unattended delegation](../unattended-delegation/SKILL.md) allows: `--force-with-lease` on the exact remote commit, recording the previous commit as the way back; a lease that fails because someone else pushed stops the push.
5. **Let hooks run.** Never skip a Git hook, such as with `--no-verify`, `git commit -n`, `HUSKY=0`, `LEFTHOOK=0` or an overridden `core.hooksPath`, without the user's approval for that repository; the approval holds for the rest of the session unless withdrawn, and each commit it covers names it in the report. When a hook fails or skips checks because a tool is missing here, read the hook and run its checks another way with tools already available; installing a tool needs its own authorization. Report a check that still cannot run as not run, name the missing tool, propose installing it, and ask before pushing. When no one can answer, push only when the workflow files show a job triggered by that push or pull request whose steps run the same commands, since a job name alone does not prove it; otherwise keep the commit local and report the push as pending.
6. **Push and open the pull request.** Before the push, run the checks of [flow-verify step 5](../flow-verify/SKILL.md) under its condition. Before a Git action that triggers CI, review, preview, deployment or merge, read that automation: an effect the authorization does not cover is resolved first, and automation settings are never changed to avoid one. Under `ready`, when that automation would merge the pull request, such as once its checks pass, ask before opening it. A review grant does not authorize autofix writes, a push or a merge. The pull request body states the problem, the resulting behavior, the checks run, the dedicated review with its mechanism and the commit it reviewed, what stayed unverified, and the assumptions the result relies on. With acceptance criteria `AC<n>`, list each one with its recorded evidence and name any task the user accepted unverified; a pull request that only publishes the change record needs none of this. When a review runs on the pull request after it opens, add its result and reviewed commit to the body. Say whether a revert fully undoes the merge or an effect would remain, such as migrated data, a published contract or a released version, and what a wrong change would affect. Follow the repository's template and contribution rules.
7. **Answer reviewers.** When the CI wait ends, read the pull request's checks once, and its reviews, review comments and comments once through REST with `gh api --paginate` (`repos/<owner>/<repo>/pulls/<n>/reviews`, `.../pulls/<n>/comments` and `.../issues/<n>/comments`), whose `user.type` tells a bot apart. Treat an assigned or requested reviewer's comments as review findings. Read each against the code before changing anything, and ask in the thread when one is unclear before implementing any. Apply the blocking comments first and the rest in any order, verifying each; push back with evidence when the code already does what a comment asks or the request would break stated behavior. Reply in each thread with what changed or why not. Those replies and the pushes carrying fixes run under the pull request's delivery authorization, when the user asks or when you check its state; never poll for comments.
   - A review bot is an account whose `user.type` is `Bot`, or a machine account that only the review automation read at step 6 posts as; an account a person also uses is not a bot. Its review counts only when its `commit_id` is the head commit; its review comment only when its `original_commit_id` is the head commit, or when it replies in a thread (`in_reply_to_id`) and was created after this work's last push; and its other comments only when created or edited after that push (`updated_at`), whose time you note when you push; older bot output and the checks of earlier commits change nothing, while an open human thread still applies. Check each bot finding against the code before changing anything, and reply with the reason to each one you dismiss. A failing check of a bot that is not a required check is a finding, not a CI failure.
   - Findings from bots and checks after the push get one round of fixes with [flow-verify step 3](../flow-verify/SKILL.md)'s definition of blocking, and without its second review: fix only the blocking ones, with an `Unreviewed: <reason>` line in each fix commit; the rest go to the close's findings, and a finding on a fix commit is reported without another round. After pushing the fixes, wait for CI on the new head commit again before the merge or the `ready` stop, and handle a failure as [flow-verify step 6](../flow-verify/SKILL.md) sets.
   - A commit on the pull request's branch that this work did not make, such as a bot's autofix, is named and asked about as «Delivery» sets for commits that are not this work item's; it is not this work's push.
8. **Merge.**
   - Use the merge method the repository declares, otherwise the one its base branch's recent merges show, such as two-parent commits in `git log --merges`, otherwise a merge commit; squash or rebase only when one of those sources sets it.
   - Merge, or stop a `ready` pull request, only on a current base: run `git fetch` and `git merge-base --is-ancestor origin/<base> origin/<branch>`, which exits 0 only when the pushed head contains the base. When it fails, merge the base into the branch and push, which the merge or `ready` authorization covers, then wait for the new CI run, or without CI rerun the local checks the merge depends on, and merge or stop only when they pass; when the base moves again, repeat once, then report the merge as pending, or the pull request as not ready, with the reason. A repository that requires a rebase needs explicit authorization for that rewrite and its force-push. Under `ready`, only this bullet and the next apply.
   - A review bot that has not reviewed the head commit when the CI wait ends does not hold the merge or the `ready` stop; name it as pending in the report.
   - With a merge queue, add the pull request to it and wait for its result.
   - Never bypass branch protection, required reviews or required checks, except an admin merge of an authorized pull request whose required checks passed where the repository does not enforce its rules on admins. Any other bypass needs an explicit grant for that repository and action, named in the report; a grant for one bypass does not cover later ones.
   - Branches after the base in the environment chain, such as `qa` and `production`, receive changes only through the declared promotion path, in order: never a direct commit or push, a cherry-pick, a hotfix straight into them, or a skipped environment. A production defect that cannot wait, as [urgent fixes](../flow-deploy/references/urgent-fixes.md) defines, follows that reference. Any deviation is its own question naming the branch, the commits and why the path cannot serve; no delivery mode or unattended delegation grants it, and without an answer the fix stays on the promotion path and the deviation is reported as pending.
9. **Verify each effect.** After each authorized action, check the resulting state instead of the command's intent: the commit and its diff, the remote branch after a push, the pull request, its checks and its merge state. When `gh` fails with a GraphQL rate-limit error, read the pull request and its checks through REST, which has its own limit: `gh api repos/<owner>/<repo>/pulls/<n>` and `.../commits/<sha>/check-runs`, and wait for CI with `gh run watch <run-id> --exit-status` as [flow-verify step 6](../flow-verify/SKILL.md) sets. Never query the REST endpoints in a loop. Step 7 already reads reviews and comments through REST. After a merge or a push to the base, check the CI it triggered there and handle a failure as [flow-verify step 6](../flow-verify/SKILL.md) sets. Complete the remaining effects the delivery already authorizes, then report what you observed, the checks omitted and the steps left, as [the final report](../flow-close/SKILL.md#final-report) sets.
10. **Close.** After verifying a merge you performed, a push to the base, or a `ready` stop, or after step 7's read for a pull request with an assigned human reviewer, run [flow-close](../flow-close/SKILL.md), which decides whether the whole close, only its cleanup, or nothing runs yet; when flow-close is already running, as when it merges the change record's closing pull request, continue it instead.
