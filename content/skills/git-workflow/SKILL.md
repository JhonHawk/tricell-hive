# Deliver an authorized Git change

This skill does not grant any Git action or change the delivery boundary already set by the user or project guidance.

## Establish the repository context

Before resolving needed project settings, read [project settings](../flow-plan/references/project-settings.md). Before a user decision, read [questions](../flow-plan/references/questions.md); before an external-work wait, read [delegation and waits](../flow-research/references/delegation.md). Before writing or cleaning an auxiliary support file, read [artifact layout and retention](../workspace-conventions/references/artifact-layout.md). Before a delivery report or message with citations, links or externally defined IDs, read [reporting](../flow-close/references/reporting.md).

Inspect the repository's documented conventions before choosing branch, commit, pull-request, review, or merge conventions. Then inspect the current branch, upstream, remotes, and staged and unstaged changes. Identify which paths belong to the requested delivery and preserve unrelated work, including another person's staged changes.

Use the repository's established conventions when they exist. Merge a pull request with the method the repository declares, otherwise with the one its base branch's recent pull-request merges show, such as merge commits with two parents in `git log --merges`, and with neither, with a merge commit; squash or rebase only when one of those sources sets it, since they collapse the per-task commits and leave the work branch looking unmerged. If it has none, `type/short-slug` is a suitable branch-name default and Conventional Commits with an optional scope are suitable commit-message defaults. These defaults do not require creating a branch or committing.

Create a worktree only when the work needs its own checkout: the current checkout holds changes this task did not make or sits on a branch other than the base, another task writes in the same repository at the same time, or the task needs two checkouts at once, such as a before-and-after comparison. Otherwise create the work branch in the current checkout; a delegated child works there too when no other work writes in it. When you do need one, create it with the host's own worktree feature when it has one, otherwise with `git worktree add` where the repository's guidance places worktrees, and never in a temporary directory, which the system may clear while it holds the only copy of the work. When its location is inside the repository, first make sure Git ignores that path, adding it to `.git/info/exclude` if needed, so the user's checkout does not list it as untracked. Right after creating it, record its path, branch and purpose in the project's persistent memory, when one is available, so another session or host can resume the work if this one stops. Name each worktree you created in the report, and remove it with its branch as [flow-close](../flow-close/SKILL.md#clean-up-after-a-merge) describes.

For review or a Git action that triggers CI, review, preview, or deployment, read [verification gates and timing](../flow-build/references/verification.md). Inspect the project's applicable automation before the triggering action. Resolve substantial effects not covered by the existing authorization; do not silently change automation settings to avoid them. A review mechanism may be local or remote: identify its candidate, scope, and effects rather than assuming all native reviews are equivalent or free. Review authorization does not itself authorize autofix writes, push, or merge.

## Prepare a coherent delivery

Stage only the paths and portions that belong to the authorized result, naming each file. Never run `git add -A`, `git add .`, or `git add` on a directory, even one limited to a folder such as `openspec/changes/`, since it also takes other work in that folder. A `git mv` stages both its source and destination; when naming the commit's paths, name both. Make commits cohesive enough to review and revert as one concern; separate independent changes when that clarifies their purpose or delivery. Do not rewrite, amend, force-push, clean, or otherwise alter existing history or unrelated work unless that effect is explicitly authorized. The one exception is the force-push that [unattended delegation](../unattended-delegation/SKILL.md) allows: `--force-with-lease` on the exact remote commit, with the previous commit recorded as the way back; a lease that fails because someone else pushed stops the push.

Before committing, record the pre-existing index and name the exact candidate paths. Inspect the candidate against both the index and working tree, and confirm that its paths and content are authorized. When unrelated paths were already staged, do not use a bare `git commit`. Use `git commit --only -- <pathspec>...` only when the complete current working-tree contents of every named path are authorized; it commits those contents while holding back staged contents for other paths. When an authorized path has mixed staged and unstaged portions, preserve the required portions through suitable isolated staging instead of forcing `--only`. Compare the remaining staged state with the recorded pre-existing index, then verify the resulting commit's paths and diff.

Let the repository's Git hooks run on every commit and push. Never skip one, such as with `--no-verify`, `git commit -n`, a variable that disables the hook manager such as `HUSKY=0` or `LEFTHOOK=0`, or an overridden `core.hooksPath`, without the user's explicit approval for that repository; that approval holds for later commits and pushes there for the rest of the session unless the user withdraws it, and you name it when reporting each commit it covers. When a hook fails because this environment lacks a tool it needs, or passes while skipping checks for that reason, read the hook to learn which checks it runs and run them another way with tools already available, since installing a tool is a separate effect that needs its own authorization. Report any check that still cannot run as not run, name the missing tool, and propose installing it. When any check remains not run, ask before pushing. When no one can answer, as under an automatic delivery or unattended delegation, push only after confirming in the workflow files that a job triggered by that push or pull request runs the same commands the hook runs, since a job name alone does not suffice, as [verification](../flow-build/references/verification.md) describes for what CI actually executes; otherwise keep the commit local and report the push as pending.

If a Git command needs an auxiliary file such as a commit message or a pathspec list, follow the canonical global artifact-placement guidance to resolve the current task's scratch directory. Remove only an auxiliary file created by this delivery when it is demonstrably reproducible and no longer needed.

When a pull request is authorized, describe the problem, the resulting behavior, the checks actually run, including the dedicated review with its mechanism and the commit it reviewed, what stayed unverified, and the assumptions the result relies on, such as the plan's. When the conversation or the change record set acceptance criteria `AC<n>`, give the checks per criterion: list each criterion with the evidence recorded for it under [verification](../flow-build/references/verification.md), meaning the test, command, or observation and its outcome, and name any task the user accepted unverified. A pull request that only publishes the change record needs no unverified items, assumptions, per-criterion list, or review record. When a review runs on the pull request after it opens, update the body with that review and the commit it reviewed once it finishes. State whether a revert fully undoes the merge or some effect would remain, such as migrated data, a published contract, or a released version, and what the change would affect if it were wrong. Follow the repository's template and contribution requirements where present.

When a human reviewer is assigned or requested on the pull request, treat their comments as review findings. Read each comment against the code before changing anything; when any comment is unclear, ask in its thread before implementing any of them. Apply them in order, blocking first, then simple, then complex, verifying each; push back with evidence when the code already does what the comment asks or the request would break stated behavior. Reply in each comment's thread with what changed or why not. Replies and the pushes that carry fixes run under the delivery authorization already given for that pull request, when the user asks or when you check the pull request's state; do not poll for comments.

## Verify the authorized effect

After an authorized local or remote Git action, inspect the relevant state rather than inferring success from command intent: the commit and its diff locally; the selected remote branch after a push; and the pull request, checks, or merge state when those effects were authorized. After a merge or push to the base branch, also check the CI it triggered there, as [verification](../flow-build/references/verification.md) describes under frequency and coverage. After local checks pass, complete any remaining Git effects already explicitly authorized, such as a selected push, pull request, or merge, then verify them. Report the observed result, omitted checks, and remaining delivery steps.

Before merging a pull request, confirm that the checks that passed ran against the current base. Check it without changing the branch: run `git fetch` and then `git merge-base --is-ancestor origin/<base> origin/<branch>`, which exits 0 only when the pull request's pushed head already contains the base; `BEHIND` in `gh pr view <number> --json mergeStateStatus` also shows the base moved, but another status does not prove it current. When that check fails, bring the branch up to date with a merge from the base and push it, which the merge authorization covers, wait for the new run, and merge only when it passes, or, when the repository has no CI, rerun the local checks the merge depends on, such as the full suite, and merge only when they pass; when the base moves again while you wait, repeat once, and after that report the merge as pending with the reason. When the repository requires a rebase instead, the rewrite and its force-push need the explicit authorization that the history rule above sets: ask for it, and when no one can answer, leave the merge pending and report it. When the repository has a merge queue, add the pull request to the queue and wait for its result instead, since the queue makes this check. A green run on a stale base does not satisfy the merge condition.

Stop at the authorization boundary. Do not infer permission to commit from permission to edit, to push from permission to commit, or to open, merge, publish, or rewrite from any earlier Git action. Authorization to merge does not authorize bypassing branch protection, required reviews, or required checks, except that an admin merge of an authorized pull request whose required checks passed is allowed where the repository does not enforce its rules on admins. Use any other bypass only when an explicit grant for that repository and that action covers it, and name the grant when reporting the result; a grant for one bypass, such as creating a branch, does not cover later pushes. Skipping a Git hook follows the hooks paragraph above instead.

Branches that follow the base branch in the repository's environment chain, such as `qa` and `production`, receive changes only through the declared promotion path, in order: never a direct commit or push, a cherry-pick, or a hotfix straight into them, and never a skipped environment. For a production defect that cannot wait, follow [urgent fixes](../flow-deploy/references/urgent-fixes.md), which [flow-deploy](../flow-deploy/SKILL.md) reads. A deviation, including an emergency fix, is its own decision: state the branch, the commits, and why the promotion path cannot serve, and ask the user for that push. Neither a delivery mode, an instruction not to ask per task, nor unattended delegation grants it; when the user cannot answer, keep the fix on the promotion path and report the deviation as pending.

## After a merge

After verifying a merge you performed, read and run [flow-close](../flow-close/SKILL.md) as its [When to run it](../flow-close/SKILL.md#when-to-run-it) sets. A merge into the base branch that integrates the work item is its completion point, also when the user asked for that merge outside any flow: the whole close runs, and the branch cleanup is one of its steps. After a promotion merge, only that cleanup runs.
