# Create a ticket

A ticket states what is needed, why, and how anyone will know it is done; [flow-plan](../flow-plan/SKILL.md) settles how it is built. The rule of [scope changes](../hive-core/plan/scope-changes.md) sets when a ticket is proposed, and [report endings](../hive-core/messages/report-endings.md) that creating one needs the user's answer. This skill sets how: creating one ticket, breaking work down into a parent ticket with children, and validating a ticket that already exists. It runs in the main thread, since a child never writes to a tracker, and it changes no repository file. It is used on its own when the user asks for the ticket directly, also when [hive-mode](../hive-mode/SKILL.md) step 0 hands that request over as a complete one, and then this skill asks its own questions; it is followed from a flow when a finding or a separate topic of that flow got the user's answer to become a ticket.

1. **Pick the use.** Creating a ticket follows the steps below. Validating a ticket that already exists, as when the user asks whether it is ready or asks to review or complete it, follows [existing ticket](references/existing-ticket.md) instead of steps 2 to 8, then ends as step 9 sets.
2. **Read before asking.** Read the source of the ticket: the finding, the request, or the requirement document with the rule it comes from. Read the repository's `## Hive` settings for its trackers and, with the code at hand, the code the work touches, enough to name where to look. Then search every tracker [project settings](../hive-core/plan/project-settings.md) declares for an existing ticket with the same outcome, open or closed, by the distinctive terms of the outcome and of the place it touches. When an open one exists, create no other: report it with its link and state, and offer to validate it. When only a closed one exists, report it, and when the work is still needed, as when a fixed defect returns, create the new ticket and relate it to the closed one. A flow that checks for an existing ticket before proposing one runs this search and nothing else of this skill. In a session without a repository, where no `## Hive` declares a tracker, ask which tracker and repository the ticket goes to before any search or write, and skip the code read. Never ask what these reads answer.
3. **Decide the level.** One ticket holds one change that is integrated and accepted on its own. A group of findings that a flow presents as one item is one ticket that lists its members. Otherwise, when the work names more than one change that integrates separately, touches more than one repository, or needs more than 7 acceptance criteria, read [breakdown](references/breakdown.md) and follow it for the rest of the steps: it proposes a parent ticket with children and sets their approval and their writes.
4. **Ask what is missing.** Ask only what changes the ticket and no read answers: at most three questions per round, the ones whose answer changes the ticket most first, each as a decision with a recommended answer, as [decision format](../hive-core/messages/questions.md) formats one. Stop asking when the questions left would not change the ticket, or when the user says to go on. Write in the ticket, as an assumption, each thing you did not ask. A business rule that the user does not decide, because it belongs to someone else or they do not know yet, is never assumed: it leaves the ticket blocked, as step 6 sets.
5. **Draft.** Read [ticket types](references/ticket-types.md), pick the type and write its sections. Write the ticket in the session language unless the project guidance sets another. When the target repository has an issue template or form, fill it: its required fields come first, and the sections of the type go where it leaves room. Add no statement that an agent wrote the ticket, unless the target repository's contribution rules ask for one; when you cannot read those rules, ask the user once.
6. **Check.** Run `python3 -I <create-issue-dir>/scripts/check_issue.py --type <type> [--finding-group] <file>` ([check issue](scripts/check_issue.py)) when `python3` runs it. Check the remaining ready-list judgments of [ticket types](references/ticket-types.md) in this thread and without a reviewer child; without a runnable helper, check the whole list. Correct the draft yourself where a check asks for writing, such as the out-of-scope line or a criterion that states two rules, and with a read or an answer where it asks for a fact; a draft that is too large goes to step 3. When a check still fails because the draft lacks a fact or a decision nobody in the session can supply, such as an undecided business rule or a bug's steps to reproduce, never invent it. That ticket is still created, marked as blocked as [trackers](references/trackers.md) sets, with the question and who it waits on; it is reported as blocked, never as ready.
7. **Confirm.** Used on its own, show the draft and create the ticket after the user confirms it. When the user's answer already chose this ticket inside a flow, such as a finding answered "ticket" or the reply "create the ticket", ask nothing more: that answer is the instruction. A parent ticket with children always takes the approval [breakdown](references/breakdown.md) sets. While [unattended delegation](../unattended-delegation/SKILL.md) is active, a single ticket for a finding needs no confirmation.
8. **Write.** Read [trackers](references/trackers.md) before the first write: it sets how to check what the account may write, how its type is set, how the ticket relates to its origin and how it is marked blocked. Create the ticket in the primary tracker of the repository the session works in, as [project settings](../hive-core/plan/project-settings.md) sets, or in the tracker and repository the user names for it, through the tracker's own CLI or tool. Then read it back and compare its type, labels and relations with what you sent, since a tracker can drop a field without an error; report a difference instead of writing again.
9. **End.** Report each ticket with its link, whether it is ready or blocked, with the question and who it waits on, and the assumptions it carries. Used on its own, offer the next step as a reply of [the reply block](../hive-core/messages/report-endings.md#the-reply-block), such as researching or planning the ticket, and stop: creating a ticket starts no work on it. Followed from a flow, return to that flow at its next step, with no ending of your own.
