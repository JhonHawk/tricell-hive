Use when the user asks to clean up, prune, tidy, reorganize, curate or archive docs, evidence, `_support` or old records, to promote a finding into durable documentation, or to apply a layout migration that harness-audit prepared; not for a work item's own support material at its close, which flow-close handles.

# Clean up documentation and support material

The user's answer to the manifest of step 4 authorizes the moves, promotions, archive tags and removals it lists; nothing is moved, written, tagged or removed before that answer. When the request asks only for an inventory or a proposal, stop after step 4 without asking.

Before writing or moving any support artifact, read [artifact layout and retention](../flow-close/references/artifact-layout.md): it sets where each kind of material belongs and which conclusions are promoted.

1. **Cover the repositories.** In a declared workspace, cover every repository it declares, the specs repository included; in a monorepo, cover its whole tree, each package's support and documentation folders included; otherwise cover the repository that holds the working directory. When neither a repository nor a declared workspace holds it, cover only what the request names, and never infer a workspace from a parent folder. Read each repository's `## Hive` section for its `Specs` and `Delivery`; a repository without one is a repository without Hive, whose delivery is asked as the global guidance's «Delivery» sets. A repository outside that set is read for context only.
2. **Take the inventory.** Read [inventory](references/inventory.md), which sets the support homes and documentation homes to list, what each holds, and what is protected. For each item record its path, whether Git tracks it, its size (the size of its tracked files when Git tracks it, otherwise its size on disk without dependency or build folders), the files that cite its path in every covered repository, found with `git grep -l -F <path>` excluding the item itself, and the date each citation was added, from `git log -S <path> --format=%cs --reverse -- <file>`. Read an item's content before classifying it; never open a secret file.
3. **Classify each item** by its content, never by its name, date or size alone:
   - **promote:** it passes the test of [Retain evidence](../flow-close/references/artifact-layout.md#retain-evidence), and no durable document states its conclusion yet;
   - **remove from tree:** versioned verification material, a superseded copy, or raw output whose conclusion a durable document already states or that no later work cites;
   - **move or rename:** a record in the wrong home for its purpose, moved to the destination artifact layout sets or to the project's existing documentation home, keeping its work identifier and initial date; move only what the request covers, and never retrofit a whole repository to a folder template;
   - **prune a living document:** a current document that a newer source contradicts, as [inventory](references/inventory.md#living-documentation) sets;
   - **archive session:** a closed `sessions/` folder, as [archive](references/archive.md) sets;
   - **keep:** current knowledge, every protected item, material of open or paused work, a finding's trace without a ticket, and anything of uncertain ownership.

   A folder that a repository's own guidance still tells agents to write into is that project's current convention: keep it unless the request retires that convention or Hive no longer creates it, as with `evidence/`. An item that a current document cites is removed or moved only together with the update of that citation, and removed only once the document states the promoted conclusion in its place. When a repository's own guidance, such as its `AGENTS.md`, still tells agents to write into a folder the manifest removes, add an entry that changes that instruction, since otherwise later work refills the folder. An approved migration manifest from [harness-audit](../harness-audit/references/project-layout.md) joins this manifest: its `git mv`, `mkdir` and `insert` entries become move entries, and its `manual` and `ask` entries stay open questions.
4. **Write the manifest.** Write it to `_support/workspace/YYYY-MM-DD-docs-cleanup/manifest.md` in the support home of the working directory, which Git ignores, grouped by repository: each entry with the item, its class, the reason (its content and the citations found), the destination of a move, the links to update and its size. In the message, show first what would be removed, with each path, its size and its reason and the total, then the moves, promotions and prunings, and the kept items in one line with their count and the protected ones among them. Name the archive tag each repository with removals gets, and say that removing files from the tree does not shrink a clone, since history keeps them and this skill never rewrites history. Ask the manifest as one decision, as the global guidance's «Questions and routes» sets: the starred option applies every entry, another keeps everything, and a reply that names paths changes their entries. Removing a backup, a dump or an export is a decision of its own, and so is removing material that Git does not track and that is not reproducible, such as a support home outside any repository: no tag can restore it, so list it apart with its size, say that its removal is irreversible, and remove only the items the user's answer names.
5. **Apply it, one repository at a time,** marking each applied entry in the manifest, which is this work's checkpoint after a compaction.
   - Before each move, check the destination for a collision; preserve both artifacts rather than overwriting, and ask when it decides which record is canonical. Move with `git mv`, then update the relative links and indexes that point to the moved path, including links from a moved record to items that stayed.
   - Write each promoted conclusion into its durable document with the fields [Retain evidence](../flow-close/references/artifact-layout.md#retain-evidence) sets, and each pruned document as [inventory](references/inventory.md#living-documentation) sets, updating the citations of the item.
   - When the repository has removals, check that the tag does not exist, locally or on the remote, then create the annotated tag `archive/<YYYY-MM-DD>-<slug>` on the commit before the cleanup with `git tag -a <tag> -m "<what it keeps>" <commit>`. Remove the items with `git rm -r -- <path>`, naming each path.
   - Archive the selected sessions with the [archive](references/archive.md) helper.
   - Commit the repository's entries in one commit whose message names the tag and how to restore an item, `git checkout <tag> -- <path>`. Deliver it as that repository's `Delivery` sets, otherwise as the delivery mode of this request, asked as the global guidance's «Delivery» sets, and push the tag with that delivery's push: `git push origin <tag>`.
   - Remove an untracked item only with positive evidence that it is reproducible or that a kept copy replaces it, or when the user's answer to its own decision names it; an old date, an ignored status or a rerunnable command is not such evidence. A tool file such as `.DS_Store` needs none.
6. **Verify.** In each repository, check `git status`, the moves with `git diff -M --stat <before>..HEAD`, that the tag exists on the remote with `git ls-remote --tags origin <tag>`, that `git show <tag>:<path>` returns a removed item, and that `git grep -F <path>` finds no remaining citation of a removed or moved path in any covered repository.
7. **Report** in the session language: each repository's tag, the removed paths with their size, the moves, the promoted conclusions and pruned documents with their files, what was kept and why, and the entries still open. Delete the manifest once every entry is applied; keep it while any is open and name its path.
