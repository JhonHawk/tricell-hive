# Writing `HIVE.local.md`

Read before you write, ignore, mark stale or prune a `HIVE.local.md` file.

- Add or update an entry with that date in the machine file when it holds whatever project you work in (an installed tool or its absence, an existing cloud profile and its region, or a host alias); otherwise in the repository's file when it concerns one repository, and in the declared workspace's file when it concerns several, or the repository's file when no workspace is declared. Sessions of other projects write the machine file too: reread it immediately before writing, use the operations below, and preserve every entry outside the authorized update, stale mark or pruning. Write only in those files of the current project, the local scripts [local script](../hive-rule-local-script/SKILL.md) sets, and in the machine file. Mark a failed entry stale with its date and cause before trying another way; an `unverified` entry keeps its mark and gains that date and cause. A fact that holds for every clone, such as a test command or a CI job, does not go there: name it once, in the final report of the work item that verified it, as a candidate for the repository's tracked guidance.
- Write no secret value: name the file in the secret location that holds it, or, for a machine fact, the tool's own credential file, such as `~/.aws/credentials`, and point to `ACCOUNTS.md` for the test accounts of an environment; which account or identity a tool uses on this machine is a fact for these files, named without its credential. An entry marked `unverified`, which only harness-audit's [local instructions](../harness-audit/references/local-instructions.md) mode writes, carries the date it was last seen, not confirmed: check it before relying on it, and when it holds, replace the mark with that date. Keep each file at or under 50 lines by removing only entries marked stale; an `unverified` entry leaves only through that mode's curation with the user. When no stale entry remains, keep recording and recommend harness-audit's [local instructions](../harness-audit/references/local-instructions.md) mode to curate it in the final report.
- This rule authorizes, in any flow, read-only ones included, writing the `HIVE.local.md` files and creating the machine file's folder; this makes the machine file, its folder and the exclude entry that keeps it out of Git an exception to «Scope and authorization»'s «Change only the current project», and the machine file is not global configuration. Before their first write inside a Git repository, ensure Git ignores them. Run `python3 -I <harness-audit-dir>/scripts/local_instructions.py <operation> --repo <root>` ([helper](../harness-audit/scripts/local_instructions.py)): `ensure-ignore` for standard paths, `add` for entries, `mark-stale` for an unambiguous match, or `check` for project diagnostics; each subcommand’s `--help` gives its required arguments and `--file` selects a nondefault entry file. These operations preserve the invariants above; before `add` can prune stale entries, save their failure details as [local record](../hive-rule-local-record/SKILL.md) requires. Read errors and `needs_curation`; success does not prove the facts or remove the no-pruning restriction after a host refusal. For unsupported operations or paths, or without Python, perform only the authorized update manually under the same invariants, preserving a trailing newline on append; Git exclusions belong in the repository's common `info/exclude`, shared by worktrees. In a worktree, read [worktree](references/worktree.md) first. The repository's or workspace's file is the one support file kept at the root rather than in the support home.
