# Set, check and apply a project's layout

[Layout](references/layout.md) is the convention: where each support artifact, document, script and data set belongs, the project's index and its `Layout:` line, and how evidence is retained. Every flow reads it before writing a support artifact, as the global guidance's «Support folder» sets; reading it does not start this skill's procedure.

Pick the mode the request asks for:

- **Check:** when the user asks whether a project follows the layout, or another skill asks for its check. Run `python3 -I <project-layout-dir>/scripts/check_layout.py --root <root>` ([check](scripts/check_layout.py)) for each root step 1 covers, and report its findings grouped by rule, each with its correction, the `review` ones apart as items for the user to judge rather than violations; it changes nothing. When it reports LAYOUT-01, LAYOUT-04 or LAYOUT-08, also run `python3 -I <project-layout-dir>/scripts/plan_layout.py plan` with the same roots ([placement planner](scripts/plan_layout.py)), which changes nothing either, and show where each item would go. End by offering to organize the project.
- **Organize or migrate:** every other request; run the steps below. When the request moves the project between layouts, such as consolidating repositories into a monorepo or into a workspace repository, when `Specs` or the workspace's knowledge hub is missing or unresolved, when a repository keeps its documentation outside `_support/docs`, or when harness-audit's onboarding asks for the check of `Specs`, also read [migrate](references/migrate.md) before step 3. When the inventory holds scripts, read [script lifecycle](references/script-lifecycle.md) before step 3.

The user's answer to the manifest of step 4 authorizes the moves, promotions, archive tags and removals it lists; nothing is moved, written, tagged or removed before that answer. When the request asks only for an inventory or a proposal, stop after step 4 without asking.

1. **Cover the repositories.** In a declared workspace, cover every repository it declares, the specs repository included; in a monorepo, cover its whole tree, each package's support and documentation folders included; otherwise cover the repository that holds the working directory. When neither a repository nor a declared workspace holds it, cover only what the request names, and never infer a workspace from a parent folder. Read each repository's `## Hive` section for its `Specs` and `Delivery`; a repository without one is a repository without Hive, whose delivery is asked as [delivery questions](../hive-rule-delivery-ask/SKILL.md) sets. A repository outside that set is read for context only.
2. **Take the inventory.** Read [inventory](references/inventory.md), which sets the support homes and documentation homes to list, what each holds, and what is protected, and run the check of the **Check** mode on each root: each finding joins the inventory as the item it names. Then run `python3 -I <project-layout-dir>/scripts/plan_layout.py plan --root <root>` with every root, adding `--out` and the path `plan.json` next to the manifest of step 4: it gives each script, code or infrastructure file and each legacy folder under `_support/` its destination, the reference rewrites a move needs, and the items no rule places, the same on every run. For each item record its path, whether Git tracks it, its size (the size of its tracked files when Git tracks it, otherwise its size on disk without dependency or build folders), the files that cite its path in every covered repository, found with `git grep -l -F <path>` excluding the item itself, and the date each citation was added, from `git log -S <path> --format=%cs --reverse -- <file>`. Read an item's content before classifying it; never open a secret file.
3. **Classify each item** the planner did not place by its content, never by its name, date or size alone. A planner row is a **move or rename** to its destination, and a row without one is an open question of the manifest; never choose another destination by hand:
   - **promote:** it passes the test of [Retain evidence](references/layout.md#retain-evidence), and no durable document states its conclusion yet;
   - **remove from tree:** versioned verification material, a superseded copy, or raw output whose conclusion a durable document already states or that no later work cites;
   - **move or rename:** a record in the wrong home for its purpose, moved to the destination [layout](references/layout.md) sets, a script to the place [script lifecycle](references/script-lifecycle.md) gives its level, or to the project's existing documentation home, keeping its work identifier and initial date; move only what the request covers, and never retrofit a whole repository to a folder template;
   - **prune a living document:** a current document that a newer source contradicts, as [inventory](references/inventory.md#living-documentation) sets;
   - **archive session:** a closed `sessions/` folder, as [archive](references/archive.md) sets;
   - **keep:** current knowledge, every protected item, material of open or paused work, a finding's trace without a ticket, and anything of uncertain ownership.

   A folder that a repository's own guidance still tells agents to write into is that project's current convention: keep it unless the request retires that convention or Hive no longer creates it, as with `evidence/`. An item that a current document cites is removed or moved only together with the update of that citation, and removed only once the document states the promoted conclusion in its place. When a repository's own guidance, such as its `AGENTS.md`, still tells agents to write into a folder the manifest removes, add an entry that changes that instruction, since otherwise later work refills the folder. The entries of a [migration manifest](references/migrate.md#migration-manifest) join this manifest: its `git mv`, `mkdir` and `insert` entries become move entries, and its `manual` and `ask` entries stay open questions.
4. **Write the manifest.** Write it to `_support/workspace/YYYY-MM-DD-project-layout/manifest.md` in the support home of the working directory, which Git ignores, grouped by repository: each entry with the item, its class, the reason (its content and the citations found), the destination of a move, the links to update and its size. In the message, show first what would be removed, with each path, its size and its reason and the total, then the moves, promotions and prunings, and the kept items in one line with their count and the protected ones among them. Name the archive tag each repository with removals gets, and say that removing files from the tree does not shrink a clone, since history keeps them and this skill never rewrites history. Ask the manifest as one decision, as [decision format](../hive-rule-questions/SKILL.md) sets: the starred option applies every entry, another keeps everything, and a reply that names paths changes their entries. Carry a changed destination into the plan with `--override <source>=<destination>`, an item the user keeps where it is with `--keep <source>` (a folder keeps every row under it, and a kept file keeps its test), a reference the user keeps as it is, such as an old path a CI selector still matches, with `--keep-ref <file>[:<line>]`, never by editing the plan file, or a whole home the user moves with `--home tools|infra|docs=<path>`, and write the `Layout:` line that plan prints at the head of the index; the planner's open rows stay questions until the user answers them. Removing a backup, a dump or an export is a decision of its own, and so is removing material that Git does not track and that is not reproducible, such as a support home outside any repository: no tag can restore it, so list it apart with its size, say that its removal is irreversible, and remove only the items the user's answer names.
5. **Apply it, one repository at a time,** marking each applied entry in the manifest, which is this work's checkpoint after a compaction.
   - Apply the planner's rows with `plan_layout.py apply --plan <plan.json>`: it refuses a stale plan or a taken destination without moving anything, moves with `git mv` or a plain move for untracked material, rewrites each reference in the form it had, never commits, and records what it did so that `plan_layout.py undo --plan <plan.json>` reverses exactly that. Back out with `undo`, never with `git checkout -- .` or `git restore`, which also drop other work's uncommitted changes. Then fix by hand only the references it listed for review, such as a glob over files with different destinations, add the index lines of the moved tools, change each exclusion file a `build contents` review names, such as `.dockerignore`, as the user decides, and ask the user about the files Git ignores that an `ignored files stay` review lists, since no tag or history restores them.
   - For every other move, check the destination for a collision; preserve both artifacts rather than overwriting, and ask when it decides which record is canonical. Move with `git mv`, then update the relative links and indexes that point to the moved path, including links from a moved record to items that stayed.
   - Write each promoted conclusion into its durable document with the fields [Retain evidence](references/layout.md#retain-evidence) sets, and each pruned document as [inventory](references/inventory.md#living-documentation) sets, updating the citations of the item.
   - When the repository has removals, check that the tag does not exist, locally or on the remote, then create the annotated tag `archive/<YYYY-MM-DD>-<slug>` on the commit before the cleanup with `git tag -a <tag> -m "<what it keeps>" <commit>`. Remove the items with `git rm -r -- <path>`, naming each path.
   - Archive the selected sessions with the [archive](references/archive.md) helper.
   - Commit the repository's entries in one commit whose message names the tag and how to restore an item, `git checkout <tag> -- <path>`. Deliver it as that repository's `Delivery` sets, otherwise as the delivery mode of this request, asked as [delivery questions](../hive-rule-delivery-ask/SKILL.md) sets, and push the tag with that delivery's push: `git push origin <tag>`.
   - Remove an untracked item only with positive evidence that it is reproducible or that a kept copy replaces it, or when the user's answer to its own decision names it; an old date, an ignored status or a rerunnable command is not such evidence. A tool file such as `.DS_Store` needs none.
6. **Verify.** Run `plan_layout.py verify --plan <plan.json>`, which exits 0 once no current reference to a moved path remains except those kept with `--keep-ref`, each moved tool has its index line, and each exclusion file a move crossed leaves the moved item in or out of its build as it did the source, or names its new path; its `note:` lines list the ignored files still left behind. In each repository, check `git status`, the moves with `git diff -M --stat <before>..HEAD`, that the tag exists on the remote with `git ls-remote --tags origin <tag>`, that `git show <tag>:<path>` returns a removed item, and that `git grep -F <path>` finds no remaining citation of a removed or moved path in any covered repository.
7. **Report** in the session language: each repository's tag, the removed paths with their size, the moves, the promoted conclusions and pruned documents with their files, what was kept and why, and the entries still open. Delete the manifest once every entry is applied; keep it while any is open and name its path.
