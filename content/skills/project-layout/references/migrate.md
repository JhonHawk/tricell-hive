# Migrate a project's layout

Read at [project-layout](../SKILL.md) before step 3 when the request moves a project between layouts, when `Specs` or the workspace's knowledge hub is missing or unresolved, when a repository keeps its documentation outside `_support/docs`, and from audit-harness's onboarding for HA-PL-01. It sets the checks of the `## Hive` settings and the layout of old records, the questions a migration asks, and its manifest entries, which join project-layout's manifest; nothing moves before the user's answer to it. Edits to the `## Hive` section itself follow audit-harness's [apply](../../audit-harness/references/apply.md).

## Choose the layout

Two layouts are equally valid. Recommend a **monorepo**, one repository holding the code and `_support/openspec`, only when all four hold: the same people can write to every repository, and no client or third party needs only one; deployments can be selected by path in one CI; no repository has a publication contract of its own with outside consumers, such as a published package, a fork or a repository the client administers; and consolidating needs no merge of Git history, since the current state is copied with its provenance. Otherwise keep a **workspace** of several repositories, which can become a coordinator repository through [workspace-repo](../../workspace-repo/SKILL.md) when the user asks.

Every migration, in either direction, follows the same order: separate current knowledge from history first; record each moved document's provenance, its source commit and blob, and point historical links at the original commit; check from the entry point of a session, in an isolated copy, that the destination is enough on its own; deliver the destination before retiring the origin; and retire the origin in a way that can be restored, such as an archive tag.

## Questions a migration asks

Ask them in the round of the manifest, as [decision format](../../hive-core/messages/questions.md) sets:

- **Knowledge hub**, when `Specs` is missing, does not resolve, or differs between repositories of one project: the detected specs repository; the repository that owns the contracts, usually the backend; a workspace repository created with workspace-repo; or `_support` of the workspace only. Say what each leaves outside Git.
- **Documentation home**, when a repository keeps its living documentation outside `_support/docs`, such as a root `docs/`: propose moving it to `_support/docs`, with the links each move updates. When the user declines, keep it, and write at the head of its index the line `Layout: docs at <path>`, keeping any key the line already has, creating `<path>/README.md` when it has no index and pointing the root `AGENTS.md` at it with an `Index: <path>` line when the index is not `_support/docs/README.md` or `docs/README.md`.

## Checks (HA-PL)

- **HA-PL-01 — Specs target.** `Specs` in each repository resolves to an existing directory inside a Git repository and is not ignored (`git check-ignore`). A missing directory is a `create` entry, or an `ask` entry for a clone when the value carries a Git URL, because a clone fetches remote content; an ignored or unversioned path is `high`. A path outside the repository with no ` · <git-url>` is `medium`: a fresh clone cannot locate or fetch it.
- **HA-PL-02 — One target per project.** Repositories of the same project point `Specs` at the same directory. Several repositories sharing a project without a specs repository need the caller's decision to create one or designate a repository.
- **HA-PL-03 — Legacy homes.** Find existing records outside the layout: `sessions/` folders, epic or delta folders, current-rule folders such as `product/`, unversioned workspace ledgers such as `_support/PROJECT.md`, and plans at repository roots. Classify each by its content, not its name.
- **HA-PL-04 — Current requirements.** Identify where current behavior is described today. A product map (`product/<module>/<view>.md` with rules in force) is the project's current-requirements home: `keep` it in place and never propose moving it into `<specs>/specs/`. Another folder that already holds only rules in force maps to `<specs>/specs/`; a document that mixes current rules with delivery history stays in place (`keep`) and remains authoritative for its areas until a change moves them, because extracting current requirements is authoring, not a move. Flag instructions that still call such documents the single source of truth so they can name the transition.
- **HA-PL-05 — Misplaced material.** Report content whose home is another repository or level, such as infrastructure configuration inside a specs repository, secrets or raw evidence inside a versioned path, or support material at a repository root. These checks propose no removal of versioned evidence or legacy records: project-layout's classes in its step 3 decide them. `HIVE.local.md` at a repository or workspace root is not misplaced: [local write](../../hive-core/local/local-write.md) keeps it there.

## Old change register and records

Read when the planner reports a legacy row: `<Specs>/changes/` (each child of the archive and each change folder), `sessions/`, `evidence/` and `reports/`, `archive/`, `archived/`, `backups/`, `plan/` or `spec/`, whether under `_support/` or at the root of a Git repository. A root outside Git plans nothing inside a repository of its own or inside another root of the same plan; that root's plan holds it. The planner, not you, decides each row's `action`:

- **move** to `workspace/<YYYY-MM-DD>-<work>/` of the support home (the repository's `_support/`; for a legacy home at the root of a repository with no `_support/`, the `_support/` of the workspace folder when it is also a root of the plan, written `../_support/workspace/...`), dated by the item's name, else its first commit, else its oldest file; dumps and exports go to `_support/data/`, which is never deleted without the user's answer. A tracked item leaves Git (`untrack`): the project's delivery commit carries the removal, and history keeps it.
- **delete**, with `--legacy remove` (the answer to step 2's question), each legacy record a **move** row would take that Git tracks and that has no uncommitted, untracked, ignored or hidden edit; an untracked or edited record still moves, since no tag restores it, a record that holds a dump or export moves as a decision of its own, and one a document cites is deleted all the same: its row lists the citations (`cited_by`, with `file:line`, at most 10 and the count of the rest) in its notes and `plan.json`, and they never change its action, except that an untracked delete row a text file names goes to review, since no tag restores it. After apply, repoint each citation of a removed record to `archive/<YYYY-MM-DD>-<slug>:<path>`, or to the document that now holds the fact; `verify` lists what remains, including a citation of the row's path anywhere in the text, and accepts a path written after a ref that holds it.
- **delete** each child of the change archive and each loose file of `changes/` when it is tracked and has no uncommitted, untracked or ignored file (the archive is planned one child per row, so a dirty child stays without keeping the rest), each change folder whose last commit is reachable from `origin/<base>` (the `Base branch` of `## Hive`, else the remote's default), and output tooling regenerates that Git ignores and that sits outside `evidence/` and `reports/` (anything else moves like a record).
- **keep** a change folder that is not reachable, named in the manifest with its last commit; one with uncommitted edits; a child of the archive or a loose file that is untracked, ignored or edited; every change folder, every child of the archive and loose files when `_support/` is outside Git, the base does not resolve or `git status` fails; `--keep` or `--override` settles any of them. Ask about it; never delete it to make the list shorter.
- **review** each child of `plan/` and `spec/`, which may hold current knowledge: promote what is current to the docs home, then name the rest with `--keep` or `--override`. A top-level folder (`sessions/`, `evidence/`, `reports/`, `archive/`, `archived/`) that code or configuration cites as a path in force is a review row too, since a tag does not fix a broken build and the planner has no rewrite for a bare folder name: update the citation, then name the folder with `--keep` or `--override`. A folder only documents cite is not held back. A destination that nests inside another row's destination (the same work in `sessions/` and `evidence/`) moves outer folder first and is no review row; one that collides with a path the outer folder already holds is.

Two steps need judgment, so the script leaves them to you; propose each one at a time, with the evidence, and apply only the answered ones:

1. **Specs that only restate guidance.** For each spec under `<Specs>/specs/`, read it against the guidance and code it describes. Propose removing it only when every requirement in it is stated in the guidance in force or enforced by a test; keep the contract specs (installer, viewer, site, branch promotion) and every requirement with no other home.
2. **Memory records of the old archive.** List the `archive-pending/` records of the project's memory (Engram topic or the host's own memory) with their titles and dates, and ask the user which to discard; delete only the records the answer names.

## Migration manifest

Group entries by repository, in the order they can be applied. Each entry has:

Each entry has an operation (`rename`, `move`, `archive`, `create`, `insert`, `keep`, `manual` or `ask`), repository-relative source and destination paths, the exact `git mv` or `mkdir` command for mechanical operations (for `insert`, the exact line and the line it follows; none for `manual` or `ask`), the reason (the evidence that places it there), the files that reference the source path, and the risk (collisions, links to rewrite, open work using the path).

Rules for proposing entries:

- Propose only mechanical moves with `git mv`; content that must be rewritten or split is `manual`.
- A repository used with Cursor CLI that lacks the HA-IF-18 pointer gets an `insert` entry: the canonical line into its root `AGENTS.md`, after the file's first paragraph and outside `## Hive`. `insert` is the only content edit a manifest carries; any other added or changed text is `manual`.
- Leave history in place by default: closed sessions and epics become `keep` or `archive` under the project's legacy archive, never merged into current specs.
- Never propose moving active work mid-change; mark it `ask`.
- Mark anything sensitive, such as secrets or credentials, `keep` with the reason, and never include its contents.
- End with the questions the caller must answer before applying, and the checks that verify the result, such as `git status`, rename detection with `git diff -M --stat`, and a link check.
