# Viewer publication

Read at a session's first UI capture, and after a compaction. Read it once per session, when the first build or verify flow that [walkthrough](walkthrough.md) gives a viewer session takes its first UI capture, and again after a compaction. The viewer holds only UI captures and their iteration: publish no stage, task, document or reason during the flow, and never read `hive view work contract`. This procedure changes only local viewer state and does not authorize project, tracker or external writes. Hive's session hooks already report the session's start, activity and end. Delegated children return captures and findings to the primary producer, which alone publishes.

## Publish captures

1. Never start or restart the viewer service; a stopped viewer is handled by the queue below.
2. Publish each batch of captures of one screen with one command: `hive view work capture --stage build|verify --view-title SCREEN --image FILE[:caption] ...` (`--help` lists the other options). On the work's first capture add `--key KEY`, the ticket key or otherwise the work's folder name or a short descriptive key, kept in the checkpoint (it also selects the work later), and `--summary TEXT`, one paragraph on what the work is about, not the research report. A later capture with the same `--view-title` supersedes the earlier view as `SCREEN · #2`: keep a screen's title identical across iterations, give each screen its own title, and after a correction capture only the screens it changed.
3. Pass no `--host` and no `--native-session-id`. When a command reports the identity missing or ambiguous, follow [host session identity](viewer/host-session-identity.md); never substitute another session's identity or invent an ID.
4. Do not read the work back after a capture: a reply that is not `queued` shows the capture is visible, and `unchanged` means it was already published. A `queued` reply (the viewer is stopped or silent) is not a failure: the capture is stored and the next command or hook run with a running viewer sends it. Continue, keep its image files until a later reply is not queued, and report each `queue.rejected` at the next handoff instead of repeating it.
5. When a reply reports a pending or uncertain operation, follow the next action it names; never delete the publisher journal or send a new request in its place. A missing `capture` command needs a Hive upgrade (`hive update`). When the binary, the viewer or the identity is unavailable, keep the inputs, record what was not published in the checkpoint, report it at handoff and continue independent work. Never claim a capture was stored.
