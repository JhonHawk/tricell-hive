# Publish captures and walk an interface

Read when an interface is captured, or a walkthrough is asked for. It applies when a build or verify captures an interface, when a flow or role publishes captures, and when the user asks for a walkthrough or demo of a built interface, which follows this leaf alone. The close of a work with captures follows [close the viewer](viewer-close.md).

A build or verify flow that was explicitly invoked (its command typed, its route accepted, or research, plan or build continuing into the next flow at the user's request or as a handoff sets), and a walkthrough or demo the user asks for, gets a viewer session at its first UI capture; research and plan publish nothing, and a flow without captures creates no viewer work. The primary producer follows [viewer publication](viewer.md) at that capture; a child never publishes.

For a walkthrough, serve the candidate locally, as [Show it in the host's pane](#show-it-in-the-hosts-pane) sets when the session has that pane, or install and launch a native app on the assigned device or emulator as [Device tool](ui-verification/device-tool.md) sets, with seeded data of realistic volume and text length (stub data only for a build's first view, as [UI decisions](ui-plan.md) defines) and an account that reaches the changed screens, chosen after reading [test accounts](../local/test-accounts.md). Take the capture scope from [UI verification](ui-verification.md) and reuse existing evidence. Publish the current captures, then give the user the Try it block the [verification floor](../build/verification-floor.md#what-the-report-carries) sets, with the observations and evidence paths. The calling flow owns its existing acceptance question and handles corrections; this reference adds only the options that [open the viewer](viewer-open.md) sets. On a correction, capture again only the affected screens under their same titles: the viewer numbers the new iteration and keeps the earlier one.

## Show it in the host's pane

This section applies at a stop where the user reviews a served app, such as a build's first view, a walkthrough or a validation request with its Try it block, when this session's tools include a browser pane the user sees inside the host app, such as a desktop app's built-in browser. A terminal session has no such pane: the stop gives its URLs as links and, for an app that needs sign-in, the window of [Sign in for the user](#sign-in-for-the-user).

- Serve the candidate through the host's own preview mechanism when it has one, such as a launch configuration its preview tool starts, instead of a shell command, keeping the build or preview command the calling flow sets. The Try it block gives the URL and port the served instance reports, not a port `HIVE.local.md` records, since the host may pick a free port each run; a port the host's preview picks is not a fact to record there.
- Open each URL the stop names in that pane, visible to the user when the host keeps it in the background by default, and signed in as [Sign in for the user](#sign-in-for-the-user) sets. When the host reaches the pane only through its own browser subagent, open it through that subagent: it is the host's access to the pane, not a Hive child, so it does not count toward [delegation](../delegation/delegation.md).
- When opening fails, give the URLs as links and say why.

Automated checks, captures and children keep the tool [Browser tool](ui-verification.md#browser-tool) sets. [Close cleanup](../close/close-cleanup.md) sets what happens to a server the host's preview started.

## Sign in for the user

This section applies at a stop where the user reviews a served web app, such as a build's first view, a walkthrough or a validation request with its Try it block, when the Try it start shows a sign-in screen and the account the block names has a source for each factor in its index row, as [test accounts](../local/test-accounts.md) sets. Without such an account, the block gives the row and the user signs in.

- Before asking, sign in with that account as [Browser tool](ui-verification.md#browser-tool) sets, so its saved state is current, then close that session, so the window below is the one browser holding the state.
- With the host's pane: when the account's password is a public local value the project documents, such as a seed password its `README.md` gives, sign in inside the pane through the host's browser tool, typing the second factor's code that [test accounts](../local/test-accounts.md) reads, and leave the pane on the Try it start; a real password never goes into a tool's input. Otherwise open the pane at its sign-in screen and offer the window below.
- In a terminal session, or with the pane left at its sign-in screen: offer `Open signed in` as [open the viewer](viewer-open.md) sets for the stop's options, only when the host's native session ID can be read as [host session identity](viewer/host-session-identity.md) names its variable; without it, the block gives the row. When the user picks it, open `agent-browser --headed --session tryit-<repo>-<id> --state <file> open <Try it start>`, where `<repo>` is the repository's folder name reduced to letters, digits, `-` and `_` and cut to 40 characters, and `<id>` is the first 16 characters of the SHA-256 of the session ID (`printf %s "$ID" | shasum -a 256 | cut -c1-16`), so no other session's window shares the name and the name stays under the 103-byte socket path agent-browser allows.
- The window is the user's: drive it only to bring it to a later stop's start, never for checks, captures or children, which keep their own sessions. When its browser is gone, because the user closed it, the next command opens it again with the same state. [Close cleanup](../close/close-cleanup.md) closes it.
