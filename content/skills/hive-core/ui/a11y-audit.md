# Automated accessibility audit

Read when reviewing the UX of a UI change. The audit measures; it does not replace the keyboard, focus and interaction checks of the review.

- When `agent-browser` drives the review, run `agent-browser a11y --tags wcag2a,wcag2aa,wcag21a,wcag21aa,wcag22aa,best-practice --json` in that review's session, under the time limit of [Browser tool](ui-verification.md#browser-tool), on each reviewed state at each width and theme the review checks: every changed screen and every state reached by interaction, such as an open dialog, popover, menu, panel or mobile navigation, since the audit sees only what is rendered. Scope it with `--selector` to the container of the reviewed regions when one holds them all; otherwise audit the page and report only the results inside the reviewed regions. Before each run, wait for a selector or text that shows the state is ready, or for `--load networkidle` on a page that does not poll or stream, not a fixed delay. Its embedded axe-core needs no network and runs under a strict page content security policy, as its documentation states. When another browser tool drives the review, run the audit there only when that tool can execute axe-core in the same page; otherwise report the audit as not run.
- A native or cross-platform mobile app has no automated audit here: report it as not run, and still check focus order and accessible labels on the device.
- A violation with a `wcag*` tag is a defect. Give it the priority that [Findings](../close/close-report.md#findings) defines from the observed effect on users, not from axe's `impact` field: axe `critical` is not P0 by itself. A violation with no `wcag*` tag, only `best-practice` and category tags, is a P3 finding marked best-practice, never reported as a WCAG failure.
- Treat each `incomplete` result as pending manual review, not as a pass; check it with rendered colors, keyboard or focus as the rule requires, and name the ones left unchecked. When an `incomplete` result comes from markup the project's UI library generates by design, such as its focus guards, portal containers or the `aria-controls` of a closed popup, note it once and do not report it as a defect.
- Count affected elements from `nodeCount`, since the JSON lists at most 10 nodes per rule, and record `axeVersion` with the evidence.
- axe-core finds on average 57% of WCAG issues, by its maintainer's measure: a run with no violations is not evidence of conformance, and the report never claims conformance from it.
- When the project guidance names a UI linter and the command that runs it, and that command is already installed in the project or on the machine, also run it on the running URL, with JSON output when it has one; never install it or fetch it with a one-off package runner, and report it as not run when it is missing. Report its findings on contrast, overflow, structure, broken images and script errors as measured defects, and its aesthetic or style rules as informational only, since the project's design system governs the look.
