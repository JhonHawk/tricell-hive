# Writing `HIVE.local.md`

Read before writing, ignoring, marking stale or pruning a `HIVE.local.md` file.

- **Where.** Write an entry with its date in the machine file when the fact holds whatever project you work in (an installed tool or its absence, a cloud profile and its region, a host alias); otherwise in the repository's file for one repository, and in the declared workspace's file for several (the repository's when no workspace is declared). Sessions of other projects write the machine file too: reread it immediately before writing and preserve every entry outside your update. Mark a failed entry stale with its date and cause before trying another way; an `unverified` entry keeps its mark and gains them.
- **No secrets.** In place of a value, name the file in the secret location that holds it or, for a machine fact, the tool's own credential file such as `~/.aws/credentials`, and point to `ACCOUNTS.md` for the test accounts of an environment. Which account a tool uses is a fact for these files, named without its credential.
- **`unverified` and size.** An entry marked `unverified`, which only audit-harness's [local instructions](../../audit-harness/references/local-instructions.md) mode writes, carries the date it was last seen, not confirmed: check it before relying on it, and when it holds replace the mark with that date. Keep each file at or under 50 lines by removing only entries marked stale; an `unverified` entry leaves only through that mode's curation with the user. When no stale entry remains, keep recording and recommend that mode in the final report.
- **Authorization.** This rule authorizes, in any flow, read-only ones included, writing these files and creating the machine file's folder; the machine file, its folder and the exclude entry that keeps it out of Git are an exception to «Scope and authorization»'s «Change only the current project», and the machine file is not global configuration. Before the first write inside a Git repository, ensure Git ignores them, in the repository's common `info/exclude`, shared by worktrees.
- **Helper.** Run `python3 -I <audit-harness-dir>/scripts/local_instructions.py <operation> --repo <root>` ([helper](../../audit-harness/scripts/local_instructions.py)); its `--help` lists the operations (`ensure-ignore`, `add`, `mark-stale`, `check`) and their arguments. Read its errors and `needs_curation`. Before `add` can prune stale entries, save their failure details as [local record](local-record.md) requires. Without the helper or Python, make only the authorized update by hand under the same rules. In a worktree, read [worktree](local-write/worktree.md) first. The repository's or workspace's file is the one support file kept at the root rather than in the support home.
