# What a `HIVE.local.md` entry records

Read before adding, updating or marking stale a `HIVE.local.md` entry. It covers `~/.config/hive/HIVE.local.md` and a project's or workspace's `HIVE.local.md`. How to write the file is [local write](local-write.md); local scripts are [local script](local-script.md).

- An entry is one line of at most 200 characters, its pointer included, that holds a fact and the date it was last verified; a stale mark, and the date and cause an `unverified` entry gains when it fails, do not count toward that length. Record a fact when all three hold: it says what this machine, account or environment has, lacks, uses or needs (a tool, app, container, port, host alias, script, cloud profile with its region, or the account or identity a tool uses, with what it serves, or a tool limitation here with the workaround that worked); a later session can run or check it; and this session confirmed it (a command exited 0, its result was observed, or a command was found missing). The line holds no sequence of steps, no account of what happened, and no version unless the project pins one this machine lacks. Never record in these files the result of a diagnosis, a count or measurement, whether a host answers right now, an event, the state of a work item (its worktrees, running processes or what its close kept), the app's design file or design library once its `DESIGN.md` holds them, or a fact the repository's tracked files state. An instruction of the user about this machine or project is a decision: save it in persistent memory, and keep in the file only one line for what it constrains here.
- When the line cannot hold the command with its flags, or reusing the fact takes two or more steps, save that detail in persistent memory under the topic `local/<slug>`. Name the slug after the fact's subject, and start it with the name of the folder that holds the file when that file sits below the folder that holds the project's `.engram/config.json`, so files that share a project never share a topic. Search that project for the topic before saving: update it when it exists and create it otherwise. Save it in the project «Persistent memory» names for an entry of a project's file, and in `hive-machine` for an entry of the machine file; when the memory tool rejects that name as unknown, save it through Engram's CLI with that project name (which creates the project), and when that fails too, save it in the current project and write that project's name in the pointer. End the line with its pointer, such as `→ engram:hive-machine/local/<slug>`. Read a detail only when the task needs its fact, and put in a child's brief the detail its task needs. Without Engram, write the line alone, since other hosts do not read a host's own memory. When a detail fails, mark its line stale as [local write](local-write.md) sets and correct the topic once another way works; before removing a stale line, write in its topic that it failed, with the date and cause, and leave the topic.
- A child reads the files and does not write them: it reports each fact it verified or found stale, and the main thread updates the right file.
