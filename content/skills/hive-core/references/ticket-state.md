# Ticket state

Read before moving, commenting on, searching or finishing a ticket, or writing its time. The tracker writes this leaf names are authorized by the global guidance's «Scope and authorization». This leaf sets when; [trackers](trackers.md) sets how to move, comment and attach.

- A ticket is done when its changes are integrated into the base branch; move it then, to the state the project uses for that, in the tracker [project settings](project-settings.md) assigns to its key.
- Before implementing a tracked ticket, move it to the in-progress state, except for an operational task, as «Scope and authorization» sets; do not start one already there unless the user confirms it is yours.
- At the delivery point (the integration, or the `ready` or `hold` stop) write the time of each ticket the work touched, and update it at the close, as [time](trackers/time.md) sets; an operational task writes it only when the user asks.
- The completion point is the merge into the base branch. When the delivery is `ready`, or a human reviewer's approval is pending, the open pull request is the completion point, reached at the stop [git-workflow step 8](../../git-workflow/SKILL.md) sets: the ticket stays in progress, and a later session that finds it merged runs a follow-up close.
- When the repository's `## Hive` declares `Completion`, a later completion point, the ticket moves to the state its tracker's value declares once the deployment verifies that the ref holds its change, as [flow-deploy](../../flow-deploy/SKILL.md) sets.
- Besides the moves and the time above, the global guidance authorizes these tracker writes: the comment and the attachments with a work item's evidence that its close writes before removing anything, as [trackers](trackers.md) sets; the comment that lists what a work item leaves open on purpose, as [close hygiene](close-hygiene.md) «Pending work» sets; and the business rules a work item adopts, at the moments [ticket write](business-ticket.md) sets. That write takes no question, though it changes a description the task did not create, and neither does correcting the rows of a rule card the work created in its design file.
- With `Other trackers`, every rule that reads, searches, moves or comments a ticket, or writes its business rules, uses all declared trackers: read and search in each, and move and comment each ticket, and write its business rules, in the tracker that declares its key prefix, the primary one for a key no tracker declares, including both tickets when one work item has one in each. Create new tickets only in the primary tracker. A declared tracker carries the same write authorization as the primary one.
