# Reuse before writing

Read before new code, or when a plan weighs approaches. The code is that of a task, and the plan is [flow-plan](../../flow-plan/SKILL.md) step 2. A task or an approach that fixes a defect first reads [defect fix](../build/defect-fix.md). Take the first rung that fully does what the task needs:

1. It need not exist: leave out features, options and flexibility the request does not name, and name them in the report. Remove dead code, redundant validators and stub references the change touches before you build on them.
2. The codebase already has it, such as a helper, component or pattern: use it as the surrounding code does when it is a sound base. It is not when (a) it is a workaround, such as one a comment marks or a guard [defect fix](../build/defect-fix.md) rejects as a fix; (b) it breaks `CODING_STANDARDS.md`, lint rules or a documented convention; (c) using it needs a boolean flag or branch inside it that only the new code turns on; or (d) the same logic lives elsewhere, diverging. Name it and its condition in the report. Do not copy or extend it; a workaround whose comment names its ticket follows defect fix step 4 instead. Except for (d) and that workaround, fix the base first, within the paths a child's brief names, when that is a small understood change, pinning its callers' behavior with a [tests](../build/tests.md) characterization test; that fix is part of the task, not a module touched against the request. Otherwise a plan offers it as an approach, and a build, or a child to its parent, reports it before building on it, for that step's choice for a cause; building on it once the user accepts follows that step's workaround handling. Prefer deleting to adding: make the smallest change that solves the problem, with no layer, abstraction or parameter the request does not need.
3. The standard library or a platform feature does it, such as a native input type or a database constraint, unless the project has its own; a design-system component beats a native control.
4. An installed dependency does it.
5. Only then write new code, or add a dependency after running `python3 -I <flow-build-dir>/scripts/check_package.py` ([check package](../../flow-build/scripts/check_package.py)) as the global guidance's package check sets, and say in the plan's approach or the report why rungs 2 to 4 do not fit.

No rung drops validation at trust boundaries, error handling that prevents data loss, security or accessibility.
