# Effects round

Read before planning or taking an external effect. Read it from [flow-plan](../../flow-plan/SKILL.md) step 4 for each plan, and from [flow-build](../../flow-build/SKILL.md) before a task takes an effect on an external system, as [external facts](external-facts.md) defines one. Reading this leaf authorizes no effect.

At [flow-plan](../../flow-plan/SKILL.md) step 4, for each plan:

1. List the effects on external systems that the tasks foresee, leaving out those the delivery answer or a rule already authorizes: commits, the push, the pull request, its merge, the ticket's moves and the write of its business rules. Group the rest into classes. A class of effect is one kind of action on one named target, such as access-policy changes in one cloud account or administrator merges in one repository, with its spending ceiling, zero when it spends nothing, and the tasks that use it.
2. Ask one decision per class, as [decision format](../messages/questions.md) formats a decision: in the delivery and review round when that round is asked, and in a round of its own when those answers are already in force or the repository gets neither question. When the target is a production one, the decision's `Situation:` line says so.
3. A class the user approved is the user's instruction for each effect of that class that the named tasks of this work item take, within the ceiling. It covers no other plan and no other work item, and no later work item reuses it. When a revision of the plan changes an approved class's kind of action, target, ceiling or tasks, its answer returns to unanswered and the class is asked again before any further effect of it. A class the user refused authorizes nothing and is not asked again: no effect of it is taken, and the tasks that need it are revised with the user as [flow-plan](change-folder.md#revise-a-plan-in-progress) sets, or skipped and reported under [unattended delegation](../../unattended-delegation/SKILL.md). A class left unanswered authorizes nothing either: in attended work each of its effects is asked when it arrives, and unattended delegation decides it as its step 4 sets.
4. No class covers these, and each keeps its own question: a production deployment, asked as [flow-deploy](../../flow-deploy/SKILL.md) step 4 sets; an effect that stops or interrupts a component serving users; an irreversible or hard-to-reverse effect; destroying or replacing infrastructure; changing or deleting data the task did not create in a non-local database; and creating accounts or records in a shared environment, as [test accounts](../local/test-accounts.md) sets.
5. Before each covered effect, record its target, the change and how to revert it in the task record, or, under [unattended delegation](../../unattended-delegation/SKILL.md) or bounded E2E coordination, in the [decision log](../../unattended-delegation/SKILL.md#decision-log) as its step 6 sets; the final report lists them. An effect no class was asked for is asked when it arrives in attended work, and decided as unattended delegation's step 6 sets otherwise. A delegated task's brief names its class, its ceiling and the cases of point 4.
6. Record one line per class in the proposal's `## Effects` section, or in the summary of a plan kept in the conversation: the class, its target, its ceiling, its tasks and the answer: approved, refused or unanswered. A plan with no effect on an external system adds no question. An operational task has no effects round: it asks each critical effect, as the global guidance's «Proportionality» sets.
