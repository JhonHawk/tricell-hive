# Checkpoint

Read at the start of a build or verify, after a compaction, and when pausing.

Keep a checkpoint in the `## Checkpoint` section of `tasks.md`: the stage and step, the last commit, the open findings with their decision, the next action, the paths of its before captures or that it has none, as one `--check` line, and the work's worktree when it has one, written with `tasks.py <folder> checkpoint` (`--finding` per open finding, `--check` per check recorded with its command, result and commit, `--worktree "<path> · <branch>"`, both of which later updates keep, and `--worktree none` once the worktree is removed, and, when pausing, `--unwritten "<text>"` with what no file holds yet, such as a decision or a next step known only to this session, `--unwritten none` once it is written; another session finds the worktree with `git worktree list`), or by hand when it cannot run. Name each stage packet the flow reads and any conditional leaf read besides them with `--rules "<flow>/<packet>.md · extra: <leaf>"` each time it reads one: the line joins the packets and leaves of the same flow, and a packet of another flow starts it again, and each code principle that changed a decision with `--principles "<name>"`; later calls keep both lines, `--principles` adds names to the line, and `--principles none` records that none did. With a plan kept in the conversation, or without a plan when the work has an approved example of [create-design](../../create-design/SKILL.md), keep it in a file named after the work in the host's temporary location, written at the start and after each task, adding the decisions, criteria, pending task IDs, viewer work key if any, the worktree's path and branch if any, the approved example's record if any, and each resource the work created outside the repository with its location.

The checkpoint also names the work's `Playbook`, the `Playbook` field of `proposal.md` or the `- Playbook: <kind>` line of a checkpoint file, which `flow-build` and `flow-verify` read at entry; [hive-mode](../../hive-mode/SKILL.md#pick-the-playbook) sets who writes it.

A close after the merge writes and reads its checkpoint, also after a compaction, with `tasks.py checkpoint --out <host temp>/<repo>-<change-id>-checkpoint.md`, since the change folder is no longer edited then.

When the host has a native task list, list the tasks in it at the start, and again with the remaining ones when you resume and the host does not show it again, such as after a compaction; mark each one in progress when it starts and completed when it is done. The native list is a live view: `tasks.md`, or the checkpoint file of a plan kept in the conversation, governs. Tasks are never declared in the viewer.

After a compaction during work, before you reply or end the turn, read in this order: the checkpoint, such as the change's `tasks.md` or a checkpoint file in the host's temporary location; the `HIVE.local.md` files «Local instructions» names; the packets its `Rules:` line names, or the leaves its flow links when a packet is missing; the extra leaves that line names; then persistent memory; add the active skill and one `git status`, and read code again only before editing it. Continue from its next step; a request the history shows already done gets no second report. Recover context with the memory's read tools, such as `mem_context`.

A restriction in a compaction summary that names no source may be your own earlier inference: keep obeying it, but before it is the only reason to stop work or ask a question, look for its source in the checkpoint, the visible history and the rule it seems to apply; when only a rule states it, follow that rule's own terms.

In `flow-verify`, keep the same checkpoint with the reviewed commit and each finding's decision.
