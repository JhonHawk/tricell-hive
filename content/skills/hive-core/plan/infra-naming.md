# Infrastructure naming

Read before choosing or creating the name of an infrastructure resource or a repository, or when existing infrastructure code generates it. A resource is anything a provider account or platform holds, such as a bucket, a role, a DNS record or an image repository. Reading this leaf authorizes no effect, which the [effects round](external-effects.md) governs.

1. **Find the convention.** It is the first of these the project has: the names it recorded, in a naming table, a decision record or its guidance; the shape its existing resources and infrastructure code share; the default of step 3. Read a provider's limits on a name (length, characters, uniqueness scope) in its current documentation, as [verify current state](../principles/verify-current-state.md) sets.
2. **Compare before copying.** Compare each name with that convention, also one that infrastructure code generates, such as a Terraform module's, instead of copying it into the plan or the change. Report each mismatch with the resource, its name and the conventional one: as a finding against recorded names, as a recommendation otherwise.
3. **Default.** `<project>-<component>-<environment>` in kebab-case; a resource every environment shares has no environment. Take the environment names from the `Environments` key of `## Hive` ([project settings](project-settings.md)); without it, recommend the name without an environment and say so. A code or image repository is `<project>-<component>`: follow the pattern of the organization's repositories of the same product or kind, a variant of a product with its other variants, listed as [external facts](external-facts.md) sets, or say that they could not be listed.
4. **Record.** List the names the work introduces and each exception the user accepts. The change that creates them adds them to the project's record; a child returns them to its parent. Without a record, recommend one in the project's documentation ([layout and retention](../../project-layout/references/layout.md)) and create it only when the user agrees.
5. **Existing names.** Renaming, keeping or accepting a mismatch as an exception is the user's decision. Keep an existing resource's name unless the request names the rename, which can change identifiers, data, permissions and deployment configuration.
