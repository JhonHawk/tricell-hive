# Infrastructure naming

Read before choosing or creating the name of an infrastructure resource or a repository, or when existing infrastructure code generates it. An infrastructure resource is one a provider account or platform holds, such as a bucket, a database, a role, a secret, a DNS record or a deployed service. Reading this leaf authorizes no effect: creating or renaming a resource follows the [effects round](external-effects.md).

1. **Find the project's convention.** Look for the names the project recorded, such as a naming table in its documentation, and for the names its infrastructure code and existing resources already use. Where a provider restricts a name's shape, such as its length, read it in the provider's current documentation, as [verify current state](../principles/verify-current-state.md) sets.
2. **Compare before copying.** When infrastructure code generates the name, such as a Terraform module or a deployment configuration, compare what it produces with the recorded convention instead of copying it into the plan or the change. With a recorded convention, report each mismatch as a finding that names the resource, the generated name and the conventional one, and add each new name the change introduces to that record. With none, compare with the default below and present a mismatch as a recommendation.
3. **Default, when the project has none.** `<project>-<component>-<environment>` in kebab-case, with the environment names of the `Environments` key of the project's `## Hive` section, read as [project settings](project-settings.md) sets. A shape the provider imposes or the project already uses wins over it; a resource every environment shares carries no environment. A repository or an image is `<project>-<component>`, with no environment: before proposing one, list the organization's repositories and follow the pattern the most comparable ones share, and for a variant of an existing product compare with the organization's other variants.
4. **Record.** When the project records no convention, recommend recording the names chosen in its documentation, as [layout and retention](../../project-layout/references/layout.md) sets, and create that record only when the user agrees.
5. **Existing names.** Whether to rename, keep or record a mismatch as a project exception is the user's decision. Keep an existing resource's name unless the request names the rename, which can change identifiers, data, permissions and deployment configuration.
