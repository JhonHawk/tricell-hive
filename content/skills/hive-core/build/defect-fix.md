# Defect fix

Read before the first edit of a defect fix. Read it also when a plan weighs the approaches to a fix for a defect. It applies in a build task, a round of fixes, an urgent production fix or a child's task, whoever found the defect. When a check fails, first decide as [Tests](tests.md) sets whether the code is wrong; this applies once it is.

1. Name the cause before you edit, and write it in the task's line or the report. The cause is the first place the code does what it should not, or fails to handle a state it should handle; the place where the failure surfaced is the symptom. Show it with the reproduction, the regression test seen failing, or the code you read; the same check passing after the fix is the evidence that the defect is gone. When finding the cause took more than two failed hypotheses or more than five large reads, propose the cheap always-on signal, such as a log line, an assertion or a metric, that would show it at first look.
2. Fix it at the cause, wherever it lies in the repository, with the smallest change that removes it, also when a finding names only the place where the symptom surfaced. Search the cause's literal values and callers for the same fault: fix each instance in the files the work already changes, and report the others as findings.
3. A guard, retry, fallback, default value, clamp, swallowed error or discarded state added where the symptom surfaced is not a fix, unless that state is legitimate: the code's documented contract, schema or specification allows it, or it comes from input that crosses a trust boundary. Then handling it there is the fix.
4. Choose between the cause and a workaround:
   - While an incident needs its impact reduced before the cause is fixed, mitigate first within existing authority.
   - Otherwise, when fixing the cause is a blocker under [reasons and blockers](../messages/reasons-and-blockers.md), such as a contract, stored data or a fix that is not a small understood change ([proportionality](../plan/proportionality.md)), report it before writing any workaround and let the user choose between the cause now and a workaround.
   - When the cause lies in a project outside the current one, ask the question [scope changes](../plan/scope-changes.md#an-external-project) sets, with a workaround here as the other option.
   - Make a mitigation or accepted workaround the smallest fix that holds, mark it with one comment line naming the cause and, once it exists, its ticket (under a project's comment lint, the marker [no comments](../review/no-comments.md) sets), and name it in the report as a workaround with the cause's location.
   - Unless this work fixes the cause, propose fixing it as [scope changes](../plan/scope-changes.md) sets for a ticket.
   - Later work that reuses a workaround whose comment names its ticket keeps or calls it without asking again, never copies it, and names both in the report; a child reports it to its parent.
5. For a repeatable error addressed by the work, enforce it at the earliest layer that prevents or detects it: architecture, types, actionable lint, tests, then prose. Run a negative check that shows the mechanism rejects the error, report its result, and remove procedural prose the mechanism replaces; when prose is the layer, record why earlier layers do not fit.
6. When two fixes that share one premise failed the same check, write the premise as one sentence and test it with an observation that would differ if it were false, before you write a third fix that assumes it.
7. A child fixes only within the paths its brief names, and reports to its parent each other instance, workaround and cause outside them instead of proposing a ticket.
