# Review findings and the round of fixes

Read when a verify's reviews and the user's answer are in. Read it before fixing anything: how to judge a finding and how to run the one round of fixes.

- **Confirm first.** Apply [Review evidence](review-evidence.md) before accepting a code finding. Report instead of fixing each finding the reviewer marked plausible rather than confirmed, or whose evidence you cannot confirm.
- **Library defaults.** Before fixing or sorting a UI finding or a defect already there whose cause the reviewer names as a default of the UI library, read the [precedence](../../create-design/references/ui-criteria.md#precedence) and apply it with the reviewer's evidence: drop an item it makes not applicable, naming it in the report with that reason, and keep every other one.
- **One round of fixes** for the user's corrections, every UI defect the change introduced, each confirmed blocking finding (P1 or higher on the scale of [close report](../close/close-report.md#findings)) and each confirmed P2 finding whose fix changes only files the change already changed and adds no task, dependency or effect; recommend approving no known defect as is. Fix only what each finding names, except that a defect is fixed as [defect fix](../build/defect-fix.md) sets, at its cause and with its other instances. Recheck and recapture as [UI verification](../ui/ui-verification.md) sets, and reread a correction of the UX reviewer's finding as [reviewer brief](../delegation/reviewer-brief.md) sets.
- **Sort the findings the round does not fix** without asking about each. Each takes the first of these decisions that matches it:
  1. Asked on its own, with fix now, ticket and ignore, its recommendation starred: a finding at a [security boundary](../build/security-boundaries.md), on stored data or on a contract, confirmed or not and whatever its priority; a P1 or higher not fixed, confirmed or not; and a P2 or higher UI defect that was already there in a region the change's layout affects, since fixing it widens the scope.
  2. One ticket proposal: every other P2 with a concrete failure scenario, grouped by shared area or cause, each member with its evidence, as the ticket rule of [scope changes](../plan/scope-changes.md) sets.
  3. Listed without a question: the rest, such as a P3 or an unconfirmed P2.

  List each in one line with its decision and how to reverse it, such as "H3 — listed (P3): say *fix H3* to fix it now". Ask the ticket proposal and the findings asked on their own as one round ([asking a round](../messages/questions.md)): before the push when the delivery stops for validation; at the `ready` stop with the pull request open, so a fix-now answer joins it, after which the pull request goes through [merge gate](../git/merge-gate.md) again before stopping; otherwise, including a finding that arrives after the push and the `automatic`, `direct-base` and `hold` deliveries, as the close's findings, as [close report](../close/close-report.md#findings-at-the-close) sets. A fix-now answer is fixed as a correction of the user. When the delivery does not stop for validation, the final report lists each difference from the approved example that remains.
- **States the UX reviewer did not cover:** cover each in your own walk, or report it as not verified, in the validation round or, when the delivery does not stop for validation, in the final report.
- **A second review** follows the round when a hunk of the fixes' diff lies outside a `.md` or test file and changes more than comment lines, or the fixes change a contract, limited to the fixes' diff and the callers of what changed. A fix whose every hunk lies in a `.md` or test file or changes only comment lines, and that changes no contract, starts no review and carries an `Unreviewed: <reason>` line in its commit message. A blocking finding of that review gets a local fix with its test and an `Unreviewed: <reason>` line in its commit message, or goes to the user when the fix is not local. Its non-blocking findings are sorted as above with no fix of their own, not in another round, since the round of fixes runs once; the report says the second review does not cover what the first one missed.
