# Wait for CI and merge

Read after a pull request's push, before its merge or a `ready` stop.

Wait for CI with one command that blocks until the run ends, such as `gh pr checks --watch` or `gh run watch --exit-status`, or the CI tool's own blocking wait, in the foreground or as a background command whose exit the host reports. When the host stops the command before the run ends, start the same command again, with no message between runs. Never redirect it to a file to read at intervals, never wait with a loop of sleeps and status queries, and send one message when it ends, not one per check or interval. Then answer the reviews as [PR reviews](pr-reviews.md) sets, and merge as the bullets below set: under `ready`, stop instead of merging once the current-base check below passes, and stop the same way while a human reviewer's approval is pending, unless an admin-merge grant lifts it. When a CI job fails, fix its cause from its log; rerun it only when the log shows a transient failure. After the merge or a push to the base, wait for the CI run it triggered there the same way, with `gh run watch <run-id> --exit-status`. When the host reports a background command's exit, run it in the background and run `flow-close` meanwhile: its message names the base CI as still running, and a cleanup leaves that command running. When it ends, report its result; handle a failure as this leaf sets, on a new branch from the base.

- Use the merge method the repository declares or its base branch's recent merges show, otherwise a merge commit; squash or rebase only when one of those sets it.
- Merge, or stop a `ready` pull request, only on a current base: run `git fetch` and `git merge-base --is-ancestor origin/<base> origin/<branch>`, which exits 0 only when the pushed head contains the base (the [state read](../../git-workflow/SKILL.md)'s `base_in_pushed_head`). When it fails, merge the base into the branch and push, which the merge or `ready` authorization covers, then wait for the new CI run, or without CI rerun the local checks the merge depends on, and merge or stop only when they pass; when the base moves again, repeat once, then report the merge as pending, or the pull request as not ready, with the reason. A repository that requires a rebase needs explicit authorization for that rewrite and its force-push. Under `ready`, only this bullet and the next apply.
- A review bot that has not reviewed the head commit when the CI wait ends does not hold the merge or the `ready` stop; name it as pending in the report.
- A human reviewer holds the merge in every delivery mode. Right before merging, read `gh api repos/<owner>/<repo>/pulls/<n>` and the reviews as [PR reviews](pr-reviews.md) sets. The hold lasts while `requested_reviewers` names a `User` or `requested_teams` a team, or while a person who reviewed, other than the author and bots, has no `APPROVED` as their latest review that is not `COMMENTED`; an approval counts on the head commit, or on one followed only by this step's base merges. During the hold, stop with the pull request open, never wait or poll, and tell the user in the report that the merge is pending and on whom, unless an admin-merge grant lifts it.
- Merging a pull request this work did not write needs the user's instruction in every case; the delivery mode in force covers only the fixes the work commits itself, and this work never merges its own pull request when that mode stops it open for the user.
- Never bypass branch protection, required reviews or required checks, except an admin merge of an authorized pull request whose required checks passed where the repository does not enforce its rules on admins. Any other bypass needs the user's explicit grant for that repository and action, which covers only that bypass, named in its report.
- A grant to admin-merge holds for the session, unless withdrawn, for its pull requests in the work's repositories whose required checks passed, or whose base requires none, as its rulesets and protection show (a required check that never reported is not none); name it in each report it covers. It lifts the hold of a reviewer whose latest review that is not `COMMENTED` approves an earlier commit, naming both in the report. It never covers the production branch (the last of `Environments` when it is not the base), a direct push, a promotion-path deviation, a requested reviewer, even one who approved before, or requested changes.
