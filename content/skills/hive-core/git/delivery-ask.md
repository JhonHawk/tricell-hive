# Asking the delivery mode and the review

Read before a work item's first edit, when no delivery answers are in force for this session and repository, or when the delivery in force is `hold` and the working tree holds uncommitted changes of an earlier work item. The modes and what each authorizes stay in the global guidance's «Delivery». These are gate questions: write and ask them with the templates of [gate questions](../messages/questions/gate.md), under their header and with no decision ID.

- **When.** Ask the delivery mode and the code review mechanism once per session and repository, in one round, before the first edit of the first work item that needs them: `flow-plan` at its step 4, beside each plan's own effects round, whose answers no later work item reuses, and `flow-build` before the first edit of work without a plan. Later work items reuse the answers in force, named in one line. Ask one again, alone, when the user asks to change it, when the delivery in force is `hold` and the working tree holds uncommitted changes of an earlier work item (the delivery, in the same round as the where-to-work question of [git-workflow](../../git-workflow/SKILL.md) step 3 when both apply), when this work item has a surface only the user can judge that the earlier one lacked, or when it needs a code review and none was asked. A mechanical change gets only the delivery question and no review. Work that leaves nothing to commit or publish, such as an operational task ([proportionality](../plan/proportionality.md)), deleting untracked or ignored files or repairing the local environment, gets neither. A repository whose `## Hive` declares `Delivery: direct-base` skips the delivery question and uses that mode, and still gets the review question for a change that is not mechanical. Commits not this work item's follow [foreign commits](foreign-commits.md).
- **Delivery.** Recommend `interactive` when the result has a surface only the user can judge, such as a screen, copy or a flow, or the project guidance requires human validation; `automatic` when the checks, the review and the verification establish the result, such as infrastructure, CI/CD, migrations or tooling with no visible change; otherwise `interactive`.
- **Review.** When the project guidance names a review mechanism that runs on your host, apart from a retired `Review:` key of its `## Hive` section, state it in one line instead of asking, saying how to change it and not ending in a question, such as "Review: Native: Claude Code /code-review, as AGENTS.md prefers; say so to change it."; that mechanism is the review answer in force. Otherwise ask which code review runs on the candidate before your validation or the push, worded to hold under every delivery answer, with a `Situation:` line that says what the change touches. The options are mechanisms, by these names in the session language: `Native: <host> <command>`, such as `Native: Claude Code /code-review`, only when your host has one, and `Agent: hive-review-code`. Recommend the one the project guidance prefers when it runs on this host, otherwise the native one, otherwise the agent, and say when the preferred one does not run here. A review the repository already runs on every pull request, such as Bugbot, is not an option: name it in the `Situation:` line. When the answer names another host's native review, run yours without asking; ask again only when your host has none.
- **Security review.** For each work item that touches a security boundary, as [security boundaries](../build/security-boundaries.md) lists them, ask in the delivery round, or alone before its first edit when the answers are reused, whether `hive-review-security` also runs on this candidate, recommending yes. Never ask or suggest a review by another provider's agent, nor check which other agents are installed: it runs only when the user asks for it. Unattended, it does not run.
