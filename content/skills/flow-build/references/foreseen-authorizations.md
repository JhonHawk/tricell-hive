# Foreseen authorizations

## When to read

Read in the round that settles the delivery and review questions, before a plan is declared ready or before the first edit of work without a plan, and when the work reaches an environment its plan did not cover. Substantial gates and their confirmation stay in [verification](verification.md#gate-selection-and-timing). Reading this reference does not invoke the build workflow.

## Ask for the foreseen authorizations

Ask for the authorizations the plan foresees for later steps, such as a costly check, publishing an artifact, or every effect beyond this machine that the work and its verification will need in each environment its scope reaches, classified as [effect authorization](../../flow-plan/references/effect-authorization.md) sets, while the user is present: in the round that settles the delivery and review questions, before the plan is declared ready or before the first edit of work without a plan, or, when no such round runs because an earlier answer, the request or a `Delivery: direct-base` repository already settles those questions, alone at that same point. When an explicit delegation or the user's leaving message activates unattended delegation before that round is answered, it is asked at activation, as [unattended delegation](../../unattended-delegation/SKILL.md#pre-authorization-round) sets. Name each with its scope, target and limits, and group effects as [effect authorization](../../flow-plan/references/effect-authorization.md) sets and the other actions as [questions](../../flow-plan/references/questions.md) sets for the steps of one objective, which keeps a production deployment apart. This is an exception to asking only at the decision point in [questions](../../flow-plan/references/questions.md): it covers what the plan, or for work without a plan the request, already names, and what those answers cover as [effect authorization](../../flow-plan/references/effect-authorization.md#what-an-answer-covers) sets; an effect neither covers is asked when it arises, together with every other effect that same step needs. When the work reaches an environment its plan did not cover, such as a validation requested in a later environment after the ticket's scope ended in an earlier one, including through a request to promote or deploy there, which covers only its delivery chain, ask when the work in that environment starts, before its first effect, for every effect its verification there will need, in one round. An authorization the user left unanswered stays unauthorized, also under unattended delegation. Under unattended delegation, decide the ones never asked under its Effects section instead of asking.
