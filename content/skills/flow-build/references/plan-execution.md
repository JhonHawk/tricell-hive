# Execute a retained plan

## When to read

Read while you execute or resume a retained plan, a change folder or a `<topic>.plan.md`, before you start, mark, verify, or commit any of its tasks. It holds the plan-specific part of [flow-build](../SKILL.md); reading it does not invoke another workflow.

## Keep the record

When a retained plan exists, keep its task list and current status consistent with the work: `tasks.md` and the status in `proposal.md` for a change folder. Update that status before reporting a delivery milestone, so the report and the record agree, and keep the update on disk only; [flow-close](../../flow-close/SKILL.md) versions the record once at close. Preserve either established `<topic>-plan.md` or `<topic>.plan.md` names; do not rename a valid retained handoff merely to normalize its filename. When the build starts, record the change's base commit in `tasks.md`. Mark a task complete only when its expected result is evidenced, as the next paragraphs describe. Record changed decisions, failed or omitted checks, and why a completed task was reopened; a revision of the plan itself follows [Revise a plan in progress](../../flow-plan/references/plan-revision.md). Keep raw output separate and link the useful evidence.

## Brief a child for a plan task

For a plan task, the brief names the change folder path and the task ID and tells the child to read, before editing, the task's block in `tasks.md`, the quoted request, when the proposal has one, and each `AC<n>` on its `Closes:` line in `proposal.md`, and the `design.md` sections the task links, and the skills and project documents that [delegation](../../flow-research/references/delegation.md#deliver-and-resolve-instructions) sets; when the brief and those files disagree, the files win. Do not paraphrase the task or its criteria in the brief: it carries what the files do not, such as the paths the child may modify, its authorized effects, and the commands to run.

## Mark and verify tasks

In a plan whose acceptance criteria are numbered `AC<n>`, tasks carry the markers defined in [plan criteria and markers](../../flow-plan/references/plan-criteria-and-markers.md#acceptance-criteria-and-task-markers), and only you, the orchestrator, change a marker or a task's status line during the build; a child's brief never assigns those lines. Set `[/]` when a task starts. A task whose test approach is `tdd` or `check` is verified by a `hive-verify-task` child:

1. When the implementer reports the task, set `[?]`. Launch the verifiers when the task's checkpoint is reached, not when the task is reported. A checkpoint is reached when each of its tasks is `[?]` or out of it: blocked before it reported (`[/]` with a `blocked:` line, and no verifier runs for it) or withdrawn by the user (with its line in the progress section). A task the user sent to redo is `[/]` again, and the checkpoint waits for it. When the checkpoint is reached, launch one `hive-verify-task` per task of the checkpoint, all together, before waiting on any of them, except that tasks whose **Locations** share a file are verified one after another, as the shared-file rule below sets, each as step 5 sets, with the change folder path, the task ID, the diff base (the task's own commits when the delivery mode makes commits, otherwise the working tree), and the skills and project documents that [delegation](../../flow-research/references/delegation.md#deliver-and-resolve-instructions) sets. The risk criterion, the `Checkpoint` field and the rule for a plan whose tasks omit it are in the "Checkpoints" paragraph of [plan criteria and markers](../../flow-plan/references/plan-criteria-and-markers.md#acceptance-criteria-and-task-markers); apply them from there. A task that was already `[x]` and goes back to `[?]` or `[/]` is verified again at the moment its own rule sets, without waiting for a checkpoint: at the UI gate of the accepted candidate for a walkthrough correction, as soon as a fix after its commit is applied, and, for a plan revision during the build, as soon as the task is `[?]` again. The acknowledgement of a background launch is not the verdict: its completion signal is, and the paragraph after this list says what to start while it runs.
2. Keep one current result for every criterion across rounds. A scoped re-verification replaces only the results it checks; retain each other result and its evidence while that evidence remains valid. When a fix affects earlier evidence, re-verify the affected criteria too. When every current criterion result is `met`, open the cited `path:line` or read the cited output to confirm it says what the verdict claims, then set `[x]`.
3. When any criterion is `not met`, even if others are `cannot verify`, set `[!]` with a line naming the round, the `AC<n>`, and the reason, and return the findings to the implementer for one fix round. Then set `[?]` again and launch one re-verification of the criteria the previous round marked `not met` and any others whose evidence the fix affected, as step 2 sets; its brief names them. If it again reports `not met`, set `[!]` again with the round-2 line. When every remaining `not met` has a fix that is small, stays within the task's **Locations**, changes no scope, contract, criterion or decision the user made, and admits only one plausible correction, do not ask the user: return that correction to the implementer as one more fix round, then set `[?]` again and launch a third verification of those criteria, recording its result like the earlier rounds with a round-3 line. Otherwise, or when the third verification also reports `not met`, set `[!]` with that round's line and ask the user.
4. When the current results have no `not met` but any criterion remains `cannot verify` because a prerequisite is missing, including one retained from an earlier round: create one that [runtime and UI gates](../../flow-verify/references/review-and-gates.md#runtime-and-ui-gates) lists as local, such as seed data or a local service, and re-verify those criteria; for one it leaves to the user, leave `[?]` with a line `blocked: <prerequisite>` and report the task as blocked; do not start a fix round. Once the prerequisite is available, re-verify the blocked criteria before marking the task `[x]`.
5. What makes the verdict independent is the verifier's context, not its model: launch `hive-verify-task` as a new child without the parent's history, as the shared delegation rule sets, and give its brief only what step 1 names, never the implementer's report, reasoning, or claims of success; it reads the plan's files and reruns the checks itself. Launch it on its configured `verifier` profile, which on the hosts that set one is a different model from the implementer's; that difference is a preference, not a condition. When the host cannot set a model, the configured model equals the implementer's, or the verifier's model is unknown or inherits the session's, launch it anyway and do not ask the user which model to use. Never launch the verifier on a smaller model or at a lower effort than the implementer's, such as a smaller model of the same family: when its configured profile is smaller, launch it on the implementer's model through the launch's model option when the host offers one; when the host offers none, launch it as configured and record the difference. In the plan's progress section, record the implementer's model and the verifier's, each as observed (the host or tool reports it, such as a child's launch result or metadata) or as "configured, not observed" (it comes from the role's profile or the `model` in its installed file); a child's own statement of its model is not a host report and does not discount its verdict. When `hive-verify-task` cannot run, for example because its model is unavailable or out of quota, launch it once more on the implementer's model with the same brief; when it still cannot run, leave `[?]` and ask the user whether to wait and retry, verify with a model the user names, or accept the task unverified.
6. Apply the user's decision: accepted sets `[x]` with a line `accepted unverified by the user: <reason>`; redo sets `[/]`; withdrawn removes the task from the list and records the reason in the progress section, and a task that depends on the withdrawn one goes to the user with the rest of that decision. Remove the withdrawn task's changes before the next commit, or before the result is presented when the delivery mode makes no commits; when they cannot be separated from a kept task's changes, ask the user.

Do not wait idle while verifications run. Start the next pending task by these rules:

- A task that depends on a task of its own checkpoint starts as soon as that task is reported, and committed when the delivery mode makes commits, without waiting for a verdict.
- A task that depends on a task of an earlier checkpoint, and a task without a checkpoint that depends on a task awaiting its verdict, start when those tasks are `[x]`.
- Two tasks whose **Locations** share a file never run at the same time: do not start the implementation, a fix round, or a verification of one while the other is being implemented, fixed, or verified, so each task's commit and diff hold only its own changes. Every rule in this reference that launches an implementation, a verifier or a fix round applies this one first.
- A task that reports after the verifiers of its checkpoint were launched, such as an added, unblocked or redone task, gets its own verifier when it reports.
- A task whose criteria are all `met` while a dependency in its own checkpoint is not yet `[x]` stays `[?]` with a line `waiting: T<n>` naming that dependency, and becomes `[x]` when that dependency does, unless the dependency was fixed or redone meanwhile, which the last rule below covers. When the user accepts the dependency unverified, the waiting task becomes `[x]`, because the tree did not change.
- A fix round for a rejected task starts only when every verifier of its checkpoint whose task shares a file with it has returned. When two rejected tasks share files, run their fixes one after the other.
- When a fix or a redo of a task lands, verify again, against all their criteria, the later tasks that depend on it, directly or through another task, and the other tasks whose **Locations** share a file with it, when they are not merged yet: one that is `[?]` or `[x]` is verified as soon as any verifier already running for it returns, and one that is `[/]` or `[!]` gets all its criteria checked at its next verification instead of only those it failed. A correction round of a walkthrough is not such a fix: its tasks are verified at the accepted-candidate gate, as the reopening rule in step 1 sets. A task whose re-verification reports `not met` goes to `[/]` with a line `reopened by the fix of T<n>` for a fix round, and its fix counts as a fix for its own dependents. A reopening does not spend the task's fix rounds; after it, step 3 applies as for any task. When a task would be reopened a third time, take it to the user instead.

Only when no such task or verification remains, wait on the completion signal under the shared waiting rule.

## Commit tasks

When the delivery mode makes commits, commit each task yourself when the implementer reports it, before its verification, staging only that task's paths and naming the task ID in the message, such as `(T2)`, following the repository's commit convention. Commit each later change to it the same way, as an additional commit named `(T<n>)`, never an amend, because [git-workflow](../../git-workflow/SKILL.md) forbids rewriting history: a fix round, a reopening's adjustment, and a fix that the full suite, the security review, the UI gate or the user's validation requires, committed in the stage that asks for it, under the general [commit rule](../SKILL.md#execute-in-verifiable-increments). A task the user withdraws is undone with a revert commit of its commits; when the revert does not apply cleanly because a later task changed the same lines, ask the user. A commit records a task, not a verdict: the work is published for merge only when every task is `[x]`, and the first rendered view and the UI gate of a task with a rendered UI effect still run before that publication, in [flow-verify](../../flow-verify/SKILL.md) as [the UI gate](../../flow-verify/references/ui-gate.md) sets. When the work pauses, the report names the tasks committed but not yet verified. Keep the change folder out of these commits, since [flow-close](../../flow-close/SKILL.md) versions it.

## Other tasks

Other tasks, such as `characterization`, tasks without a test approach, and delivery tasks, go from `[/]` to `[x]` on the evidence of their own check. `hive-verify-task` is part of the authorized implementation and needs no separate approval. It checks the task against the plan; it is not a code review and does not replace `hive-review-code` at publication or `hive-verify-change` and `hive-review-ux` at the end of the change. A plan without `AC<n>` criteria uses only `[ ]` and `[x]`, and you mark a task on the evidence of its check.
