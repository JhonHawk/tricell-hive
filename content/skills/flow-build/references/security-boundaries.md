# Security boundaries and dependencies

Read when changing untrusted inputs, permissions, process execution, public data exposure, or dependencies. Apply the affected boundaries using existing project controls; this is not a mandate for an unrelated security audit.

- Identify the actor, resource, operation, and tenant or ownership boundary. Enforce authorization at the trusted execution boundary, including denied and cross-owner cases where applicable; authentication alone does not establish permission.
- Validate external data at runtime. Keep data separate from executable syntax through parameterized queries, structured process arguments, and context-appropriate output encoding. Inspect downstream interpretation even when the first API accepts an argument array; avoid interpolating untrusted values into shell, query, template, or path expressions.
- Preserve useful internal diagnostics while keeping secrets and unintended internal fields out of public errors, responses, logs, and retained evidence. Check the affected failure path as well as success.
- Before introducing, updating or installing a dependency, run [Check a dependency before installing](#check-a-dependency-before-installing). Also check its installation and build scripts and its runtime or build exposure, and use the project's existing lockfile, provenance and advisory controls. Review automated remediation before running it: it may execute project-controlled scripts or use configured registries.

Select checks for the actual trust boundary and reachable failure mode. Report findings with preconditions, impact, and evidence rather than treating a severity label or tool exit as the conclusion. This procedure does not authorize exploitation, credential rotation, or unrelated remediation.

## Check a dependency before installing

Run this before you add, update or install a package or tool from a registry, inside or outside a build, including a one-off run such as `npx`, `uvx` or `pnpm dlx`. An install can run the scripts of the package and of its dependencies on this machine, so the check comes first, wherever the project will run.

Every install takes steps 4 and 5. Steps 1 to 3 also apply to each package you name on the command or add to a manifest. An update with no package argument, such as `pnpm update`, also takes step 2 for the versions it changes. An install that only restores the lockfile, such as `pnpm install` with no package argument, takes only steps 4 and 5. Where this section says to ask the user, a delegated child stops and reports to its parent instead. A check holds for the same package and exact version for the rest of the session.

1. **Confirm the package.** Check that the exact name exists in its registry and is the package you mean: its repository, publisher and description match the purpose, and the name is not a near-miss of a better-known package. A name a model suggested, including your own, is unverified until this check. For a private or internal package, confirm instead that it resolves from the private registry assigned to its scope or index, and that the same name either does not exist in the public registry or cannot resolve from it, since a public package under a private name is a known attack.
2. **Pick a version the release cooldown accepts.** When the project sets a minimum release age, such as pnpm's `minimumReleaseAge`, pick a version at least that old, also for a one-off run whose runner does not apply it. Never lower or bypass the cooldown without asking the user. For a one-off run, name that exact version, such as `npx <name>@<version>`, never `@latest` or no version, so what runs is what you checked.
3. **Look up advisories for that exact version.** A version can be safe while the next patch is compromised. Query `POST https://api.osv.dev/v1/query` with `{"version": "<version>", "package": {"name": "<name>", "ecosystem": "<ecosystem>"}}`. Ecosystems: npm, pnpm, yarn and bun → `npm`; pip and uv → `PyPI`; Maven and Gradle → `Maven`; Go modules → `Go`; Cargo → `crates.io`; NuGet → `NuGet`; RubyGems → `RubyGems`; Pub → `Pub`. Send only a public package's name: never query OSV with a private or internal package, as the global rule on requests to third-party services sets.
4. **Scan the lockfile**, since the package's dependencies install with it and run their own scripts.
   - When the package manager can update the lockfile without installing, such as `npm install <name>@<version> --package-lock-only`, or `pnpm install --lockfile-only` after adding the exact version to the manifest, do that and scan before installing. Otherwise scan right after the install and report that the scan came after it.
   - Use only a scanner that keeps private package names off third-party services, in this order: the project's configured advisory scanner when it meets that condition; otherwise `osv-scanner --offline --download-offline-databases <project-dir>` when `osv-scanner` is installed, since offline mode sends no project or dependency names; otherwise the package manager's own audit, such as `pnpm audit` or `npm audit`, only when every dependency comes from that manager's default registry, because the audit sends every package name in the tree there. For Go modules, also run `govulncheck ./...` when it is installed.
   - An empty result means no known advisory, not a safe package. A record whose ID starts with `MAL-` marks a known malicious package.
5. **Resolve by severity**, using the advisory's rating. An advisory without a rating takes the rating of a CVE or GHSA alias; with none, treat it as CRITICAL or HIGH.
   - A compatible fixed version that the cooldown accepts exists, meaning a patch or minor, or a major you verified as non-breaking: install that version and report the change. A fix that exists only in a new major is a version-bump decision: for MEDIUM or LOW, proceed and report the bump; for CRITICAL or HIGH, treat it as having no safe path, and so is a fixed version the cooldown still rejects.
   - MEDIUM or LOW with no fixed version: proceed and report the severity and the affected range.
   - CRITICAL or HIGH with no safe path, or a `MAL-` record: stop and ask the user before installing, every time. The install itself is the exposure, and a compromised install script cannot be rolled back.
   - A private package confirmed in step 1: proceed and report it as not checked against advisories. Only its own lookup is skipped; its public dependencies still go through step 4 and these rules.
   - Any other check that could not run, for lack of a tool, network or a scanner that keeps names private: say so before installing; ask the user when a package is new to the project or its version changes, and proceed and report it when the install only restores the lockfile.

Report what this check changed or left open in the work's report: the versions you swapped, the advisories you accepted, and the packages or scans you could not check.
