# Defect fix

Read before the first edit of a fix for a defect, and when a plan weighs the approaches to one: in a build task, a round of fixes, an urgent production fix or a child's task, whether the user reported the defect or a check, a review or a verification found it. When a check fails, first decide as [Tests](../SKILL.md#tests) sets whether the code is wrong; this applies once it is.

1. Name the cause before you edit, and write it in the task's line or the report. The cause is the first place the code does what it should not, or fails to handle a state it should handle; the place where the failure surfaced is the symptom. Show it with the reproduction, the regression test seen failing, or the code you read.
2. Fix it at the cause, wherever it lies in the repository, with the smallest change that removes it, also when a finding names only the place where the symptom surfaced. Search the cause's literal values and callers for the same fault: fix each instance in the files the work already changes, and report the others as findings.
3. A guard, retry, fallback, default value, clamp, swallowed error or discarded state added where the symptom surfaced is not a fix, unless that state is legitimate: the code's documented contract, schema or specification allows it, or it comes from input that crosses a trust boundary. Then handling it there is the fix.
4. While an incident needs its impact reduced before the cause is fixed, mitigate first within existing authority. Otherwise, when fixing the cause is a choice the global guidance's «Scope and authorization» makes a blocker for a defect that blocks work, such as a contract, stored data or a fix that is not a small understood change (its «Proportionality»), report it before writing any workaround, and the user chooses between fixing the cause now and a workaround. When the cause lies in a project outside the current one, ask the question «Scope and authorization» sets for code in an external project, with a workaround here as the other option. Make a mitigation or an accepted workaround the smallest fix that holds, mark a code change with one comment line that names the cause, and name it in the report as a workaround with the cause's location. Unless this work fixes the cause, propose fixing it as the global guidance's «Scope changes» sets for a ticket.
5. A child fixes only within the paths its brief names, and reports to its parent each other instance, workaround and cause outside them instead of proposing a ticket.
