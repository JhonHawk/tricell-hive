# Verification by risk and surface

Read when planning or executing integration, runtime, UI, performance, hardware, test replacement/removal, promotion, deployment, or costly checks. The build skill owns the essential test-first and completion procedure; this reference selects depth and timing. Follow the project's established commands, environments, and delivery policy. Verification does not grant deployment, publication, destructive effects, or external access.

## Select evidence for the change

Identify the failure being guarded against, affected users and dependencies, reversibility, and boundaries crossed: persistence, permissions, processes, devices, or concurrency. Classify the changed surface, not the entire repository. A text edit in a busy service does not automatically need load testing; a landing page's payment flow is not merely presentation.

Choose the lowest-cost layer that can detect the relevant failure. The following are candidates, not a checklist to run in full for every change:

| Changed surface | Useful evidence | Escalation trigger |
| --- | --- | --- |
| Informational landing or presentation | Build/checks when available; rendered layout, links and actions, keyboard access, relevant viewports and console errors | Forms, authentication, payments or data changes add their functional and security checks |
| Application or API | Behavior tests, changed contracts and persistence integration, a real affected journey; UI review when visible surfaces change | Roles, tenant isolation, migrations, retries or shared middleware widen coverage |
| Mobile | Host/component tests and affected emulator/device journey | Lifecycle, offline, permissions or sensors require corresponding states; release candidates and representative devices when release fidelity matters |
| Driver or firmware | Isolated logic tests, cross-build/static checks, appropriate kernel/RTOS integration or simulation | Physical timing, interrupts, energy, device interaction or recovery require target hardware evidence; simulation alone cannot establish it |
| Transactional or high-throughput path | Invariants, real persistence, targeted concurrency, duplicate/retry/partial-failure checks | Query, transaction, cache, pool, queue or retry changes can require representative load and recovery tests |
| Configuration or agent guidance | Schema, diff, consistency and readback checks available in the project | Runtime effects need corresponding runtime evidence; model pilots require explicit authorization when paused |

When replacing or removing tests, compare the old and new scenarios, fixtures, preconditions, and assertions; justify any retired coverage against the current contract rather than preserving obsolete tests or assuming similar assertions cover the same behavior.

## Gate selection and timing

Apply the shared authorization rule before substantial gates. Use existing project conventions to discover required versus offered gates, preferred mechanisms, and where availability can be checked. Keep capability, preference, execution authorization, and technical verdict distinct. Do not launch a review to test availability or infer approval from repeated historical choices. Present the concrete scope/candidate, mechanism, environment, relevant cost or effects, and expected evidence when a decision is missing. A plan may carry explicit advance authorization; its mere inclusion of a check is insufficient.

| Boundary | Required decision or evidence |
| --- | --- |
| Research / task entry | Inspect state, risks, project commands and automatic triggers; propose experiments exceeding ordinary authorized investigation before running them. |
| Plan / implementation brief | Select applicable checks, prerequisites and pass criteria; place substantial gates and resolve or record execution authorization. Bounded read-only feedback on a saved implementation plan follows the [plan-review procedure](../../flow-plan/references/plan-review.md) as part of planning; broader review services remain subject to gate authorization. |
| Build iteration | Run targeted tests and routine checks; inspect the implementation's own diff. This is not a dedicated independent code-review gate. Per-task verification by `hive-verify-task` follows the build skill. |
| Local candidate | Complete applicable local in-vivo and UI verification, using the built artifact for final UI/runtime validation where the stack has a build step; a rendered UI effect adds the independent UI review and in-vivo children when the UI gate below requires them. Propose dedicated code review separately unless the delivery decision already settled it. |
| Publication / integration | Review the identified candidate with the selected mechanism, if one was selected, and inspect actual CI coverage. Account for automatic review/deployment effects before the push or PR event that triggers them. |
| Predeploy | Reconcile the complete promoted candidate, affected destinations, migrations, compatibility, recovery and reusable prior evidence. A promotion label does not prove the candidate was reviewed. |
| Postdeploy | Verify active artifact/revision and routine health per affected surface. Offer the functional in-vivo/UI gate in that environment unless its concrete execution is already authorized. |
| Close | Reconcile evidence and remaining gates. Separate published, healthy and functionally accepted; keep pending, failed and blocked checks visible. |

Large integration suites, load/soak, hardware exercises and external-service scenarios need scope and effect assessment, regardless of whether their command starts locally. Their phase follows the required environment and artifact, not a universal final-stage checklist. For authorized re-review, focus on affected changes and invalidate previous evidence when relevant inputs change; do not assume unlimited rounds or a broader mechanism are covered.

When the selected mechanism is `hive-review-code`, or any review that does not verify its own findings, send each P0 or P1 finding, and any finding that would block the merge, to a `hive-refute-claim` child before acting on it. Fix confirmed and plausible findings under the normal rules, drop refuted ones with the refuter's evidence, and report both. Native reviews that already verify each finding, such as Claude Code's `/code-review` at medium effort or above, need no second pass.

When a mechanism reports its own severity levels, map each finding to P0–P3 by the same observable impact before applying these rules. Fix P0 and P1 findings that are confirmed or plausible after refutation, or verified by a mechanism that checks its own findings. Fix a P2 finding the change introduced when the fix is local and inside the change's scope; otherwise handle it under the shared incidental-findings rule. Report P3 findings without fixing or recording them elsewhere; they are not defects under the shared incidental-findings rule. Dispose of pre-existing findings under the shared incidental-findings rule. Review each pull request in full once. Re-review at most once, limited to the diff of the fixes against the reviewed commit, and only when a P0 or P1 fix changed logic or a contract; a finding still open after that round, including a new one it reports, goes to the user as a decision. Later edits to the same pull request, including added scope, never start another full review: report what changed since the reviewed commit and ask the user whether to review it. Use one code reviewer per candidate, and add `hive-review-security` only when the change crosses a boundary in [security boundaries](security-boundaries.md) and within the agreed review authorization.

A technical verdict does not authorize delivery. A required gate declined or unavailable remains an unmet transition condition; an optional gate may be deferred explicitly. Interpret actual findings and terminal status rather than treating absent comments, a queued run, or a non-failing check as approval.

## Runtime and UI gates

Decide local in-vivo applicability from the actual changed behavior. When needed, include and execute the relevant walk within authorized implementation without asking whether to run it. When judged unnecessary, explain why and ask whether the user wants it anyway, offering Skip (Recommended) and Run with the concrete proposed scope. Reuse an explicit answer for the same scope; do not repeat this question per task or check. While unanswered, continue independent work and record the optional walk as pending, not declined or passed. This does not waive a required gate, override paused model pilots, or grant external effects. Deployed-environment walks retain the explicit authorization boundary above.

For local implementation, always exercise the applicable changed path and relevant failure or permission states. Perform the corresponding deployed-environment exercise only within its explicit gate authorization. A mocked integration or source inspection does not establish behavior in the running system. Resolve authorized local setup, accounts, roles and seed data; access only the user can supply remains a reported prerequisite.

Use dev/HMR for iteration. For the final in-vivo or UI handoff, build and serve the compiled candidate using the project's production-style start or preview command where the stack distinguishes build from dev. Services without a build step use their normal runtime. Build only the affected applications and required dependencies, not every app per edit.

Default the handoff stack to local frontend, backend, database and necessary dependencies unless a different target was explicitly specified. Check effective connections, including build-time frontend URLs and backend persistence targets, without exposing credentials; localhost in the browser does not prove the whole path is local. Prepare authorized local accounts, roles and seed data before the walk. Report missing dependencies and any uncovered integration; never silently substitute a remote environment. External authentication, messaging, payments and similar effects need their own authorized boundary.

For UI changes, local rendered and interactive inspection is part of completion, not an optional gate: layout, content, feedback, error recovery, responsive behavior, keyboard/focus and accessibility relevant to the change. Capture the prior state when comparing an existing interface and practical before editing; missing baseline limits claims of visual improvement, not unrelated functional checks. Automated accessibility or screenshot checks support, but do not replace, inspection of the affected experience.

Compare changed UI with the selected application/area’s accepted shell and screen pattern, including justified differences. Distinguish pattern conformity, functional behavior, and user suitability. A screenshot diff against a prior baseline does not establish that a new screen follows a different reference screen’s pattern. When shared UI code changes, inspect affected consumers across applications according to impact.

Any change with a rendered UI effect, other than one that changes only text or a style value without altering layout, state, or flow, requires two independent children on the built local candidate before completion is reported: a `hive-review-ux` review and a `hive-verify-change` in-vivo check of the changed journeys. They are part of authorized local implementation and need no separate approval. The implementer checks its own change only with bounded inline checks, such as a `read`, the console, or a one-off `eval`; the walk and any measurement suite belong to these children. Brief the reviewer with [UI review criteria](ui-review-criteria.md), the affected screens, the base revision for comparison, realistic and extreme data, and the viewports and themes; do not pre-rate findings or say what to ignore. Resolve its findings before completion: fix introduced or worsened Blocker and High findings and re-review, and dispose of pre-existing ones under the shared incidental-findings rule. Run both in parallel with isolated data, accounts and browser sessions; otherwise serialize state-changing work. If a child, the browser or the stack is unavailable, report the gate as not passed. Backend or infrastructure work without a UI effect needs neither; add other specialists by actual risk rather than by default. The implementer checks such a text or style change in the rendered page at the affected viewports, with the longest realistic text and in each theme; if the check shows it alters layout, the two children apply.

Before driving a browser, read [browser automation](browser-automation.md) and pass it to children that drive one.

## Human UI handoff

When a change adds or rearranges a layout, such as a new screen, dialog, or component composition, show the user the first rendered version as soon as it exists: one capture per changed view at a desktop width with realistic data volume, taken on the dev server as a bounded check. Ask whether the composition is right as a question in text, which ends the turn even while children keep running, opening with the in-progress item; keep independent work, such as backend tasks and code review, running in parallel rather than holding it for the answer. Do this before the independent UI review, so a composition the user rejects is not reviewed and repaired first. The final validation still happens on the built candidate.

While the user requests corrections during a validation pause, whether to text, behavior, or layout, run one correction round per request: apply the correction; write its test in the same round when it alters behavior of a kind the build skill's test-first rule covers; run the affected tests; rebuild; capture the affected views; and ask again right away, as that question in text, which ends the turn even while children keep running, opening with the in-progress item. Between rounds, run no `hive-review-ux`, `hive-verify-change`, `hive-verify-task`, or dedicated code review. When you offer alternatives, sketch them as [UI planning](../../flow-plan/references/ui-planning.md) describes.

When the user accepts, run one gate scoped to the diff between the last candidate that passed the gate and the accepted one: `hive-review-ux` on the changed views, `hive-verify-change` on the journeys that touch changed files, and `hive-verify-task` on the tasks whose files changed. If no gate has run yet, run the full gate. When a gate child reports an introduced Blocker or High finding, fix it, show the user the result, and re-review it only with the child that reported it. The delivery's dedicated code review runs on the accepted candidate, at the point the delivery mode already sets.

Markers: when a correction changes the files of a task marked `[x]`, set that task back to `[?]` with a line `reopened by correction round <n>`, and verify it at the accepted-candidate gate. Record a correction outside the plan's tasks in the progress section; `hive-verify-change` covers it at that gate.

During every UI walk before a human validation pause, including the implementer's own walk of a text or style change, capture a small useful selection of changed screens and relevant states; do not repeat the walk solely to produce images. The assigned reviewer returns screenshots, observed state and reproduction steps to the orchestrator without editing the application. Grant a specific temporary evidence destination when delegating; an observe role does not imply general filesystem write permission. If the host cannot capture there, return observations and have the orchestrator capture within its available tools. Avoid credentials and sensitive user data in images.

Use the global UI-image placement and hygiene rule: put review captures where that rule places them and link or display them in the handoff. Offer them in the handoff even when the user did not ask. Preserve them until the session ends; hygiene then removes the task's review images except those the user selected to keep. Screenshots do not replace interactive checks.

For UI work awaiting human validation, leave the same verified built stack running, confirm its URLs are reachable, and name the candidate and relevant local targets. Provide clickable application URLs and the required account/role without secrets. Write the walkthrough as one block per flow, headed by the ticket and a short description (`ARK-123 - <description>`), followed by bullet steps from a named starting point: preconditions such as the role and signed-in state in parentheses on the first step, navigation with `>` between screens, the action, and what the user should see. Condense obvious steps. When several tickets share one flow or module, cite the ticket in the step it concerns; separate flows get separate blocks. Link the selected captures, state what the agent verified and what remains for the human, and explain how to stop task-owned processes. This walkthrough is a manual validation request under the global guidance: it ends with the question in text, without the native question tool, and the delivery, route and close questions are unchanged. Do not claim availability beyond the host's process lifetime; disclose inability to keep the stack alive and give the exact restart instructions.

## Frequency and coverage

- During implementation, run the small checks that give feedback on the current behavior. Use the project's affected-test selection while iterating, such as a related-files or filter command that the project guidance names, or the changed package's tests when the project has none, and inspect transitive impact; file proximity alone may miss affected callers. Widen to the whole package suite when a schema, a migration, test setup or test configuration, or a widely shared module changes. Widen to the whole repository's suite when the lockfile, the workspace configuration, or the CI configuration changes. A selection that selects no test leaves the change not verified, not passed. Do not rerun a full suite on an unchanged candidate; a repeat to detect flakiness is a declared exercise, announced before it runs.
- Each of these is an incidental finding, reported with its evidence; its failure scenario is the measured cost, meaning what was stopped or waited on, for how long, and how many times: a deadlock or lock-timeout error in tests (for example Postgres `40P01`); a test run that goes 3 minutes without new output and is stopped; a test that fails and then passes on an unchanged rerun; a local test run over 5 minutes; a verification round (a `hive-verify-task`, `hive-verify-change`, or `hive-review-ux` child) over 5 minutes; a post-merge CI wait over 5 minutes. Propose the findings about the project's test infrastructure or CI for the project's tracker. Report the findings about the cost of the workflow itself, the verification rounds, as a guidance finding for the Hive session, with no ticket in the project, under the global rule for findings that belong to another project; they accept the answer "don't mention again" but not "open a ticket".
- At a coherent increment's close, verify the final affected scope and applicable build/integration/runtime/UI gates. Avoid duplicating every edge case at every layer.
- When a local integration run makes no progress for several minutes, such as a database setup or teardown that does not finish, or it shares local services such as a test database with another session, stop that run and let the pull request's CI run the integration suite instead of waiting on it; report which check ran where.
- At integration or promotion, satisfy the project's broader regression and release gates. Confirm what CI actually executes; do not assume it covers a missing check. Local checkpoints, branch publication, merge and release are distinct boundaries, governed by the project's policy and existing authorization.
- After a merge or push you performed to the base branch, find the CI runs its commit triggered there; skip this for a repository that declares `Delivery: direct-base`, whose pushes wait for no CI. Wait for a run before reporting the integration complete only when it executes a job that tests a changed file and did not already run on the pull request, such as one shown there as skipped or absent; without a pull request, every such job counts. A job tests a changed file when the file is in the packages it tests or in their dependencies, or when it runs the whole repository's suite. Judge a job by what it tests, not by the filter that triggers it, which can be broader. Also wait when the workflow does not show what a job tests, or when a workflow that the push should trigger has no run listed yet. Otherwise, do not wait: give the run's link as a reminder. A deployment or publication job that the push triggers falls under the deployment checks below, not under this rule. Wait on the run's completion signal under the shared waiting rule. Until the run passes, the ticket move that global guidance makes at integration and the closing of the change folder wait; if the turn must end first, report the open run as a pending item.
- When a run you waited for fails, read its failed jobs' logs. A failure that the base branch's previous run already had is not this change's: handle it under the shared incidental-findings rule. For an infrastructure failure, such as a registry or network timeout or an unavailable runner, rerun only the failed test jobs, once; this rule authorizes that rerun, not a rerun of a deployment or publication job. When the rerun fails too, or the failure comes from the change's code, the integration is not complete and its ticket stays out of its completion state: report the failed jobs, the diagnosis, and the run link as a pending item.
- After authorized deployment, identify the artifact or revision actually served in each affected target and check routine health: health endpoints and the project's smoke checks. An HTTP smoke proves liveness, not functional behavior. Prove on the provider itself, not from the pipeline result, that the served artifact is the integrated candidate: its identity, such as the image digest, revision, or build commit, matches what was built from the merged commit, and the rollout finished stable. A green pipeline does not prove this, because a rollout can stall, roll back, or keep old instances serving. Send this check to a `hive-build-infra` child with the candidate identity and, for each target, the concrete provider resource to inspect, such as the ECS cluster and service, the Cloud Run service, the Vercel project, or the VPS host, taken from the project's `AGENTS.md` or deployment configuration; an environment name alone is not enough. That role can write, so the brief forbids any provider change, such as redeploying, scaling, restarting, or rolling back, and passes a read-only identity when the project has one; a stalled or mismatched rollout is reported, not fixed. Evidence by platform includes, for example:

  | Platform | Evidence that the change is applied |
  | --- | --- |
  | Container service, such as AWS ECS | The service runs the new task definition, whose image digest is the candidate's; the deployment is completed; running tasks equal desired tasks; no new task stopped with an error; startup logs are healthy. |
  | Kubernetes or serverless containers, such as GKE or Cloud Run | The revision or rollout receiving all traffic references the candidate digest; the rollout is complete and pods or instances are ready. |
  | Managed frontend hosting, such as Amplify or Vercel | A deployment of the exact commit succeeded and is the one active on the domain. |
  | VPS host, such as Hetzner, with Docker, Compose, or systemd | The running container has the candidate digest and restarted after the deployment; the unit is active; the health endpoint reports the build commit or version. |

  If the identity does not match or the rollout did not finish, the deployment is not verified, whatever the pipeline reports. Then send the functional walk to a `hive-verify-change` child against the environment's URLs, plus `hive-review-ux` when a UI changed, each with its own account or session. Launch both before waiting on either, not one after the other: neither needs the other's result. The orchestrator does not script its own walk. Run it only when the project declares it or the user asked to validate the deployment; a promotion or deployment request alone does not ask for it, and you do not offer it. Otherwise report the walk as not run. A walk that was due and did not run is reported as not verified, and its tickets stay out of their completion state until it runs. Recovery exercises stay within their authorized scope. Use appropriate readbacks, logs, metrics, traces, or journeys; a successful pipeline or an available shell alone does not establish service health. Check recovery against the data/configuration changes made, not only the previous code version.
- Reuse evidence only for unchanged relevant inputs. Code, configuration, dependency, environment or external-state changes can invalidate it. Performance trends, changing data/traffic and experimental noise can justify scheduled or repeated checks even without a code change.

Parallelize independent checks; isolate or serialize shared state. After a correction, rerun its failing check and affected scope. Broaden for cross-cutting changes or new failure evidence. Bound review/repair loops by material findings and explicit stopping conditions rather than arbitrary repetition for confidence.

## Capacity is separate from correctness

Before load testing, define the workload, dataset scale, arrival pattern, tenant distribution, environment and agreed latency/error/saturation objectives. Validate that thresholds measure meaningful behavior; a green threshold with a poor workload can mislead. Distinguish throughput from transactional integrity and tail latency. Run stress, soak or recovery scenarios when their failure modes matter, not on every commit. Record environment limits rather than extrapolating local results to production.

## Keep the evidence small

Record criterion, command or journey, relevant revision/environment, observed outcome and limitation in the existing plan or closing response. Retain selected evidence only when useful. An unavailable device, missing credential or exhausted time budget leaves its required check unverified; it does not reduce the acceptance bar. If a cheaper substitute observes the same failure mode, explain the substitution and its limits.
