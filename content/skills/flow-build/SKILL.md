# Implement authorized work

Read the [verification floor](../hive-rule-verification-floor/SKILL.md) at the start: it sets what always runs for the change's kind, in every delivery mode. Keep a checkpoint as [checkpoint](../hive-rule-checkpoint/SKILL.md) sets, written at the start and after each task. After a compaction, resume from it, the active skill and one `git status`; read code again only before editing it.

For explicit E2E work, read [coordination](references/e2e-coordination.md) before dispatch; for its multiunit checkpoint, read [execution record](../flow-plan/references/execution-record.md). When adding or changing project verification commands or feature coverage, read [project verification](../hive-rule-project-verification/SKILL.md).

When the build captures an interface, the primary producer publishes the captures as [walkthrough](../hive-rule-walkthrough/SKILL.md) sets, except the before captures; for a changed interface read [UI verification](../hive-rule-ui-verification/SKILL.md) for capture scope, and [before captures](../hive-rule-before-captures/SKILL.md) before the first edit.

Enter with a ready plan, in a change folder or kept in the conversation as [flow-plan](../flow-plan/SKILL.md#where-the-plan-lives) sets, or with a small understood change the user asked for, handed over by `hive-mode` in the same turn or started by the user's typed command, or with a fix that the close footer or a findings round sends when that fix is a small understood change; other fixes go to `flow-plan`. Without a plan, ask the delivery and review questions as [delivery questions](../hive-rule-delivery-ask/SKILL.md) sets, before the first edit; when it changes a behavior an existing `<Specs>/specs/<capability>/spec.md` describes, first follow [spec delta](references/spec-delta.md).

1. Check the plan's prerequisites. For each unmet one, ask the user for it and start the tasks that do not need it; mark it done once confirmed, without writing a secret's value. Move the tracked ticket to in progress, except for an operational task, as [ticket state](../hive-rule-ticket-state/SKILL.md) sets, and write the work's business rules to it as [business rules ticket](../hive-rule-business-ticket/SKILL.md) sets. When the delivery makes commits, work on a branch named by the repository's convention.
2. For each task: implement it, or delegate it as [delegation](../hive-rule-delegation/SKILL.md) sets, applying, before writing new code, [Reuse before writing](../hive-rule-reuse-before-writing/SKILL.md) and [code principles](../hive-principle-index/SKILL.md), [defect fix](../hive-rule-defect-fix/SKILL.md) before the first edit of a defect fix, and [Tests](../hive-rule-tests/SKILL.md) before writing, changing or deleting a test or when a check fails; run the checks that cover it, reading their results and ordering the reruns of a round of fixes as [check reuse](../hive-rule-checks/SKILL.md#check-reuse) sets, and commit it when the delivery makes commits, reading the file [git commit](../hive-rule-git-commit/SKILL.md) before its first `git add`. Before a task takes an effect on an external system, read the [effects round](../hive-rule-external-effects/SKILL.md). When a decision or an assumed rule changes a business rule, read [business rules](../hive-rule-business-rules/SKILL.md). When the work has a change folder, tick the task's boxes in `tasks.md` and add one line: done, its commit, and anything left unverified, including each criterion whose only evidence is a check against a substitute or whose `Observed in:` names a deployed environment, as [flow-plan](../flow-plan/SKILL.md#acceptance-criteria) sets, with `python3 -I <flow-plan-dir>/scripts/tasks.py <folder> done T<n> --commit <sha> --unverified "<what>"` ([tasks](../flow-plan/scripts/tasks.py)), passing `none` as the commit when the delivery makes none and as the text when nothing stayed unverified, or by hand when it cannot run; and write one progress line in the message, such as `✓ T3 · 3/5 · export button`, which the script prints.
3. When a task of a plan with a change folder is a risky change, as the global guidance's «Proportionality» defines it, have one `hive-verify-task` child check it against its criteria, briefed as [reviewer brief](../hive-rule-reviewer-brief/SKILL.md) sets.
4. When the change adds or rearranges a screen, follow the dependencies the plan declares rather than its listing order. Before asking the first-view question, decide what keeps going while the user reviews: each task that does not need that answer. Launch one as a child only when [delegation](../hive-rule-delegation/SKILL.md) sends it to one; keep the others in the main thread while the children work. Show the user its first rendered view with the walkthrough as soon as the UI task is done, compared against the plan's sketch, or against the approved example when the work has one; ask the user to accept it or request corrections, with the open-viewer option that [viewer publication](../hive-rule-viewer-open/SKILL.md) sets, and adjust only the UI before continuing, adding to the approved example's record each correction that departs from it. Apply the first-view exception when [unattended delegation](../unattended-delegation/SKILL.md) is active. Skip the first rendered view when the UI task is the plan's last task: the walkthrough of `flow-verify` validates it once.
5. When every task is done, reproduce the repository's CI as [local CI](../hive-rule-checks/SKILL.md#local-ci) sets. Then continue into `flow-verify` in the same turn, with no next-step block: read its skill whole, then hand it the candidate and that evidence. When the user asked to stop after build, end instead with the next-step block toward `flow-verify`; when they asked to skip verify, integrate as the delivery says and run `flow-close`. Verify owns [check reuse](../hive-rule-checks/SKILL.md#check-reuse), checks the acceptance criteria in its walk, and holds the delivery's validation stop. A mechanical change skips verify: check its criteria, if it has any, then, under `interactive`, hold the delivery's validation stop yourself before the push, showing what changed and asking the user to approve it or request corrections; integrate as the delivery says, and run `flow-close`. An operational task skips the CI run and verify: check its criteria and run `flow-close`. End the final report with one line naming each principle read from the code principles that changed a decision, or none.

Repairing the local environment the work needs, such as reinstalling or relinking dependencies, regenerating a client or seeding local data (read [test accounts](../hive-rule-test-accounts/SKILL.md) first when the data includes accounts), is part of the authorized work and needs no question: do it and name it in the final report, and record what it showed about this machine in `HIVE.local.md` as [local record](../hive-rule-local-record/SKILL.md) sets. It never quits, restarts or kills a program other sessions may use, such as Docker Desktop, as the global guidance's «Preservation» sets.

Between tasks, continue with the next tool call instead of ending the turn with a progress report. End the turn only to ask a question that must be asked now, at a validation stop, at a blocker that stops all remaining work, or when the user stops the work.

Before a change to stored data, read [stored data](../hive-rule-stored-data/SKILL.md). When the change touches untrusted input, permissions, process execution or data exposure, read [security boundaries](../hive-rule-security-boundaries/SKILL.md).
