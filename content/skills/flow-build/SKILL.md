# Implement authorized work

At entry, read `stage.md` in this skill's folder whole: it holds the leaves verification-floor, checkpoint, checks, tests, reuse-before-writing, delegation, git-commit, so a step that links one of them needs no new read until a compaction, after which read the packet again. If it is missing, read the linked leaves instead; if its last line is not its packet end line, read the rest; if a `## ` heading the end line names is missing, read that leaf; if the output says it was cut, read the linked leaves.

Read the [verification floor](../hive-core/build/verification-floor.md) at the start: it sets what always runs for the change's kind, in every delivery mode. Keep a checkpoint as [checkpoint](../hive-core/plan/checkpoint.md) sets, written at the start and after each task, and resume from it after a compaction. At entry, read the work's `Playbook` record in it; without a plan file, write that line first when research named a playbook, as [Pick the playbook](../hive-mode/SKILL.md#pick-the-playbook) «Record» sets. A kind with no file in `hive-mode/playbooks/` is read from its row there.

For explicit E2E work, read [coordination](references/e2e-coordination.md) before dispatch, and [execution record](../flow-plan/references/execution-record.md) for its multiunit checkpoint. When adding or changing project verification commands or feature coverage, read [project verification](../hive-core/build/project-verification.md).

When the build captures an interface, the primary producer publishes the captures as [walkthrough](../hive-core/ui/walkthrough.md) sets, except the before captures; for a changed interface read [UI verification](../hive-core/ui/ui-verification.md) for capture scope, and [before captures](../hive-core/ui/before-captures.md) before the first edit.

Enter with a ready plan, in a plan file or kept in the conversation as [flow-plan](../flow-plan/SKILL.md#where-the-plan-lives) sets, or with a small understood change (as [proportionality](../hive-core/plan/proportionality.md) defines it) handed over by `hive-mode` in the same turn, started by the user's typed command, or sent by the close footer or a findings round; other fixes go to `flow-plan`. When the change touches what a spec under `<Specs>/specs/` describes, read [plan record](../hive-core/plan/plan-record.md). Without a plan, ask the delivery and review questions as [delivery questions](../hive-core/git/delivery-ask.md) sets before the first edit.

1. Check the plan's prerequisites. For each unmet one, ask the user for it and start the tasks that do not need it; mark it done once confirmed, without writing a secret's value. Move the tracked ticket to in progress, except for an operational task, as [ticket state](../hive-core/tracker/ticket-state.md) sets, and write the work's business rules to it as [business rules ticket](../hive-core/business/business-ticket.md) sets. When the delivery makes commits, work on a branch named by the repository's convention.
2. For each task, in this order:
   1. Implement it, or delegate it as [delegation](../hive-core/delegation/delegation.md) sets. Read each leaf at its moment:
      - before writing new code, apply [Reuse before writing](../hive-core/plan/reuse-before-writing.md) and [code principles](../hive-core/principles/index.md);
      - before the first edit of a defect fix, apply [defect fix](../hive-core/build/defect-fix.md);
      - before writing, changing or deleting a test and when a check fails, apply [Tests](../hive-core/build/tests.md);
      - before a task takes an effect on an external system, read the [effects round](../hive-core/plan/external-effects.md);
      - when a decision or an assumed rule changes a business rule, read [business rules](../hive-core/business/business-rules.md).
   2. Run the checks that cover the task, reading their results and ordering the reruns of a round of fixes as [check reuse](../hive-core/build/checks.md#check-reuse) sets.
   3. Commit it when the delivery makes commits, reading [git commit](../hive-core/git/git-commit.md) before its first `git add`.
   4. When the work has a plan file, tick the task's boxes in it and add one line: done, its commit, and anything left unverified, including each criterion whose only evidence is a check against a substitute or whose `Observed in:` names a deployed environment, as [flow-plan](../flow-plan/SKILL.md#acceptance-criteria) sets.
      Use `python3 -I <flow-plan-dir>/scripts/tasks.py <plan-file> done T<n> --commit <sha> --unverified "<what>"` ([tasks](../flow-plan/scripts/tasks.py)), passing `none` as the commit when the delivery makes none and as the text when nothing stayed unverified, or write the line by hand when it cannot run.
   5. Write one progress line in the message, such as `✓ T3 · 3/5 · export button`, which the script prints.
3. When a task of work with a plan file is a risky change, as the global guidance's «Proportionality» defines it, have one `hive-verify-task` child check it against its criteria, briefed as [reviewer brief](../hive-core/delegation/reviewer-brief.md) sets.
4. When the change adds or rearranges a screen, run the tasks in the order of the dependencies the plan declares rather than its listing order, and read [first view](references/first-view.md) at the build's start: it sets what keeps going while the user reviews the screen's first rendered view.
5. When every task is done, reproduce the repository's CI as [local CI](../hive-core/build/checks.md#local-ci) sets. Then continue into `flow-verify` as [same-turn continuations](../hive-core/messages/report-endings.md#same-turn-continuations) sets, with no next-step block: read its skill whole, then hand it the candidate and that evidence. When the user asked to stop after build, end instead with the next-step block toward `flow-verify`; when they asked to skip verify, integrate as the delivery says and run `flow-close`. Verify owns [check reuse](../hive-core/build/checks.md#check-reuse), the walk of the criteria and the delivery's validation stop. A mechanical change or an operational task skips verify and takes the checks, validation stop and integration that [proportionality](../hive-core/plan/proportionality.md) sets for it; then run `flow-close`. When a principle read from the code principles changes a decision, record it in the checkpoint as [checkpoint](../hive-core/plan/checkpoint.md) sets, and at this step record `none` when no line holds one, so the line survives a compaction. Hand `flow-close` that line, naming each principle that changed a decision, for the **Principles** part its report holds as [close report](../hive-core/close/close-report.md#final-report) sets; write no report here.

Repairing the local environment the work needs, such as reinstalling or relinking dependencies, regenerating a client or seeding local data (read [test accounts](../hive-core/local/test-accounts.md) first when the data includes accounts), is part of the authorized work and needs no question: do it, name it in the final report, and record what it showed about this machine in `HIVE.local.md` as [local record](../hive-core/local/local-record.md) sets. Before naming, writing or running a local script for this machine, read [local script](../hive-core/local/local-script.md).

When the user changes the work while it is open, classify the change as [scope changes](../hive-core/plan/scope-changes.md) sets. When a blocker or a failure stops a task, report it as [reasons and blockers](../hive-core/messages/reasons-and-blockers.md) sets.

Between tasks, continue with the next tool call instead of ending the turn with a progress report. End the turn only to ask a question that must be asked now, at a validation stop, at a blocker that stops all remaining work, or when the user stops the work.

Before a change to stored data, read [stored data](../hive-core/build/stored-data.md); when the change touches a boundary that [security boundaries](../hive-core/build/security-boundaries.md) lists, read that.

Reply: ends with [the same-turn continuation](../hive-core/messages/report-endings.md#same-turn-continuations) into `flow-verify`, handing it the candidate and the local CI evidence; only when the user asked to stop after build does it end with [the next-step block](../hive-core/messages/report-endings.md#the-next-step-block) toward `flow-verify`.
