# Implement authorized work

Use the requested outcome or supplied plan as the execution brief.

## Entry and exit

Enter with authorized work: a ready plan, or the user's request for a small understood change: one coherent result whose approach the request, ticket or code settles, in one repository unless it is mechanical, as the global guidance defines it. Send a request for other work, such as one spanning several tickets, repositories or steps, to [flow-plan](../flow-plan/SKILL.md) when its goal has a scope, else to [flow-research](../flow-research/SKILL.md) first; build it here only when the user explicitly chose to skip the plan. Leave with a built candidate: its tasks committed, or the working tree under `hold`, and verified at their checkpoints, the affected tests passing, and the first rendered view accepted, or listed in the final report where the delivery mode has no validation stop or under unattended delegation, when one applies; hand it to [flow-verify](../flow-verify/SKILL.md) naming the checks it still owes; verify, not this skill, runs the UI children, the local in-vivo run, the full suite, the dedicated code review and the human validation. When verify is skipped, integrate as [iterate and integrate](references/iterate-and-integrate.md#integrate-when-verify-is-skipped) sets.

## Reconcile before execution

Before resolving needed project settings, read [project settings](../hive-core/references/project-settings.md). Before formulating a user decision or manual validation request, read [questions](../hive-core/references/questions.md). Before delegating or starting an external-work wait, read [delegation and waits](../flow-research/references/delegation.md).

Read the relevant project guidance, current source and tests, and the supplied plan and references. Inspect existing changes and completed work. Treat the record as a claim to reconcile with current evidence, not a script to replay blindly.

Identify the candidate, affected applications/services and environments, and the checks needed to close each surface. Keep a small task’s criteria in the conversation. Identify the next unmet acceptance criterion and its dependencies. Preserve valid completed work. If the current state invalidates a decision that sets scope, a contract, an acceptance criterion, or delivery, investigate the mismatch and update the affected plan as [Revise a plan in progress](../flow-plan/references/plan-revision.md) sets, or resolve the missing decision as [questions](../hive-core/references/questions.md) sets for a build. A consumer or a reachable path that [change impact](../flow-research/references/change-impact.md) finds and the plan does not account for invalidates the plan's scope or contract in the same way. When no plan exists, or the plan records no change-impact result for it, read [change impact](../flow-research/references/change-impact.md) before a change that removes, closes, disables, migrates, or renames something that runs in production, moves it to another host or process, or changes untested production behavior. When work grows beyond its request, classify the change as [scope changes](../hive-core/references/scope-changes.md) sets. Resolve ordinary implementation details within scope; do not stop at every task boundary merely to ask again.

Identify the available test runner, project check/build commands, baseline failures, and the evidence needed for acceptance. Before choosing the affected tests in any build, read [verification by risk and surface](references/verification.md) to select checks, prerequisites, and their timing. Reconcile a supplied verification plan rather than silently weakening it.

Before the delivery and review round below, move a tracked ticket to its in-progress state as the global ticket rule sets, so a ticket another agent already took stops the work before any question. Then, before the first edit and unless a plan, an earlier answer, or the user's request already settled it, ask once for the case that applies:
- Non-mechanical work that will end in a Git delivery: read [delivery decisions](../flow-plan/references/delivery-decisions.md) and resolve its delivery-mode question and the review question of [review decisions](../flow-plan/references/review-decisions.md), with the `UI verification` value for a rendered UI effect in the same round. The selected mode then carries the later gates, including the CI wait its merge depends on, without asking again.
- A mechanical change that will end in a Git delivery: only the delivery question, with the same `UI verification` value.
- Work that will not end in a Git delivery and is not mechanical: only the review question of [review decisions](../flow-plan/references/review-decisions.md), the [foreseen authorizations](references/foreseen-authorizations.md), and, for a rendered UI effect, the `UI verification` value of [the UI verification decision](../flow-plan/references/ui-verification-decision.md); first decide whether the UI gate applies, as [delivery decisions](../flow-plan/references/delivery-decisions.md) sets for that value.
- An explicit delegation or the user's leaving message that activates unattended delegation before the round is answered: it is asked as [unattended delegation](../unattended-delegation/SKILL.md#pre-authorization-round) sets, and the work continues without waiting for it.

Before dependent changes, read the applicable situational reference: [security boundaries](references/security-boundaries.md) for untrusted inputs, permissions, process execution, public data exposure, or dependencies; [persistent data changes](references/data-changes.md) for stored schema, representation, migration, or backfill changes; and [diagnosis](../flow-research/references/diagnosis.md) when a failure’s cause remains uncertain. These apply even without a retained plan or specialist assignment.

For new or changed screens, shells, layouts, reusable UI patterns, or a dialog or form where the end user enters or chooses data, read [UI planning](../flow-plan/references/ui-planning.md) and any existing applicable project UI guide before dependent edits. Reconcile the supplied view decisions; if no plan exists, resolve the same decisions in a bounded implementation brief rather than inventing a new composition.

Before you install a missing tool or add a dependency, read [tools and dependencies](references/tools-and-dependencies.md).

## Execute in verifiable increments

Before writing or cleaning a support artifact, read [artifact layout and retention](../workspace-conventions/references/artifact-layout.md). Before the first message of the build and before ending a turn while work of your own remains, read [work-item boundary](../flow-close/references/work-item-boundary.md): it sets when the turn may end. Before reports or messages containing citations, links or externally defined IDs, read [reporting](../flow-close/references/reporting.md).

Choose a coherent next result and implement it in the existing source layout. Look for an existing solution or pattern before adding a mechanism or abstraction, and justify a new one by the need it serves. Keep dependent edits ordered. Confirm that reused tools or patterns meet this project's requirements. Use the project's declared dependency manager and preserve its lockfile conventions. Select technical references from the project stack and affected behavior.

Delegation is internal work and needs no separate approval. Assign each unit by the criterion in [delegation and waits](../flow-research/references/delegation.md#split-work), following a plan's execution assignments unless current state invalidates them; launch all independent units, such as tasks or tickets that touch different files, before waiting on any of them. For a plan task, write the brief as [plan execution](references/plan-execution.md) sets. Without a retained plan, the brief quotes the user's request for the work verbatim, without any secret value, besides any summary of it. The main thread keeps coordination, integration, and user decisions. Work outside the plan's tasks, such as fixes after review or human validation, gets its own execution decision before its first edit. Corrections the user requests during a validation pause follow the correction rounds in [flow-verify](../flow-verify/SKILL.md) instead; [flow-walkthrough](../flow-walkthrough/SKILL.md) owns the first rendered view of a new or rearranged layout during the build.

The independent children that [the UI gate](../flow-verify/references/ui-gate.md) selects by the `UI verification` value run in verify, not during the build, without being proposed. Propose other independent verification or specialist review when the acceptance criteria or risk warrant it, and dispatch within the agreed gate authority. Independent surface checks may run in parallel; keep one owner for shared mutations and wait for the required deployed version before dependent checks. The implementer still verifies its own change: before reporting a task with a rendered UI effect, read [Scope](../flow-verify/references/ui-gate.md#scope) and [the implementer's inspection](../flow-verify/references/ui-gate.md#the-implementers-inspection).

When choosing an infrastructure resource name, or creating resources whose names existing infrastructure code generates, read [the infrastructure naming reference](../flow-plan/references/infra-naming.md), even if no retained plan exists. Preserve an existing name unless its authorized change includes the necessary impact and migration work.

For a changed shared interface, read [interface changes](../flow-plan/references/interface-changes.md) before implementation.

Before you change code or tests, read [test-first development](references/tdd.md): it sets when a change needs a failing test first, characterization, or a direct check, what counts as red, which kind of test to write, and the filter to apply before writing one.

Before writing a retained supporting artifact, resolve its destination through the applicable global artifact-placement instructions and existing work identifier. While you execute or resume a retained plan, a change folder or a `<topic>.plan.md`, read [plan execution](references/plan-execution.md) before you start, mark, verify, or commit any of its tasks: it holds the record, the task markers, the `hive-verify-task` procedure, and the per-task commits.

When the delivery mode makes commits, commit each coherent result once its check passes; a retained plan's task commits follow [plan execution](references/plan-execution.md). Every later commit of the work, in any stage, such as a fix after a gate or a correction round, is an additional commit under this rule, never an amend. Before the first branch, worktree or commit, read [git-workflow](../git-workflow/SKILL.md).

For any multi-step work, with or without a retained plan, when the host exposes a native task list, list the tasks or tickets in it at the start, and again with the remaining tasks whenever you resume or continue a plan, such as after a close, and mark each one in progress when it starts and completed when it completes, including tickets added during the session. A plan task completes in the native list when it reaches `[x]`, not `[?]`. A retained plan's record, when it exists, still governs.

Keep the processes the task starts identifiable. For a child's processes and a child that stops while it waits on work of its own, follow [check returned work](../flow-research/references/delegation.md#check-returned-work). Silence alone does not mean a command is hung: inspect available liveness and progress signals before terminating it. Use the host’s supported long-running execution controls when needed and continue independent work. Do not stop unrelated processes.

## Check and hand off

Before running the checks of your change, while iterating on those checks, and before integrating when verify is skipped, read [iterate and integrate](references/iterate-and-integrate.md).

Compare the final changes and observed behavior against the acceptance criteria and authorized scope. The implementer's own checks below need no separate approval request; an unavailable prerequisite leaves the affected criterion unverified only when [runtime and UI gates](../flow-verify/references/runtime-gates.md#runtime-and-ui-gates) leaves it as a reported prerequisite; resolve first the local setup that rule lists. Run affected tests and applicable build, typecheck, and lint commands that the project provides. Exercise changed runtime behavior through the real integration path; inspect changed user-facing surfaces rendered and interactive, including relevant states and viewports; this is the implementer's own inspection, not the gate. In deployed environments, follow the deployed-walk rules in [flow-deploy](../flow-deploy/SKILL.md).

When verify runs, hand it the candidate with your next tool call. Use a separate report only when a retained deliverable needs it. A successful tool exit, a checked box, or an agent's assertion alone does not establish completion.

Run [flow-close](../flow-close/SKILL.md) as its [When to run it](../flow-close/SKILL.md#when-to-run-it) sets, which also says what is not a pause; an iterative route closes as [flow-research](../flow-research/SKILL.md) sets. It closes the change record (a pause leaves it on disk), cleans up, writes the completion report, and ends the turn with the global close question. The record's versioned delivery follows the closing route recorded in the delivery answer.
