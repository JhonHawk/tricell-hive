# Implement and verify authorized work

Use the requested outcome or supplied plan as the execution brief. For work the user asked for, this skill does not require a formal plan or a prior research skill invocation; a failure reported without a fix request enters through `flow-research` first, as the global guidance sets. It does not grant effects beyond the user's instructions.

## Reconcile before execution

Before resolving needed project settings, read [project settings](../flow-plan/references/project-settings.md). Before formulating a user decision or manual validation request, read [questions](../flow-plan/references/questions.md). Before delegating or starting an external-work wait, read [delegation and waits](../flow-research/references/delegation.md).

Read the relevant project guidance, current source and tests, and the supplied plan and references. Inspect existing changes and completed work. Treat the record as a claim to reconcile with current evidence, not a script to replay blindly.

Identify the candidate, affected applications/services and environments, and the checks needed to close each surface. A supplied plan is optional; keep a small task’s criteria in the conversation. Identify the next unmet acceptance criterion and its dependencies. Preserve valid completed work. If the current state invalidates a decision that sets scope, a contract, an acceptance criterion, or delivery, investigate the mismatch and update the affected plan as [Revise a plan in progress](../flow-plan/references/plan-revision.md) sets, or ask for the missing decision before dependent edits. A consumer or a reachable path that [change impact](../flow-research/references/change-impact.md) finds and the plan does not account for invalidates the plan's scope or contract in the same way. When no plan exists, or the plan records no change-impact result for it, read [change impact](../flow-research/references/change-impact.md) before a change that removes, closes, disables, migrates, or renames something that runs in production, moves it to another host or process, or changes untested production behavior. Resolve ordinary implementation details within scope; do not stop at every task boundary merely to ask again.

Identify the available test runner, actual project check/build commands, relevant baseline failures, and the evidence needed for acceptance. For integration, runtime, UI, performance, hardware, test replacement/removal, code review, promotion, deployment, or costly verification, read [verification by risk and surface](references/verification.md) before execution to select checks, prerequisites, and their timing. Reconcile a supplied verification plan rather than silently weakening it.

When the work will end in a Git delivery, read [delivery decisions](../flow-plan/references/delivery-decisions.md) before the first edit and resolve its delivery-mode and review questions once, as that reference sets, with the `UI verification` value for a rendered UI effect in the same round. The selected mode then carries the later gates, including waiting for the CI its merge depends on, without asking again for each operation. When the work will not end in a Git delivery and is not mechanical, ask only that reference's review question, the foreseen authorizations, and, for a rendered UI effect, its `UI verification` value, once, before the first edit, unless a plan, an earlier answer, the user's request, or a declared `Review` setting already settled it, so the review gate does not stop the work later.

Before dependent changes, including deployment of existing code, read the applicable situational reference: [security boundaries](references/security-boundaries.md) for untrusted inputs, permissions, process execution, public data exposure, or dependencies; [persistent data changes](references/data-changes.md) for stored schema, representation, migration, or backfill changes; and [diagnosis](../flow-research/references/diagnosis.md) when a failure’s cause remains uncertain. These apply even without a retained plan or specialist assignment.

For new or changed screens, shells, layouts, or reusable UI patterns, read [UI planning](../flow-plan/references/ui-planning.md) and any existing applicable project UI guide before dependent edits. Reconcile the supplied view decisions; if no plan exists, resolve the same decisions in a bounded implementation brief rather than inventing a new composition.

Before you install a missing tool or add a dependency, read [tools and dependencies](references/tools-and-dependencies.md).

## Execute in verifiable increments

Before writing or cleaning a support artifact, read [artifact layout and retention](../workspace-conventions/references/artifact-layout.md). Before progress reports, completion reports or messages containing citations, links or externally defined IDs, read [reporting](../flow-close/references/reporting.md).

Choose a coherent next result and implement it in the existing source layout. Look for an existing solution or pattern before adding a mechanism or abstraction, and justify a new one by the need it serves. Confirm that reused tools or patterns meet this project's requirements. Use the project's declared dependency manager and preserve its lockfile conventions. Select technical references from the actual project stack and affected behavior. Keep dependent edits ordered.

Delegation is internal work and needs no separate approval; prefer it. Announce the split before the first edit under the shared delegation rules, following a plan's execution assignments unless current state invalidates them. Delegate each unit whose interface is settled and whose writes do not overlap concurrent work, and launch all such independent units, such as tasks or tickets that touch different files, before waiting on any of them, not one after the other; keep a unit in the main thread only when it is coupled to work in progress or its brief would be longer than the change itself. A change spanning several files with its tests, unless it is mechanical, or a diagnosis likely to produce long output, goes to a child by default. For a plan task, write the brief as [plan execution](references/plan-execution.md) sets. Without a retained plan, the brief quotes the user's request for the work verbatim, without any secret value, besides any summary of it. The main thread keeps coordination, integration, and user decisions. Work outside the plan's tasks, such as fixes after review or human validation, gets its own execution decision, announced before its first edit. Corrections the user requests during a validation pause follow the correction-round rule in [flow-walkthrough](../flow-walkthrough/SKILL.md) instead, which also owns the first rendered view of a new or rearranged layout during the build.

For changes with a rendered UI effect, the independent children that [the UI gate](../flow-verify/references/ui-gate.md) selects by the `UI verification` value run without being proposed. Propose other independent verification or specialist review when the acceptance criteria or risk warrant it, and dispatch within the agreed gate authority. Independent surface checks may run in parallel; keep one owner for shared mutations and wait for the required deployed version before dependent checks. The implementer still verifies its own change.

When choosing an infrastructure resource name, or creating resources whose names existing infrastructure code generates, read [the infrastructure naming reference](../flow-plan/references/infra-naming.md), even if no retained plan exists. Preserve an existing name unless its authorized change includes the necessary impact and migration work.

For a changed shared interface, read [interface changes](../flow-plan/references/interface-changes.md) before implementation.

Before you change code or tests, read [test-first development](references/tdd.md): it sets when a change needs a failing test first, characterization, or a direct check, what counts as red, which kind of test to write, and the filter to apply before writing one.

Before writing a retained supporting artifact, resolve its destination through the applicable global artifact-placement instructions and existing work identifier. While you execute or resume a retained plan, a change folder or a `<topic>.plan.md`, read [plan execution](references/plan-execution.md) before you start, mark, verify, or commit any of its tasks: it holds the record, the task markers, the `hive-verify-task` procedure, and the per-task commits.

When the delivery mode makes commits without a retained plan, commit each coherent result once its check passes.

For any multi-step work, with or without a retained plan, when the host exposes a native task list, list the tasks or tickets in it at the start, and again with the remaining tasks whenever you resume or continue a plan, such as after a close, and mark each one in progress when it starts and completed when it completes, including tickets added during the session, so the user sees progress. A plan task completes in the native list when it reaches `[x]`, not `[?]`. A retained plan's record, when it exists, still governs.

Keep the processes the task starts identifiable. For a child's processes and a child that stops while it waits on work of its own, follow [check returned work](../flow-research/references/delegation.md#check-returned-work). Silence alone does not mean a command is hung: inspect available liveness and progress signals before terminating it. Use the host’s supported long-running execution controls when needed and continue independent work. Do not stop unrelated processes.

## Verify and close

Compare the final changes and observed behavior against the acceptance criteria and authorized scope. Local in-vivo verification and UI review are required when applicable, without a separate approval request; unavailable prerequisites leave the affected criterion unverified. Run affected tests and applicable build, typecheck, and lint commands that the project provides. Exercise changed runtime behavior through the real integration path; inspect changed user-facing surfaces rendered and interactive, including relevant states and viewports. In deployed environments, follow the deployed-walk rules in [verification](references/verification.md). Tests passing or a successful build do not replace those observations. Before reporting a UI change complete, obtain the results of the independent UI review and in-vivo children that [the UI gate](../flow-verify/references/ui-gate.md) selects by the `UI verification` value; the implementer's own walk satisfies neither. In any delivery mode that stops for validation, run these steps in order on the built candidate before asking the user to validate a result; they do not run before the first rendered view that [flow-walkthrough](../flow-walkthrough/SKILL.md) shows:

1. The UI gate that the `UI verification` value selects.
2. The full suite of each affected application, locally, even when CI will run it later, since under `interactive` CI runs after the push that follows validation.
3. `hive-review-security` when the user asked for it; otherwise the validation message offers it for any boundary no earlier offer named. Both follow [Offer the security review](references/security-boundaries.md#offer-the-security-review), which also applies without a validation stop.
4. The delivery of [flow-walkthrough](../flow-walkthrough/SKILL.md), which gives the page's path and asks the validation question it sets.

These steps run before the first validation request. Correction rounds and the reruns of the accepted-candidate gate then follow [flow-walkthrough](../flow-walkthrough/SKILL.md). Before delivering any later fix with a UI effect, follow [changes after a gate or approval](../flow-verify/references/ui-gate.md#changes-after-a-gate-or-approval). Apply the shared verification reference for domain-specific depth and timing.

Use existing evidence only while its relevant code, configuration, and environment remain valid. While iterating, run the project's affected-test selection for the changed code, widened and bounded as the verification reference sets. Close regression coverage through the project's actual CI gate, except that the full suite also runs locally before asking the user to validate, as the sequence in the verification paragraph sets. When no CI gate will run it, run the full suite once on the final candidate of any change that is not mechanical, as the global guidance defines it, and rerun it only when a later edit could affect what it covers. For a mechanical rename or move, find every reference to the old name or path, including strings and paths the compiler cannot see, and run the tests of the packages that hold them. Do not rerun a passing suite for confidence. When the verification the change needs is much larger than the change itself, say so in the progress update with the reason. After a fix, rerun the failing check and affected scope; broaden to affected callers and consumers when the fix touches shared code or new failure evidence appears. Do not mark a required but unavailable check as passed or silently omit it. Distinguish failed, not verified/blocked, and not applicable with a reason; resolve authorized local prerequisites and report any remaining delivery constraint. Check that the handoff's paths and next step still match the final state.

For UI work awaiting human validation, keep the verified stack and the handoff as [flow-walkthrough](../flow-walkthrough/SKILL.md) sets.

Report what changed, what was verified, unresolved failures or uncertainty, and the next step. Use a separate report only when a retained deliverable needs it; a concise update to the plan can be enough. A successful tool exit, a checked box, or an agent's assertion alone does not establish completion.

Complete delivery actions already explicitly authorized, subject to their conditions; for a branch, worktree, commit, push, pull request, or merge, read [git-workflow](../git-workflow/SKILL.md) first. Otherwise stop at the authorized result with remaining delivery steps identified. Run [flow-close](../flow-close/SKILL.md) when any one of these happens: the work item reaches its completion point, the change is abandoned, or the work is paused. Inside an iterative route that [flow-research](../flow-research/SKILL.md) defines, a verified round is not the completion point: report it in one line and continue with the next round; run `flow-close` when the route stops. It closes the change record (a pause leaves it on disk), cleans up, writes the completion report, and ends the turn with the global close question. The record's versioned delivery follows the closing route recorded in the delivery answer.
