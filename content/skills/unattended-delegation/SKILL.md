# Unattended delegation

This skill grants no broader tools or host permissions. Forbidden even when authorized in advance: the irreversible or destructive actions of step 6.

1. **Activate from one of three sources.** An explicit delegation; a user's message that they are leaving while authorized work is running; or the user's silence after they answered the route of the current work (its next-step block) and each delivery and review value it needs. Each source delegates the objective of the work already authorized, up to the delivery point the answers chose. Task duration alone, silence before those answers, and a background or scheduled turn activate nothing. Never record a delegation the user did not give: an inferred activation is reported as inferred, with the answer it rests on.
2. **Say so in visible text**, not only in your reasoning: the source and the message or answer it rests on, quoted, then the objective, root or repository, references, destination, evidence, an expiry or deadline and, for work that repeats cycles, its measure and cap (step 8). For every source, the same message states the unforeseen-spend amount the user gave, one amount of money for spend no answer covers (step 6), or asks for it in one line; that question is not one of step 4's open answers, never puts the work under `hold`, and no answer means an amount of zero. While it runs, every message to the user carries `· unattended, active` as an added part of its context line, or in its first line when it has none; the message that ends the delegation says that it ended and why.
3. **Keep or end it.** The delegation expires when the objective completes or the user sends a message that changes the objective, the scope or an answer in force, asks for other work, or tells you to stop. These messages, in any language, keep it: one that tells you to continue, acknowledges progress, or asks how the work is going; an answer to a question this delegation asked; one that adds information, a resource, feedback or a correction within the objective and scope. A message that fits both lists, such as a correction that changes the delivery mode, ends it; every other message ends it. Apply what a kept message adds as input, answer a question in one line, say that the delegation continues, and keep deciding.
4. **Close the open answers at activation.** For an explicit delegation or a leaving message whose objective reaches a build or a delivery, find which answers the work still lacks: the delivery mode and review that [flow-build](../flow-build/SKILL.md) asks before the first edit, and each critical effect it foresees that no class of the plan's effects round was asked for, classified as «Scope and authorization» sets, with its exact target and ceiling. State the answers already in force, which include each class of effect the user approved in the plan's effects round, as [outside the repository](../flow-plan/references/outside-the-repository.md#effects-round) sets, its ceiling counting as spend authorized for that target. A class the user refused stays refused: skip its effects and report them. A class left unanswered adds no authorization and is not an open answer of this step, so it is not asked again at activation and puts no work under `hold`: step 6 decides each of its effects. Ask the missing ones in one round, in the activation message, as «Questions and routes» formats a question when no waiting card carries it, and keep working; this is the named exception to its rule that the turn ends with the round's last card, and to «Delivery»'s rule that its questions are asked before the first edit: never ask through a tool that blocks your turn, since the user may be gone. A reply that answers or changes an answer keeps the delegation. Until the answers arrive, work under `hold` and decide nothing they cover: edit and verify the working tree as [flow-verify](../flow-verify/SKILL.md) does under `hold`, with the full suite when it runs, and no commit, publication, dedicated review or critical effect. The `hive-review-ux` child still runs for a UI change, since it publishes nothing. The work is then not complete; the end report (step 9) names the review and any child that did not run as not run, lists the unanswered questions with their IDs and ends with its pause line, which is not asking them a second time.
5. **Decide everything else yourself.** Take the option you would recommend for every other question, record the decision and its reason in the task record, and list them in the end report. This includes the questions whose own rule says never to act without the user's answer: adding test infrastructure, as [flow-build](../flow-build/SKILL.md#tests) sets, opening a ticket for a finding and the close's support-material decision, as [flow-close](../flow-close/SKILL.md) sets. This step is the instruction for those effects, which count as effects the objective needs. Opening such a ticket is allowed although the tracker notifies its watchers, and closing it as not planned reverts it; step 6 bounds the rest, so a deletion with no verified way back is skipped and reported. The end report presents each one with how to revert it, and the close's memory write records them as your decisions, not the user's; the test-infrastructure choice is not saved as the project decision flow-build names. The exceptions are a question whose own rule says what unattended work does with it, such as the external-project question of «Scope and authorization», the open answers of step 4, which stay unauthorized, a security review, which runs only when the user asked for it, skipping [flow-verify](../flow-verify/SKILL.md), which only the user's own message can do, and the choice or the approval of a screen example, which stays unanswered and is reported as unresolved, as [flow-figma-design](../flow-figma-design/SKILL.md#unattended-delegation) sets. Research makes no offer of proposals while the delegation is active: the plan settles the UI. While the delegation is active, capture and publish the first rendered view through [walkthrough](../flow-verify/references/walkthrough.md) without waiting for human validation; this replaces only [flow-build](../flow-build/SKILL.md)'s first-view question, not its evidence or review requirements. Delegate and wait as [delegation](../flow-build/references/delegation.md) and [flow-verify step 6](../flow-verify/SKILL.md) set (a completion signal, no polling). Keep decisions and evidence in the existing task record; require no ledger, branch, hook or tracking system for this mode.
6. **Take effects within bounds.**
   - Any effect the objective needs, deployments and writes to shared or production systems included, is allowed when it is reversible or made reversible first and disrupts no other component beyond an interruption within the window the user stated at activation; with no window stated, no interruption. Before each, record the exact target, the change and how to revert it in the task record; this replaces asking for confirmation. Examples: creating a cloud resource only this work uses that spends no money or paid quota; editing a pull request's title or body, or replying on its threads, with the previous text saved; the force-push that [git-workflow step 4](../git-workflow/SKILL.md) allows for this mode.
   - A critical effect (as «Scope and authorization» defines it) that spends within a stated ceiling, or that is reversible or made reversible first, such as a migration after a verified backup with the service suspended only while it runs, is taken only when authorized in advance for that exact target and ceiling. The one exception is unforeseen spend, spend that no answer covers: take it only when an unforeseen-spend amount is in force (step 2), a command recorded before the effect undoes the resource or setting change, and the total of unforeseen spend stays within the amount, each effect counted at the provider's price until the delegation's expiry, or at the effect's maximum when it has one; when neither a price nor a maximum can be read, skip it. Money already spent counts against the amount and does not make the effect irreversible. Record it as the bullet above sets; the end report lists it with how to revert it. Skip an effect that keeps charging after the expiry, unless its maximum is known and fits in what remains of the amount.
   - Forbidden: deleting or overwriting data, resources, credentials, history or branches without a verified way back; any change that breaks or interrupts other components or their users beyond that window; and every other irreversible effect, such as sending messages to real people, even when authorized in advance.
   - Skip an effect that is not allowed, continue the work that does not depend on it, and report it with its target, cost, revert and the decision it needs. The secret rules apply unchanged.
7. **Support artifacts.** Before writing or cleaning one, read [artifact layout and retention](../workspace-conventions/references/artifact-layout.md).
8. **Loops.** Work that repeats cycles of acting and measuring until a condition holds has a measure (an observable check run every cycle) and a cap (cycles, time or tokens), both stated at activation and set before the first cycle; without them it does not start. After each cycle, record the measure and the decisions in the change's `tasks.md`, or the saved-state destination of the artifact layout reference when there is none. When two cycles in a row bring no measurable improvement, stop and escalate: report what was tried, what failed, the current measure and what is needed to continue. Reaching the cap stops the loop. Record the final status.
9. **End.** At expiry or when the objective is complete, stop unattended effects, then report the completed and unresolved work, every effect applied with how to revert it, and the decisions taken, as [flow-close#final-report](../flow-close/SKILL.md#final-report) sets, and return control to the user.
