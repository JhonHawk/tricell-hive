# Unattended delegation

Activate this mode from one of four sources: an explicit delegation; a user's message that they are leaving while authorized work is running; a declared scheduled job whose scope and expiry match the current work; or the user's silence after they answered the route question of the current work, with each delivery and review value it needs answered, which the user decided on 2026-10-18 and 2026-10-25 counts as delegating that work. Each source delegates the objective of the work already authorized, up to the delivery point the answers chose, and expires when that objective completes or the user sends a message that changes the objective, the scope or an answer in force, asks for other work, or tells you to stop. Only these messages, in any language, keep the delegation for the same objective and expiry: one that tells you to continue, acknowledges progress, or asks how the work is going or about the work; an answer to a question this delegation asked; and one that adds information, a resource, feedback or a correction within the objective and scope. When a message fits both lists, such as a correction that changes the delivery mode, it ends the delegation. Apply what a kept message adds as input to the work, answer a question in one line, say that the delegation continues, and keep deciding. Every other message ends it. Task duration alone, silence before those answers, and a background or scheduled turn without a matching declared job activate nothing.

At activation, state in visible text, not only in your reasoning, the source and the message or answer it rests on, quoted, then the objective, root or repository, references, destination, evidence, and an expiry or deadline. While it runs, every message to the user names the delegation's state, such as `· unattended, active`: as a fourth part added to the context line that [reporting](../flow-close/references/reporting.md#open-with-the-context-line) sets, after the progress or, without one, after the ticket, or in the first line of a message that takes no context line; the message that ends it says that it ended and why. This skill grants no broader tools or host permissions.

Before delegating or starting an external-work wait, read [delegation and waits](../flow-research/references/delegation.md). Before resolving needed settings, read [project settings](../flow-plan/references/project-settings.md); before writing or cleaning support artifacts, read [artifact layout and retention](../workspace-conventions/references/artifact-layout.md); before reporting, read [reporting](../flow-close/references/reporting.md). Keep consequential decisions and evidence in the existing task record when one exists. Do not require a ledger, branch, hook, or new tracking system solely for this mode.

## Pre-authorization round

When an explicit delegation or a message that the user is leaving activates this mode, and its objective reaches a build or a delivery, find at once which answers the work still needs to reach its delivery point: the questions that [flow-build](../flow-build/SKILL.md) asks before the first edit for this kind of work, as [delivery decisions](../flow-plan/references/delivery-decisions.md) sets them, such as only the delivery question for a mechanical change, the `UI verification` value for a rendered UI effect, and the foreseen authorizations that [verification](../flow-build/references/verification.md#gate-selection-and-timing) sets, classified as [effect authorization](../flow-plan/references/effect-authorization.md) sets, each critical effect with its exact target and ceiling. Answers in force, from the session or the request, need no question; state them in the same message, and a reply that changes one of them answers this round and keeps the delegation, an exception to the rule above that a message changing an answer in force ends it. Ask the missing ones in one round in the activation message, formatted as [questions](../flow-plan/references/questions.md) sets for a question no waiting card carries, never through a tool that blocks your turn until the answer, since the user may already be gone; then keep working. An answer keeps the delegation. A delivery point and the effects it authorizes take effect only once every question that point depends on is answered, such as the review question, the `UI verification` value and the foreseen authorizations that a delivery that publishes needs; until then, and when no answer arrives, decide nothing those questions cover: edit and verify as `hold` sets, so the work may start before the first-edit delivery round that [delivery decisions](../flow-plan/references/delivery-decisions.md) sets; run no dedicated review without a review answer; without a `UI verification` answer, run only the implementer's rendered inspection that [the UI gate](../flow-verify/references/ui-gate.md) sets and no independent UI child; take the work to the working tree that [flow-verify](../flow-verify/SKILL.md) verifies under `hold`, with the full suite when it runs, without commit or publication. The checks an unanswered question selects stay pending gates, so the work is not reported complete: this changes, for this round only, flow-verify's entry condition that the review values be resolved, and leaves its level unlowered. At the end, the completion report names the dedicated review and each independent UI child that did not run as not run, lists the unanswered questions with the same IDs and ends with its pause line: this changes two rules of [questions](../flow-plan/references/questions.md#pause-and-handle-the-answer) for this round only, since that report is not a second report appended to an unanswered question, and repeating the round in it is not asking it again.

## Decisions

Decide every question that comes up yourself instead of asking or waiting, except an authorization the user was asked for and left unanswered, which stays unauthorized, and the questions of the pre-authorization round above, which only the user answers (an offered security review is not a request until the user asks for it, and only the user's own message can skip [flow-verify](../flow-verify/SKILL.md) or lower its level): take the option you would recommend, record the decision and its reason in the task record, and list them in the final report as [reporting](../flow-close/references/reporting.md#report-a-running-or-completed-item) sets. The first rendered view of a layout is captured and reported without a question, as [flow-walkthrough](../flow-walkthrough/SKILL.md) sets.

## Effects

Within the objective, you may take any effect the work needs, including deployments and writes to shared or production systems, when it is reversible or made reversible first and it disrupts no other component beyond a brief planned interruption. Before each such effect, record in the task record the exact target, the change, and how to revert it; this replaces asking for confirmation. A critical effect, as [effect authorization](../flow-plan/references/effect-authorization.md) defines it, that spends within a stated ceiling, or that is reversible or made reversible first, such as a migration after a verified backup, is taken only when it was authorized in advance for that exact target and ceiling; otherwise skip it, continue the work that does not depend on it, and report it with its target, cost and revert. For example:

- Enabling or creating a cloud resource that only this work uses and that spends no money or paid quota is allowed.
- A database migration that was authorized in advance is allowed after a verified backup, with the service suspended only while it runs.
- A force-push that the objective needs, such as realigning a pull-request branch, is allowed under the exception that [git-workflow](../git-workflow/SKILL.md) sets for this mode.
- Editing the title or body of a pull request, or replying on its review threads, is allowed with the previous text saved in the task record.

Irreversible or destructive actions stay forbidden: deleting or overwriting data, resources, credentials, history, or branches without a verified way back, any change that breaks or interrupts other components or their users beyond that planned interruption, and every irreversible effect that [effect authorization](../flow-plan/references/effect-authorization.md) lists as critical other than spending within an authorized ceiling, such as sending messages to real people, even when authorized in advance. Skip such an action, continue the work that does not depend on it, and report it with the decision it needs. The secret rules apply unchanged.

## End

At expiry or when the objective is complete, stop unattended effects, report completed and unresolved work, every effect applied with how to revert it, and the decisions taken, listed as the reporting reference sets for a completion report, and return control to the user. Do not imply activation or success when none of the four sources applies, and never record a delegation the user did not give: an inferred activation is reported as inferred, with the answer it rests on.
