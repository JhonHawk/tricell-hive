# Unattended delegation

This skill grants no broader tools or host permissions. Forbidden even when authorized in advance: the irreversible or destructive actions of step 6.

1. **Activate from one of three sources.** An explicit delegation; a user's message that they are leaving while authorized work is running; or the user's silence after they answered the route of the current work (its next-step block) and each delivery and review value it needs. Each source delegates the objective of the work already authorized, up to the delivery point the answers chose. Task duration alone, silence before those answers, and a background or scheduled turn activate nothing. Never record a delegation the user did not give: an inferred activation is reported as inferred, with the answer it rests on.
2. **Say so in visible text**, not only in your reasoning: the source and the message or answer it rests on, quoted, then the objective, root or repository, references, destination, evidence, an expiry or deadline and, for work that repeats cycles, its measure and cap (step 8). While it runs, every message to the user carries `· unattended, active` as an added part of its context line, or in its first line when it has none; the message that ends the delegation says that it ended and why.
3. **Keep or end it.** The delegation expires when the objective completes or the user sends a message that changes the objective, the scope or an answer in force, asks for other work, or tells you to stop. These messages, in any language, keep it: one that tells you to continue, acknowledges progress, or asks how the work is going; an answer to a question this delegation asked; one that adds information, a resource, feedback or a correction within the objective and scope. A message that fits both lists, such as a correction that changes the delivery mode, ends it; every other message ends it. Apply what a kept message adds as input, answer a question in one line, say that the delegation continues, and keep deciding.
4. **Close the open answers at activation.** For an explicit delegation or a leaving message whose objective reaches a build or a delivery, find which answers the work still lacks: the delivery mode and review that [flow-build](../flow-build/SKILL.md) asks before the first edit, and each critical effect it foresees, classified as «Scope and authorization» sets, with its exact target and ceiling. State the answers already in force. Ask the missing ones in one round, in the activation message, as «Questions and routes» formats a question when no waiting card carries it, and keep working; this is the named exception to its «a response ends with the question» rule, and to «Delivery»'s «before its first edit»: never ask through a tool that blocks your turn, since the user may be gone. A reply that answers or changes an answer keeps the delegation. Until the answers arrive, work under `hold` and decide nothing they cover: edit and verify the working tree as [flow-verify](../flow-verify/SKILL.md) does under `hold`, with the full suite when it runs, and no commit, publication, dedicated review or critical effect. The `hive-review-ux` child still runs for a UI change, since it publishes nothing. The work is then not complete; the end report (step 9) names the review and any child that did not run as not run, lists the unanswered questions with their IDs and ends with its pause line, which is not asking them a second time.
5. **Decide everything else yourself.** Take the option you would recommend for every other question, record the decision and its reason in the task record, and list them in the end report. The only exceptions are the open answers of step 4, which stay unauthorized, a security review, which runs only when the user asked for it, skipping [flow-verify](../flow-verify/SKILL.md), which only the user's own message can do, and the choice or the approval of a screen example, which stays unanswered and is reported as unresolved, as [Examples for a screen](../flow-research/SKILL.md#examples-for-a-screen) sets. Research makes no offer of proposals while the delegation is active: the plan settles the UI. While the delegation is active, capture and publish the first rendered view through [flow-walkthrough](../flow-walkthrough/SKILL.md) without waiting for human validation; this replaces only [flow-build](../flow-build/SKILL.md)'s first-view question, not its evidence or review requirements. Delegate and wait as [delegation](../flow-build/references/delegation.md) and [flow-verify step 6](../flow-verify/SKILL.md) set (a completion signal, no polling). Keep decisions and evidence in the existing task record; require no ledger, branch, hook or tracking system for this mode.
6. **Take effects within bounds.**
   - Any effect the objective needs, deployments and writes to shared or production systems included, is allowed when it is reversible or made reversible first and disrupts no other component beyond an interruption within the window the user stated at activation; with no window stated, no interruption. Before each, record the exact target, the change and how to revert it in the task record; this replaces asking for confirmation. Examples: creating a cloud resource only this work uses that spends no money or paid quota; editing a pull request's title or body, or replying on its threads, with the previous text saved; the force-push that [git-workflow step 4](../git-workflow/SKILL.md) allows for this mode.
   - A critical effect (as «Scope and authorization» defines it) that spends within a stated ceiling, or that is reversible or made reversible first, such as a migration after a verified backup with the service suspended only while it runs, is taken only when authorized in advance for that exact target and ceiling.
   - Forbidden: deleting or overwriting data, resources, credentials, history or branches without a verified way back; any change that breaks or interrupts other components or their users beyond that window; and every other irreversible effect, such as sending messages to real people, even when authorized in advance.
   - Skip an effect that is not allowed, continue the work that does not depend on it, and report it with its target, cost, revert and the decision it needs. The secret rules apply unchanged.
7. **Support artifacts.** Before writing or cleaning one, read [artifact layout and retention](../workspace-conventions/references/artifact-layout.md).
8. **Loops.** Work that repeats cycles of acting and measuring until a condition holds has a measure (an observable check run every cycle) and a cap (cycles, time or tokens), both stated at activation and set before the first cycle; without them it does not start. After each cycle, record the measure and the decisions in the change's `tasks.md`, or the saved-state destination of the artifact layout reference when there is none. When two cycles in a row bring no measurable improvement, stop and escalate: report what was tried, what failed, the current measure and what is needed to continue. Reaching the cap stops the loop. Record the final status.
9. **End.** At expiry or when the objective is complete, stop unattended effects, then report the completed and unresolved work, every effect applied with how to revert it, and the decisions taken, as [flow-close#final-report](../flow-close/SKILL.md#final-report) sets, and return control to the user.
