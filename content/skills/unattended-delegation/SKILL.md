# Unattended delegation

For explicit E2E work, read [coordination](../flow-build/references/e2e-coordination.md); E2E alone does not activate this skill.

This skill grants no broader tools or host permissions; step 6's irreversible or destructive actions stay forbidden even when authorized.

1. **Activate from one of three sources.** An explicit delegation; a user's message that they are leaving while authorized work is running; or the user's silence after they answered the route of the current work (its next-step block) and each delivery and review value it needs. Each delegates the authorized objective up to the delivery point the answers chose. Task duration alone, silence before those answers, and a background or scheduled turn activate nothing. Never record a delegation the user did not give: an inferred activation is reported as inferred, with the answer it rests on.
2. **Say so in visible text**: the source and the message or answer it rests on, quoted, then the objective, root or repository, references, destination, evidence, an expiry or deadline and, for work that repeats cycles, its measure and cap (step 8). The same message states the unforeseen-spend amount the user gave, one amount of money for spend no answer covers (step 6), or asks for it in one line; that question is not one of step 4's open answers, never puts the work under `hold`, no answer means zero. While it runs, every message to the user carries `· unattended, active` as an added part of its context line, or in its first line when it has none; the message that ends the delegation says that it ended and why.
3. **Keep or end it.** The delegation expires when the objective completes or the user sends a message that changes the objective, the scope or an answer in force, asks for other work, or tells you to stop. These messages, in any language, keep it: one that tells you to continue, acknowledges progress, or asks how the work is going; an answer to a question this delegation asked; one that adds information, a resource, feedback or a correction within the objective and scope. A message that fits both lists, such as a correction that changes the delivery mode, ends it; every other message ends it. Apply what a kept message adds, answer a question in one line, and say it continues.
4. **Close the open answers at activation.** For an explicit delegation or a leaving message whose objective reaches a build or a delivery, find which answers the work still lacks: the delivery mode and review that [flow-build](../flow-build/SKILL.md) asks before the first edit, and each critical effect it foresees that no class of the plan's effects round was asked for, classified as «Scope and authorization» sets, with its exact target and ceiling. State the answers already in force, which include each class of effect the user approved in the plan's effects round, as [outside the repository](../hive-rule-external-effects/SKILL.md) sets, its ceiling counting as spend authorized for that target. A class the user refused stays refused: skip its effects and report them. A class left unanswered adds no authorization, is not an open answer of this step and puts no work under `hold`: step 6 decides each of its effects. Ask the missing ones in one round, in the activation message, as [asking in text](../hive-rule-questions/SKILL.md) formats a question when no waiting card carries it, and keep working; this is the named exception to the rule of [asking a round](../hive-rule-questions/SKILL.md) that the turn ends with the round's last card, and to the rule of [delivery questions](../hive-rule-delivery-ask/SKILL.md) that its questions are asked before the first edit: never ask through a tool that blocks your turn, since the user may be gone. A reply that answers or changes an answer keeps it. Until the answers arrive, work under `hold` and decide nothing they cover: edit and verify the working tree as [flow-verify](../flow-verify/SKILL.md) does under `hold`, with the full suite when it runs, and no commit, publication, dedicated review or critical effect. The `hive-review-ux` child still runs for a UI change; it publishes nothing. The work is then incomplete; the end report (step 9) names the review and any child that did not run as not run, lists the unanswered questions with their IDs or headers and ends with its pause line, not a second ask.
5. **Decide everything else yourself.** Take the recommended option for every other question, log each decision with its reason, and list them in the end report. This includes questions whose own rule says never to act without the user's answer: adding test infrastructure, as [flow-build](../hive-rule-tests/SKILL.md) sets, opening a single ticket for a finding and the close's support-material decision, as [flow-close](../flow-close/SKILL.md) sets. This step is the instruction for those effects, which the objective needs. Opening such a ticket is allowed (closing it as not planned reverts it); a parent ticket with children is never created here and is reported as unresolved, as [breakdown](../create-issue/references/breakdown.md) sets; step 6 bounds the rest, so a deletion with no verified way back is skipped and reported. The end report presents each with how to revert it; the close's memory write records them as your decisions, not the user's, and not the test-infrastructure choice as a project decision. The exceptions are a question whose own rule says what unattended work does with it, such as the external-project question of «Scope and authorization», the open answers of step 4, which stay unauthorized, a security review, which runs only when the user asked for it or accepted it, skipping [flow-verify](../flow-verify/SKILL.md), which only the user's own message can do, and the choice or the approval of a screen example, which stays unanswered and is reported as unresolved, as [flow-figma-design](../flow-figma-design/SKILL.md#unattended-delegation) sets. Research offers no proposals while active: the plan settles the UI. While the delegation is active, capture and publish the first rendered view through [walkthrough](../hive-rule-walkthrough/SKILL.md) without waiting for human validation; this replaces only [flow-build](../flow-build/SKILL.md)'s first-view question, not its evidence or review requirements. Delegate and wait as [delegation](../hive-rule-delegation/SKILL.md) and [merge gate](../hive-rule-merge-gate/SKILL.md) set (a completion signal, no polling). Require no branch, hook or tracking system for unattended status.
6. **Take effects within bounds.** Before each effect, read [unattended effects](../hive-rule-unattended-effects/SKILL.md): allowed effects, the unforeseen-spend test, what stays forbidden, what to report for a skipped one.
7. **Support artifacts.** Before writing or cleaning one, read [layout and retention](../project-layout/references/layout.md).
8. **Loops.** Work that repeats cycles of acting and measuring until a condition holds has a measure (an observable check run every cycle) and a cap (cycles, time or tokens), both stated at activation and set before the first cycle; without them it does not start. After each cycle, log the measure and the decisions in the decision log. When two cycles in a row bring no measurable improvement, stop and escalate: report what was tried, what failed, the measure and what is needed to continue. Reaching the cap stops the loop. Record the final status.
9. **End.** At expiry or when the objective is complete, stop unattended effects, then report the completed and unresolved work, each effect applied with how to revert it, and the decisions taken, as [close report](../hive-rule-close-report/SKILL.md#final-report) sets, and return control to the user.

## Decision log

Unattended work and bounded E2E coordination keep one log at `<support home>/workspace/YYYY-MM-DD-<work>/decisions.tsv`, in the main checkout's support home (the declared workspace's `_support/` for work across repositories), never in a worktree the close removes, started from [the template](assets/decision-log.tsv): tab-separated, columns `ts`, `phase`, `decision`, `why`, `evidence`, `result`.

- One single-line row per decision and one per external effect. For an effect, evidence names the target and the change, and result says how to revert it.
- Evidence is a link or path (commit, PR, `file:line`, capture), never a paragraph.
- The task record keeps only progress. Never commit or publish the log unless the user asks; the end report cites it by path.
- In E2E only the coordinator writes it.
