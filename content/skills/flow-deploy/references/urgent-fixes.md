# Urgent production fixes

Read by [flow-deploy](../SKILL.md) when a production defect cannot wait for the next scheduled promotion.

A production defect cannot wait for the next scheduled promotion when the user says so, or when the defect is P0 by [close report](../../hive-core/close/close-report.md#findings); this paragraph is the definition other files point to. Use this route for such a defect when the repository has environment branches. Enter with the fix integrated, as the skill's entry sets: it follows the chosen delivery mode through [flow-build](../../flow-build/SKILL.md) into the base branch and is then promoted at once through each environment in the declared order, each promotion with its usual gates.

Before each promotion, list the commits it would carry besides the fix, such as `git log --oneline production..qa`. When it carries other work, name that work and ask whether it may reach production now; a commit that was not in the run's candidate is classified as step 5 of the skill sets. When the user holds any of it back, stop and offer a hotfix branch cut from the production branch with a pull request into it, only where the project's branch policy accepts a pull request from that branch; otherwise name the policy that blocks it. That pull request is a deviation from the promotion path, which the user confirms for that push under [promotion path](../../hive-core/git/promotion-path.md). After it merges, merge the same hotfix branch into the base branch, not a cherry-pick, so later promotions carry the same commits.

Under `ready` the promotion waits for the user's merge and asks its own authorization; under `hold` the verified fix is reported as a blocker, with the question of changing the delivery mode.

Verify each environment as [deployment checks](deployment-checks.md) sets; while an incident lasts, reduce its ongoing impact within existing authority, keep the evidence, and tell a temporary mitigation from a verified fix; mark a mitigation that changes code, and report each mitigation, as [defect fix](../../hive-core/build/defect-fix.md) sets for a workaround. At the fix's close, offer a short postmortem: what failed, the impact window, the cause, the fix, which layer should have caught it (a check, a test, a standard, a review criterion, or a deployment check), and a preventive action in that layer with its owner. Write it only when the user accepts, in the work's folder under `workspace/` when one exists, otherwise in the ticket.
