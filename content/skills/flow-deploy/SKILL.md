# Promote and verify what is served

## Entry and exit

This is a stage of its own, after integration, and one run can cover several tickets. Enter with an integrated, identified candidate (the commits on the base branch), and the repository's declared `Environments`; the authorization for each environment is asked in step 4. When these exist, enter directly, with no plan or build before it, and a request to promote or deploy is such an entry. Exit with, per environment, the served identity, the health and the functional acceptance each stated as met, failed, blocked, or "not run". This skill does not grant effects beyond the user's instructions.

## Procedure

1. **Name the run.** Say in one line the candidate, the environments in the declared order, and the tickets it carries. Without an `Environments` setting, ask once which environments the request reaches.
2. **Reconcile the promoted candidate.** Do the predeploy reconciliation in [deployment checks](references/deployment-checks.md#predeploy): what the promotion carries, destinations, migrations, compatibility, recovery and reusable prior evidence.
3. **Decide the rollback triggers.** Before a production deployment of code or infrastructure, record them as [deployment checks](references/deployment-checks.md#predeploy) sets, in the plan or in the conversation when there is none, before the first effect.
4. **Get the authorization.** Classify each effect and ask for what is missing as [effect authorization](../flow-plan/references/effect-authorization.md) sets: one answer per environment the run reaches, with a production deployment kept apart. A request to promote or deploy covers its delivery chain, not the effects a later environment's verification needs. An authorization left unanswered stays unauthorized, also under unattended delegation.
5. **Promote and deploy**, one environment at a time and in order, only through the declared promotion path that [git-workflow](../git-workflow/SKILL.md) keeps, and wait for the CI or deployment run the promotion triggers to reach a final state before step 6; its promotion pull request reviews only the commits not reviewed before their integration, as [delivery decisions](../flow-plan/references/delivery-decisions.md) sets, under the shared waiting rule; a run that fails leaves the promotion not verified. When a defect causes the failure, apply the global rule on defects that block the authorized work: the fix goes through [flow-build](../flow-build/SKILL.md) under the delivery answer in force, then from step 2 again for what the new promotion carries, without asking when that rule allows it.
6. **Check what is served.** After each deployment, verify the served identity and the health of every affected target as [deployment checks](references/deployment-checks.md#postdeploy) sets. A trigger that fires is reported to the user with its evidence; its recovery action runs only when an existing authorization covers it. A deployment with an unmatched identity, an unfinished rollout or an error observed after it is reported as not verified, never as healthy.
7. **Functional walk gate.** The walk runs only when the project declares it or the user asked to validate the deployment, through the children [deployment checks](references/deployment-checks.md#functional-walk) names; otherwise report it as not run, and do not offer it.
8. **Report** per environment: the identity served, the health and the functional acceptance, each as met, failed, blocked or "not run", the triggers decided, and the tickets that stay out of their completion state until a due check runs; at a later completion point, move each ticket whose `Completion` ref now holds it to its final state, as [project settings](../flow-plan/references/project-settings.md#later-completion-point) sets. Record the promotion in the project's mechanism, without reopening the ticket. Run [flow-close](../flow-close/SKILL.md) as its [When to run it](../flow-close/SKILL.md#when-to-run-it) sets.
