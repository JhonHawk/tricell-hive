# Promote and verify what is served

## Entry and exit

This is a stage of its own, after integration, and one run can cover several tickets. Enter with an integrated, identified candidate (the commits on the base branch), and the repository's declared `Environments`; the authorization for each environment is asked in step 4. When these exist, enter directly, with no plan or build before it, and a request to promote or deploy is such an entry. The run's candidate and tickets are fixed when it starts; classify a request to change them as the global guidance's «Scope changes» section sets. Exit with, per environment, the served identity, the health and the functional acceptance each stated as met, failed, blocked, or "not run". A production defect whose fix is not integrated yet is not an entry: send it to [flow-research](../flow-research/SKILL.md) while its cause is unknown, or to [flow-build](../flow-build/SKILL.md) once it is known, and enter here with the integrated fix.

## Prepare

Before delegating, read [delegation](../flow-build/references/delegation.md). Before a branch, merge or push that carries a promotion, read [git-workflow](../git-workflow/SKILL.md), which keeps the promotion invariant. Before stored-data changes, read [stored data](../flow-build/SKILL.md#stored-data). For the checks of this stage, read [deployment checks](references/deployment-checks.md). For a production defect that cannot wait (urgent fixes defines when), read [urgent fixes](references/urgent-fixes.md).

## Procedure

1. **Name the run.** Identify the candidate, the environments in the declared order, and the tickets it carries; state them in step 4's question when one is asked, and in the report. Without an `Environments` setting, ask once which environments the request reaches.
2. **Reconcile the promoted candidate.** Do the predeploy reconciliation in [deployment checks](references/deployment-checks.md#predeploy): what the promotion carries, destinations, migrations, compatibility, recovery and reusable prior evidence.
3. **Decide the rollback triggers.** Before a production deployment of code or infrastructure, record them as [deployment checks](references/deployment-checks.md#predeploy) sets, in the plan or in the conversation when there is none, before the first effect.
4. **Get the authorization.** Classify each effect and ask for what is missing as the global guidance's «Scope and authorization» section sets: one answer per environment the run reaches, with a production deployment kept apart.
   - In the promotion task of a plan, a non-production environment or an effect that a class answered in that plan's effects round covers is not asked again: read the answer in the `## Effects` section of its change folder, or in the summary of a plan kept in the conversation, as [outside the repository](../flow-plan/references/outside-the-repository.md#effects-round) sets. A run that does not come from that plan, or that carries tickets of other work, asks as this step sets. A production deployment is always asked apart.
   - A request to promote or deploy to a named environment is itself the delivery choice, so do not ask the delivery mode. It covers the chain the project defines for that environment: the promotion, its merge once the gates pass, the deployment with its identity and health checks, and the ticket moves they trigger. It covers production only when the user names production; any other effect beyond it is asked as «Scope and authorization» sets. It excludes the functional walk and the effects that walk needs in the environment, which are asked as [deployment checks](references/deployment-checks.md#functional-walk) sets.
   - A production question also names the recovery action of each rollback trigger from step 3, with the target it acts on and how to revert it, so one answer covers the actions step 6 may run; a critical recovery action, such as restoring data without a backup, keeps its own question in that round. A fix-forward is not such an action: when a trigger calls for one, report it, send the fix through [flow-build](../flow-build/SKILL.md), and promote it as [urgent fixes](references/urgent-fixes.md) sets when production cannot wait, otherwise as a new run from step 1, each with its own production question.
   - Record the promotion in the project's mechanism, without reopening the ticket. A mechanism that publishes, such as a release, is a critical effect and takes its own question unless the user asked for it («Scope and authorization»).
5. **Promote and deploy**, one environment at a time and in order, and wait for the CI or deployment run the promotion triggers to reach a final state before step 6; a run that fails leaves the promotion not verified, unless each of its failures, such as a failing test, is one the target environment's last run before this promotion already had with the same error and does not block the promotion: handle those as [findings](../flow-close/SKILL.md#findings) sets.
   - **Path:** when the environments are branches, promote only through the declared promotion path that [git-workflow](../git-workflow/SKILL.md) keeps; its promotion pull request reviews only the commits not reviewed before their integration, which includes every commit whose message has an `Unreviewed: <reason>` line ([flow-verify step 3](../flow-verify/SKILL.md) writes those); wait for its CI as [flow-verify step 6](../flow-verify/SKILL.md) sets, on a completion signal, without polling. When they are not branches, promote through the mechanism the project's guidance documents for moving a build to the next environment and open no promotion pull request; when none is documented, ask for it once, before the first effect.
   - **A defect causes the failure:** apply the global rule on defects that block the authorized work: the fix goes through [flow-build](../flow-build/SKILL.md) under the delivery answer in force, without asking when that rule allows it. Before step 2 runs again, list the commits on the base branch that were not in the candidate fixed in step 1. The fix is the only one the run adds without asking: name the others and ask once, for each, whether it goes out with the fix or is reverted on the base branch as its own change; then, since the candidate changed, stop this run at a safe point and start the next one from step 1, carrying the fix. With no others, step 2 runs again for what the new promotion carries.
6. **Check what is served.** After each deployment, verify the served identity and the health of every affected target as [deployment checks](references/deployment-checks.md#postdeploy) sets. A trigger that fires is reported to the user with its evidence. Run its recovery action when the answer of step 4 covers it; otherwise ask for it as step 4 sets and run nothing meanwhile. A deployment with an unmatched identity, an unfinished rollout, or a failed check or error observed after it, such as an error status on login, is reported as not verified, never as healthy.
7. **Functional walk gate.** Run the walk, or report it as not run and do not offer it, as [deployment checks](references/deployment-checks.md#functional-walk) sets.
8. **Report** the run named in step 1 and, per environment, the identity served, the health and the functional acceptance, each as met, failed, blocked or "not run", the triggers decided, the pre-existing CI failures step 5 let through, and the tickets that stay out of their completion state until a due check runs. Record the promotion as step 4 sets.
   - **Completion:** when the repository's `## Hive` declares `Completion` (`<state> on <ref> · …`), once the deployment is verified move each ticket whose change that ref now holds to the state its tracker's value declares, as «Project settings» sets; a ticket whose due check did not run stays out of it.
   - Then run [flow-close](../flow-close/SKILL.md) for the deploy's cleanup: the tickets and the change record closed at integration, so what remains is the temporaries and processes this run started, and its final report, run at once as flow-close sets for a deploy's cleanup close.
