# Promote and verify what is served

## Entry and exit

This is a stage of its own, after integration, and one run can cover several tickets. Enter with an integrated, identified candidate (the commits on the base branch), and the repository's declared `Environments`; the authorization for each environment is asked in step 4. When these exist, enter directly, with no plan or build before it, and a request to promote or deploy is such an entry. The run's candidate and tickets are fixed when it starts; classify a request to change them as [scope changes](../hive-core/references/scope-changes.md) sets. Exit with, per environment, the served identity, the health and the functional acceptance each stated as met, failed, blocked, or "not run". A production defect whose fix is not integrated yet is not an entry: send it to [flow-research](../flow-research/SKILL.md) while its cause is unknown, or to [flow-build](../flow-build/SKILL.md) once it is known, and enter here with the integrated fix. This skill does not grant effects beyond the user's instructions.

## Prepare

Before resolving needed project settings, read [project settings](../hive-core/references/project-settings.md). Before a user decision or manual validation request, read [questions](../hive-core/references/questions.md). Before asking to authorize an effect beyond this machine, read [effect authorization](../hive-core/references/effect-authorization.md). Before delegating or starting an external-work wait, read [delegation and waits](../flow-research/references/delegation.md). Before progress reports, completion reports or messages containing citations, links or externally defined IDs, read [reporting](../flow-close/references/reporting.md). Before a branch, merge or push that carries a promotion, read [git-workflow](../git-workflow/SKILL.md), which keeps the promotion invariant. Before stored-data changes, read [persistent data changes](../flow-build/references/data-changes.md). For the checks of this stage, read [deployment checks](references/deployment-checks.md). For a production defect that cannot wait, read [urgent fixes](references/urgent-fixes.md).

## Procedure

1. **Name the run.** Say in one line the candidate, the environments in the declared order, and the tickets it carries. Without an `Environments` setting, ask once which environments the request reaches.
2. **Reconcile the promoted candidate.** Do the predeploy reconciliation in [deployment checks](references/deployment-checks.md#predeploy): what the promotion carries, destinations, migrations, compatibility, recovery and reusable prior evidence.
3. **Decide the rollback triggers.** Before a production deployment of code or infrastructure, record them as [deployment checks](references/deployment-checks.md#predeploy) sets, in the plan or in the conversation when there is none, before the first effect.
4. **Get the authorization.** Classify each effect and ask for what is missing as [effect authorization](../hive-core/references/effect-authorization.md) sets: one answer per environment the run reaches, with a production deployment kept apart.
   - A request to promote or deploy to a named environment is itself the delivery choice, so do not ask the delivery mode. It covers the chain the project defines for that environment: the promotion, its merge once the gates pass, the deployment with its identity and health checks, and the ticket moves they trigger. It covers production only when the user names production, and the rest as [what an answer covers](../hive-core/references/effect-authorization.md#what-an-answer-covers) sets. It excludes the functional walk and the effects that walk needs in the environment, which are asked as [deployment checks](references/deployment-checks.md#functional-walk) sets.
   - A production question also names the recovery action of each rollback trigger from step 3, with the target it acts on and how to revert it, so one answer covers the actions step 6 may run; a critical recovery action, such as restoring data without a backup, keeps its own question in that round. A fix-forward is not such an action: when a trigger calls for one, report it, send the fix through [flow-build](../flow-build/SKILL.md), and promote it as [urgent fixes](references/urgent-fixes.md) sets when production cannot wait, otherwise as a new run from step 1, each with its own production question.
   - Record the promotion in the project's mechanism, without reopening the ticket. A mechanism that publishes, such as a release, is a critical effect and takes its own question unless the user asked for it, as effect authorization sets.
   - An authorization left unanswered stays unauthorized, also under unattended delegation.
5. **Promote and deploy**, one environment at a time and in order, and wait for the CI or deployment run the promotion triggers to reach a final state before step 6; a run that fails leaves the promotion not verified, unless each of its failures, such as a failing test, is one the target branch's last run before this promotion already had and does not block the promotion: handle those under the shared incidental-findings rule and list them in step 8's report.
   - **Path:** when the environments are branches, promote only through the declared promotion path that [git-workflow](../git-workflow/SKILL.md) keeps; its promotion pull request reviews only the commits not reviewed before their integration, as [delivery decisions](../flow-plan/references/delivery-decisions.md) sets, under the shared waiting rule. When they are not branches, promote through the mechanism the project's guidance documents for moving a build to the next environment and open no promotion pull request; when none is documented, ask for it once, before the first effect.
   - **A defect the promoted commits bring causes the failure:** apply the global rule on defects that block the authorized work: the fix goes through [flow-build](../flow-build/SKILL.md) under the delivery answer in force, without asking when that rule allows it. Before step 2 runs again, list the commits on the base branch that were not in the candidate fixed in step 1. The fix is the only one the run adds without asking: name the others and ask once, for each, whether it goes out with the fix or is reverted on the base branch as its own change; then, as the Promotion bullet of [scope changes](../hive-core/references/scope-changes.md#where-the-work-returns) sets for a changed candidate, stop this run at a safe point and start the next one from step 1, carrying the fix. With no others, step 2 runs again for what the new promotion carries.
6. **Check what is served.** After each deployment, verify the served identity and the health of every affected target as [deployment checks](references/deployment-checks.md#postdeploy) sets. A trigger that fires is reported to the user with its evidence. Run its recovery action when the answer of step 4 covers it; otherwise ask for it as step 4 sets and run nothing meanwhile. A deployment with an unmatched identity, an unfinished rollout, or a failed check or error observed after it, such as an error status on login, is reported as not verified, never as healthy.
7. **Functional walk gate.** Run the walk, or report it as not run and do not offer it, as [deployment checks](references/deployment-checks.md#functional-walk) sets.
8. **Report** per environment: the identity served, the health and the functional acceptance, each as met, failed, blocked or "not run", the triggers decided, the pre-existing CI failures step 5 let through, and the tickets that stay out of their completion state until a due check runs; at a later completion point, move each ticket whose `Completion` ref now holds it to its final state, as [project settings](../hive-core/references/project-settings.md#later-completion-point) sets. Record the promotion as step 4 sets. Run [flow-close](../flow-close/SKILL.md) as its [When to run it](../flow-close/SKILL.md#when-to-run-it) sets.
