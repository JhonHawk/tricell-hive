# Backlog report

Read before answering a question about the project's status or a request to list its backlog.

Give the delivery state and, when the project declares a tracker, a backlog report that groups five or more tickets by product module in the first answer, queried across all non-terminal states rather than by recent activity, never as a flat list or per-state dump, and never grouped by tracker state, application, repository, or layer. When the user asks for another cut of the tickets, such as those that fit one session, those blocking a release, or a single module's tickets, structure the answer by that cut instead, and include state counts or delivery state only when they change the answer. The bullets below set the default report; a requested cut replaces its grouping, state-count line and rework counts, while the ticket IDs and the read-only collection still apply. Run the tracker queries the report needs as [Split work](delegation.md#split-work) sets for queries that list tickets.

- Take modules from tracker labels or projects, otherwise from titles; a tracker state, application, repository, or layer may appear only as a suffix.
- After the modules, group cross-cutting work such as infrastructure, CI, tests, tooling, and technical debt by type.
- Keep an initiative's umbrella and its phases together and in order, list deferred tickets apart, and name those blocking the next promotion.
- Give every ticket its ID.
- Open with one line per non-terminal state and its count, in-progress first; after the backlog, list relevant workspace state outside the tracker.
- In a status report, not a plain backlog listing, give the rework of recent integrations right after the state counts, or within the delivery state when the project declares no tracker. Its window starts at the last promotion to the last environment that the repository's `Environments` setting declares after the base branch, as Git or the project's promotion mechanism records it, such as a merge into that environment's branch, a release, or a tag; with no such environment or no recorded promotion, the window is the last 30 days. Open with one line that names the window's start and gives three counts, then put each counted item on its own list line with its ID or link:
  - reverts made in the window of commits integrated into the base branch in it, found by the revert message, such as `This reverts commit` or `Revert "`;
  - tickets closed by work integrated in the window and reopened since;
  - bug tickets, meaning those the tracker labels or types as a bug, opened in the window whose body or links cite a ticket or pull request integrated in it.

  Give counts, never rates or targets, collected read-only through Git and the tracker's existing CLI or tool; run their tracker queries as the opening paragraph sets, and delegate any other collection that would produce long output as [flow-research](../SKILL.md) sets for the state of named targets. Without a tracker, give only the reverts and say that the tracker counts are unavailable; when nothing was integrated in the window, say so in the opening line instead of giving zeros.
- Close by recommending which group or ticket to take first and why: production user-visible bugs, then security or data integrity, then promotion blockers, then debt and tooling; among equals, the smallest and most visible first. List a ticket another session has in progress apart, never as the recommendation, as the global ticket rule sets. A status report ends with these recommendations; ask the route question only when the user asked what to take next.
