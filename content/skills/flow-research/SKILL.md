# Research what the user needs

Research settles what the work is; `flow-plan` settles how. It publishes nothing to the viewer, and changes nothing in the project, tracker or shared data except through the work it hands to `flow-build`, a single action the user asks for, the examples [Examples for a screen](#examples-for-a-screen) sets, and the writes the global guidance's «Local instructions» authorizes. Follow-up questions keep it open and authorize nothing.

0. **Complete request.** When the request already says everything that changes the result, such as "add this user to the repository", keep the next steps short: read what it touches (step 1), check that nothing blocks it, such as missing access or a false premise, and skip step 3's questions, except the offer of [Examples for a screen](#examples-for-a-screen) when its conditions hold. An action that changes no repository file is then done and reported, under the global guidance's effect rules; a change to repository files takes step 5's route. A request whose deliverable is a design, such as replicating a screen in a design file, is drawn as [Examples for a screen](#examples-for-a-screen) sets, and is not reported as done before the user approves the example. When one bounded lookup (as «Proportionality» defines it) answers a question, report the answer with its source and uncertainty, and stop.
1. **Read before asking.** Before the first read, unless the reads fit one bounded lookup, write in the message the aspects the answer needs, the sources each takes and which go to a child under step 4. Then read the code, ticket, configuration and verified memory the request touches; these reads count toward step 4's limits. Never ask what they answer.
2. **Play the request back.** State in your words what the user wants, for whom and why, with what you found: a conflict, a false premise, a cheaper path, or that the request is really several.
3. **Ask what is missing.** When something that changes what gets built is still open, such as why now, what success looks like, what must not happen or what they already tried, ask one open question per message, in the text, with why you ask and no menu of example answers, and add that they can tell you to just start. When they say to just guess, propose something concrete. Choices between options go through the question tool, as «Questions and routes» sets. When the conditions of [Examples for a screen](#examples-for-a-screen) hold, make its offer.
4. **Investigate what is unknown.**
   - Delegate to a `hive-research` child each aspect of step 1's list that needs more than 5 large reads, as the global guidance's «Proportionality» defines them, before reading it, and do not read in the main thread what a child covers; filtered reads do not count. When the main thread reaches its sixth large read on one aspect without its answer, stop and delegate what remains of it. Add an aspect found later to the list in the message before its first read. Launch independent children together, briefed and awaited as [delegation](../flow-build/references/delegation.md) sets. A host's built-in explorer only locates files; verify what it returns.
   - Run a tracker query that lists tickets in the main thread, capped at 50 tickets and short fields; use `hive-read-state` children only for several independent collections at once. Search each declared tracker for an existing ticket before proposing one.
   - For a failure whose cause is not yet shown, list the plausible causes and check each one, in parallel when independent; report the ones ruled out with their evidence.
   - Name each system the decision touches and whether you searched it.
   - Open the source of each claim that decides the answer instead of recalling it. Resolve conflicting sources by date, version, scope and direct observation; missing delivery evidence means delivery is not verified, not that it did not happen.
5. **Close the what.** Report the answer, its evidence and what remains uncertain, and play back what you understood, marking what the user said apart from what you propose. Then:
   - When the user asked to analyze, explain, review or diagnose without asking for a change, end at the findings with the block of «Questions and routes», recommending no flow; when the findings confirm a defect in the current project, list the reply that fixes it among its options. When the user picked a ticket for research without asking for a change, and the findings confirm work it asks for, end instead with the next-step block toward `flow-plan`, or toward `flow-build` when that work is a small understood change (the global guidance's «Proportionality»), and never continue into build in the same turn; when they confirm no work, end at the findings with that block.
   - When the user asked for a change, not whether or how to make one, and its how leaves no decision for them and could be finished from the request and `git diff` alone, continue into `flow-build` in the same turn.
   - Otherwise, end with the route to `flow-plan` and its reason.

   When this step ends with a route to `flow-plan` or `flow-build`, or continues into `flow-build`, write one line with the scope estimated from the reads, before the next-step block when there is one, so the user can narrow it before choosing: about how many files and which areas (for a chosen ticket, its complexity from «Assess a chosen ticket»), and the stages and checks the guidance sends such work through, such as plan, per-task verification, a review, CI, and a promotion only when the request asks for one. Mark it as an estimate, since delivery and review are asked later, such as "Scope (estimate): ~42 files (contracts, runtime, tests, manual) · plan + per-task verification + review + UX review · PR and CI". A reply that narrows the scope without naming a flow gets the revised line and the same ending again.

   When the user approved an example, as [Examples for a screen](#examples-for-a-screen) sets, name it in the report with its record, and in the scope line.

   Creating a ticket is a single action, offered as a reply or asked, never part of a route. The user's reply authorizes only the flow it names, or the single action it answers.

## Examples for a screen

An example is a drawing of one screen that the user picks or corrects before the work is planned. It settles what the screen is; the plan, the build and the verification then compare against it.

**When to offer.** Offer examples when all of these hold: the user asked for a change, not only an analysis or the assessment of a ticket; what gets built includes a new screen, or an existing one that adds, removes or moves a region; and neither the request nor an existing screen of the project fixes its composition. Make no offer for a change that keeps the screen's layout, such as a button, a copy, a field or a column, nor while [unattended delegation](../unattended-delegation/SKILL.md) is active: the plan then settles the UI as [UI decisions](../flow-plan/SKILL.md#ui-decisions) sets.

**The offer.** Ask once per work, as a decision of the global guidance's «Questions and routes», whether the user wants you to design and present proposals for the screen. Its options:

- **In the design file**, only when the app's `DESIGN.md` declares one, as [design record](../hive-ui-criteria/references/design-record.md) sets its `**Design file:**` field, or the user named one in the conversation, and the host has a connection that can write to it. Check both yourself; never ask which tool to use. The option's label or description names the file and says that you will create frames on a page of it. The user's choice of this option is their instruction for that write. It replaces no question a critical effect takes: a write that spends money or paid quota still gets its own.
- **As text sketches**, always, in the format [UI decisions](../flow-plan/SKILL.md#ui-decisions) sets.
- **No proposals**, always: the plan settles the UI.

Recommend the design file when it is offered, otherwise text sketches.

**Draw.** Load the project's design system first, as [hive-ui-criteria](../hive-ui-criteria/SKILL.md) sets. Draw two or three examples when the composition is open, and one when the request or an existing screen fixes it. Draw each at desktop width with the project's tokens and components, the real labels, and data of realistic volume. In a design file, create frames on a page named after the work, and change or delete only the nodes this work created: never variables, styles, components or existing pages. One `hive-design-ui` child draws the frames when the host gives its children that connection, as [delegation](../flow-build/references/delegation.md) sets, briefed with the file, the page and, for a correction or a removal, the nodes this work created; otherwise the main thread draws them. The main thread draws text sketches.

**Choose.** Ask the user to pick or correct, as one decision with one option per example: each option carries its frame's location and a summary of its composition, or its sketch in the preview; with a single example, the options are to approve it or to correct it. Redraw the chosen example for each correction. When the screen is served on mobile, draw the chosen example at 440 px wide too, and ask the user to approve or correct it before recording it. While unattended delegation is active, leave this decision unanswered and report it as unresolved.

**Record.** Write the approved example in the report and in `examples.md` in the work's folder under `_support/workspace/`, placed as [artifact layout](../workspace-conventions/references/artifact-layout.md) sets: for a frame, the tool, the file's location, each frame's node, and the path of its local image in that folder's `images/`; for a text sketch, the sketch itself. The location and the nodes are the record: the image is a local copy, read again from them where it is missing. Remove the examples not chosen. The plan takes the approved example as the screen's reference.

**A request for the design itself.** When the request's deliverable is the design, such as replicating a screen in a design file, draw it as this section sets, without the offer: the request is the instruction. When it names a page or frames as the target, draw there instead of on a page of the work's own, and change only the frames it names and the nodes this work creates. When the host cannot write to that file, report it as a blocker, with text sketches as the other route. Do not report the work as done before the user approves the example; while unattended delegation is active, leave that approval unanswered and report it as unresolved. After the approval, report the result with the example's record and run [flow-close](../flow-close/SKILL.md), which closes it as an operational task.

## Assess a chosen ticket

When the user picks a ticket, add to the report its **impact** (what uses what it changes, found by searching its literal values and direct callers, and whether it touches production), **complexity** (the files, modules and contracts it changes), **readiness** (settled criteria and decisions, and the access or answers missing) and **dependencies** (the tickets it waits on or blocks). A ticket whose criteria are missing, that names more than one change, or that the specs contradict is not ready: settle its scope here, in rounds, before step 5.
