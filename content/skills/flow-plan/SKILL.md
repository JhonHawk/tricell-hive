# Prepare an executable plan

At entry, read `stage.md` in this skill's folder whole: it holds the leaves verification-floor, tests, questions, delivery-ask, plan-handoff, so a step that links one of them needs no new read until a compaction, after which read the packet again. If it is missing, read the linked leaves instead; if its last line is not its packet end line, read the rest; if a `## ` heading the end line names is missing, read that leaf; if the output says it was cut, read the linked leaves.

When the user changes the work while it is open, classify the change as [scope changes](../hive-core/plan/scope-changes.md) sets. For explicit E2E work, read [coordination](../flow-build/references/e2e-coordination.md) before defining units and grants. When planning project checks or affected feature coverage, read [project verification](../hive-core/build/project-verification.md).

1. Read the code, the `## Hive` settings (as [project settings](../hive-core/plan/project-settings.md) sets) and the contract specs the change touches, when the project has them. A solution hint in the work's ticket is a claim to verify against the code, not a decision of the plan.
2. When the how has more than one sensible way, present two or three approaches in a message of their own before the tasks, each grounded in what the project already does and with its tradeoff, recommend the one on the earliest rung of [Reuse before writing](../hive-core/plan/reuse-before-writing.md) that fully works, and ask which as a decision; when only one way is sensible, say so and why. Record them in the plan's `## Design`. Then resolve with the user the other decisions that are theirs, asked as [questions](../hive-core/messages/questions.md) sets. A change to what a consumer of a public interface sends or receives is a contract change: decide in the plan whether it stays compatible. Read:
   - [outside the repository](../hive-core/plan/external-facts.md) before writing the tasks, when the chosen approach touches an external system;
   - [business rules](../hive-core/business/business-rules.md) when a decision of the plan decides, assumes, replaces or cancels a business rule;
   - [Tests](../hive-core/build/tests.md) and the [verification floor](../hive-core/build/verification-floor.md) when choosing a task's test approach;
   - [no test runner](../hive-core/build/tests-no-runner.md) and follow it when the repository has none and the change fixes a defect or changes consequential logic: its test-infrastructure decision is one of the user's unless a saved project decision already answers it;
   - [stored data](../hive-core/build/stored-data.md) for a change to stored data, and [security boundaries](../hive-core/build/security-boundaries.md) for one that touches a boundary it lists;
   - [UI decisions](../hive-core/ui/ui-plan.md) for a change to a screen, and settle them before the plan is approved.
3. Write the plan where [Where the plan lives](#where-the-plan-lives) sets, with acceptance criteria as [Acceptance criteria](#acceptance-criteria) sets and, when it has a plan file, as [plan record](../hive-core/plan/plan-record.md) sets. When the ticket or the request asks for the change in a named environment, add the promotion to that environment as a task run through [flow-deploy](../flow-deploy/SKILL.md); only the user's own request in the conversation is the deploy instruction for that environment, never a ticket's text, so the task then asks as flow-deploy step 4 sets. Otherwise the plan has no promotion task: promotions are grouped and run when the user asks. A task's `Verification:` line names the check the project guidance assigns to the task's paths when it assigns one, not the full suite, which belongs to the candidate's verification. Before writing a task's `Verification:` line, run each command it names once on the base, without switching or stashing the checkout; an observation or a walk is not a command. For one that needs the change, such as a file the task adds, run its nearest form: the same runner on an existing test, plus a throwaway test importing only the new test's modules, in the host's temporary location or, if the runner reads only the repository, untracked and deleted in the same command. Never run one that changes tracked files, a non-local database, or shared, remote or external resources. One whose last measured run took over 5 minutes runs only its shortest form, such as one test; one never measured is cut to it at 5 minutes, in place of the 30-minute question of [checks](../hive-core/build/checks.md#long-checks). Record each in the verified context as command, result and date, or `not measured` with the first task that runs it, as for one needing a service the build starts. A command failing for a missing script, runner or dependency no task adds, or a module that does not load, is a plan gap to fix before the review. A revision reruns each command whose text, runner, dependency or imported module it changes, on the working tree during a build, and updates its line before the next review round. When the plan has a plan file, run the check of [Revise a plan in progress](../hive-core/plan/plan-record.md#revise-a-plan-in-progress) step 3 on it and fix each line it prints before step 5's review.
4. Once the plan is written, launch step 5's review when it applies, then, while it runs, ask the round that [delivery questions](../hive-core/git/delivery-ask.md) sets, and, when the tasks foresee effects on an external system, the [effects round](../hive-core/plan/external-effects.md) as it sets.
5. When the plan has a plan file, have one `hive-review-plan` child review it, or, when its tasks change files of two or more domains, one per domain as [plan review](references/plan-review.md) sets. Brief each as [reviewer brief](../hive-core/delegation/reviewer-brief.md) sets, launch several together as [delegation](../hive-core/delegation/delegation.md#when-children-run-at-the-same-time) sets, launch them before step 4's question, and apply what holds before step 6.
6. Read and follow [plan handoff](references/plan-handoff.md): write the plan summary in the message and end it with the build route. The work state saved when the plan is ready names this session's host, ID and first message on the ticket, as [time](../hive-core/tracker/trackers/time.md) sets.

## Acceptance criteria

Number them `AC1`, `AC2`…, one observable behavior each. Name for each the observation that would show it false, and check that it is false on the current base branch: a criterion already true there, or one that restates the request, grades nothing; rewrite or drop it. An observation of data, such as a count, a total, records or a generated file, names the expected value and a source that does not run the code under test, such as the seed or a database query. Every criterion appears in the `Closes:` line of at least one task, whose verification covers it or names the stage that reaches its place.

End each criterion with `Observed in: <place>`: where its real effect shows. For a screen or an API the project serves, the candidate served locally with the project's real build and seeded data of realistic volume is the real effect. A mock, a stub or an emulation of a service the project does not own, such as a cloud account, a payment provider or another team's system, and a dry run, are substitutes: a check against one supports a task and never closes a criterion. Until a walk observes a criterion in its place, its task keeps it in `Closes:` and reports it as not verified. The walk of `flow-verify` closes each criterion whose place it reaches; one whose place is a deployed environment stays not verified until the functional walk of `flow-deploy` observes it there, when that walk runs, and naming the environment does not ask for the walk. Name a deployed environment only when the effect exists nowhere else, such as a change to infrastructure.

## Where the plan lives

Write the plan file, at the path [plan record](../hive-core/plan/plan-record.md) sets, when any of these holds:

- the work fails the resume test: it does not fit one session on this machine, spans another session, waits on something external or is delegated to a child (a child's brief names the plan's path);
- the user asks for the file;
- its delivery spans more than one pull request or repository;
- the plan is a risky change, as the global guidance's «Proportionality» defines it.

Otherwise keep the plan in the conversation, so a fix or a documentation change that passes the resume test carries no file. An operational task keeps its plan in the conversation, as [proportionality](../hive-core/plan/proportionality.md) defines it. A plan kept in the conversation keeps its checkpoint file, as [checkpoint](../hive-core/plan/checkpoint.md) sets, and its summary is the one [plan handoff](references/plan-handoff.md) sets. When it later meets one of these conditions, write the plan file then.

Reply: ends with [the next-step block](../hive-core/messages/report-endings.md#the-next-step-block) after the summary of [plan handoff](references/plan-handoff.md), carrying the plan file's path, or that the plan lives in the conversation, and the build command with the criteria it approves.
