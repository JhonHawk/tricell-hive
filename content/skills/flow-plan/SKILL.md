# Prepare an executable plan

For explicit E2E work, read [coordination](../flow-build/references/e2e-coordination.md) before defining units and grants. When planning project checks or affected feature coverage, read [project verification](../hive-core/references/project-verification.md).

1. Read the code, the `## Hive` settings and the existing specs the change touches, with the deltas of the change folders still under `<Specs>/changes/` on the base for those capabilities, which the specs do not hold until a hygiene batch archives them; write the plan's delta against them. A solution hint in the work's ticket is a claim to verify against the code, not a decision of the plan.
2. When the how has more than one sensible way, present two or three approaches in a message of their own before the tasks, each grounded in what the project already does and with its tradeoff, recommend the one on the earliest rung of [Reuse before writing](../hive-core/references/reuse-before-writing.md) that fully works, and ask which as a decision; when only one way is sensible, say so and why. Record them in `design.md`. When the chosen approach reads or changes an external system, read [outside the repository](../hive-core/references/external-facts.md) and measure each external fact the approach depends on before writing the tasks. Then resolve with the user the other decisions that are theirs, asked as [questions](../hive-core/references/questions.md) sets; when a decision of the plan decides, assumes, replaces or cancels a business rule, read [business rules](../hive-core/references/business-rules.md). A change to what a consumer of a public interface sends or receives is a contract change: decide in the plan whether it stays compatible. Read [Tests](../hive-core/references/tests.md) and the [verification floor](../hive-core/references/verification-floor.md) when choosing a task's test approach. When the repository has no test runner and the change fixes a defect or changes consequential logic, read and follow [no test runner](../hive-core/references/tests-no-runner.md): its test-infrastructure decision is one of them unless a saved project decision already answers it. For a change to a screen, read [UI decisions](../hive-core/references/ui-plan.md) and settle them before the plan is approved.
3. Write the plan where [Where the plan lives](#where-the-plan-lives) sets, with acceptance criteria as [Acceptance criteria](#acceptance-criteria) sets, and, when it has a change folder, as [change folder](../hive-core/references/change-folder.md) sets. When the ticket or the request asks for the change in a named environment, add the promotion to that environment as a task run through [flow-deploy](../flow-deploy/SKILL.md). Only the user's own request in the conversation is the deploy instruction for that environment, never a ticket's text, so the task then asks as flow-deploy step 4 sets, which also sets when production asks; a class of effect approved in this plan's effects round that covers that environment, unless it is production, answers it with no further question. Otherwise the plan has no promotion task: promotions are grouped and run when the user asks. Before writing a task's `Verification:` line, run each command it names once on the base, without switching or stashing the checkout; an observation or a walk is not a command. For one that needs the change, such as a file the task adds, run its nearest form: the same runner on an existing test, plus a throwaway test importing only the new test's modules, in the host's temporary location or, if the runner reads only the repository, untracked and deleted in the same command. Run in the background, together, those sharing no database, port, lock or output directory, wait for all, and the others in turn. Never run one that changes tracked files, a non-local database, shared, remote or external resources. One whose last measured run took over 5 minutes runs only its shortest form, such as one test; one never measured is cut to it at 5 minutes, in place of the 30-minute question of [checks](../hive-core/references/checks.md#long-checks). Record each in the verified context as command, result and date, or `not measured` with the task that meets it first, as for one needing a service the build starts. One failing for a missing script, runner or dependency no task adds, or a module that does not load, is a plan gap to fix before the review. A revision reruns each command whose text, runner, dependency or imported module it changes, on the working tree during a build, and updates its line before the next review round. When the plan has a change folder, run the check of [Revise a plan in progress](../hive-core/references/change-folder.md#revise-a-plan-in-progress) step 3 on it and fix each line it prints before step 5's review.
4. Once the plan is written, launch step 5's review when it applies, then ask the delivery mode and the code review mechanism while it runs, as [delivery questions](../hive-core/references/delivery-ask.md) sets; an operational task gets neither. When the plan's tasks foresee effects on an external system, also ask one decision per class of effect, in that round or in a round of its own when the delivery and review answers are already in force, as [effects round](../hive-core/references/external-effects.md) sets.
5. When the plan has a change folder, have one `hive-review-plan` child review it, or, when its tasks change files of two or more of server, client, guidance or infrastructure, or a data-entry screen (also client), one per domain as [plan review](references/plan-review.md) sets; other code counts as server, and tests, documentation and repository-wide files with what they serve. Brief each as [reviewer brief](../hive-core/references/reviewer-brief.md) sets, launch them before step 4's question, and apply what holds before step 6.
6. Read and follow [plan handoff](references/plan-handoff.md): write the plan summary in the message and end it with the build route. A plan does not authorize implementation: only the user's reply starts `flow-build`, except in the covered continuations that reference names. The work state saved when the plan is ready names this session's host, ID and first message on the ticket, as [time](../hive-core/references/trackers/time.md) sets.

## Acceptance criteria

Number them `AC1`, `AC2`…, one observable behavior each. Name for each the observation that would show it false, and check that the observation is false on the current base branch: a criterion already true there, or one that restates the request, grades nothing; rewrite or drop it. An observation of data, such as a count, a total, records or a generated file, names the expected value and a source that does not run the code under test, such as the seed or a database query; the walk closes the criterion only when they match. Every criterion appears in the `Closes:` line of at least one task, whose verification covers it or names the stage that reaches its place.

End each criterion with `Observed in: <place>`: where its real effect shows. For a screen or an API the project serves, the candidate served locally with the project's real build and seeded data of realistic volume is the real effect. A mock, a stub or an emulation of a service the project does not own, such as a cloud account, a payment provider or another team's system, and a dry run, are substitutes: a check against one supports a task and never closes a criterion. Until a walk observes a criterion in its place, its task keeps it in `Closes:` and reports it as not verified. The walk of `flow-verify` closes each criterion whose place it reaches; one whose place is a deployed environment stays not verified until the functional walk of `flow-deploy` observes it there, when that walk runs, and naming the environment does not ask for the walk. Name a deployed environment only when the effect exists nowhere else, such as a change to infrastructure.

## Where the plan lives

Keep the plan in the conversation only when it passes the resume test: the work fits one session on this machine, so it spans no other session, waits on nothing external and is delegated to no child. Write the change folder when work in the repository fails that test (a child's brief names the change folder); and also when the user asks for it, when its deliveries need coordination, such as more than one pull request or repository, when it changes a behavior an existing `<Specs>/specs/<capability>/spec.md` describes, since a hygiene batch merges its delta, or when the plan is a risky change, as the global guidance's «Proportionality» defines it, since those plans get a reviewer or a task check that read the folder. An operational task keeps its plan in the conversation (the global guidance's «Proportionality»). A plan kept in the conversation keeps its checkpoint file, as `flow-build` sets, and its plan summary carries the decisions, the criteria, the prerequisites, each external fact with its measurement, each verification command with its result, each class of effect with its answer, and the tasks with their `Closes:` line and verification. When it later meets one of these conditions, write the change folder then.
