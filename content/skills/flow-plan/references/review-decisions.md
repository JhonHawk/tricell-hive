# Review decisions

## When to read

Read when resolving the implementation code-review mechanism, in the delivery round that [delivery decisions](delivery-decisions.md) sets or, for work that will not end in a Git delivery, before its first edit as [flow-build](../../flow-build/SKILL.md) sets, or when placing the dedicated code review in time. Before presenting the review question, read [questions](questions.md). Reading this reference does not invoke the planning workflow.

## Resolve the review mechanism

Resolve the implementation code-review mechanism and boundary in the same exchange as the delivery mode, for every mode including hold, so delivery does not ask again. A mechanical change, as the global guidance defines it, gets only the delivery question, since [flow-verify](../../flow-verify/SKILL.md) runs no dedicated review for it. A review answer given earlier in the session for the repository is reused under the shared workflow-choice rule: run that mechanism as a routine check of the candidate, at the moment [Dedicated review timing](#dedicated-review-timing) sets, without asking, or run no dedicated code review when the answer was "No dedicated review"; name it in the one-line statement that [delivery decisions](delivery-decisions.md) sets. Confirm without launching it, as the first bullet below sets, that the mechanism exists on this host; when it does not, ask the question below and state that limitation. A review answer, including "No dedicated review", does not authorize `hive-review-security`: it settles the dedicated code review only. When the planned change crosses a security boundary, the one-line statement, or this round, carries the offer that [Offer the security review](../../flow-build/references/security-boundaries.md#offer-the-security-review) sets, also when every answer is reused; it is a line, not a question, and the review itself runs as [flow-security](../../flow-security/SKILL.md) sets. Without a reused answer, build the question in the session language:

- Name the actual current harness and its command in the native option, so the choice maps to one executor: for example, “Claude Code's `/code-review`”, “Codex's `/review`”, or “Grok's `/review`”. Verify the capability without launching it; if unavailable or unverified, state that limitation rather than inventing a command or offering it as executable. Some hosts ship no AI review, such as OpenCode, whose review view is for human reading, and Pi.
- Always offer the installed `hive-review-code` role, with `hive-refute-claim` checking its blocking findings, as a separate option; it is the only executable reviewer on hosts without a native one. Record which of the two was chosen, since both may be described as a review by the agent.
- Offer other named mechanisms only when mentioned for code review in an applicable project/workspace `AGENTS.md`; cite that source. Beyond these, installed tools, memory and examples in Hive do not add options. Check availability separately from the declaration. Do not invent combinations unless that guidance names them.
- Offer “No dedicated review” as its own option: the implementer's own diff inspection and the project's checks, without an independent reviewer.
- Include “Other: define it” so the user can specify a different tool or human review and its timing. When the question tool supplies a built-in free-text Other, use that instead of duplicating it; in the message text, omit it.

Recommend a dedicated review when the change touches a public or persisted contract, security, permissions, or stored data, or concurrency, or changes more behavior than its tests and local in-vivo checks can show to be correct. Then mark the available mechanism explicitly preferred by applicable project guidance as Recommended; otherwise recommend the verified native option, or `hive-review-code` where the host has none. When the change has none of these and project guidance does not require review, recommend “No dedicated review” and name what the change lacks; the user may still choose a mechanism. When `automatic` is already the chosen delivery, by a reused answer or the user's request, it has no human stop, so the Recommended option is always a mechanism, chosen as the previous sentences set, and “No dedicated review” stays available but is never Recommended. When `automatic` is only an option of the same round, recommend by the change as above, and word “No dedicated review” so it says that under `automatic` no independent review would run before the merge. Word the delivery, review and `UI verification` options so each holds with any answer to the other questions of the round, such as `automatic` “with the review you choose in D<n>”, as [questions](questions.md) sets for one round. A mere mention is not a preference. A retired `Review` value still written in the `## Hive` section is such a preference: recommend that mechanism when it exists on this host, otherwise the closest available one, and say which value the section names. If no executable choice is verified, recommend defining the mechanism instead of pretending one works. State candidate, timing, relevant effects and whether execution is authorized. A listed tool is not consent, and implementation code review is distinct from read-only plan feedback. Record the chosen mechanism and pending execution consent explicitly when the user is only approving the design.

## Dedicated review timing

The dedicated code review, whichever mechanism the answer selects, runs once on the local candidate, after the affected tests and the full suite when it runs locally, and before the next step that publishes it or asks for its validation: under `interactive`, before the validation request; under `automatic`, and under `direct-base` chosen for a code repository, before the push; under `hold`, on the verified working tree. Fix its findings before that step, so the user validates, and the pull request carries, a reviewed candidate. A mechanism that only works on a pull request, such as a pull-request bot or a human reviewer, runs on the pull request right after the push instead, and the merge waits for its findings; under `interactive` that push follows the validation, so the validation message says the review is still due, and under `hold` or a chosen `direct-base`, which open no pull request, ask for a local mechanism or report the review as not run. Record in the pull request body which mechanism reviewed which commit, so a later promotion can tell which commits were reviewed. The corrections the user's validation asks for get one more review, limited to the diff between the reviewed candidate and the accepted one, alongside the accepted-candidate gate of [the UI gate](../../flow-verify/references/ui-gate.md); no correction round runs a full review. A later edit to the same candidate follows [review and gates](../../flow-verify/references/review-and-gates.md#dedicated-code-review). A follow-up pull request of the same ticket gets its review on its own local candidate in the same way, and a promotion pull request reviews only the commits not reviewed before their integration, as the promotion rule in [delivery decisions](delivery-decisions.md) sets.
