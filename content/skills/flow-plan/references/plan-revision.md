# Revise a plan in progress

## When to read

Read when a retained plan changes after it was written, during planning or during the build: a decision the current state invalidates, an answer that invalidates tasks already written, a correction the user requests, a review or verification finding, a scope clarification, a task added during the build, or a reconciliation on resume.

## Revise the change folder

- Draft the revision in the conversation first and name what it changes: the quoted request, an `AC<n>`, a design decision or contract, a task, or a delta file. Then edit the change folder one file at a time; only the orchestrator edits it.
- Keep the files coherent in every direction. A changed criterion updates each task whose `Closes:` names it, that task's verification, and the delta that states the behavior; a changed delta updates its criterion; a changed task keeps its criteria falsifiable at the base commit. A task already `[x]` that a changed criterion, decision, contract, or delta affects, or whose own scope the revision changes, goes back to `[/]` when it needs implementation again and to `[?]` when only its verification changes, with a line naming the revision; [flow-build](../../flow-build/SKILL.md) then verifies it again under the per-task procedure in [plan execution](../../flow-build/references/plan-execution.md).
- A task added during the build or after the user's validation follows the same plan rules as any other: criteria falsifiable at the base commit, a `Closes:` line and a test approach. A `tdd` or `check` task is verified by `hive-verify-task` before its commit, as [plan execution](../../flow-build/references/plan-execution.md) sets, and the completion report never claims independent verification for a task that did not get it. When it lands after the dedicated code review ran, report it and ask whether to review it, as [verification](../../flow-build/references/verification.md) sets for later edits. A correction of the validated result during a validation pause follows the correction rounds in [flow-walkthrough](../../flow-walkthrough/SKILL.md); new behavior the user asks for then is an added task.
- When the revision changes the outcome or the scope the request named, it is a new change, not an edit: close or pause this one as [flow-close](../../flow-close/SKILL.md) sets and plan the new one.
- Return the revised plan to `hive-review-plan` only when the revision meets the re-review criterion in [plan review](plan-review.md); each such revision gets at most one re-review round of its own, and a gap that survives it goes to the user as a decision. A revision outside that criterion is reconciled by the orchestrator without a round. During a human validation pause, a re-review that a correction makes due runs with the accepted-candidate gate that [flow-walkthrough](../../flow-walkthrough/SKILL.md) sets, not between correction rounds.
- Record each revision in the plan's progress section with its reason and what it invalidated, and tell the user in one line what the change settles or returns to an earlier flow, as [questions](questions.md) requires for an answer.
