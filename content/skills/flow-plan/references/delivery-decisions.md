# Delivery decisions

Before resolving repository settings needed here, read [project settings](../../hive-core/references/project-settings.md). Before presenting a delivery or review decision, read [questions](../../hive-core/references/questions.md), including its card/text and citation rules. The provisional-shortlist procedure below preserves every delivery mode when one choice exceeds a card's option limit.

**Condition:** an implementation plan is about to be declared ready, or work implemented without a plan is about to get its first edit, and no request to promote or deploy settles the delivery.

**Actions:** resolve the Git delivery mode for its named repositories and target branches. When an explicit delegation or the user's leaving message activates unattended delegation before this round is answered, ask it as [unattended delegation](../../unattended-delegation/SKILL.md#pre-authorization-round) sets, and continue the work without waiting for it. At that same point, ask for the authorizations the plan, or the request and its verification, foresee for later steps, as [foreseen authorizations](../../flow-build/references/foreseen-authorizations.md) sets, also when this round asks nothing. When no earlier choice is reused, ask once, in the session language, mark one option Recommended, which a retired `## Hive` value may inform as the next block sets, and explain the actual effects. The round is not a prerequisite for research or for edits that will not end in a Git delivery; for those edits, `flow-build` asks only the review question of [review decisions](review-decisions.md) and the foreseen authorizations.

**Condition:** the session already holds an explicit choice for the same repository and target branch, including one made for an earlier ticket.

**Actions:** reuse it under the shared workflow-choice rule. A remembered preference, a default stated in project guidance, or a retired `Delivery`, `Review` or `UI verification` value still written in the repository's `## Hive` section only informs the recommendation and never answers the question, as [project settings](../../hive-core/references/project-settings.md) sets. A narrower instruction in the request, such as `hold` or commit only, overrides a reused choice. Before the first edit, state the reused answers in one line, inside the round's message when the round asks anything else: the mode and where the work stops; the review mechanism that will apply; any deployment the destination triggers; and the change record's closing route the reused answer chose. The user can change any of them in reply. When the work has a change folder that the change-folder paragraph below covers and the reused answer chose no closing route for it, ask only that route in this round, before the first edit, so the close does not ask it. The rule below that marks `automatic` unavailable for a change that needs human validation still applies: the work then runs under `interactive`, and the line names that rule and the stop.

**Condition:** the user asks to promote or deploy to a named environment, such as "promote to QA".

**Actions:** that request is itself the delivery choice, as step 4 of [flow-deploy](../../flow-deploy/SKILL.md#procedure) sets, so do not ask the delivery mode.

**Condition:** commits integrated earlier are to be reviewed, such as in a promotion pull request.

**Actions:** review only the commits that were not reviewed before their integration, as the change record or each pull request's body records; when all were, apply no new review and say so.

| Mode | Delivery contract to present |
| --- | --- |
| `interactive` | Work branch from the named base, local commits, verification, the agreed dedicated review and the gates [flow-verify](../../flow-verify/SKILL.md) runs before asking the user to validate, then stop before push with the built result available for human validation; that stop holds also when verify is skipped, and [flow-verify](../../flow-verify/SKILL.md#decide-whether-to-run-and-at-what-level) sets what a skipped verify does to the dedicated review. After the user validates that result, the agent continues with push, PR and merge into the named base once the required gates pass. Present this entire chain in the option; interactive includes merge, not merely opening a PR. Recommend it when the result has a surface only the user can judge, such as a screen, copy, or flow. |
| `automatic` | Work branch, commits, the agreed dedicated review on the local candidate, push, PR to the named base and merge when the agreed checks pass. Name any deployment triggered by the destination before asking. Recommend it for work whose acceptance checks, review, and verification establish, such as infrastructure, CI/CD, migrations, refactors, tooling, or a promotion the user requested: a stop before push there adds a gate with nothing for the user to validate. It never stops for human validation: only when a rule in the project's guidance requires human validation for the change, mark automatic unavailable for that change and name that rule. A rendered UI change alone does not make it unavailable, since the independent checks of [the UI gate](../../flow-verify/references/ui-gate.md) judge it. Production promotion still needs its own request. |
| `direct-base` | Verified commits and push directly to the named base, without a PR, only where project policy permits. Disclose triggered deployment. Chosen this way for a code repository, it keeps the dedicated review on the local candidate before the push and the wait for CI; the exceptions that a declared `Delivery: direct-base` grants below apply only to that declared value. |
| `hold` | Implement and verify in the working tree; no commit or publication. Present the diff; the delivery the user chose not to make is reported as a reminder, not as a pending item. |

Offer these modes with their concrete effects, marking an unavailable route with the reason rather than suggesting bypassing project policy. An explicit narrower instruction such as commit only or PR without merge takes precedence; do not force it into a broader mode. An unanswered question leaves the proposed delivery unapproved. A mode authorizes only its expressly selected delivery effects for otherwise authorized work, not implementation, production deployment or other external effects by implication, except those the project's documented procedure prescribes for the delivery it names, as [effect authorization](../../hive-core/references/effect-authorization.md#what-an-answer-covers) sets.

With a native question card that waits for the answer, the message carries the one-line summary [questions](../../hive-core/references/questions.md) describes, and the card carries the per-option wording this reference asks for, such as the full chain inside each option, the support repositories named in each, and the change record's closing route that the change-folder paragraph below sets, with what the options share in its question; the card must stand alone. When a single delivery choice exceeds the card's option limit, use staged cards: label the first selection as a provisional shortlist, not a delivery authorization; then present that candidate alongside the remaining modes and let the user revise the shortlist. Show every available mode and its effects before recording the final choice; a choice from the first subset never settles delivery. Whenever no such card carries the question, the message text carries the options under the shared one-line format: each option states what sets it apart, such as where it stops, whether it publishes, when it publishes each support repository in the work and the deployment that push triggers, and, when the change-folder paragraph below applies, how it versions the change record, and the steps several modes share, the ticket moves, and an unavailable route with its reason go once in a line after the options.

A repository whose `## Hive` section declares `Delivery: direct-base` is a support repository, such as a specs or mocks repository. It takes no delivery-mode or review question: that declaration authorizes committing the current work's changes there and pushing them straight to its base branch, without a pull request, a dedicated review, or waiting for CI. It is also the explicit grant for any branch-protection bypass that push needs, such as an administrator bypass of a required pull request; name the bypass when reporting the push. It does not authorize a deployment: when a push there triggers one, name it, and ask before that push unless an answer given for this change named that deployment; an answer for another change, or a delivery mode reused from earlier work, does not cover it, an exception to the same-kind rule of [effect authorization](../../hive-core/references/effect-authorization.md#what-an-answer-covers). When the work's changes, other than its change record, are only in repositories that declare `Delivery: direct-base` and the change adds or rearranges a rendered layout, show its first rendered view and ask before that push even when an answer named the deployment, as [flow-walkthrough](../../flow-walkthrough/SKILL.md) sets. Every other repository in the work is a code repository and goes through each question, as the paragraphs above and below set. Inside each option, name every support repository, its branch, and when that option publishes it and any deployment that push triggers, including the closing push of a change record, such as "ark-specs and ark-frontend-mocks: commit and push straight to master after you validate the result" under `interactive`, or "ark-specs and ark-frontend-mocks: stay unpublished" under `hold`, so the answer covers them without another question. Publish a support repository with the code: under `interactive`, after the user validates the result; under `automatic` or `direct-base`, with the code's push; under `hold`, it stays unpublished and is reported as a reminder. A specs repository publishes the change record once, at close, as [flow-close](../../flow-close/SKILL.md) describes. When the implementation touches only support repositories, publish without asking, except a push that triggers a deployment, as above. A change record in a `direct-base` specs repository is hygiene, even when it plans work in a code repository: [flow-close](../../flow-close/SKILL.md) commits and pushes it once, at close, after the code is integrated, without waiting for the code's question.

When the work spans several code repositories, ask one delivery-mode question and one review question for those without a choice reused from the session, and name the reused ones with their values: each option lists every code repository the question covers with its base branch, and one answer covers them all. Ask separately only for a repository where a mode is unavailable under its policy, or whose environments give the same mode different effects, and name that difference.

When the work has a change folder in a repository without `Delivery: direct-base`, the same question covers versioning that record once, at close, by [flow-close](../../flow-close/SKILL.md). When `<specs>` lives in a code repository, or in a separate specs repository that does not declare `Delivery: direct-base`, state inside each option the record's closing route: a direct push to the base branch, or a small closing pull request without dedicated review and who merges it, plus any automation that publication triggers, so one answer authorizes it. Under `hold`, the record stays unversioned like the code and is reported as a reminder.

For interactive and automatic delivery, the agent owns merge into the agreed integration base once CI is green on the current base, as [git-workflow](../../git-workflow/SKILL.md) sets, conflicts are resolved and required review findings are addressed or refuted with evidence under project policy. Pending or failed gates do not permit merge. A check the user asked to skip does not hold the merge, as [flow-verify](../../flow-verify/SKILL.md#decide-whether-to-run-and-at-what-level) sets. A human PR-review route hands the open PR to that reviewer and leaves merge to them; state this exception in the chosen delivery contract. An explicit PR-without-merge restriction also overrides the mode. Production or other environment promotion remains separately scoped. Do not retroactively add merge to a past answer whose presented option did not clearly include it. A follow-up pull request that fixes the same ticket's change, such as a CI or defect fix after its merge, belongs to the same delivery: the chosen delivery contract, with its exceptions above, covers its agreed review, including a human reviewer's route, and its merge without a new question. A condition the user attaches to a grant, such as "no merge until I return", lasts only for the scope it states, and one with no stated end holds until the user lifts it; when that scope ends, the mode's own rule applies again, and a handoff to another session records the condition with its scope, or as holding until lifted when it states no end.

Resolve the code-review mechanism as [review decisions](review-decisions.md) sets and, for a rendered UI effect, the `UI verification` value as [the UI verification decision](ui-verification-decision.md) sets, in this same round.

Record the selected mode, repositories/base, the change record's closing route, included operations, stop/resume conditions, review mechanism, security-review request when the user made one (run as [flow-security](../../flow-security/SKILL.md) sets), `UI verification` value and the user answer/date in the existing plan, or state them in the conversation when there is none. Separate implementation authority from conditional delivery consent: a planning-only request may settle delivery for later authorized implementation. Do not describe selected local commits as both included and unapproved; record implementation as pending and publication as waiting for result validation. User validation satisfies that recorded condition, not a new consent request for each already granted operation. On resume, read this record and reconcile the candidate, targets and gates; reuse unchanged decisions instead of asking the mode again. A loop's state never supplies these answers, since it authorizes nothing: without a retained plan's record, a new session asks again. Avoid another questionnaire or a separate policy file per task. Changing the authorized target or effects requires resolving only that changed decision.

For a production defect that cannot wait for the next scheduled promotion, read [urgent fixes](../../flow-deploy/references/urgent-fixes.md).
