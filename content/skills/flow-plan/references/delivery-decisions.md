# Delivery decisions

Before declaring an implementation plan ready, or before the first edit of work implemented without a plan, resolve the Git delivery mode for its named repositories and target branches. Reuse an explicit choice made earlier in the session for the same repository and target branch, including for a later ticket, under the shared workflow-choice rule; a repository default or remembered preference only informs the recommendation. A user request to promote or deploy to a named environment, such as "promote to QA", is itself the delivery choice for that work: it authorizes the chain the project defines for that environment, meaning the promotion pull request, its merge once the gates pass, the environment's deployment with its identity and health checks, and the ticket moves they trigger; it excludes the functional walk, which runs only as [verification](../../flow-build/references/verification.md) allows, so do not ask the delivery mode. It covers production only when the user names production. Review only the commits that were not reviewed on their own pull request; when all were, apply no new review and say so. Otherwise ask once, in the session language, mark one option Recommended and explain the actual effects. It is not a prerequisite for research or for edits that will not end in a Git delivery.

| Mode | Delivery contract to present |
| --- | --- |
| `interactive` | Work branch from the named base, local commits and verification, then stop before push with the built result available for human validation. After the user validates that result, the agent continues with push, PR, the agreed review and merge into the named base once the required gates pass. Present this entire chain in the option; interactive includes merge, not merely opening a PR. Recommend it when the result has a surface only the user can judge, such as a screen, copy, or flow. |
| `automatic` | Work branch, commits, push, PR to the named base, agreed checks/review and merge when its conditions pass. Name any deployment triggered by the destination before asking. Recommend it for work whose acceptance checks, review, and verification establish, such as infrastructure, CI/CD, migrations, refactors, tooling, or a promotion the user requested: a stop before push there adds a gate with nothing for the user to validate. Required human acceptance and production promotion still stand. |
| `direct-base` | Verified commits and push directly to the named base, without a PR, only where project policy permits. Disclose triggered deployment. |
| `hold` | Implement and verify in the working tree; no commit or publication. Present the diff and leave delivery pending. |

Offer these modes with their concrete effects, marking an unavailable route with the reason rather than suggesting bypassing project policy. An explicit narrower instruction such as commit only or PR without merge takes precedence; do not force it into a broader mode. An unanswered question leaves the proposed delivery unapproved. A mode authorizes only its expressly selected delivery effects for otherwise authorized work, not implementation, production deployment or unspecified external effects by implication.

A repository whose `## Hive` section declares `Delivery: direct-base` is a support repository, such as a specs or mocks repository. It takes no delivery-mode or review question: that declaration authorizes committing the current work's changes there and pushing them straight to its base branch, without a pull request, a dedicated review, or waiting for CI. It is also the explicit grant for any branch-protection bypass that push needs, such as an administrator bypass of a required pull request; name the bypass when reporting the push. It does not authorize a deployment: when a push there triggers one, name it, and ask before that push when no question is otherwise asked. Every other repository in the work is a code repository and goes through the question. Inside each option, name every support repository, its branch, and when that option publishes it, such as "ark-specs and ark-frontend-mocks: commit and push straight to master after you validate the result" under `interactive`, or "ark-specs and ark-frontend-mocks: stay unpublished" under `hold`, so the answer covers them without another question. Publish a support repository with the code: under `interactive`, after the user validates the result; under `automatic` or `direct-base`, with the code's push; under `hold`, it stays unpublished and is reported as pending. A specs repository publishes the change record at the points the change-folder paragraph below names. When the implementation touches only support repositories, publish without asking; a change record that plans work in a code repository follows that code's question.

When the work spans several code repositories, ask one delivery-mode question and one review question for all of them: each option lists every code repository with its base branch, and one answer covers them all. Ask separately only for a repository where a mode is unavailable under its policy, whose environments give the same mode different effects, or whose `Review` setting differs, and name that difference.

When the work has a change folder, the same question covers versioning that record in the repository holding `<specs>`, so the plan never waits on a separate commit request. State inside each option the record's repository and branch, how it is published under that repository's policy, any automation that publication triggers, and when it is versioned: when the plan is approved, at each delivery milestone the plan records, such as the pull request opening and the merge, and at the closing archive. Under `hold`, the record stays unversioned like the code and is reported as pending.

For interactive and automatic delivery, the agent owns merge into the agreed integration base once CI is green, conflicts are resolved and required review findings are addressed or refuted with evidence under project policy. Pending or failed gates do not permit merge. A human PR-review route hands the open PR to that reviewer and leaves merge to them; state this exception in the chosen delivery contract. An explicit PR-without-merge restriction also overrides the mode. Production or other environment promotion remains separately scoped. Do not retroactively add merge to a past answer whose presented option did not clearly include it.

Resolve the implementation code-review mechanism and boundary in the same exchange as the delivery mode, for every mode including hold, so delivery does not ask again. Build the question in the session language:

- Name the actual current harness and its command in the native option, so the choice maps to one executor: for example, “Claude Code's `/code-review`”, “Codex's `/review`”, or “Grok's `/review`”. Verify the capability without launching it; if unavailable or unverified, state that limitation rather than inventing a command or offering it as executable. Some hosts ship no AI review, such as OpenCode, whose review view is for human reading, and Pi.
- Always offer the installed `review-code` role, with `review-refuter` checking its blocking findings, as a separate option; it is the only executable reviewer on hosts without a native one. Record which of the two was chosen, since both may be described as a review by the agent.
- Offer other named mechanisms only when mentioned for code review in an applicable project/workspace `AGENTS.md`; cite that source. Beyond these, installed tools, memory and examples in Hive do not add options. Check availability separately from the declaration. Do not invent combinations unless that guidance names them.
- Offer “No dedicated review” as its own option: the implementer's own diff inspection and the project's checks, without an independent reviewer.
- Include “Other: define it” so the user can specify a different tool or human review and its timing. When the question tool supplies a built-in free-text Other, use that instead of duplicating it.

Recommend a dedicated review when the change touches a public or persisted contract, security, permissions, or stored data, or concurrency, or changes more behavior than its tests and local in-vivo checks can show to be correct. Then mark the available mechanism explicitly preferred by applicable project guidance as Recommended; otherwise recommend the verified native option, or `review-code` where the host has none. When the change has none of these and project guidance does not require review, recommend “No dedicated review” and name what the change lacks; the user may still choose a mechanism. A mere mention is not a preference; a `Review` setting in the repository's `## Hive` section is an explicit preference. If no executable choice is verified, recommend defining the mechanism instead of pretending one works. State candidate, timing, relevant effects and whether execution is authorized. A listed tool is not consent, and implementation code review is distinct from read-only plan feedback. Record the chosen mechanism and pending execution consent explicitly when the user is only approving the design.

Record the selected mode, repositories/base, the change record's versioning points, included operations, stop/resume conditions, review mechanism and the user answer/date in the existing plan, or state them in the conversation when there is none. Separate implementation authority from conditional delivery consent: a planning-only request may settle delivery for later authorized implementation. Do not describe selected local commits as both included and unapproved; record implementation as pending and publication as waiting for result validation. User validation satisfies that recorded condition, not a new consent request for each already granted operation. On resume, read this record and reconcile the candidate, targets and gates; reuse unchanged decisions instead of asking the mode again. Avoid another questionnaire or a separate policy file per task. Changing the authorized target or effects requires resolving only that changed decision.
