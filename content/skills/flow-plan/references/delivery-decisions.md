# Delivery decisions

Before resolving repository settings needed here, read [project settings](project-settings.md). Before presenting a delivery or review decision, read [questions](questions.md), including its card/text and citation rules. The provisional-shortlist procedure below preserves every delivery mode when one choice exceeds a card's option limit.

Before declaring an implementation plan ready, or before the first edit of work implemented without a plan, resolve the Git delivery mode for its named repositories and target branches. At that same point, ask for the authorizations the plan or request foresees for later steps, as [verification](../../flow-build/references/verification.md#gate-selection-and-timing) sets, also when this round asks nothing. Reuse an explicit choice made earlier in the session for the same repository and target branch, including for a later ticket, under the shared workflow-choice rule; a remembered preference, a default stated in project guidance, or a retired `Delivery`, `Review` or `UI verification` value still written in the repository's `## Hive` section only informs the recommendation and never answers the question, as [project settings](project-settings.md) sets. A narrower instruction in the request, such as `hold` or commit only, overrides a reused choice. Before the first edit, state the reused answers in one line, inside the round's message when the round asks anything else: the mode and where the work stops; the review mechanism that will apply; any deployment the destination triggers; and the change record's closing route the reused answer chose. The user can change any of them in reply. The rule below that marks `automatic` unavailable for a change that needs human validation still applies: the work then runs under `interactive`, and the line names that rule and the stop. A user request to promote or deploy to a named environment, such as "promote to QA", is itself the delivery choice for that work: it authorizes the chain the project defines for that environment, meaning the promotion pull request, its merge once the gates pass, the environment's deployment with its identity and health checks, and the ticket moves they trigger; it excludes the functional walk, which runs only as [deployment checks](../../flow-deploy/references/deployment-checks.md#functional-walk) allows, and the effects that walk needs in that environment, which are asked when the work there starts, so do not ask the delivery mode. It covers production only when the user names production. Review only the commits that were not reviewed before their integration, as the change record or each pull request's body records; when all were, apply no new review and say so. Otherwise ask once, in the session language, mark one option Recommended and explain the actual effects. It is not a prerequisite for research or for edits that will not end in a Git delivery; for those edits, `flow-build` asks only the review question below and the foreseen authorizations.

| Mode | Delivery contract to present |
| --- | --- |
| `interactive` | Work branch from the named base, local commits, verification, the agreed dedicated review and the gates [flow-verify](../../flow-verify/SKILL.md) runs before asking the user to validate, then stop before push with the built result available for human validation; that stop holds also when verify is skipped, and a skipped verify skips the dedicated review unless the repository requires one, as [flow-verify](../../flow-verify/SKILL.md#decide-whether-to-run-and-at-what-level) sets. After the user validates that result, the agent continues with push, PR and merge into the named base once the required gates pass. Present this entire chain in the option; interactive includes merge, not merely opening a PR. Recommend it when the result has a surface only the user can judge, such as a screen, copy, or flow. |
| `automatic` | Work branch, commits, the agreed dedicated review on the local candidate, push, PR to the named base and merge when the agreed checks pass. Name any deployment triggered by the destination before asking. Recommend it for work whose acceptance checks, review, and verification establish, such as infrastructure, CI/CD, migrations, refactors, tooling, or a promotion the user requested: a stop before push there adds a gate with nothing for the user to validate. It never stops for human validation: only when a rule in the project's guidance requires human validation for the change, mark automatic unavailable for that change and name that rule. A rendered UI change alone does not make it unavailable, since the independent checks of [the UI gate](../../flow-verify/references/ui-gate.md) judge it. Production promotion still needs its own request. |
| `direct-base` | Verified commits and push directly to the named base, without a PR, only where project policy permits. Disclose triggered deployment. Chosen this way for a code repository, it keeps the dedicated review on the local candidate before the push and the wait for CI; the exceptions that a declared `Delivery: direct-base` grants below apply only to that declared value. |
| `hold` | Implement and verify in the working tree; no commit or publication. Present the diff; the delivery the user chose not to make is reported as a reminder, not as a pending item. |

Offer these modes with their concrete effects, marking an unavailable route with the reason rather than suggesting bypassing project policy. An explicit narrower instruction such as commit only or PR without merge takes precedence; do not force it into a broader mode. An unanswered question leaves the proposed delivery unapproved. A mode authorizes only its expressly selected delivery effects for otherwise authorized work, not implementation, production deployment or unspecified external effects by implication.

With a native question card that waits for the answer, the message carries the one-line summary [questions](questions.md) describes, and the card carries the per-option wording this reference asks for, such as the full chain inside each option and the support repositories named in each, with what the options share in its question; the card must stand alone. When a single delivery choice exceeds the card's option limit, use staged cards: label the first selection as a provisional shortlist, not a delivery authorization; then present that candidate alongside the remaining modes and let the user revise the shortlist. Show every available mode and its effects before recording the final choice; a choice from the first subset never settles delivery. Whenever no such card carries the question, the message text carries the options under the shared one-line format: each option states what sets it apart, such as where it stops or whether it publishes, and the steps several modes share, the support repositories' publication, the ticket moves, and an unavailable route with its reason go once in a line after the options.

A repository whose `## Hive` section declares `Delivery: direct-base` is a support repository, such as a specs or mocks repository. It takes no delivery-mode or review question: that declaration authorizes committing the current work's changes there and pushing them straight to its base branch, without a pull request, a dedicated review, or waiting for CI. It is also the explicit grant for any branch-protection bypass that push needs, such as an administrator bypass of a required pull request; name the bypass when reporting the push. It does not authorize a deployment: when a push there triggers one, name it, and ask before that push when no question is otherwise asked. Every other repository in the work is a code repository and goes through each question, as the paragraphs above and below set. Inside each option, name every support repository, its branch, and when that option publishes it, such as "ark-specs and ark-frontend-mocks: commit and push straight to master after you validate the result" under `interactive`, or "ark-specs and ark-frontend-mocks: stay unpublished" under `hold`, so the answer covers them without another question. Publish a support repository with the code: under `interactive`, after the user validates the result; under `automatic` or `direct-base`, with the code's push; under `hold`, it stays unpublished and is reported as a reminder. A specs repository publishes the change record once, at close, as [flow-close](../../flow-close/SKILL.md) describes. When the implementation touches only support repositories, publish without asking. A change record in a `direct-base` specs repository is hygiene, even when it plans work in a code repository: [flow-close](../../flow-close/SKILL.md) commits and pushes it once, at close, after the code is integrated, without waiting for the code's question.

When the work spans several code repositories, ask one delivery-mode question and one review question for those without a choice reused from the session, and name the reused ones with their values: each option lists every code repository the question covers with its base branch, and one answer covers them all. Ask separately only for a repository where a mode is unavailable under its policy, or whose environments give the same mode different effects, and name that difference.

When the work has a change folder in a repository without `Delivery: direct-base`, the same question covers versioning that record once, at close, by [flow-close](../../flow-close/SKILL.md). When `<specs>` lives in a code repository, or in a separate specs repository that does not declare `Delivery: direct-base`, state inside each option the record's closing route: a direct push to the base branch, or a small closing pull request without dedicated review and who merges it, plus any automation that publication triggers, so one answer authorizes it. Under `hold`, the record stays unversioned like the code and is reported as a reminder.

For interactive and automatic delivery, the agent owns merge into the agreed integration base once CI is green on the current base, as [git-workflow](../../git-workflow/SKILL.md) sets, conflicts are resolved and required review findings are addressed or refuted with evidence under project policy. Pending or failed gates do not permit merge. A check the user asked to skip does not hold the merge, as [flow-verify](../../flow-verify/SKILL.md#decide-whether-to-run-and-at-what-level) sets. A human PR-review route hands the open PR to that reviewer and leaves merge to them; state this exception in the chosen delivery contract. An explicit PR-without-merge restriction also overrides the mode. Production or other environment promotion remains separately scoped. Do not retroactively add merge to a past answer whose presented option did not clearly include it. A follow-up pull request that fixes the same ticket's change, such as a CI or defect fix after its merge, belongs to the same delivery: the chosen delivery contract, with its exceptions above, covers its agreed review, including a human reviewer's route, and its merge without a new question. A condition the user attaches to a grant, such as "no merge until I return", lasts only for the scope it states, and one with no stated end holds until the user lifts it; when that scope ends, the mode's own rule applies again, and a handoff to another session records the condition with its scope, or as holding until lifted when it states no end.

Resolve the implementation code-review mechanism and boundary in the same exchange as the delivery mode, for every mode including hold, so delivery does not ask again. A mechanical change, as the global guidance defines it, gets only the delivery question, since [flow-verify](../../flow-verify/SKILL.md) runs no dedicated review for it. A review answer given earlier in the session for the repository is reused under the shared workflow-choice rule: run that mechanism as a routine check of the candidate, at the moment [Dedicated review timing](#dedicated-review-timing) sets, without asking, or run no dedicated code review when the answer was "No dedicated review"; name it in the one-line statement above. Confirm without launching it, as the first bullet below sets, that the mechanism exists on this host; when it does not, ask the question below and state that limitation. A review answer, including "No dedicated review", does not authorize `hive-review-security`: it settles the dedicated code review only. When the planned change crosses a security boundary, the one-line statement, or this round, carries the offer that [Offer the security review](../../flow-build/references/security-boundaries.md#offer-the-security-review) sets, also when every answer is reused; it is a line, not a question, and the review itself runs as [flow-security](../../flow-security/SKILL.md) sets. Without a reused answer, build the question in the session language:

- Name the actual current harness and its command in the native option, so the choice maps to one executor: for example, “Claude Code's `/code-review`”, “Codex's `/review`”, or “Grok's `/review`”. Verify the capability without launching it; if unavailable or unverified, state that limitation rather than inventing a command or offering it as executable. Some hosts ship no AI review, such as OpenCode, whose review view is for human reading, and Pi.
- Always offer the installed `hive-review-code` role, with `hive-refute-claim` checking its blocking findings, as a separate option; it is the only executable reviewer on hosts without a native one. Record which of the two was chosen, since both may be described as a review by the agent.
- Offer other named mechanisms only when mentioned for code review in an applicable project/workspace `AGENTS.md`; cite that source. Beyond these, installed tools, memory and examples in Hive do not add options. Check availability separately from the declaration. Do not invent combinations unless that guidance names them.
- Offer “No dedicated review” as its own option: the implementer's own diff inspection and the project's checks, without an independent reviewer.
- Include “Other: define it” so the user can specify a different tool or human review and its timing. When the question tool supplies a built-in free-text Other, use that instead of duplicating it; in the message text, omit it.

Recommend a dedicated review when the change touches a public or persisted contract, security, permissions, or stored data, or concurrency, or changes more behavior than its tests and local in-vivo checks can show to be correct. Then mark the available mechanism explicitly preferred by applicable project guidance as Recommended; otherwise recommend the verified native option, or `hive-review-code` where the host has none. When the change has none of these and project guidance does not require review, recommend “No dedicated review” and name what the change lacks; the user may still choose a mechanism. Under `automatic`, which has no human stop, and whenever `automatic` is an option of the same round, the Recommended option is always a mechanism, chosen as the previous sentences set, and “No dedicated review” stays available but is never Recommended. Word the delivery, review and `UI verification` options so each holds with any answer to the other questions of the round, such as `automatic` “with the review you choose in D<n>”, as [questions](questions.md) sets for one round. A mere mention is not a preference. A retired `Review` value still written in the `## Hive` section is such a preference: recommend that mechanism when it exists on this host, otherwise the closest available one, and say which value the section names. If no executable choice is verified, recommend defining the mechanism instead of pretending one works. State candidate, timing, relevant effects and whether execution is authorized. A listed tool is not consent, and implementation code review is distinct from read-only plan feedback. Record the chosen mechanism and pending execution consent explicitly when the user is only approving the design.

Resolve the `UI verification` value in the same exchange when the work has a rendered UI effect other than a text or style change that alters no layout, state, or flow. An explicit answer given earlier in the session for the same repository is reused under the shared workflow-choice rule; name it in the one-line statement. Without one, ask once, in the session language, with the three values as options, each with its effect and its time cost: `full` runs `hive-review-ux` and `hive-verify-change` on the built candidate before completion; `functional` runs only `hive-verify-change` on the acceptance journeys and leaves visual judgment to the human validation, or, under `automatic`, to no one; `none` runs neither and keeps the implementer's bounded checks, which are the last checks before the human validation under `interactive` or `hold` and the only ones before merge under `automatic`, so the user chooses it there knowingly, and records the walkthrough passes with a `hive-verify-change` child that returns no verdict. These definitions are the values' only home; [project settings](project-settings.md) lists `UI verification` as a retired key. Recommend `full` when the change adds or rearranges a screen, dialog, or shared pattern, and `functional` when it changes behavior inside an accepted pattern. Say in each option that the answer holds for the rest of the session in that repository, including later tickets with another surface, and that the user can change it in any request. [The UI gate](../../flow-verify/references/ui-gate.md) applies the value to the gate on the built candidate and to the accepted-candidate gate.

Record the selected mode, repositories/base, the change record's closing route, included operations, stop/resume conditions, review mechanism, security-review request when the user made one (run as [flow-security](../../flow-security/SKILL.md) sets), `UI verification` value and the user answer/date in the existing plan, or state them in the conversation when there is none. Separate implementation authority from conditional delivery consent: a planning-only request may settle delivery for later authorized implementation. Do not describe selected local commits as both included and unapproved; record implementation as pending and publication as waiting for result validation. User validation satisfies that recorded condition, not a new consent request for each already granted operation. On resume, read this record and reconcile the candidate, targets and gates; reuse unchanged decisions instead of asking the mode again. Avoid another questionnaire or a separate policy file per task. Changing the authorized target or effects requires resolving only that changed decision.

For a production defect that cannot wait for the next scheduled promotion, read [urgent fixes](../../flow-deploy/references/urgent-fixes.md).

## Dedicated review timing

The dedicated code review, whichever mechanism the answer selects, runs once on the local candidate, after the affected tests and the full suite when it runs locally, and before the next step that publishes it or asks for its validation: under `interactive`, before the validation request; under `automatic`, and under `direct-base` chosen for a code repository, before the push; under `hold`, on the verified working tree. Fix its findings before that step, so the user validates, and the pull request carries, a reviewed candidate. A mechanism that only works on a pull request, such as a pull-request bot or a human reviewer, runs on the pull request right after the push instead, and the merge waits for its findings; under `interactive` that push follows the validation, so the validation message says the review is still due, and under `hold` or a chosen `direct-base`, which open no pull request, ask for a local mechanism or report the review as not run. Record in the pull request body which mechanism reviewed which commit, so a later promotion can tell which commits were reviewed. The corrections the user's validation asks for get one more review, limited to the diff between the reviewed candidate and the accepted one, alongside the accepted-candidate gate of [the UI gate](../../flow-verify/references/ui-gate.md); no correction round runs a full review. A later edit to the same candidate follows [review and gates](../../flow-verify/references/review-and-gates.md#dedicated-code-review). A follow-up pull request of the same ticket gets its review on its own local candidate in the same way, and a promotion pull request reviews only the commits not reviewed before their integration, as the promotion rule near the start of this reference sets.
