# hive-build-mobile

1. Identify the stack from the repository's files: `pubspec.yaml` (Flutter or Dart), `expo` or `react-native` in a `package.json`'s dependencies, a Gradle build with the Kotlin Multiplatform or Android plugin, an `.xcodeproj` or `Package.swift`. Inspect the installed versions, the targets the project actually builds and its test conventions. Read the `## Skills` lines your brief carries, and the repository's `AGENTS.md` `## Skills` section when you can read it: before the work a line names, read that skill's `SKILL.md` whole. Read the assigned activity instructions and applicable project conventions before dependent work.

2. For a screen, keep the project's UI library and theme as the [precedence](skill:create-design/references/ui-criteria.md#precedence) of [UI criteria](skill:create-design/references/ui-criteria.md) sets, read [UI decisions](skill:hive-core/references/ui-plan.md) and the project's `DESIGN.md`, and build the changed regions as the plan's `UI` section records them, reusing existing components and design tokens. Handle the loading, empty, error and success states the change introduces or alters, and preserve accessibility labels and focus order. Put portable behavior in shared code and isolate platform responsibilities through the established interfaces; preserve coroutine or async cancellation and lifecycle ownership; check interop and exposed types at the Swift, Kotlin or JavaScript boundary against current toolchain documentation. Before writing new code, apply [Reuse before writing](skill:hive-core/references/reuse-before-writing.md). Before writing new code, read [code principles](skill:hive-principle-index/SKILL.md), and name in your return each principle read that changed a decision.

3. Build with the stack's own tooling, such as `flutter`, the Expo CLI with a development build, Gradle or `xcodebuild`. Do not edit an Xcode `.pbxproj` by hand: use the project's generator or report the change needed. Never test an Expo release build, which embeds an earlier JavaScript bundle. Write, change or delete tests, and handle a failing check, only as [Tests](skill:hive-core/references/tests.md) sets.

4. Verify on the device or emulator your brief assigns by its serial, as [Device tool](skill:hive-core/references/ui-verification/device-tool.md) sets; when the brief assigns none, do not run on a device and report it as not run. Report each platform and target not exercised; do not infer cross-platform success from one build.

Stay within the parent’s assigned scope, write ownership, and output destination. Do not commit, push, open or merge pull requests, write to trackers, or launch children of your own. Modify or delete only the paths the brief names, list planned deletions before applying them, and stop and report when the work needs a change outside them. A Git command that rewrites working-tree files, such as `git stash`, `git reset`, `git checkout` or `git restore` of paths, `git clean`, or `git switch`, modifies every path it touches: never run one in a working tree that other agents may be writing; compare with the base through `git diff` or `git show <base>:<path>`. `git stash` also writes the stash list that every worktree of the repository shares: never run it while another agent works in any worktree of the same repository. Unless the brief says your dependency installation is not shared, run no command that installs, prunes, or relinks dependencies, such as `npm ci`, `pnpm install`, or adding a package, and do not add one to a manifest or lockfile yourself: pause only the work that needs the dependency, name it in your report, and continue the rest. Run a test suite that sets up, resets, or binds a local service, such as a test database, a cache, or a port, only on the instance the brief assigns; when it assigns none, do not run the suite and report it as not run. Run every install, build and test command in the foreground with an explicit timeout of at most 10 minutes rather than behind a background monitor, and report one that hits the timeout as not completed. Stop any process you started before returning. Return evidence, limitations, and any decision needed from the parent in one final reply; before it, send the parent at most one message, for a blocker that needs the parent's decision, and return it as the final reply when no independent work remains.
