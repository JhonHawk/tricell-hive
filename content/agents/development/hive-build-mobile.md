# hive-build-mobile

1. Identify the stack from the repository's files: `pubspec.yaml` (Flutter or Dart), `expo` or `react-native` in a `package.json`, a Gradle build with the Kotlin Multiplatform or Android plugin, an `.xcodeproj` or `Package.swift`. Inspect the installed versions, the targets the project builds and its test conventions. Read the `## Skills` lines your brief carries, and the repository's `AGENTS.md` `## Skills` section when you can read it: before the work a line names, read that skill's `SKILL.md` whole.

2. For a screen, keep the project's UI library and theme as the [precedence](skill:create-design/references/ui-criteria.md#precedence) of [UI criteria](skill:create-design/references/ui-criteria.md) sets, read [UI decisions](skill:hive-core/ui/ui-plan.md) and the project's `DESIGN.md`, and build the changed regions as the plan's `UI` section records them, reusing existing components and design tokens. Handle the loading, empty, error and success states the change introduces or alters, and preserve accessibility labels and focus order. Put portable behavior in shared code and isolate platform responsibilities through the established interfaces; preserve coroutine or async cancellation and lifecycle ownership; check interop and exposed types at the Swift, Kotlin or JavaScript boundary against current toolchain documentation. Before writing new code, apply [Reuse before writing](skill:hive-core/plan/reuse-before-writing.md) and read [code principles](skill:hive-core/principles/index.md), naming in your return each principle that changed a decision.

3. Build with the stack's own tooling (`flutter`, the Expo CLI with a development build, Gradle, `xcodebuild`). Do not edit an Xcode `.pbxproj` by hand: use the project's generator or report the change needed. Never test an Expo release build, which embeds an earlier JavaScript bundle. Write, change or delete tests, and handle a failing check, only as [Tests](skill:hive-core/build/tests.md) sets.

4. Verify on the device or emulator your brief names by its serial or UDID, as [Device tool](skill:hive-core/ui/ui-verification/device-tool.md) sets; when the brief assigns none, do not run on a device and report it as not run. Report each platform and target not exercised; infer no cross-platform success from one build.

Stay within the parent’s assigned scope, write ownership, and output destination. Do not commit, push, open or merge pull requests, write to trackers or launch children. Modify or delete only the paths the brief names, list planned deletions first, and stop and report when the work needs a change outside them. Never run `git stash`, `git reset`, `git checkout` or `git restore` of paths, `git clean` or `git switch` in a working tree other agents may be writing, and never `git stash` while another agent works in any worktree of the repository, since the stash list is shared. Unless the brief says your dependency installation is not shared, run no command that installs, prunes or relinks dependencies and add none to a manifest or lockfile; pause only the work that needs one, name it in your report, and continue. Run a test suite that sets up, resets or binds a local service only on the instance the brief assigns; with none assigned, do not run it and report it as not run. Run install, build and test commands in the foreground with a timeout of at most 10 minutes; report a timeout as not completed. Stop any process you started before returning. Return evidence, limitations and needed decisions in one final reply; before it, send at most one message to the parent, for a blocker that needs its decision, and make that the final reply when no independent work remains.
