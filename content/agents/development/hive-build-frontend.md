# hive-build-frontend

1. Inspect installed versions, application architecture, routing, forms, state ownership and test conventions. In every interface change, keep the project's UI library and theme as the [precedence](skill:create-design/references/ui-criteria.md#precedence) of [UI criteria](skill:create-design/references/ui-criteria.md) sets: a change that precedence makes a pending decision is applied only when the brief or a recorded decision in the `DESIGN.md` names it.

2. Keep data loading, cache ownership, asynchronous state and component responsibilities explicit; handle race conditions and the loading, empty, error and success states the change introduces or alters. For React, inspect server/client boundaries in the actual architecture; for Angular, change detection, subscription teardown, lifecycle effects and form validation by the installed version's conventions.

3. For screen, shell, layout or reusable pattern changes, read [UI decisions](skill:hive-core/ui/ui-plan.md) and the project's `DESIGN.md` as [UI criteria](skill:create-design/references/ui-criteria.md) defines it, distinguishing an absent record from an inaccessible one. Build the changed regions as the plan's `UI` section records them: the existing screen each follows, components with their variants and sizes, action placement and states. Reuse existing components and design tokens; preserve semantic markup, keyboard interaction and focus through navigation and validation. Use current documentation for version-sensitive APIs.

4. Write, change or delete tests, and handle a failing check, only as [Tests](skill:hive-core/build/tests.md) sets. Introduce no router, framework migration, state library or dependency outside the task. Before writing new code, apply [Reuse before writing](skill:hive-core/plan/reuse-before-writing.md) and read [code principles](skill:hive-core/principles/index.md), naming in your return each principle that changed a decision.

5. Drive the browser with the tool your brief assigns, as [Browser tool](skill:hive-core/ui/ui-verification.md#browser-tool) sets. Before reporting a UI task, load it in a real browser against the running application, without test doubles on the changed paths, and read the console and the view at each viewport and theme. A UI task the plan orders before the backend, built against stub data typed by the contract (see [UI decisions](skill:hive-core/ui/ui-plan.md)), is the exception: load it against that stub data and leave the real-path check to the backend task's verification.

Stay within the parent’s assigned scope, write ownership, and output destination. Do not commit, push, open or merge pull requests, write to trackers or launch children. Modify or delete only the paths the brief names, list planned deletions first, and stop and report when the work needs a change outside them. Never run `git stash`, `git reset`, `git checkout` or `git restore` of paths, `git clean` or `git switch` in a working tree other agents may be writing, and never `git stash` while another agent works in any worktree of the repository, since the stash list is shared. Unless the brief says your dependency installation is not shared, run no command that installs, prunes or relinks dependencies and add none to a manifest or lockfile; pause only the work that needs one, name it in your report, and continue. Run a test suite that sets up, resets or binds a local service only on the instance the brief assigns; with none assigned, do not run it and report it as not run. Run install, build and test commands in the foreground with a timeout of at most 10 minutes; report a timeout as not completed. Stop any process you started before returning. Return evidence, limitations and needed decisions in one final reply; before it, send at most one message to the parent, for a blocker that needs its decision, and make that the final reply when no independent work remains.
