# hive-review-ux

When your brief gives frames in a design file, as [flow-figma-design](skill:flow-figma-design/SKILL.md) draws them, review them by this paragraph in place of steps 1 to 3. Read each frame and the sibling screens it names through the design tool's connection: its image and its node tree. Judge each frame against the request, what the siblings fix as your brief lists it, or, when it lists nothing, what you measure in the named siblings yourself, and the decisions recorded for the app, by [hive-ui-criteria](skill:hive-ui-criteria/SKILL.md) and its precedence, including the components and the copy; when the app's `DESIGN.md` declares a design library, a piece or variable that library holds, drawn other than as its instance or binding, is a finding unless your brief says the file could not use the library. List apart, as unsettled rules, each business rule a frame shows, as step 5 of [flow-figma-design](skill:flow-figma-design/SKILL.md) defines one, that neither your brief's requirements and recorded decisions nor the siblings settle; an unsettled rule does not fail the verdict. Measure the alignment: edges and spacing shared with the siblings, a shell whose size matches theirs, nodes outside the tool's automatic layout or absolutely positioned where the siblings use neither, and text that does not fit its container. Driving a browser, the loading, empty and error states, keyboard order, focus, the automated audit, the list of defects the base already shows and the captures for the human handoff do not apply. Without a connection that reads the file, judge from the images in your brief and report each alignment measurement as not run. The verdict starts as not passed and is passed when the frames show no finding against the request, the siblings, the recorded decisions or the declared library. A follow-up after a fix rereads only the corrected frames. Report as step 4 sets, with the unsettled rules after the findings, without the list of defects the base already shows and without states not covered. Never change the frames.

1. Drive the browser with the tool your brief assigns, or else the `agent-browser` skill when it is installed, otherwise the host's browser tool, as the browser tool section of [UI verification](skill:flow-verify/references/ui-verification.md) sets. Read [UI verification](skill:flow-verify/references/ui-verification.md) for the proportional widths, themes and correction scope. Identify the intended users and task. Review what the change shows and every region its layout affects, the ones it displaces, resizes or reflows, such as the list below a new toolbar, not the whole screen, with the longest real values and with text 30–50% longer. Inspect the rendered experience when available. For screen, shell, layout, or pattern changes, read the `UI` section of the plan's `design.md` when the brief names one, the design system the project guidance names, and the project's `DESIGN.md` as [hive-ui-criteria](skill:hive-ui-criteria/SKILL.md) defines it, distinguishing an absent record from an inaccessible one; judge the result against the approved sketches as well, and against the approved example when the brief carries its image, reporting each difference, as step 1 of [flow-verify](skill:flow-verify/SKILL.md) defines it, as a finding. Judge the changed regions against the decisions recorded under [UI decisions](skill:flow-plan/SKILL.md#ui-decisions): the existing screen each follows, the components, their variants and sizes, the action placement and the states. Sign in only with the accounts your brief gives, as the global guidance's «Test accounts» sets for a child.

2. Judge the rendered result against the project's UI library, its theme and its `DESIGN.md`, following the [precedence](skill:hive-ui-criteria/SKILL.md#precedence) of `hive-ui-criteria` for library defaults and recorded decisions, but layout integrity, loading, empty and error states, keyboard order, focus and accessible names are always checked, by measurement and interaction rather than by eye. Report each failure the change introduced in a check marked measured in [criteria](skill:hive-ui-criteria/references/criteria.md) as a defect with its priority; do not judge its screen modes or the refinement guidance. Run the automated audit on each reviewed state as the [automated accessibility audit](skill:flow-verify/references/ui-verification.md#automated-accessibility-audit) section sets. Layout integrity means: a value that does not fit in two lines is truncated with an ellipsis and its full value is shown on hover and in its accessible name; short values, such as dates, badges and button labels, stay on one line; no word breaks mid-word; the page has no horizontal scroll; no element overlaps another; and at a mobile width the layout reflows to that width, such as one column where the desktop shows columns side by side. You are an independent, skeptical reviewer: the verdict starts as not passed, and an observed defect keeps its severity. The verdict judges only the defects the change introduced in the reviewed regions: it is passed when the reviewed states show no defect the change introduced, of any priority, and it stays not passed when no state could be reviewed, with the report saying the review did not run. Give each finding a priority from P0 to P3 by observable impact, as [Findings](skill:flow-close/SKILL.md#findings) defines. Report every defect in those regions that the base already shows in a separate list, each with its priority; that list does not change the verdict.

3. For the human handoff, read [flow-walkthrough](skill:flow-walkthrough/SKILL.md); return evidence to the primary producer rather than publishing it yourself. You do not record video. The brief gives you the captures of the changed screens and states, and how to reach each state step 2 always checks or which of them cannot be reached. Cover the regions the change alters and their possible impact on the layouts and other components that contain or reuse them, such as containers, lists, dialogs and shared components: measure and interact with the running view instead of capturing again, and capture only what the brief lacks, in the parent-assigned evidence destination when tools and permissions allow; do not change application code. A state you cannot reach with the brief's means is not covered: list it with what blocked it; it does not fail the verdict, and you do not stop to ask for it. When the parent sends a follow-up after a fix, or briefs you only to reread corrected findings, review only the corrected regions and states it names, the layouts that contain them and those regions' loading, empty and error states, against the findings that fix answers, which the follow-up, your brief or your own earlier report gives, instead of the full scope of steps 1 and 2; on them still run step 2's automated audit and its layout-integrity, keyboard order, focus and accessible-name checks, with the longest real values and text 30–50% longer; and answer in one reply. Return capture links, the actual URL, required role, navigation/actions and expected versus observed results. Disclose unavailable capture access rather than claiming evidence exists.

4. Report the verdict (passed or not passed) and each finding the change introduced with its priority, user impact, location, reproduction, and evidence; then the list of defects the base already shows, and the states not covered. Distinguish source-based concerns from observed interaction failures. Do not modify the interface during review.

Stay within the parent’s assigned scope, write ownership, and output destination. A Git command that rewrites working-tree files, such as `git stash`, `git reset`, `git checkout` or `git restore` of paths, `git clean`, or `git switch`, modifies every path it touches: never run one in a working tree that other agents may be writing; compare with the base through `git diff` or `git show <base>:<path>`, or in a separate worktree. `git stash` also writes the stash list that every worktree of the repository shares: never run it while another agent works in any worktree of the same repository. Unless the brief says your dependency installation is not shared, run no command that installs, prunes, or relinks dependencies, such as `npm ci`, `pnpm install`, or adding a package, and do not add one to a manifest or lockfile yourself: pause only the work that needs the dependency, name it in your report, and continue the rest. Run a test suite that sets up, resets, or binds a local service, such as a test database, a cache, or a port, only on the instance the brief assigns; when it assigns none, do not run the suite and report it as not run. Run every install, build and test command in the foreground with an explicit timeout of at most 10 minutes rather than behind a background monitor, and report one that hits the timeout as not completed. Stop any process you started before returning. Return evidence, limitations, and any decision needed from the parent in one final reply; before it, send the parent at most one message, for a blocker that needs the parent's decision, and return it as the final reply when no independent work remains.
