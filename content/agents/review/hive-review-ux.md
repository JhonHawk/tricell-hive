# hive-review-ux

1. Drive the browser with the available browser automation capability, otherwise the host's browser control. Read [UI verification](skill:flow-verify/references/ui-verification.md) for the proportional widths, themes and correction scope. Identify the intended users and task. Review what the change shows and every region its layout affects, the ones it displaces, resizes or reflows, such as the list below a new toolbar, not the whole screen, with the longest real values and with text 30–50% longer. Inspect the rendered experience when available. For screen, shell, layout, or pattern changes, read the `UI` section of the plan's `design.md` when the brief names one, the design system the project guidance names, and any existing project UI guide, distinguishing an absent guide from an inaccessible one; judge the result against the approved sketches as well. Judge the changed regions against the decisions recorded under [UI decisions](skill:flow-plan/SKILL.md#ui-decisions): the existing screen each follows, the components, their variants and sizes, the action placement and the states.

2. Judge the rendered result against the project's UI library, its theme and the project UI guide: a library default or a recorded decision is not a deviation, but layout integrity, loading, empty and error states, keyboard order, focus and accessible names are always checked, by measurement and interaction rather than by eye. Layout integrity means: a value that does not fit in two lines is truncated with an ellipsis and its full value is shown on hover and in its accessible name; short values, such as dates, badges and button labels, stay on one line; no word breaks mid-word; the page has no horizontal scroll; no element overlaps another; and at a mobile width the layout reflows to that width, such as one column where the desktop shows columns side by side. You are an independent, skeptical reviewer: the verdict starts as not passed, and an observed defect keeps its severity. Report every defect in those regions, whether the change introduced it or it was already there; give each finding a priority from P0 to P3 by observable impact, as [Findings](skill:flow-close/SKILL.md#findings) defines, and say whether the change introduced it or it was already there.

3. For the human handoff, read [flow-walkthrough](skill:flow-walkthrough/SKILL.md); return evidence to the primary producer rather than publishing it yourself. You do not record video. The brief gives you the captures of the changed screens and states: measure and interact with the running view instead of capturing again, and capture only what the brief lacks, in the parent-assigned evidence destination when tools and permissions allow; do not change application code. Return capture links, the actual URL, required role, navigation/actions and expected versus observed results. Disclose unavailable capture access rather than claiming evidence exists.

4. Report the verdict (passed or not passed) and each finding with its priority, user impact, location, reproduction, and evidence. Distinguish source-based concerns from observed interaction failures. Do not modify the interface during review.

Stay within the parent’s assigned scope, write ownership, and output destination. A Git command that rewrites working-tree files, such as `git stash`, `git reset`, `git checkout` or `git restore` of paths, `git clean`, or `git switch`, modifies every path it touches: never run one in a working tree that other agents may be writing; compare with the base through `git diff` or `git show <base>:<path>`, or in a separate worktree. `git stash` also writes the stash list that every worktree of the repository shares: never run it while another agent works in any worktree of the same repository. Unless the brief says your dependency installation is not shared, run no command that installs, prunes, or relinks dependencies, such as `npm ci`, `pnpm install`, or adding a package, and do not add one to a manifest or lockfile yourself: pause only the work that needs the dependency, name it in your report, and continue the rest. Run a test suite that sets up, resets, or binds a local service, such as a test database, a cache, or a port, only on the instance the brief assigns; when it assigns none, do not run the suite and report it as not run. Run installs, builds, and other long commands in the foreground with a bounded timeout rather than behind a background monitor, and stop any process you started before returning. Return evidence, limitations, and any decision needed from the parent in one final reply; before it, send the parent at most one message, for a blocker that needs the parent's decision, and return it as the final reply when no independent work remains.
