# hive-review-code

1. Read the diff, then the code it depends on: callers, types, invariants, data flow and relevant tests. When the repository root has a `CODING_STANDARDS.md`, its standards apply to this review, not to the implementer. Follow [suppression review](skill:hive-core/review/suppression-review.md) for changes that weaken checks and return its inventory and dispositions to the parent.

2. Search the change line by line through each hunk, and for behavior the diff removes or weakens, callers and contracts in other files it affects, language and framework pitfalls, wrappers, proxies or adapters that must stay consistent with what they wrap, concurrency against a second actor, consistency between predicates and writes, error handling, resource lifetimes and public compatibility. Rate a change the task did not ask for, such as an unrelated refactor or an added feature, as P2. Check that a defect fix sits at its cause as [defect fix](skill:hive-core/build/defect-fix.md) sets, and that new code does not copy or extend a base that [reuse before writing](skill:hive-core/plan/reuse-before-writing.md) does not count as sound; a fix those leaves have the author make is not a change the task did not ask for. Before reviewing a diff, read [code principles](skill:hive-core/principles/index.md). Judge each new or changed test by points 3 and 4 of «Before writing a test» in [Tests](skill:hive-core/build/tests.md) and flag each one that fails either.

3. Report a finding only when all of these hold: the change introduced it, or makes reachable or widens access to code already there (such as re-enabling a disabled path), but not code that stays as reachable as before; it is discrete and actionable; you can state a concrete failure scenario, meaning the inputs or state that lead to the wrong output, crash or broken contract; and you identify the affected code instead of speculating that something elsewhere might break. When confidence is limited but the impact would be high, such as data loss or a security exposure, report it and state what remains unverified. A change that violates a `CODING_STANDARDS.md` standard is also a finding: the violation replaces the failure scenario, and when it is mechanical (a banned API, an import shape, a file's language or location) name the automated check that could enforce it. A name the change introduces in a language other than English is a finding of the same kind, even without a `CODING_STANDARDS.md`, unless [naming language](skill:hive-core/principles/naming-language.md) keeps it: that leaf sets which names count and which stay as written. For a fix placed at the symptom or a copied or extended unsound base, the failure scenario is the bad state the cause still produces for its other consumers, or that base's spread. Do not report a finding whose only fix guards against, or tests, a case the change cannot produce; input that crosses a trust boundary can produce any case. Report nothing rather than guess; no findings is a complete result.

4. Give each finding a priority from P0 to P3 by observable impact, as [Findings](skill:hive-core/close/close-report.md#findings) defines, with its exact location, the failure scenario, the evidence, and whether the code confirms it or it is plausible, following [Review evidence](skill:hive-core/review/review-evidence.md). When a finding rests on a project rule, cite that rule's file and line. Rank correctness defects above maintainability ones, and report a defect that appears in several places once, naming the defect class and every location.

5. Report no style-only rewrites or arbitrary size thresholds that no project standard states. Do not modify source or delegate parts of the review.

End with the number of findings at each priority and a one-line verdict: whether the change is correct as written, with its main reason. Add one line naming each principle you read that changed a decision, or none. Then say whether the diff crosses a boundary listed in [Security boundaries](skill:hive-core/build/security-boundaries.md), naming each one it crosses, so the parent can offer a security review.

Stay within the parent’s assigned scope, write ownership, and output destination. Never run `git stash`, `git reset`, `git checkout` or `git restore` of paths, `git clean` or `git switch` in a working tree other agents may be writing, and never `git stash` while another agent works in any worktree of the repository, since the stash list is shared. Stop any process you started before returning. Return evidence, limitations and needed decisions in one final reply; before it, send at most one message to the parent, for a blocker that needs its decision, and make that the final reply when no independent work remains.
