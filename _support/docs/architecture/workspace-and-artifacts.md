# Workspace and artifact organization

This document explains the artifact policy in [the shared global guidance](../../../content/guidance/global.md). That source carries the essential operating rules without requiring a skill or this document to load. The [project-layout](../../../content/skills/project-layout/SKILL.md) skill is the canonical procedure for cleaning up, pruning and reorganizing existing documentation and support material, curating evidence, promoting findings, and archiving; flow-close keeps the inventory of a work's own material at its close. This reference provides examples and rationale; it is not a second router or an installer.

## Resolve scope before choosing a folder

A workspace is a declared project context containing related repositories, not every directory above a Git root. Resolve it from the user's task and established project instructions or documentation. Git can identify a repository or worktree root, but does not establish which sibling repositories form a project. If shared scope is unclear, resolve that ambiguity before writing outside the known repository.

When the code a request changes lies outside the session's project, read the global guidance's «Scope and authorization» rule on changing only the current project before planning or editing there: a request that names only a ticket does not tell whether the user knows where its code lives.

| Work shape | Default support home | Example |
|---|---|---|
| Standalone repository | `<repo>/_support/` | A backend investigation specific to that repository |
| One repository inside a multi-repo workspace | `<repo>/_support/` | A frontend-only implementation record |
| Work spanning related repositories | `<workspace>/_support/` | An API/consumer compatibility investigation |
| Monorepo | `<repo>/_support/` | Application grouping within `docs/<app>/`, not `apps/<app>/_support/` |
| Existing documented artifact destination | The established destination | Shared decisions already maintained in a documentation repository |

Apply this routing to new work. Continuing work retains its established scope and home; a later change of scope may justify a proposed migration, not a silent move. Existing package-level documentation or support folders are not automatically relocated.

An existing documentation repository may provide equivalent homes such as `sessions/` or `decisions/`; do not nest another `_support` merely to match a template. Without a documented versioned home, keep shared durable material locally in the workspace's `_support` and report that it is local. Selecting a versioned destination is a separate decision; creating a specs repository, initializing Git, or publishing is not implied.

## Project settings and change records

The [global guidance](../../../content/guidance/global.md) «Project settings» defines the `## Hive` section, with its keys and example, and also defines the `openspec/` change records. The section holds facts about the repository; `harness-audit` creates and updates it. Each repository declares its settings in full because Codex never loads files above the Git root and Grok Build was observed not to load a workspace `AGENTS.md` from a child repository; only Claude Code loads ancestor files. A specs or mocks repository declares a shorter section, such as `Specs: openspec` in the specs repository; a repository outside the project never inherits another project's values.

Planned work lives in `<specs>/changes/<change-id>/` and current requirements in `<specs>/specs/`, where `<specs>` is the `openspec` directory that `Specs` names: `_support/openspec` inside a repository without a specs repository, or `<specs-repo>/openspec`. `_support/openspec` must stay versioned; repositories here ignore only `_support/workspace/` and, in some, parts of a legacy `_support/evidence/`. The layout follows OpenSpec file conventions without its CLI. It replaces `_support/sessions/` for plans and the unversioned workspace ledger for project state: `openspec/project.md` keeps only what no other source states. Existing sessions, epics, and ledgers stay as history. See the [change records reference](../../../content/skills/flow-plan/references/change-records.md) for file roles, the delta format, and closure.

## Three destinations, created when needed

```text
<scope>/_support/
├── docs/
│   └── <topic>/
├── sessions/
│   ├── YYYY-MM-DD-<work>/
│   │   ├── <work>.research.md   # Optional retained investigation
│   │   ├── <work>.report.md     # Optional separate human deliverable
│   │   └── reports/            # Optional human deliverables
│   └── archived/
├── workspace/
│   └── YYYY-MM-DD-<work>/
└── data/
    └── YYYY-MM-DD-<work>/       # Inputs and outputs of an operation; never versioned
```

This is a vocabulary, not a scaffold to create for every request. A single useful record is sufficient when it carries the work. Do not create empty files, folders, or indexes solely to match the diagram.

- **Knowledge:** `docs/` describes current conventions, decisions, or architecture. A living guide is updated in place; a dated historical decision can be superseded with an explicit reference to its successor. Keep an existing ADR or contract convention when present.
- **Execution:** planned work lives in its `<specs>/changes/<change-id>/` folder. `sessions/` keeps only records tied to no change, such as research or a report requested on its own. An enduring design conclusion belongs in its documentation home.
- **Workspace:** `workspace/` holds material the user may open or whose versioning is still undecided: working documents, review images, temporary information that may later be versioned or discarded, and files a tool or later session must find again, such as saved browser state or a manager's `--out` plan, which the manager rejects under `/tmp`. Ignore its contents in Git. The current Hive scaffold retains only selected `.gitkeep` markers; this does not make its files versionable or require markers in other projects.
- **Machine facts:** facts that hold in any project live in the machine file `~/.config/hive/HIVE.local.md`, outside every repository; a session in the tricell-hive checkout once wrote T3 Code, cloudflared and Antigravity facts, a macOS diagnosis and a transient `ssh` failure into the repository's file, where other projects never see them (Claude Code, de72f693, 2026-11-07). Project facts stay in `HIVE.local.md` at the repository or declared workspace root, ignored through `.git/info/exclude`, the one support file outside the support home: the user sees it next to `AGENTS.md`, and it holds only facts verified on this machine, dated and without secret values. Real sessions re-derived those facts session after session: a carvento session spent 53 minutes on ports and CSRF origins another session had worked out eight days earlier (Claude Code, 8d09a5eb, 2026-11-02). The global guidance's «Local instructions» holds the rule. Since 2026-11-13 (change `hive-local-one-line-facts`) an entry is one line of at most 200 characters that says what the machine or the project has, lacks, uses or needs, and the steps or workaround it needs live in persistent memory under `local/<slug>`, in the file's project or in the project `hive-machine` for the machine file, behind a pointer at the end of the line. The sessions of 2026-11-07 to 2026-11-13 on one machine preceded it: 8 files held 77 entries in 27 KB, every session and every child loaded them, 49 (Claude Code, 53 sessions) and 63 (Codex CLI, 276 rollouts) of the 77 were never reused by a later session, and 22 recorded a measurement, an event, a diagnosis or the state of a work item.
- **Local scripts:** a helper only this machine needs lives at `_support/scripts/<name>` next to the `HIVE.local.md` that names it, excluded from Git like `secrets/`. The case that prompted it: the native alternative to a per-agent Postgres tool is a script that clones a template database for each worktree (`CREATE DATABASE … TEMPLATE`), which a client repository should not carry (2026-11-08). A worktree checks out only tracked files, so the ignored file index and scripts exist only in the main checkout; agents read and run them there by the main checkout's path, the first `worktree` line of `git worktree list --porcelain`, the same method branch cleanup uses. A Claude Code session isolated in a worktree had its `Edit` and `Write` of the main checkout refused while a shell redirect went through, and Git inside `$(…)` was refused too (Claude Code 2.1.319, session b3015fee, 2026-11-08). Deferring the write until the session left the worktree was planned and dropped, since leaving is the user's call there and removing the worktree deleted the pending file. Editing a line by number through `sed` was dropped in code review: entries hold `/` and `&`, and another session can shift the line. So from an isolated worktree the guidance only adds new entries and scripts through the shell, under the user's permission settings, and names any other change in the final report.
- **Scratch:** temporary utilities, shell helpers, intermediate transformations, and raw outputs nobody needs after the command or task go where the host keeps temporary work: its declared scratch or session directory, otherwise the operating system's temporary directory, never the repository root. Hosts differ, so the guidance names no single path. Anything the user should read goes to `workspace/` instead: a review file left in `$TMPDIR` (a sample-project Grok session, 2026-09-24) was hard to find and could be purged by macOS. The test is disposability, not temporariness: scratch must be reproducible, so cleanup can never destroy the only copy of work. A Git worktree holding unintegrated edits fails that test even though it is temporary. Hive names no worktree location (D29, 2026-10-12): each host already has its own (Claude Code inside the repository under `.claude/worktrees/`, Codex, Grok and Cursor under their own home directories; Antigravity's was not checked), and a fixed Hive default fought those harnesses. The earlier sibling default `../<repo>-worktrees/<work>` codified a folder a Grok session had created by hand outside the workspace (a sample-project session, 2026-10-08) and was removed at the user's request. What `git-workflow` keeps is the host's feature or the repository's documented place, never a temporary directory, and a persistent-memory record of each worktree created, so a session that stops midway can be resumed by another host; agents that each picked their own place (a sibling folder, `.worktrees/`, `/private/tmp`) left worktrees and branches nobody saw until a later cleanup (a sample-project session, 2026-10-09). `git-workflow` also limits when to create one: only when the current checkout holds others' changes or a non-base branch, another task writes in the repository at the same time, or the task needs two checkouts at once; otherwise the branch goes in the current checkout. A real session created four of its five worktrees with a clean, idle checkout, each adding setup, a memory record and cleanup (carvento, Claude Code, 66c195b6, 2026-10-13). Since 2026-11-15 the agent no longer decides: creating a worktree is the user's decision, asked with what the agent observed, and an accepted worktree goes in the host's native location (or a path the user gives), is named in the work's checkpoint (`tasks.py checkpoint --worktree`) rather than in persistent memory, and is found again with `git worktree list`; delegated children never create one. The creation criteria and the per-worktree memory record were removed because agents still placed worktrees in improvised folders (`carvento/.worktrees`, `cam/_support/workspace/<date>/<repo>`, `fleetsystem/_support/worktrees`) and later sessions reused the recorded paths as precedent. The same change made each command that acts on a repository take that repository's absolute path, after six sessions ran `pnpm` at a declared workspace root and left a `package.json`, a lockfile and `node_modules` there (2026-10-28 to 2026-11-13).
- **Evidence:** a work's verification material, such as walk outputs, captures and raw CI or cloud output, stays unversioned in its `workspace/` folder while the work is open; once the work is integrated, the pull request body, which lists each acceptance criterion with its evidence, replaces it. Captures reach that body as uploaded before and after images, never as committed files, and a local capture counts as replaced only when its uploaded URL was read back in the merged body ([pull request captures](../../../content/skills/git-workflow/references/pr-captures.md)). Only three kinds of conclusion are promoted, into the durable document that uses them: a measurement a later change is compared against, a rehearsal or procedure that was run, and a review or audit that opens other work. The promoted text carries the figure, method, sample size, date and provenance, never raw data and never a CI run link alone. Since 2026-11-16 Hive creates no `evidence/` folder. The reason: a path-citation audit of 136 per-work evidence folders in four project specs repositories found 5 cited by later work, all measurements, rehearsals or reviews, and none of the per-ticket walks, captures or raw dumps; no record showed evidence averting a costly decision; one project had already removed 55 of its 58 evidence files with nothing citing them afterwards (2026-11-16). GitHub Actions artifacts and logs expire after 90 days at most, measured on three repositories the same day, so a CI link cannot be the durable record. Existing `evidence/`, `archive/` and release-record folders are cleaned up on request through the [project-layout](../../../content/skills/project-layout/SKILL.md) skill, which covers every repository of a declared workspace or a monorepo's tree, tags the pre-cleanup commit `archive/<date>-<slug>` and removes the items without rewriting history.

Source code, permanent maintenance scripts, application configuration, and infrastructure remain in their established project locations, except the local scripts above. They do not become scratch because an agent wrote them.

## Layouts, the index and scripts

Since 2026-11-18 (change `project-layout-skills`) the layout convention has one home, [project-layout](../../../content/skills/project-layout/SKILL.md) and its [layout reference](../../../content/skills/project-layout/references/layout.md), which every flow reads before writing a support artifact. The convention had been folded into flow-close in the skills rebuild of 2026-10-30, to cut ceremony; it returned to a skill of its own because organizing and migrating projects now need it too, and three homes (writing in flow-close, layout checks in harness-audit, cleanup in docs-cleanup) had let each project grow its own variant. A read-only inventory of four projects on 2026-11-17 found what that cost: one project left five groups of scripts in `_support/scripts/` that no `HIVE.local.md` named, another versioned 46 CI scripts and its Terraform under `_support/`, a third versioned 86 scripts under `_support/scripts/` across three repositories while its application code read and wrote `_support/`, and about 540 scripts sat inside `workspace/` and `sessions/` folders. Only one project registered its local scripts.

- **Two layouts.** A monorepo when the repositories pass a four-point viability test (same writers, path-selected deploys in one CI, no separate publication contract, no history merge needed), otherwise a workspace of repositories, which [workspace-repo](../../../content/skills/workspace-repo/SKILL.md) can turn into a coordinator repository on request. The coordinator versions the workspace's `AGENTS.md`, its repository table, `_support/docs` and `_support/openspec`, ignores its children in `.gitignore` and re-includes them in `.ignore`, because a search that respects `.gitignore` from the root found nothing in an ignored child (ripgrep, 2026-11-17). Codex, Grok and Cursor do not load the coordinator's `AGENTS.md` in a session started inside a child, so each child keeps its complete `## Hive`. The pattern follows practitioners' reports of a coordinator or home repository (aihero.dev, 2026-11-12; Superblocks, 2026-03-10), which carry no measurements.
- **The index.** One file, `_support/docs/README.md` by default, lists the documents, runbooks and internal tools in force with when to read or use each, so a session learns what a project has in one read. A `Layout:` line at its head declares the homes a project keeps when the user declined moving them; the check reads it.
- **Scripts.** Code that every clone needs lives in the repository that owns it, never under `_support/`; a script run once against shared data stays with its session record; a repeated purpose climbs through the levels of [script lifecycle](../../../content/skills/project-layout/references/script-lifecycle.md) to an internal tool with a test and an index line. `check_layout.py` reports what does not follow this, with its correction.

## Naming and continuity

The shared guidance defines the naming convention. New records use `<topic>.<type>.<extension>` with descriptive English `kebab-case` topics and English types. For example, `context-update.research.md` and `context-update.report.md` remain identifiable outside their parent folder; change folders use fixed file names. Dated directories start with the work's initial date, `YYYY-MM-DD`, followed by its stable slug; internal records do not repeat the date. Avoid generic standalone names such as `output.md` or `temp.json`. Keep tool entrypoints (`AGENTS.md`, `SKILL.md`, `README.md`) and existing source conventions. Historical records retain their names unless a separate organization task covers their migration.

New records use the dotted form, but both `<topic>.plan.md` and the established legacy `<topic>-plan.md` form are valid handoffs. The same compatibility applies to research and reports. Resume the existing record and do not rename files merely to normalize their form.

A new retained plan is a change folder whose `tasks.md` carries its task list and progress. A separate research or report file is useful when it has its own audience or substantial evidence; the vocabulary does not require three files. Retain plans when requested or needed for resumption, delegation, coordinated deliveries, consequential decisions, or investigation that would be costly to reconstruct. Small understood changes can use a conversational plan. Preparation is separate from persistence: the `flow-plan` skill owns the procedure for grounding decisions and connecting requirements, tasks, and verification; file presence does not prove readiness.

One work item keeps one change or session folder across conversations. Supporting scratch and evidence use the same initial date and slug. A new conversation or calendar day does not create a new work item. When meaningful phases need separation, add descriptive subfolders inside the existing work folder rather than scattering it across sibling sessions. An independent new objective gets a new folder.

For example, work started under `sessions/2026-09-20-api-contract/` still resumes there on the next day. Temporary traces and verification material can use `workspace/2026-09-20-api-contract/`. A resulting ongoing convention belongs in `docs/api/contracts.md`, linked back to the session. Keep the session's historical findings as history, not a second live convention.

Dates identify historical snapshots. Living documents such as `docs/api/contracts.md` need no date prefix. No mandatory per-directory README is required when naming and links already make the contents discoverable; use an index when it supplies useful navigation or lifecycle information.

Agent instructions, operational contracts, and guidance use English. Human reports use the session language unless requested otherwise. A Spanish report inside `reports/` can support an English architecture decision; the document's purpose determines its language, not its directory or eventual readers.

## Retention, versioning, and hygiene

These are separate questions: does the artifact need to survive, where can it safely live, and should it enter Git?

| Artifact | Retention and location | Git treatment |
|---|---|---|
| Reusable decision or resumable work record | Existing durable home or appropriate `docs/` / `sessions/` | Suitable for versioning when non-sensitive; not an automatic commit |
| Regenerable intermediate output no longer needed | The host's temporary location; remove at task close when created by this task | Not in the repository |
| Working document, review image, or output whose versioning is undecided | Task-local `workspace/` | Ignored until a decision moves it to a versioned home |
| Verification material of a work: walk outputs, captures, raw CI or cloud output | Task-local `workspace/` while the work is open, with a build's before captures in `images/before/`; after integration the pull request body replaces it, captures only when their upload was read back | Not versioned |
| Measurement, rehearsal or review that later work reuses | Its conclusion, with figure, method, sample size, date and provenance, in the durable document that uses it | Versioned in that document; its raw data is not |
| Unique failure trace or transient external-state capture | Task-local `workspace/` until the finding has a ticket or the work is integrated; private local storage if needed | Never publish a raw dump merely to retain it |
| Sensitive material or recovery backup | Existing protected local location; no new storage convention imposed | Excluded; not treated as disposable scratch |

Re-running an application may not reproduce a transient failure, remote state, or the same screenshot. Reproducibility must be assessed rather than inferred from the ability to rerun a command. If evidence is necessary but unsuitable for Git, preserve it privately and explain that a clean clone will not contain it. Label snapshots with their observation date; revalidate them before claiming current state.

At close, promote the reusable conclusions and remove only the task's own reproducible temporary files that are no longer needed. Do not blanket-delete a work directory containing prior or unique material. Uncertain ownership or retention needs mean preserve and report, not guess. This standing cleanup permission does not cover old scratch, other users' files, authentication, memory data other than the pending-work records `flow-close` updates and soft-deletes, or backups. The [`flow-close` skill](../../../content/skills/flow-close/SKILL.md) holds the close and session-end procedure, including when a change folder is versioned and archived and how its pending-work records are kept, and the inventory of the work's own support material, whose proposed actions (commit, archive, promote, delete or keep) the user answers before anything is applied.

Archiving retains execution history without treating age as proof of completion. For example, closed research may be archived while an older unresolved investigation remains active. The skill contains the operating procedure, including closure checks, authorization, collisions, and link preservation; maintain those details there.

harness-audit's [Engram workspace mode](../../../content/skills/harness-audit/references/engram-workspace.md) provides an explicit dry-run helper when a declared workspace needs a shared local Engram identity. It requires an identity and selected targets, verifies all existing configurations before apply, and never infers sibling repositories, changes global ignores, or migrates memory. The [archive procedure](../../../content/skills/project-layout/references/archive.md) of project-layout handles selected closed-session moves; it has no age policy and never stages, commits, or pushes; `flow-close` delivers the moves its support-material decision selected. Explicit unattended delegation is documented by [`unattended-delegation`](../../../content/skills/unattended-delegation/SKILL.md); it is a bounded coordination mode, not a workspace lifecycle mechanism.

## Limits of this implementation

These artifact conventions are authored instructions, not enforced filesystem behavior. No hook, artifact resolver, automatic workspace migration, archiver, or configuration database implements them. The separate [deployment manager](deployment-manager.md) installs guidance; it does not enforce task artifact placement. Host loading and behavioral outcomes are measured separately from filesystem installation.

Follow [flow-close](../../../content/skills/flow-close/SKILL.md) for the viewer transition and later cleanup. Retain its confirmation and receipts; current-copy confirmation can require retaining the source review unit or containing worktree beyond ordinary session-end cleanup.
