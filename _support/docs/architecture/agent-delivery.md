# Canonical agents and native delivery

Agent instructions have one source at `content/agents/<category>/<name>.md`. Categories organize authorship; all native destinations use the unique filename stem. Do not keep converted host copies in the repository or a tracked distribution directory.

`integrations/agents` parses a deliberately small frontmatter contract: `name`, `description`, `model_profile`, and `access_profile`; optional `effort` (`low`, `medium`, `high`, `xhigh`, or `max`) overrides the profile's effort for that role where the host can render it. Optional `effort_claude` overrides only Claude Code's effort and leaves other hosts on their profile defaults. OpenCode encodes effort as a model variant instead of a separate field. Values are single-line strings, optionally JSON-quoted. The body is preserved. Unknown fields, malformed sources, and unknown profiles fail validation. `integrations/agent-profiles.json` is the single host mapping. The deployment manager converts in memory during planning and freezes the native bytes for apply and recovery.

### Effort

Every profile that can carry an effort declares one, so no role inherits the session effort on Claude, Codex, or Pi: a user lowering the session effort to stay in the loop would otherwise lower delegated children that nobody steers. A role declares `effort` only when its task needs a different level on every host that can represent it; the value is absolute and replaces the profile's. Current exceptions: `hive-review-security` `max`, where effort gains most for security work ([Spending your effort](https://claude.dev/blog/spending-your-effort/)); `hive-read-state` `low`; `hive-review-plan` and `hive-write-docs` `medium`. Six roles also set `effort_claude: medium`, so on Claude Code they run at `medium` instead of their profile's `high` while other hosts keep their profile effort: `hive-build-backend`, `hive-build-frontend`, `hive-build-kmp`, `hive-build-infra`, `hive-write-tests`, and `hive-design-ui`.

| Host | Rendered key | Levels |
| --- | --- | --- |
| Claude Code | `effort` | `low`–`max`; the active model clamps an unsupported level to its highest supported one ([model configuration](https://code.claude.com/docs/en/model-config)) |
| Codex | `model_reasoning_effort` | `low`–`max`, plus `ultra`, which Codex also lists and the validator accepts but no Hive profile uses; behavior for a level the model does not support is undocumented, and `max` is not documented for GPT-6 Astra ([subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)) |
| Pi + pi-subagents | `thinking` | `off`–`max` (0.67.0 `src/shared/model-info.ts`); the level is appended to the resolved model without a capability check, so provider handling is unverified |
| OpenCode V2 | `model: provider/model#variant` | Only when a model override sets a model: the variants each model in the `variants` table offers (`low`/`high`/`max` for Flash and GLM, `high`/`max` for DeepSeek v4 Pro); an override's effort the model lacks is refused. The profiles set no model, so by default roles inherit the session's model and effort and role exceptions have no effect |
| Grok, Cursor | none | Role exceptions have no effect. Grok has no effort field, so children inherit the session effort; Cursor binds effort to a concrete model, which Hive leaves as `inherit`, with the same result |

A level missing from a host's scale would render as that host's highest documented level; the configured Claude, Codex, and Pi profiles use `low`–`max`. The mapping follows the host's scale, not the model's: a role on the `inherit` profile, such as `hive-review-security`, runs on the session's model, whose support for `max` the renderer cannot know. Codex uses GPT-6.1 Sol at `medium` for execution and `high` for reasoning, GPT-6.1 Terra at `medium` for focused work, and GPT-6.1 Sol at `high` for its `verifier` profile; Pi inherits the session model at those same efforts.

Profiles are delivery defaults, not a replacement for the host's authentication, model loop, or permissions. The canonical JSON contains the exact model identifiers. A configured model is not proof of account availability or a successful run.

`observe` selects native read-oriented defaults where available; on Codex there are none, so it renders no key there. `implement` retains host permissions; `verify` also retains them because builds and tests may write artifacts. Role instructions constrain verification to evidence rather than source fixes. These categories are not universal security sandboxes: shell tools, external services, parent overrides, and native policy resolution still matter. Claude parent auto, acceptEdits or bypassPermissions modes can override a child's plan mode. Codex has no per-role sandbox (next paragraph). Grok's documented permission field does not demonstrate enforcement of every mode in the installed build. Grok removes a tool only by its tool ID: `write` removes the write tool and `search_replace` the edit tool, while the display name `Write` removes nothing (Grok 1.0.55 user guide, headless mode). Until `write` joined the observe list, a `hive-review-code` child wrote its notes file with it (dened Grok session, 2026-10-13).

Codex has no per-role sandbox. ## Delegation and instruction delivery

`content/guidance/global.md` retains essential delegation boundaries and explicit read conditions; `content/skills/flow-research/references/delegation.md` owns the detailed dispatch, resource-delivery and wait procedure. Questions and reporting have their own canonical references; reporting is read under the conditions in `content/guidance/global.md`. Activity skills own their specific decomposition and review procedure; role descriptions identify stable responsibilities. Project guidance and situational references supply technical conventions. Keep these sources canonical rather than maintaining a second role-by-stack routing table.

A role's native configuration does not establish that it received or read a skill. The caller supplies project context, decisions and applicable resource identities or accessible paths. The child locates skills through the host catalog/loader or an explicit task path and reads the required resource before dependent work. Missing context blocks only the affected dependency. Hive does not implement portable skill preloading or filesystem-permission overrides.

For example, a backend implementation assignment identifies the authorized API change, root, owned files, compatibility contract and acceptance checks, then points to the available `flow-build/SKILL.md` and existing project conventions for the detected stack. A read-only reviewer receives the review question and relevant evidence instead of implementation authority. Neither assignment requires creating a new agent for its framework.

Role links use `skill:owner/path` logical resource identities, for example `skill:flow-plan/references/ui-planning.md`. They resolve from the named skill's discovered directory, not the native agent file. This is an authoring convention interpreted through instructions, not a new CLI URI handler. The release validator checks the owning skill and resource exist in the bundle; the renderer rewrites inline locators outside fences to installed resource paths without embedding resource content. See [instruction resources](instruction-resources.md) for authoring and validation limits.

## Native selection and evidence

The shared delegation contract lives in `content/skills/flow-research/references/delegation.md`, with its boundaries in `content/guidance/global.md`, as a capability-first rule: select the installed role through the child-launch tool's own selector, and when the tool does not list the role, give a bounded generic child the contract read from the installed role file and disclose the fallback. The per-host table that used to follow it was removed from the always-loaded block after [issue #30](https://github.com/JhonHawk/tricell-hive-private/issues/30): on 2026-09-25, all six hosts delegated the same way with and without it, one run per cell. The dialects below are maintainer reference, not distributed guidance; follow the session's actual tool schema.

Codex CLI keeps its waits short by itself (obs (log) in two cam sessions, `01a15822` on 0.163.0, 2026-10-20, and `01a1679c` on 0.164.0, 2026-10-23; obs (src) tag `rust-v0.164.0`). Its base instructions say "Avoid performing blocking sleep or wait calls longer than 60 seconds" and ask for a commentary update at least every 60 seconds, and the model followed them over the wait stretch that [delegation](../../../content/skills/flow-research/references/delegation.md#launch-and-wait) sets, which it had read: every `wait_agent` used 60,000 ms or less. Children sent the parent regular updates with `send_message`, about 375 per session, the first after a median of 40 to 64 seconds, and on the v2 runtime each message ends the parent's wait (`multi_agents_spec.rs:306`). Guidance alone did not change this, so two levers apply: the children's final-result rule reaches Codex as developer instructions through the role files, and the optional Codex wait floor capability writes `min_wait_timeout_ms = 300000` and `default_wait_timeout_ms = 600000` under `[features.multi_agent_v2]` in `config.toml`, which Codex enforces by raising any shorter wait to the minimum (`multi_agents_v2/wait.rs:57-65`). A wait still ends early when a child finishes or the user writes. `subagent_developer_instructions` is not used: it "Overrides inherited developer instructions for subagents without role-specific instructions" (`fc.rs:313`), so it would miss Hive's roles and replace other children's instructions. The minimum applies to the v2 runtime; v1 is unverified.

Claude Code shows a notice when a child has stopped while background work of its own, such as a monitor it started, is still running, and the result that child returns may then be interim (runtime observation, obs (local) in cam session `e2c8d39f`, 2026-10-18, Claude Code 2.1.302). The completion notification carried the summary "Agent \"Verify T4\" is waiting on its own background work" and the note "This agent stopped with background work of its own still running. It may resume on its own when that work completes or reports, and the same task-id notifies again if it does; the result below may be interim." It did not resume on its own. In that session the `hive-verify-task` child ended its turn with "Waiting for the monitor to report" at 23:13:05Z and its transcript has no event until it was resumed by hand at 00:31:07Z (read from the session transcript). Hive's rule is capability-first and names no host phrase: [delegation](../../../content/skills/flow-research/references/delegation.md#check-returned-work) treats a child that returns, or that the host reports as stopped, while it waits on work of its own as stopped.

Non-interactive runs are unverified on every host. On OpenCode, `opencode run --format json` prints no synthetic message and returns when the parent finishes, so a child that completes later probably goes unreported.

## Native user questions

History (superseded by change gh-9-communication-decision-flow, 2026-10-08): Codex 0.157.0 (VS Code, Default mode) asks through `request_user_input_async`, which returns before the answer; its reply arrives wrapped in `<send_user_message_question_reply>`, which is not a tool name (corrected 2026-10-02 against the 0.160.0 source); the synchronous `request_user_input` is not available in `codex exec`. Observed on 2026-09-25, not documented: a question answered while the turn was still open reached the user (7 cases), but a question followed by the end of the turn before any answer was not visible, and the user asked for it again. Evidence: `<private-local-session-evidence>` lines 1727–1748 and `<private-local-session-evidence>` lines 4060–4231. The same sample-project session later repeated a pending close question in text before ending the turn, and the user answered by typing its option ID (lines 6599–6634). The global guidance then kept the turn working while a question was unanswered and repeated a pending question with its options when the turn ended first.

History (superseded by change gh-9-communication-decision-flow, 2026-10-08): Codex 0.160.0 confirmed the lifecycle and showed the cost of that repetition. In session `<recorded-session-id>` (VS Code, Default mode, `gpt-6.1-sol`, 2026-10-02) the orchestrator twice wrote its report, called `request_user_input_async`, received `{"accepted":true}`, and wrote a second report that repeated the question before the turn ended (`<private-local-session-evidence>` lines 171–181 and 645–655): the user saw two blocks, typed `D4-A` because the card had closed, and answered the second card only because they did so before the turn ended. Source at tag `rust-v0.160.0`: the handler emits the question as its own final-answer message with fallback text and returns without waiting (`codex-rs/core/src/tools/handlers/request_user_input_async.rs:121-146`). A maintainer called the close at turn end the intended lifecycle ([openai/codex#49146](https://github.com/openai/codex/issues/49146), 2026-10-01). The synchronous `request_user_input` reaches Default mode only behind the under-development `default_mode_request_user_input` feature, and its client then resolves an unanswered question empty after about a minute ([openai/codex#37472](https://github.com/openai/codex/issues/37472)); no setting removes the asynchronous tool. Across 73 asynchronous calls in 29 local VS Code rollouts (0.157.0–0.160.0), all 49 answered cards were answered within the same turn, and none of the 24 cards pending at turn end was answered through the card. The global guidance therefore uses such a tool only while independent work continues in the turn, asks a question that blocks the remaining work in text, and ends a turn with a pending tool question by repeating only the question and its options, not the report.

History (superseded by change gh-9-communication-decision-flow, 2026-10-08): The same session family showed a duplication on hosts with a synchronous tool: Claude Code session `<recorded-session-id>` (2026-10-02) listed decision options in its message and then repeated them in `AskUserQuestion`, because the rule asked for the option list in the message and for the tool. The global guidance now keeps the option list in the tool and the context and recommendation in the message.

History (superseded by change question-flow-checkpoints, 2026-10-11): every choice was complete in the message text, and the native card, used on every host that offers one and waits for the answer, was written to stand alone; a question tool that returned before the answer was used only while independent work continued.

Current rule (change question-flow-checkpoints, 2026-10-11): when a card that waits for the answer carries the question, the message holds the explanation plus one summary line per question with its Recommended option, and the options appear only in the card; whenever no waiting card carries the question, the message holds the full options, one line each. The per-host application is in the table after the card table below.

The pilot trace model cannot express this case yet ([#34](https://github.com/JhonHawk/tricell-hive-private/issues/34)).
