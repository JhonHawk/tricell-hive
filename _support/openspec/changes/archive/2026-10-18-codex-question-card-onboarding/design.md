## Diseño propuesto

**DS1 — Proveedor `codex-question-card`.** Nuevo `ID` en `types.go` con `Hosts: []string{"codex"}`, `Source: "github.com/openai/codex"`, `Reason` en inglés: run `codex features enable default_mode_request_user_input` so Codex shows its question card in Default mode. Se añade al final del catálogo, después de agent-browser, para conservar los índices. Un solo paso: ID `codex-question-card-enable`, `Method: "codex"` (nueva constante `MethodCodex`), argv fijo `["codex","features","enable","default_mode_request_user_input"]`, y un paso manual `codex-question-card-manual` cuando `codex` no está en `PATH`. `ValidateStep` generaliza la rama `planned` a una tabla `allowedPlannedSteps` de ID → (proveedor, método, argv), con agent-browser y este paso; cualquier otro par se rechaza como hoy; el `switch` de proveedores (`run.go:32`) admite el nuevo ID y su paso manual se limita a `codex-question-card-manual` como el de agent-browser (`run.go:44`). `TestCatalogEndsWithAgentBrowserForAllHosts` (`providers_test.go:26-40`) pasa a comprobar que el orden existente se conserva y que agent-browser precede a la entrada nueva; nada en producción indexa el catálogo por posición. Los comentarios de paquete que dicen que agent-browser es la única receta ejecutable (`types.go:1-7`, `run.go:20-23`, `tooling/providers/README.md:10`) se actualizan.

**DS2 — Oferta y plan.** `Detect` ofrece `codex-question-card` cuando `codex` está en la selección de hosts y, en instalación real, `codex` está en `PATH` (`sys.lookPath`) y una sonda única `codex features list` (ejecutor acotado, 30 s, hook `codexFeaturesProbe`, solo bajo `runsPrograms()`) reporta `default_mode_request_user_input` (revisión R1 del 2026-10-18, hallazgo P2 de la revisión de código: un Codex anterior dejaría la instalación parcial por defecto): oferta ejecutable con `DefaultOn: true` y etiqueta propia; con `codex` presente pero sin esa respuesta, oferta manual con la razón de actualizar Codex a 0.163.0 o posterior; en seco o no interactivo no corre la sonda y la oferta se lista desde `PATH`. Si `codex` no está en `PATH`, o bajo `--home` sintético, ofrece el paso manual (`ManualOnly: true`, **sin** `DefaultOn`, razón: install Codex and run the command): un paso manual seleccionado deja la instalación parcial y con salida distinta de cero (`onboarding.go:374-376,416`), lo que rompería las instalaciones con `--hosts codex` y home sintético que ya prueban `install_test.go:140,156,417,711,723`. El adaptador cachea el resultado de `PATH` en un campo propio (`a.codex`, como `a.browser`) para que `Plan` sepa qué paso construir y qué razón manual usar en lugar de la genérica del catálogo (`provider_adapter.go:130-131`). `Plan` añade un `providerDetail` con el efecto «writes `default_mode_request_user_input = true` to `<CodexHome>/config.toml` through `codex features enable`; undo with `codex features disable …`», que `showInstallSummary` muestra antes de «Apply these changes?».

**DS3 — Marcado por defecto (Q2-A).** `providerOffer` gana `DefaultOn bool` y `Effect string` (texto de la etiqueta para una capacidad que no instala un programa: «enables Codex's question card in Default mode»); `providerOfferLabel` usa `Effect` cuando está, en lugar de «installs the latest version» (`tui_hosts_view.go:1166-1177`). TUI: `capsView` arranca con `checked[i] = offer.DefaultOn` (`:1015`) y el texto de ayuda «None is fine: leave them unchecked and continue.» (`:1124`) pasa a «The checked ones are selected by default; uncheck any you do not want.». Texto: la línea de cada oferta marcada por defecto lleva `(selected by default)`; el prompt (`install.go:655`) pasa a «Enter capability numbers separated by commas, press Enter to accept the default selection, or type `none` to skip»; Enter con alguna oferta `DefaultOn` devuelve esas; sin ninguna, el comportamiento actual (vacío); `none` devuelve vacío. Una sesión no interactiva sigue devolviendo vacío (`install.go:646-648`): el paso nunca corre sin alguien que confirme «Apply these changes?».

**DS4 — Ejecución y reconciliación.** `providerRunner.run` ejecuta el argv de cualquier paso `planned` validado por el mismo `agentBrowserExec` (se renombra el helper a `providerExec` solo si el cambio queda local; no es requisito). Mensaje de fallo específico cuando la salida contiene `unrecognized subcommand` o `unexpected argument`: «this Codex version has no `features` subcommand; update Codex (0.163.0 or later) and run the command by hand». Tras una ejecución con salida 0, `run` confirma la clave con `FeatureEnabled`; si no la confirma, el resultado sigue fallido con el mensaje «Codex reported success but Hive could not confirm the setting in `<codexHome>/config.toml`[: error]; run `codex features list` to check it» (R1, hallazgo P3/F2). La salida capturada del paso de Codex se vacía antes de guardarse, porque un error de parseo de Codex imprime la línea ofensiva de `config.toml` (R1, hallazgo F1 de seguridad). `Reconcile` para `codex-question-card-enable` lee primero la configuración: `verified` si `integrations/codex.FeatureEnabled(codexHome, "default_mode_request_user_input")` devuelve `true`, aunque no haya resultado almacenado (una interrupción tras la escritura de Codex no debe quedar como fallida, `agent_browser_runner.go:267-268`); `skipped` cuando el resultado lo marca (runner sintético; en seco `Execute` nunca corre, `install.go:370-373`); `failed` en otro caso o ante error de lectura. `stepResultDetail` reconoce el prefijo del proveedor nuevo igual que `agent-browser-`. `CodexHome` se resuelve al crear el adaptador: `nativeProviderAdapterFactory` llama a `management.NormalizeOptions(in.Options)` (precedente en `main.go:331-337`) y guarda `CodexHome` en el adaptador, que lo pasa a `providerRunner` desde `Runner()` (`provider_adapter.go:184`, también en la recuperación `install.go:523`, `main.go:343`, `tui.go:156`). Es coherente con el hijo, que hereda `CODEX_HOME` por `os.Environ()` (`agent_browser_runner.go:118`; `types.go:296-299`).

**DS5 — Lector `integrations/codex.FeatureEnabled`.** Función `FeatureEnabled(home string, key string) (bool, error)` modelada en `grok.CursorAgentsEnabled`: abre `<home>/config.toml`, ausencia del archivo o de la clave devuelve `false, nil`; reconoce `key = true|false` dentro de la tabla `[features]` (también con la cabecera entre comillas, `["features"]`, bajo la que Codex escribe si ya existe; R1), un BOM inicial y líneas de hasta 1 MiB, y la forma punteada raíz `features.<key> = true|false`; formas no soportadas (tabla `features` inline, tabla duplicada, `[[features]]`, la clave en ambas formas con valores distintos) devuelven error. No escribe nunca. Solo el runner la usa; doctor no. Observado en local (0.163.0): `codex features enable` añade la clave a la tabla `[features]` existente; no se verificó si escribe en `[profiles.*]` con un perfil activo (la puerta compartida con `CODEX_HOME` temporal lo comprueba sin perfil).

**DS6 — Doctor.** Fila `Codex question card` (ID `codex-question-card`) cuando `codex` está entre `management.RegisteredHosts`, o cuando esa lectura falla (como Pi codemode). `Found: "not checked"` con evidencia «Not checked: finding it would mean reading Codex's configuration, which Hive does not do.»; `Record` desde el registro de onboarding por prefijo; siguiente paso con caso propio en `nextStep` (hoy cae en el texto de agent-browser, `doctor_integrations.go:222-227`): «Run `codex features enable default_mode_request_user_input` to show Codex's question card in Default mode, or `codex features disable …` to turn it off; `codex features list` shows the current state.» más la frase del registro. Orden de filas: después de agent-browser. Las fixtures existentes registran `claude` o `claude,pi` (`doctor_integrations_test.go:86-97`), así que las pruebas de orden actuales siguen válidas; se añaden una fixture con `codex` registrado, el ajuste a 80x24 con seis filas (`tui_integrations_view_test.go:69-85`) y la prueba de que una `config.toml` con la clave activa sigue mostrando «not checked».

**DS7 — Documentación.** Invariante de configuración de host, en `tool-dependencies.md` § Boundaries como casa: «Hive edits no host configuration file itself; with the operator's consent it runs the host's own command, which writes it (`pi install`, `codex features enable`)»; `installer.md` apunta ahí. Frases que contradicen el cambio y se reescriben: `installer.md:98,102,106,117` («installs no CLI executable except agent-browser», cuatro capacidades, «the one recipe», Pi como «the other exception»); `tool-dependencies.md:10-17` («all four capabilities», «Only `agent-browser` has a provider recipe», configuración de host «untouched»); `README.md:157-160` («Two steps are automated», el consentimiento y la salida distinta de cero de un paso manual); `deployment-manager.md:76` (fila nueva) y `:79` (añadir `codex` a los programas que `--home` nunca ejecuta). `agent-delivery.md`: `:191` («Checked … Codex CLI 0.162.1» pasa a 0.163.0), fila `:196` (la autorresolución es 60 s ocultos + 60 s visibles, cancelable al teclear; el resultado vacío llega como `{"answers":{}}`, obs (src) `bottom_pane/request_user_input/mod.rs:73-74,303-311,922-934` y `handlers/request_user_input.rs:84-100`), fila `:208` y párrafo `:211` condicionales: con `default_mode_request_user_input` activo, tarjeta que espera en Default; sin él, opciones en texto; citar la plantilla de Default de `rust-v0.163.0` en lugar de 0.162.1. `questions.md` no cambia: la condición «dismissed or timed-out question is asked once more in text» cubre el resultado vacío. `CHANGELOG.md` Unreleased/Added (nivel menor). `llms.txt:39` añade el nombre de la capacidad.
